# 企业业务资料与自主分析上下文方案

版本 v0.1 · 2026-10-31 · 方案与最新 spec/UI 已通过；产品实施已获授权，当前进行中

本方案将本轮讨论整理为正式可读的 Markdown 文档，采用用户指定方向：在“分析资产 → 企业业务资料”集中维护公共材料，SAP／RAP／Case 保持各自职责；Case 引用公共资料并补充本案信息，Host 提供环境和上下文，Agent 自主分析。用户随后确认方案、spec 和最新 UI，并授权开始产品实施、检查与非作者独立复核。当前进展见[规格](../openspec/changes/enterprise-business-context/spec.md)和[记录](../openspec/changes/enterprise-business-context/result.md)；[UI Demo](prototypes/enterprise-business-context-ui-demo.html)仍仅用合成资料演示交互。分类页真实入口已实施；原 spec 留下的五项持久合同已整理为[实施决策包](../openspec/changes/enterprise-business-context/structure-decisions.md)，五项 A 已整体确认，结构、接线和产品页面已实施，本地 514 项测试与构建通过，完整候选非作者复核完成；范围见结果记录。模型质量评估、Git 交付及运行采用分别按实际授权和证据报告。

后续用户明确“spec 方案及 UI 通过”，要求再次核对产品原则，并将“指标体系／需求梳理”纳入四大类。用户进一步纠正：功能应填入现有方块目录页，不能挂侧栏树；纯占位方块灰显，已有真实功能正常显示，必须有清楚区别。原则与分类说明见[专项复核](../openspec/changes/enterprise-business-context/principles-review.md)。需求梳理归“业务插件”；指标体系按此前推荐在“分析资产”目录展示。原 UI 通过不追认已被纠正的树状增量。

依据为[产品讨论稿 v0.2](OptraCall_产品讨论稿_v0.2.md)、[工程规范](engineering-workflow.md)、[统一会话接入说明](agent-session-integration.md)和此前[业务语义方案](business-semantics-and-independent-verification-phase1-proposal.md)。本文承接本轮讨论，不改写已交付 SV01–SV12 的规格、成绩、失败或验收记录。

## 一 大白话要点

1. **公司的常用资料放一个地方维护。** 企业介绍、组织渠道、业务流程、制度、数据字典等，放在“分析资产 → 企业业务资料”，不用每个 Case 重新录一遍。
2. **指标定义继续归 SAP，本次问题继续归 RAP。** 公共入口可以找到、引用它们，但不再复制一份同名口径或需求。
3. **Case 选用公共资料，再补本案特殊情况。** 比如公司平时的活动规则放公共资料，这一次活动的特殊合同放本案材料；两份有差异时保留差异，不偷偷覆盖。
4. **Host 把资料准备好，让 Agent 自己看、自己判断、自己算。** Host 可以提供目录、检索、版本和原文；不要求先填完表，不按场景锁定分析方法。
5. **关键条件和数据含义由 Agent 按需要说明。** 影响答案的条件不知道，就澄清、保留未知或给出条件化结果；不要求每个问题都套相同模板。
6. **重要结论能追查当时的依据。** 能看到用了哪版资料、哪份数据、哪个计算文件；缺少旧数据副本时，如实说明不能完整重算。
7. **先证明更好用、更少误解。** 用固定合成任务比较效果；评估规则留在工程验证中，不变成产品运行时的通关规则。

## 三 公共维护入口：分析资产 → 企业业务资料

### 3.1 入口与页面内容

建议在“分析资产”内提供可识别的“企业业务资料”入口，集中完成下列操作。这里是业务资料的维护位置，不增加强制分析向导。

能力侧栏只保留“分析资产、场景组合、连接器、业务插件”四个平级入口，点击进入对应方块目录页，不展开功能树。分析资产页放企业业务资料、指标体系；业务插件页放需求梳理；三个功能均不在桌面或移动侧栏重复。后续功能通过页内检索／筛选扩展，避免侧栏随功能数量增长。

指标体系、需求梳理属于已有真实产品入口，方块采用正常样式和正常功能入口表达；纯规划占位采用灰色表面／图标，明确标注“规划中／未接入”，不提供正常进入动作。企业业务资料是本次新增设计，Demo 单独标“本轮新增·演示”，可进入维护原型但不冒称后端已接入。状态同时通过文字和动作表达，灰显文字仍保持可读。

企业业务资料从方块进入维护列表，并能返回分析资产目录。指标体系主要维护可复用定义和 SAP，辅助生成、编辑和审核是资产维护能力；界面分类不要求移动现有插件源码，也不改变 Runtime 或会话归属。

| 位置 | 拟提供的内容与操作 |
| --- | --- |
| 资料列表 | 查看标题、资料类别、所属企业／业务范围、来源、修订及可用情况；按关键词、类别和范围筛选 |
| 新建／补充 | 编写正文，或显式选择获准的文件作为来源；填写已知来源、适用范围、有效期间等说明 |
| 资料详情 | 阅读正文、查看原始来源及历史修订；查看与 SAP、Case 等的引用关系 |
| 编辑与修订 | 保留旧修订；修改后明确启用新修订，不原地覆盖历史分析使用的内容 |
| 选用与停用 | 供 Case／任务明确选用某一修订；停用后提示不再用于新选择，已有历史仍可解释地回读 |

首轮建议以可定位的 UTF-8 正文和普通文件引用为主。其他格式如尚不能提取正文，只显示可取得的文件及读取限制，不将“已登记文件”写成“已提供全文”。不以全面 OCR、自动联网采集或全盘扫描作为前提。

资料可按企业或业务单元分组，便于找到适用材料。分组是产品组织概念，本方案不据此引入企业账号、多租户或新的权限体系；读取仍服从实际授权范围。

### 3.2 维护什么内容

建议从真实任务反复需要的材料开始：

- 企业业务介绍、业务模式、组织／渠道／门店等对象关系。
- 业务流程、经营制度、结算约定及明确的适用范围和例外。
- 数据字典、文件或表的含义、单位、粒度、时间归属等资料。
- 有日期和来源的重要业务事件，如促销、渠道调整、组织变化。
- 可定位的来源文档及相关 SAP 精确版本引用。

标题、可读正文或有效来源是基本内容。来源、维护人、时间、适用范围未知时如实显示；不为凑齐字段让模型补造。正文中的事实、用户陈述、推断和建议尽量说明性质，“资料已启用”仅表示可被选择，不代表整份资料已经核实为真。

Agent 可以在用户已有任务中提出资料整理或纠错建议。建议先作为普通产物展示，由用户显式决定是否保存为公共资料修订；不能因为一次分析 completed 就自动升级为企业事实或发布资产。

### 3.3 产品分类与技术保存分开

“分析资产”是用户找资料的入口。实际企业内容保存在本机获准的业务数据位置，不放进公开仓库的 `extensions/` 源码或随合成示例发布。

推荐采用“正文／文件加轻量索引”的最小落点，优先复用现有文件与资料管理能力。具体索引格式、修订身份、数据根目录和权限校验方式须在实施前结合引用要求固定；本文不创建表列、隐藏备注协议或另一个语义数据库。

企业公共资料属于获准业务范围内的共享来源。“公共”不表示对所有项目、Case 或外部模型无条件开放；Case 关联也不扩大原项目文件的权限。

## 四 与 SAP／RAP／Case／场景组合的引用关系

### 4.1 唯一权威来源

| 对象 | 负责的内容 | 如何引用其他内容 | 避免的重复 |
| --- | --- | --- | --- |
| 企业业务资料 | 可复用的企业背景、制度、流程、数据说明等原文及修订 | 可引用来源文件和具体 SAP 发布版本 | 不复制 SAP 成另一份可独立编辑的指标库，不接管本次 RAP |
| SAP | 经过既有审核发布流程的指标定义、适用范围、粒度和版本 | 可定位说明口径来源的企业材料；现有格式表达不足时在原文及公共展示中提供可读出处 | 不把生成／审核 provenance 当作实际数据血缘，不硬塞企业百科或真实列绑定合同 |
| RAP | 本次任务的问题、目标、范围、事实／假设／未知和所需数据 | 引用本次选用的公共材料、SAP 及 Case 背景；已有 source／evidence 等字段按原语义使用 | 不保存整套企业资料副本，不为引用临时增加 RAP 0.2 未知字段 |
| Case | 本案经营背景、判断、决策记录、公共资料选择及特殊补充 | 关联公共资料修订和既有项目／文件／报告 | 不成为企业基础资料主维护库，不静默回写公共来源 |
| 场景组合 | 某类用途的可选目标、资产与能力引用集合 | 可推荐相关公共资料类别、SAP、skill 和工具 | 不复制公共事实，不规定 Agent 必须采用的分析路线 |
| 项目／任务 | 实际数据、独立会话、计算与报告 | 使用用户为本次任务选定或在授权范围内明确允许检索的材料 | 不因属于某 Case 自动读取其全部关联项目资料 |

共同维护入口不要求所有资料落入同一种格式。SAP／RAP 继续采用现有 0.2 校验和发布流程，Case 继续使用原有项目关系和记录；新增引用不能靠解析自由文本中的暗号实现。

### 4.2 选用、更新与历史

1. 用户选用公共资料时，记录所选资料的具体修订及来源位置；实际发送时核对其可读性和身份。
2. 公共资料出现新修订时显示变化提示，用户决定后续任务是否改用；不追改已经发送的消息或历史报告。
3. Case 的当前引用可以调整，已经完成任务保留当时实际提供的内容和引用。当前 Case 页面不冒充历史任务的原始条件。
4. 历史回读依靠保留的明确修订、原有请求快照和必要来源摘录；正文不可读时显示缺失，不拿最新版替代。
5. 资料停用或取消引用不删除既有报告和必要证据。物理删除及保留策略另按明确范围执行，本方案不增加清理动作。

## 五 Case 特殊资料怎样补充

### 5.1 两类入口

Case 详情建议提供两个可展开区域：

- **引用的企业资料**：搜索或浏览获准资料，选择修订，查看来源及更新提示；可取消关联。
- **本案补充**：填写简短背景／特殊约定／未知说明，或选择本案关联项目内的普通资料文件。

对短说明，优先复用 Case 已有背景与说明记录，并保留来源说明；需要单独正文时，以原项目 `020_clean` 中的普通文件承载，沿用 Case 的项目文件引用。公共资料的新增跨模块引用属于待补接缝，不能冒称当前 Case Artifact 已能直接关联任意全局资料。

本案补充应说明适用对象或活动、时间、来源和确认情况，未取得的部分保留未知。它是供 Agent 理解本案的材料，不自动成为企业公共规则。

“本案”描述业务适用范围，不承诺文件的物理隔离。项目文件仍由项目各任务共享；同一项目关联多个 Case 时，选择来源和用途必须明确，不能靠把文件名写成 Case 名称就宣称获得独立权限。

### 5.2 任务怎样使用

从 Case 进入原项目任务时，可展示该 Case 的资料作为候选选择。用户可增减选用材料，也可直接提出问题；产品不要求必须补齐 Case、RAP 或公共资料才能开始探索。

任务实际发送时，Host 展示并捕获本次选用来源，而非默默传入整个 Case 或全企业资料库。后续用户补充材料可进入新的显式消息，原先结论仍保留原条件；不自动重发旧任务。

### 5.3 本案例外与公共规则冲突

公共规则和本案补充都保留原文、版本、来源及范围。Agent 自主判断是否存在适用差异，必要时向用户澄清。产品不设“Case 总是优先”“最新资料总是优先”或“SAP 永远优先”的自动业务裁决。

用户明确解决后，经原来源的编辑／确认流程形成新内容，再用于后续消息。本案内容若有公共复用价值，由用户显式整理为企业资料修订；不因本案采用或业绩变化自动发布为通用经验。

## 六 Host 怎样提供上下文

以下描述产品提供材料的时机和责任，不是 Agent 必须通过的分析阶段。

### 6.1 提供可用环境

Host 维护材料入口、权限、索引和读取能力。用户明确选择的材料可直接提供必要正文或摘要；其余获准材料通过可发现的目录和按需检索入口提供。Agent 可以自行决定是否搜索、读哪份、看哪些章节及是否继续核对原文。

**勾选仅决定随本轮消息主动附带的材料，不构成 Agent 的读取白名单。** 在已经授权的资料范围内，Agent 可以自主检索、发现并读取公共资料，无需先关联 Case 或由用户逐份勾选。Host 继续核对真实资源权限，但不以用户未勾选、本案未绑定或前提表未填齐作为业务读取门槛；目录是否可见、是否已主动提供和实际工具读取分别记录。

首轮检索建议采用标题、关键词、类别等可解释索引，返回候选内容和位置。检索排序仅帮助找资料，不表示 Host 已判定其业务适用或真实性；不依赖先建完整知识图谱或自动语义裁判。

资源不存在、越权或文件身份不符时，Host 按明确技术边界报错。业务资料不足时，Agent 仍可澄清、条件分析或保留未知；Host 不按“业务条件未凑齐”建立新门禁。

### 6.2 区分指令、资料与历史

- 产品系统指令继续表达资源、目录、权限和运行边界。
- 企业资料、SAP／RAP 摘要、Case 内容及本案补充明确标为来源材料，不因导入而获得系统指令权限。
- 资料标题、修订、来源、适用范围及未知说明与原文一起可见；摘要不冒充全文。
- 数据文件仍由 Agent 用现有工具读取和计算。Host 不替 Agent 从企业资料中推导公式、挑数据列或验证业务前提。
- SDK 原生历史、压缩与任务续接保持现有责任；不追加一套 Host 分析状态机。

按需读取较长材料时，提供清楚的章节／位置及片段范围，保留全文取得方式；不能静默截去例外后把片段标为完整依据。普通分析可继续自主读取；附属 fixed-draft 修订仍遵守现有全文和 20,000 个 JavaScript UTF-16 字符限制，不因接入业务资料退回全工具。

### 6.3 区分实际交付时点

普通任务当前 SAP 索引在资源初始化时取得，RAP／Case 在每次消息准备时取得。新资料引用需要明确本次选用修订和实际读取时点，不能用“当前公共资料列表”重建过去。

SAP 保持当前精确版本及显式新建任务采用新版本的边界。本方案不暗含 SAP 热切换或自动重建活会话。公共资料更新也不自动替换会话中已经见过的内容；需要新版本时，在新的显式请求中标明变化。Agent 面对新旧内容继续保留来源差异。

### 6.4 共用 Runtime 与工程责任

沿用[工程规范 IN01–IN07](engineering-workflow.md#统一会话接入规范interface-v1)和 Interface v1。普通任务保留原 project／task owner 和 `project-tasks` 域；资料维护模块不自行 new SDK、ProjectAgent 或维护 opening／busy／代际集合。需要模型帮助整理资料时，优先使用用户已有普通任务，按其实际授权执行。

Codex 负责 Host／Agent 的读取能力、实际提供记录和主链路；Qoder 负责适用 Extension 页面、资产内容与接入。字段、引用和调用合同共同核对；本文件不表示已向另一方派发开发任务。

当前 `SessionTurn.providedContext` 只承载已有 RAP／Case 输入，worker 补充 SAP 初始化记录。新增公共资料来源回执尚需补齐兼容契约，不能直接声称已支持任意来源。实施前在规格记录 Interface／规则版本、owner/profile、能力范围、变更合同和验收，并按 IN06 共同维护。

## 七 Agent 自主性与三项改进

### 7.1 关键前提显式化

Agent 自行判断哪些条件会影响当前结论，可利用 RAP 的事实、澄清、假设、证据及验证条件，并读取公共和本案原文。关键条件不明确时，可询问、给条件化结果或说明无法确定的部分。

产品引导关注来源和不确定性；不要求固定数量的假设／澄清，不设置“前提表齐全后才能分析”，也不由 Host 枚举一套必须匹配的业务条件或答案分支。

### 7.2 口径与实际数据对应

SAP 提供业务定义，RAP 提供本次所需数据，企业资料提供数据字典和制度背景。Agent 自主检查实际文件，决定字段、粒度、期间、筛选、连接、去重和计算方法，并按重要性在过程产物或报告中解释。

需要持久说明时，使用项目普通文档或报告内容，记录本任务实际对应及未知。它不是新的必填机器协议，不要求全部任务采用同一个表。SAP 现有 `type_params` 不冒充真实表列绑定，布尔 `caliber_switches` 不用 false 代替未知，生成／审核 `provenance` 不冒充执行血缘。

### 7.3 结论采用依据可回读

Agent 对重要结论说明必要的前提、口径条款、数据和计算产物；表达可以是正文、脚注、表格或附录。Host 负责保存、链接和技术身份核对，不凭格式齐全给专业正确盖章。

此处“采用依据”指 Agent 声明用于分析的依据；“用户采用报告”仍是另一个显式操作，不从 Agent 引用或 completed 推定。结论数量、报告结构及分析方法随任务变化，描述性分析不强制匹配指标计算模式。

### 7.4 防止退回固定分析流程

| 产品情形 | 应当允许的行为 | 不纳入本方案的 Host 行为 |
| --- | --- | --- |
| 没有 Case、RAP 或公共资料 | 在既有授权环境中直接提问、探索和补充 | 因缺少业务表单而禁止分析 |
| 任务属于某场景 | Agent 参考有关资产，也可调整方法 | 自动锁定固定方法、算式或步骤 |
| 前提缺失或含义冲突 | Agent 澄清、条件分析或保留未知 | 自行补事实、自动决定哪份资料胜出 |
| 报告解释不够充分 | 用户继续追问，Agent 在原上下文响应 | 因漏一段模板而自动拉起补写／重算／裁判循环 |
| 完成固定评测 | 工程人员据结果决定版本是否值得采用 | 把评分规则塞进运行器作为每轮通关程序 |

普通分析现有工具能力和自主执行责任保持原范围；真实资源、授权和副作用边界继续由 Host 执行。本文不把自主性理解为业务数据或经营动作权限的扩大。

## 八 来源、版本和回读的产品语义

以下是拟达到的可观察行为，不是已冻结的数据库或 JSON 合同。

| 记录层面 | 应说明什么 | 不能据此声称什么 |
| --- | --- | --- |
| 目录可见 | Agent 能找到哪些获准资料 | 已把这些资料全文发送给模型 |
| 本次已提供 | 实际交付的内容、所选修订／指纹、片段范围和请求身份 | Agent 已理解或认可 |
| 可观察读取 | 捕获到的工具读取及具体来源 | 所有可能读取均已完整审计，或读取就代表正确理解 |
| Agent 声明采用 | 报告引用的条款、前提、数据和计算产物 | 所有引用都支持结论，或等于用户已采用 |
| 用户显式采用 | 原有采用入口保存的具体报告副本及来源回执 | 业务已执行、有效果或结论全部正确 |

报告默认仍放 `060_reports`，过程文件默认 `020_clean`。Case 文件关联和“保存并采用此版本”复用已有行为；普通任务也能查看自己的报告及依据，不以 Case 存在为条件。

公共资料修订、已有 RAP／SAP 发布物和 Case 请求快照按实际保存能力回读。报告按需保留必要来源摘录和任务级数据对应说明，摘录标明范围，不代替原来源。输入数据记录当时的文件身份；没有固定数据副本时，文件变化后明确不能完整复算。是否保留选定数据副本、保留多久及其存储范围在实施方案中另行明确，不隐含复制全部项目或形成完整审计保证。

旧记录没有来源时保持未知，不回填为“当时已采用”。取消、失败和中断的未知结果保持 UNKNOWN，不自动重放。普通分析、初次核算、知情复查和附属修订的当前差异继续遵守[核算接入说明](verification-agent-integration.md)；本方案不扩大冷读材料、不向核算提前透露作者答案。

## 九 一个合成使用例子

以下仅用于说明资料组织，不是固定分析模板或实际运行结果。

- 企业业务资料维护“结算说明 v1”“订单数据字典 v2”，说明适用期间和来源。
- SAP 中保留经过审核的“净收款”指标版本，并能找到相应业务说明。
- 某 Case 引用上述资料，另补充“本次活动特殊结算附件”；附件放在已关联项目的 `020_clean`，来源和确认情况可见。
- 用户在原项目任务询问本期经营变化，明确选用这些资料，也可以直接先问问题。
- Agent 自主读取数据字典和附件，发现“退款是否已包含在实付字段”还不能确定。它自行选择询问用户、先给条件化结果或开展不依赖该条件的分析。
- 用户确认后，Agent 自主写代码、计算和解释，报告引用实际采用的定义、条款和输入版本。Host 保存结果，用户需要时再显式关联或采用到 Case。

Host 没有因为这是经营复盘就安排固定分解步骤，也没有替 Agent 判断附件应当覆盖哪条企业规则。用户以后修订公共资料，旧报告仍能说明当时使用的版本；缺少旧数据时不宣称可以重算全部过程。

## 十 怎么验证效果

以下均为后续建议；本次不执行产品工程测试、真实模型评估或旧失败复测。

### 10.1 工程与正常入口

将确定性行为与模型内容质量分开验证：

1. 公共资料新建／修订／选用／停用的可读性和历史；版本缺失、文件变化和越权引用有准确反馈。
2. Case 公共引用与本案补充归属清楚；共享项目不冒充 Case 隔离；普通无 Case 项目仍能工作。
3. SAP／RAP 的原校验、发布和精确版本采用保持兼容，公共入口不制造第二份权威内容。
4. 实际提供的内容与选择一致，未选内容不冒充已提供；可检索目录、读取片段和全文回执明确区分。
5. 报告／来源重开可回读；当前版本与历史版本差异可见，旧记录缺失保持未知。
6. 原项目、任务、会话指针／父链、配置和普通文件保全；取消、配置变化、迟到结果、保存失败和恢复维持原边界。
7. 自主性反例：无公共资料仍可开始；非指标描述任务可直接回答；场景建议可不采用；不因缺少解释模板而触发 Host 重算。
8. 无 Case、零主动附带材料时，Agent 仍能在已授权公共目录中发现并读取所需资料；导航分组、Case 关联和材料勾选不改变工具／读取权限或分析方法。

未来实现按工程规范建立适用测试及统一入口约束；完整候选再做相称的兼容、RAP＋SAP＋Case 联合回归和非作者复核。工程 PASS 不当作分析质量 PASS。

### 10.2 固定合成任务与对照

建议预先冻结 6 个新任务，各覆盖以下一种主要风险：

| 任务方向 | 冻结条件与观察目标 |
| --- | --- |
| 关键条件缺失 | 资料确实不足时，不补造事实；澄清、合理未知或条件分支均按事前标准评分 |
| 公共规则与本案例外 | 两份来源均存在，检查 Agent 是否正确解释适用范围，或在冲突未解决时保留差异 |
| 同名字段／单位 | 用实际字典和数据检查字段含义、单位及换算是否对应 |
| 粒度与处理规则 | 订单／明细、连接、退款、去重等是否按定义和事实正确处理 |
| 修订与历史引用 | 公共资料或 SAP 新版与本次选定版本不同，检查是否用对本轮版本并如实引用 |
| 历史依据缺失 | 旧报告缺少原输入时，不伪造复原；能说明本次新选择和实际回读范围 |

- **A 当前方式**：既有装配和资料组织。
- **B 同事实改进**：与 A 完全相同的企业事实、数据和工具，采用公共维护、明确引用、本案补充及上述上下文提供方式；不偷偷多给答案信息。
- **C 新增事实**：仅对事前选定的两个信息不足任务，补充已冻结的确认资料，单独观察新信息收益。

建议 A／B 每题各 2 次独立运行，C 两题各 2 次，共 28 次作者运行。完整模型配置、原生实际参数、工具、数据与运行条件固定并记录；每次使用独立会话。次数是待确认的评估建议，不是本轮运行授权或不断补跑至通过的预算。

另在上述任务的产品操作中观察：同一公共资料能否被不同任务明确引用、是否减少重复录入／解释、用户补充或纠错是否顺畅。该操作证据不混作模型正确率。

### 10.3 独立评分与采用判断

运行前由非作者评审固定计算答案、合法条件分支、关键来源和未知边界，模型不得取得评分答案。评分时隐藏 A／B／C 标识，独立核对计算及引用是否真的支持结论；不依赖两个 Agent 一致。

分别报告正确、合理未知、重要错误、交付不完整及运行失败，并单列前提臆造、字段／粒度误用、引用不支持结论、过度保守及同题 A 正确而 B 出错的配对。保留全部尝试，不以绿色重跑覆盖失败。

建议推广前要求固定集内无新增重要错误、无 A 正确而 B 重要出错的退化，关键依据可回读且支持其对应结论。只有 B 实际改善结果时才称组织方式有收益；A／B 都正确只能说明该组未见退化；C 单列为新增事实收益。小样本不宣称统计显著或通用准确率，不把同题配对当成确定的单次因果证明。

验证应使用新合成根和新任务，不读取、恢复或补跑原六稿事故现场；旧 FAIL／UNKNOWN 和专业 PARTIAL 保持原记录。后续若专门处理旧质量问题，另按用户指定范围形成任务。

## 十一 后续实施前需要固定的接缝

本方案先给出产品行为和推荐落点。后续用户授权开发时，应将以下内容作为一个完整接缝包记录，而非写代码时临时扩字段：

| 接缝 | 推荐方向 | 实施前需固定的内容 |
| --- | --- | --- |
| 公共资料保存 | 本机普通正文／文件加轻量索引，按修订引用 | 来源身份、修订与历史保留、实际数据根、可读格式和受控读写入口 |
| 跨模块引用 | 公共正文保持一处权威，Case／任务持明确来源引用 | Case、项目、任务的引用归属与生命周期；现有 Artifact 无法表达的部分采用何种兼容合同 |
| 本案补充 | 复用 Case 说明及原项目文件，保持项目共享语义 | 哪些短说明直接复用、哪些需文件引用，修订及实际发送时点 |
| 实际提供回执 | 复用既有请求／JSONL 证据路径，新增内容保持可选兼容 | 公共资料目录可见／实际提供／片段读取的表示，旧读取器兼容和失败语义 |
| 回读与文件保留 | 保留明确资料修订，报告解释必要依据 | 是否及何时保存选定数据副本、保留范围、变更与缺失提示 |
| 界面 | 分析资产公共入口，Case 选择和补充区域，任务按需展开 | 根据实际增量提供 UI Demo；真实能力和其他演示目录标识分清 |

这些事项不以另建事实总库、会话库或替换 SAP／RAP／Case 权威作为默认解法。如果确需新增持久结构或改变公共合同，先整理完整结构与兼容决定再实施；本文件不提前冻结表结构或绕过相关确认。

届时再建立相应 OpenSpec 变更规格并记录本方案的确认版本、修改路径、Interface v1、owner/profile、技术结构及验收。必要设计、实现、日常修正和受影响验证在同一范围内持续完成；最终 Git／CI、合并、运行采用与产品验收分别按授权和证据报告。
