## 2 要解决的问题与理念（继承自 target-forecast 的思想内核）

业务决策者面对"明年目标定多少才靠谱""这次券要不要发、满多少减多少""这笔投放会不会亏"这类问题时，缺的是**把假设严谨展开成可审计结论**的测算方法。拍脑袋定目标无法复盘；随手心算无法保证口径一致、结果可复现。

继承的五个理念（实现载体为 skill + 确定性脚本）：

1. **测算不是预测，是假设的严谨展开**——情景（保守/基准/挑战）是同一份数据下的推演，结论持续声明"情景推演 · 非预测承诺"；允许"净亏损""不发券"成为结论，不强行推荐；
2. **口径与数据质量先行**——输入数据先经脚本校验（定位化 blocker 拦截 / 需确认项 / 质量披露三级），口径与假设先讲清再算数；数据或假设一变，旧结论即声明过期；
3. **结果绑定身份、可复盘**——脚本输出携带引擎版本与输入摘要；同输入同输出；测算结果落项目文件域，日后可精确复盘；
4. **同源账本、交叉校验**——所有指标出自同一脚本的同一次计算（优惠券：分支概率合计=1、贡献拆解对平；目标测算：人/货/场三视角互为校验），差异超阈值如实显示"需复核"不粉饰；
5. **建议不越权**——Agent 只在对话中给出测算结果与建议，采纳由用户决定；数字必须出自脚本输出，不心算、不编造。

不继承的（原仓具体设计）：workbench 壳与工具注册协议、独立 HTTP 服务与启动器、页面交互流程、assistant-sidecar 副车与凭据发现、插件存储 schema、Python pandas/numpy 依赖、旧版 CLI。

## 3 产品定义：能力清单

产品成功的标准是以下能力经 3 个 skill 在项目任务中原生可用：

| # | 能力 | 说明 |
| --- | --- | --- |
| C1 目标测算方法 | 人/货/场三视角对线上 GMV 做目标测算（人=新老客拆解、场=UV×转化×客单、货=品类梯队校验），每平台独立核算+全渠道汇总，多情景一次计算，交叉校验差异如实呈现 |
| C2 数据质量与口径纪律 | xlsx 输入经脚本校验（三级质量、定位化报错）；口径/假设/数据覆盖先行确认；修改即声明旧结论过期 |
| C3 优惠券情景测算方法 | 满减券四子模型（命中核销/凑单流失/转化响应/统一账本），无券候选始终参与，输出"回本所需转化提升"等结论与敏感度 |
| C4 投放 ROI 测算方法 | 多计划盈亏链路核算（点击→订单→GMV→净贡献），保本转化率、情景敏感度、多计划并排比较与排名 |
| C5 确定性脚本 | 三测算内核各带引擎版本，纯计算无状态；同输入同输出；黄金案例自检作为长期基线 |
| C6 结果即证据 | 测算报告是项目文件域普通文件（最终报告入 `060_reports`），可按既有文件引用合同被 Case/决策板引用，不新建证据机制 |
| C7 Agent 自主 | skill 是能力注入不是流程编排：Agent 自主决定是否、何时、如何测算；红线约束诚实性，不约束方法选择 |

## 4 产品设计

### 4.1 形态：分析资产 3 个 skill

```
extensions/analysis-assets/
├── target-forecast/     # 经营目标测算（人/货/场）
│   ├── SKILL.md
│   ├── scripts/         # 确定性计算与校验脚本（纯 Python + openpyxl）
│   └── references/      # 公式与口径、黄金案例、输入模板说明
├── coupon-forecast/     # 优惠券情景测算
└── roi-forecast/        # 投放 ROI 测算
```

- 经 [project-session.ts](../src/agent/project-session.ts) 既有 `additionalSkillPaths` 接线，普通任务与受管执行任务的 Agent 均可见（SDK 按需激活）；新增目录即生效，**无路由/视图/agentOptions/边界清单改动**。唯一 Host 侧改动是能力目录 3 条登记（D5，Codex 归属）。实施中若发现还需其他 Host 改动，停下按规范先对齐（属范围变化，另请示）。
- 三个 skill 的 description 明确分工与边界（何时用谁），避免互相抢激活。

### 4.2 SKILL.md 共性骨架（三件同构）

- **何时用**：用户带着目标测算/发券决策/投放盈亏类问题且需要可复算结论时；
- **红线**：数字一律出自脚本输出（不心算不编造）；先报口径再报数；结论带"情景推演 · 非预测承诺"；交叉校验差异如实呈现；输入有 blocker 时如实报告不硬算；无执行环境（如纯文本任务）时如实声明该 skill 不适用；
- **工作流**（方法指引非强制步骤）：理解测算目标 → 输入数据校验（脚本）→ 口径与假设确认 → 脚本计算与情景对比 → 交叉校验 → 结论（含敏感度与未建模边界）→ 报告产出；
- **脚本用法与资源索引**。

### 4.3 确定性脚本（数学内核）

- 三内核**纯 Python 重实现**（参考原仓数学，黄金案例对照验收）：coupon 与 roi 原本即近纯 Python，剥离余量小；forecast 需去 pandas 化重写（均值/季节分摊/平台分组聚合为纯 Python）；不引入 pandas/numpy；
- 脚本无状态：读输入文件 → 输出结果文件（JSON/CSV/Markdown 表），带 `--version`（引擎身份）与输入摘要；幂等可重放；
- 依赖仅 openpyxl（xlsx 读取，`scripts/requirements.txt` 模式，参照 ppt-report）；pandas/numpy **不引入**——通用分析 Python 环境属 Host 环境决策（Codex 归属+安装授权），需要时另立提案，不随本变更捆绑（用户 2026-11-02 确认此边界）；
- 原仓黄金案例（目标测算 A 系列合成场景、优惠券黄金表、ROI 合成计划）转为各脚本 `--selftest` 基线：确定性回归随身携带，脱离本仓测试基建也能自检。

### 4.4 数据与产出

- **输入**：项目文件域用户资料（`020_clean` 等准备区；`010_draw` 原件软约束继续适用）；xlsx 为主要形态，skill 附输入模板生成脚本（参照原仓 templates）；
- **产出**：中间结果默认 `020_clean`，最终测算报告 `060_reports`（Markdown 报告 + 结果数据文件）；报告含口径、假设、情景结果、交叉校验、引擎版本与输入摘要、未建模边界声明；
- 不建插件存储、不建会话域、不建页面与目录入口。

## 5 架构与接入

- 无新会话接入：不涉及 Interface 版本、owner/profile、agentOptions、边界清单变化（IN01 记录"无接入变更"）；Host 侧仅 catalog-data 三条"已接入"目录登记（D5，Codex 归属数据级接缝）；
- 交付仍走[移交交付模式](engineering-workflow.md#qoder--codex-移交交付模式)的简化形态：Qoder 在 `qoder/target-forecast` 分支交付 skill 三件套 + 规格 + 自检与走查证据 → 候选清单+移交包 → 移交 Codex 做非作者独立复核与 Git/CI 至合并（无接缝互查需求，独立复核照常强制）。

## 6 风险与代价（skill 形态的如实 tradeoff）

| 风险/代价 | 应对 |
| --- | --- |
| 无页面直算：测算经任务对话由 Agent 执行，消耗模型额度 | 用户已选择的形态；脚本承担全部数字计算，模型只做理解、口径确认与解读，费用可控 |
| Agent 可能绕过脚本心算 | SKILL.md 红线（数字必须出自脚本输出）+ 报告模板含"引擎版本/输入摘要"栏位，缺失即可识别；验收含对话实测 |
| 纯 Python 重实现与原仓数值一致性 | 黄金案例对照回归进各脚本 `--selftest`；实施时逐例对表原仓期望值 |
| skill 激活不确定 | description 按使用场景明确分工；验收含合成任务实测激活与调用 |
| xlsx 环境差异（openpyxl 缺失） | `scripts/requirements.txt` + SKILL.md 写明安装一步；缺失时如实报错不降级硬算 |

## 8 交付与验收方式

流程：本讨论稿确认 → openspec 规格（**无 UI Demo 环节**——无界面变更）→ Qoder 实施三 skill（方法论红线、脚本、黄金案例自检、模板）→ `npm run check` 全量 + 合成任务走查（skill 激活、Agent 用脚本完成三类测算全流程、报告产出与 Case 引用）→ 候选清单 + 移交包 → 移交 Codex 非作者独立复核 + Git/CI 至合并 main。

验收分项：三 skill 方法论与红线齐备；脚本黄金案例全对、确定性（同输入同输出）；合成 Provider 任务内实测激活与三类测算全流程；报告产出符合 020/060 目录约定且可被 Case/决策板引用；既有链路回归。真实模型端到端、原仓退役按届时授权另行执行。
