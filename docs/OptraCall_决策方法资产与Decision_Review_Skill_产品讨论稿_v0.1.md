# OptraCall 决策方法资产体系与 Decision Review Skill 产品讨论稿

**版本：** v0.1\
**日期：** 2026-11-07\
**状态：** 产品讨论稿（首期建设建议已明确，后续能力按使用反馈演进）\
**适用范围：** OptraCall 分析资产模块、Agent Skill、决策分析与 Decision
Case\
**核心决策：** 首期先建设一个官方内置
`decision-review`（决策审视）Skill；不在首期铺开完整决策理论库，也不为每一种理论单独建设
Skill。

------------------------------------------------------------------------

## 0. 执行摘要

OptraCall 的定位不是单纯的数据分析
Agent，而是帮助用户持续做出更好决策的决策
Agent。数据分析是其中的重要能力，但决策还需要处理定性事实、领域知识与经验、目标和价值判断、行动约束，以及不确定性和执行反馈。

因此，决策理论不应只作为知识文章供 Agent
检索，而应被加工成能够在真实任务中使用的方法资产：Agent
能识别适用情境、选择方法、组织证据、检查推理、比较方案，并形成可审视、可验证、可复盘的决策说明。

本方案提出：

1.  **首期只建设一个 `decision-review` Skill。**
    它面向"是否应该做、应该选择什么、现有建议是否可靠"等决策审视任务。
2.  **以组合方法而不是理论目录组织能力。** 首期复用
    TOC/TP、循证分析、因果推理、Decision
    Analysis、有限理性、风险与不确定性分析、Decision Quality
    等已有方法思想，不把每个理论都拆成独立 Skill。
3.  **资产与运行时分离。** 分析资产包是管理、版本和分发单位；Skill 是
    Agent 在 pi-coding-agent Harness 中按需发现、加载和使用的方法载体。
4.  **Agent 自主选择与组合。** Skill
    提供适用条件、方法指导、输出要求和质量检查，不把 Agent
    锁定为固定七步或固定理论流程。
5.  **后续渐进扩展。**
    根据真实任务和评测结果，再逐步拆分方案比较、风险与不确定性分析、决策复盘等
    Skill。
6.  **连接 Decision Case 学习闭环。**
    将决策问题、依据、假设、策略、用户采纳、执行结果和反馈关联起来，但不把
    Agent 建议自动视为用户决定，也不把一次成功直接沉淀为通用规律。

本方案不新增第四层架构、不修改 pi-coding-agent SDK 内核、不建设独立决策
Agent，也不在首期建设完整的决策管理平台。

## 1. 背景与问题定义

### 1.1 为什么 OptraCall 需要决策方法资产

科学管理和管理数字化让组织能够更系统地测量目标、过程和结果。数据让问题可见、让方案可比较，也让行动效果能够被检验。但"有数据"不等于"已经具备完整决策依据"。

一项实际决策通常同时涉及：

-   **事实认识：** 发生了什么，当前状态如何；
-   **因果与机制判断：** 为什么发生，采取行动可能改变什么；
-   **未来与不确定性：** 可能出现哪些结果，判断有多大把握；
-   **目标与价值取舍：** 什么结果更重要，哪些代价可以接受；
-   **行动选项与约束：**
    有哪些可行方案，资源、时间、制度和能力边界是什么；
-   **反馈与修正：** 如何判断选择是否有效，什么情况出现时需要重新考虑。

数据是重要依据，但不是全部依据。访谈、观察、制度、流程、案例、专家经验、行业知识、战略目标和风险偏好，都可能影响判断。不同材料的证明力不同，必须识别来源、适用范围和可信程度，不能将所有信息简单等同。

### 1.2 从"分析结论"到"决策理由"

OptraCall 不应只回答：

-   指标发生了什么变化？
-   哪个因素与结果相关？
-   预测结果是多少？

还应在需要时继续帮助用户回答：

-   当前真正要作出的决定是什么？
-   目标和约束是否明确？
-   现有解释有哪些证据支持或反驳？
-   是否存在其他可行方案？
-   每种方案的收益、代价和风险是什么？
-   哪些未知信息可能改变选择？
-   为什么推荐某个方案，什么条件下应改变建议？
-   后续如何验证、复盘和学习？

这并不意味着每个数据分析任务都必须变成完整决策流程。Agent
应根据任务性质和决策重要程度，判断是否需要调用决策审视能力。

### 1.3 产品目标

建设一套轻量、可组合、可验证、可演进的决策方法资产，使 OptraCall：

1.  不把量化数据当作唯一决策依据；
2.  能区分事实、证据、假设、经验、偏好与价值判断；
3.  能在证据不完整时保持诚实，不伪造确定性；
4.  能识别替代方案、关键取舍和行动约束；
5.  能根据任务需要组合不同决策理论与分析方法；
6.  能把决策理由与后续行动结果连接起来，支持持续学习。

## 2. 产品定位与核心概念

### 2.1 决策理论在分析资产模块中的定位

建议将决策理论作为分析资产中的**决策方法资产（Decision Method
Assets）**建设。它不是一组理论文章，也不是一个独立的决策 Agent，而是可被
Agent 发现、加载、组合和应用的方法能力。

建议采用以下关系：

  ------------------------------------------------------------------------------------------------------
  对象                    定位                    主要职责
  ----------------------- ----------------------- ------------------------------------------------------
  分析资产包（Analysis    资产管理与分发单位      管理方法、规则、模板、参考资料、版本和适用范围
  Asset Pack）                                    

  分析方法（Analysis      可复用的方法定义        描述方法的目标、原理、输入、适用条件、局限和判断规则
  Method）                                        

  Skill                   Agent 运行时方法载体    告诉 Agent 何时使用、如何应用、如何输出和自检

  Tool                    可调用的软件能力        执行计算、检索、模拟、数据查询和确定性校验

  Scenario Bundle         场景化任务组合          在明确场景下组合目标、资产、依赖和交付要求

  Decision Case           决策过程与结果载体      关联问题、项目、任务、依据、决定、行动、结果和学习
  ------------------------------------------------------------------------------------------------------

**核心区别：分析资产包负责"管理什么"，Skill 负责"Agent 如何使用"，Tool
负责"实际执行什么"。**

### 2.2 理论、方法、Skill、Tool 的关系

以有限理性为例：

-   理论：现实决策者受信息、时间和认知能力限制；
-   方法：明确决策期限、最低可接受条件、信息价值和停止分析条件；
-   Skill：在适用任务中指导 Agent
    识别信息缺口、判断继续分析是否可能改变选择，并说明停止或继续的理由；
-   Tool：必要时计算信息获取成本、方案收益或敏感性，但不能替代偏好和价值判断。

因此，不应采用"一个理论 = 一个 Skill = 一个 Tool"的机械拆分方式。

### 2.3 与既有四类决策输入的关系

OptraCall 已采用四类信息组织决策依据：

  -----------------------------------------------------------------------------------------------------------
  信息类别                典型来源                                 典型分析方式
  ----------------------- ---------------------------------------- ------------------------------------------
  量化事实                数据库、业务系统、经营指标               统计分析、趋势、对比、实验、因果效应估计

  定性事实                访谈、观察、制度、流程、案例             事实核验、过程追踪、定性分析

  知识与经验              行业规律、业务经验、历史案例、专业知识   逻辑推理、类比分析、机制解释

  目标与价值判断          战略、经营目标、资源约束、风险偏好       TOC、冲突分析、方案权衡、决策分析
  -----------------------------------------------------------------------------------------------------------

这四类是**决策信息的组织方式，不是四个固定工作流，也不是四个
Skill**。`decision-review` 在任务需要时可以组合使用其中任意几类。

## 3. 首期建设范围：Decision Review Skill

### 3.1 首期产品定义

  ----------------------------------------------------------------------------------------------------------------
  项目                                定义
  ----------------------------------- ----------------------------------------------------------------------------
  Skill 名称                          `decision-review`

  中文名称                            决策审视

  类型                                官方内置决策方法 Skill

  所属                                OptraCall 分析资产模块／决策方法资产包

  运行载体                            pi-coding-agent SDK 的 Skill 机制

  核心任务                            审视一项业务建议或待定决策，检查目标、证据、假设、备选方案、取舍与验证条件

  主要用户                            业务分析与决策人员、经营管理者，以及承担决策支持任务的 Agent

  首期原则                            轻量、按需调用、允许未决、不强制完整流程
  ----------------------------------------------------------------------------------------------------------------

### 3.2 典型触发场景

当用户提出以下类型的问题时，Agent 可以判断是否加载该 Skill：

-   "会员复购下降了，要不要发优惠券？"
-   "这个经营建议是否有充分依据？"
-   "两个方案各有利弊，应该怎样选择？"
-   "这份分析报告得出的结论，能否支持这个行动？"
-   "我们还缺少哪些信息，才能作出决定？"
-   "这个项目是否应该继续投入？"
-   "如果现在不能确定，是否可以先做小范围试验？"

### 3.3 不应触发的场景

以下任务通常不需要启动完整决策审视：

-   纯数据查询、指标解释和报表生成；
-   单纯的数据清洗、统计计算或图表制作；
-   理论概念解释、文献摘要；
-   用户明确只要求完成某项分析，不要求评价或选择行动；
-   已有明确操作指令且没有实质决策空间的常规任务。

Agent 可以在普通分析中借用某条检查规则，但不应为了"使用
Skill"而增加无意义的决策流程。

### 3.4 Skill 的核心职责

`decision-review` 不负责替用户作出价值选择，而是帮助 Agent：

1.  识别当前真正需要决定的问题；
2.  明确目标、约束、决策期限和已知偏好；
3.  组织事实、证据、假设、经验和未知；
4.  判断当前解释是否有充分依据，是否存在反证或替代解释；
5.  识别可行的替代方案，包括暂缓、不行动或先试行；
6.  比较方案可能产生的后果、代价和风险；
7.  说明建议依赖的关键假设、适用条件和不确定性；
8.  给出验证安排和重新考虑条件；
9.  区分 Agent 建议、用户确认的决定和实际执行结果。

### 3.5 方法组合原则

首期不重新建设所有理论，而是复用和组合已有方法资产：

  -------------------------------------------------------------------------------------------------------
  理论／方法              首期承担的职责                                   产品处理方式
  ----------------------- ------------------------------------------------ ------------------------------
  TOC                     聚焦目标、约束和关键矛盾                         复用既有 TOC 方法资产

  TP（Thinking            检查因果逻辑、冲突与行动后果                     复用既有 TP 方法资产
  Processes）                                                              

  科学方法与循证分析      区分假设、支持证据、反证和证伪条件               复用既有循证方法

  因果推断                检查相关与因果、观察与干预效果                   复用分析方法及相应工具

  Decision Analysis       组织选项、后果、偏好与不确定性                   首期作为轻量方法指导

  有限理性                考虑时间、信息和认知成本，明确分析停止条件       作为通用方法规则

  风险与不确定性分析      区分可估计风险与未知，识别情景和敏感因素         按任务需要使用

  行为决策／前景理论      检查参照点、损失表述和认知偏差                   作为审视检查项

  专家直觉与自然决策      检查经验适用范围、反馈质量和环境可预测性         作为证据审查规则

  Decision Quality        检查决策框架、选项、信息、价值、推理和行动安排   作为质量检查框架，不首期单建
                                                                           Skill
  -------------------------------------------------------------------------------------------------------

TOC/TP
是既有决策思考框架的重要组成，但不能单独覆盖所有方案比较、不确定性处理和决策质量问题。首期以
`decision-review` 做轻量整合，不复制既有 TOC/TP
内容，也不把方法组合固化为必须逐项执行的固定流程。

### 3.6 Skill 的方法选择原则

Agent 应按任务需要选择方法，而不是每次执行完整理论清单：

-   有明确约束或系统冲突时，可优先考虑 TOC/TP；
-   需要判断"为什么发生"或"行动是否有效"时，考虑循证分析与因果推断；
-   存在多个可行方案时，考虑 Decision Analysis；
-   信息不足且决策期限明确时，考虑有限理性与信息价值；
-   后果差异大、概率不确定时，考虑情景与风险分析；
-   需要检查经验判断时，检查经验的适用条件和反馈质量；
-   决策重要、影响范围大时，使用 Decision Quality 进行综合审视。

方法可以组合、调整或停止。不得因为某个方法存在于资产包中，就强制使用它。

## 4. Decision Review Skill 的运行设计

### 4.1 建议的 Skill 目录结构

首期可以采用轻量目录：

``` text
decision-methods/
└── decision-review/
    ├── SKILL.md
    ├── references/
    │   ├── decision-theory-primer.md
    │   ├── toc-tp-usage.md
    │   ├── evidence-and-causality.md
    │   ├── decision-analysis.md
    │   ├── uncertainty-and-bounded-rationality.md
    │   └── decision-quality-checklist.md
    ├── templates/
    │   └── decision-brief.md
    ├── examples/
    │   ├── coupon-decision-example.md
    │   └── insufficient-evidence-example.md
    └── scripts/
        └── (按实际需要增加)
```

说明：

-   `SKILL.md`
    是入口，只保留触发条件、方法选择、核心规则、输出要求和自检要求；
-   `references/` 保存理论摘要、方法边界和专业说明，按需读取；
-   `templates/` 保存决策说明模板；
-   `examples/` 保存正例、反例和边界案例；
-   `scripts/` 只放确实需要确定性执行的代码，不把所有推理逻辑写成脚本。

以上是建议结构，不代表首期必须一次性创建所有文件。应先保证入口 Skill
可用，再根据评测补充资源。

### 4.2 SKILL.md 的建议内容骨架

``` markdown
---
name: decision-review
description: 审视业务建议或待定决策，检查目标、证据、假设、
备选方案与取舍，形成决策说明及验证建议。用于“是否应该做”
“怎样选择”“方案是否可靠”等任务；不用于纯查数或报表生成。
---

# Decision Review

## Objective
帮助用户理解一项选择的依据、主要取舍、不确定性和后续验证方式。

## When to use
识别真实决策问题、多个可行方案、重要行动建议或决策依据审查任务。

## Method selection
按任务需要组合 TOC/TP、循证分析、因果推断、Decision Analysis、
有限理性、风险分析和 Decision Quality 检查。

## Evidence discipline
区分事实、证据、假设、经验、偏好和未知。
保留来源、适用范围和核验状态。
不得将相关关系直接写成因果结论。

## Decision discipline
考虑替代方案、不行动、暂缓和小范围试行。
不伪造概率、效用、收益、权重或用户偏好。
区分 Agent 建议与用户最终决定。

## Output
形成适合当前任务的决策说明。
明确关键依据、假设、取舍、建议、验证安排和重新考虑条件。

## Self-check
检查是否存在未标注假设、遗漏反证、虚构精确性、
忽略硬约束或将建议误记为已决定等问题。
```

### 4.3 运行时处理方式

建议采用以下逻辑：

1.  Agent 理解用户任务及 Host 提供的 Case、目标、约束和业务上下文；
2.  Agent 判断是否存在实质决策审视需求；
3.  如适用，发现并加载 `decision-review`；
4.  Skill 提示 Agent 选择适合的方法和参考资料；
5.  Agent 自主选择工具、数据源和其他 Extension；
6.  Agent 形成决策说明，必要时创建或更新 Analysis IR；
7.  Agent 对结论、证据和假设进行自检；
8.  将适合长期保留的依据和决策记录关联到 Case；
9.  后续执行结果进入 Case 反馈，供复盘与经验修正。

这是一种可能的运行路径，不是 Host 强制编排的固定流程。Agent
可以根据任务直接进入某个方法、跳过不必要的环节，或在证据不足时停止并说明原因。

## 5. 决策说明（Decision Brief）交付规范

### 5.1 输出目标

决策说明不是一份强制的长报告，而是将决策理由显性化的轻量交付物。内容应随决策重要性和任务复杂度伸缩。

### 5.2 标准内容结构

  ---------------------------------------------------------------------------------------------------------
  模块                    应回答的问题                                   注意事项
  ----------------------- ---------------------------------------------- ----------------------------------
  决策问题                当前要决定什么？何时需要决定？                 区分业务现象与实际选择

  目标与约束              希望改善什么？哪些条件不能突破？               区分用户确认与 Agent 推测

  候选方案                有哪些可行选择？是否考虑不行动、暂缓或试行？   避免只比较用户最先提出的两个选项

  事实与证据              已知什么？依据来自哪里？                       标注来源、时间、口径和核验状态

  假设与未知              哪些判断尚未证实？关键缺口是什么？             不把假设写成事实

  方案后果                各方案可能带来什么收益、成本和风险？           区分已知后果与预测

  取舍与建议              为什么推荐？牺牲了什么？适用条件是什么？       允许条件性建议或暂时无法推荐

  验证与调整              观察什么？何时复查？什么情况触发重新考虑？     指标和观察周期应与目标相符
  ---------------------------------------------------------------------------------------------------------

### 5.3 输出状态

建议至少区分：

-   `draft`：信息尚不完整，正在形成判断；
-   `ready_for_review`：Agent 已形成建议，等待用户审视；
-   `accepted`：用户明确采纳或确认；
-   `rejected`：用户明确拒绝；
-   `deferred`：暂缓决定；
-   `superseded`：被后续版本或新决定取代。

状态的正式枚举和持久化字段需与现有 Decision Case
数据模型协调，不能在首期重复建设一套决策状态系统。

### 5.4 不允许混淆的对象

以下对象必须分别记录：

1.  Agent 的分析结论；
2.  Agent 的建议；
3.  用户确认的决定；
4.  实际执行的行动；
5.  行动产生的结果；
6.  对原有假设和策略的复盘结论。

Agent
生成建议不代表用户已经决策；用户采纳不代表行动已经执行；行动结果好也不自动证明原有因果解释正确。

### 6.2 与 analysis-ir Extension 的关系

`analysis-ir` 已确定为官方内置 Extension。`decision-review` 不替代
IR，也不把 IR 当作决策工作流引擎。

-   `decision-review`：指导 Agent 如何审视决策问题和组织判断；
-   `analysis-ir`：在适用时承载结构化分析意图、方法、数据映射、执行计划和分析结果；
-   Host：提供存储、权限、原子写入、版本治理及 Case/Project/Session
    关联。

不是每次决策审视都必须创建 IR。对于轻量判断，可以直接形成决策说明并关联
Case；当任务需要结构化、可复用的分析执行表达时，再使用 IR。

### 6.3 与 TOC/TP 既有方案的关系

既有 TOC-centered Decision Thinking Framework
继续作为方法体系的重要基础：

-   TOC 是整体聚焦主线；
-   TP 是主要逻辑推理工具；
-   科学方法和循证思维提供证据纪律；
-   系统思维与系统动力学解释结构和长期影响；
-   战略思维连接诊断与协调行动；
-   Decision Quality 与 Decision Analysis 补充决策质量和方案比较；
-   OSM、PDCA、Toyota Kata 和效果验证连接执行、反馈与学习。

`decision-review` 是这些方法在 Agent
运行时的轻量使用入口，不是重新定义或取代这套理论框架。它也不要求每个任务都执行完整框架。

### 6.4 与假设库、策略库和 Decision Case 的关系

决策审视会产生或更新以下内容：

-   假设：可能的原因、机制和成立条件；
-   策略：可选择的行动方向及其适用条件；
-   证据：支持、反驳或尚未核验的材料；
-   决定：用户实际确认的选择；
-   结果：执行后观察到的变化；
-   经验：经过复盘后形成的可复用认识。

这些对象优先关联到现有 Decision
Case，并按需进入假设库、策略库。首期不新增独立数据库，不将临时推测自动沉淀为长期资产。

## 7. 后续产品演进方案

后续不按理论数量扩张
Skill，而根据真实任务的重复性、独立性和评测结果拆分能力。

### 7.1 目标能力地图

  ------------------------------------------------------------------------------------------------------------------------------------
  能力方向          未来可能的 Skill                 主要任务                                       首期状态
  ----------------- -------------------------------- ---------------------------------------------- ----------------------------------
  决策问题澄清      `decision-framing`               定义决策问题、目标、约束、决策期限和关键未知   先由 decision-review 覆盖

  决策审视          `decision-review`                综合审视依据、假设、方案、取舍和验证           **首期建设**

  方案比较          `option-analysis`                比较选项、后果、成本、收益、偏好和权衡         先作为 decision-review 的方法分支

  风险与不确定性    `risk-uncertainty-analysis`      情景、敏感性、概率边界、稳健性和退出条件       后续按需拆分

  约束与冲突分析    `constraint-conflict-analysis`   约束识别、冲突图、TP 推理和方案构造            复用
                                                                                                    TOC/TP，是否独立由复用情况决定

  决策复盘          `decision-retrospective`         比较预期与实际、分析偏差、修正假设和策略       后续建设

  决策质量评测      `decision-quality-check`         检查决策框架、选项、信息、价值、推理和承诺     先作为共同检查规则

  系统影响分析      `system-impact-analysis`         反馈回路、延迟效应、二阶影响和长期副作用       先复用系统思维方法，仿真按需接入
  ------------------------------------------------------------------------------------------------------------------------------------

表中是能力演进方向，不代表所有项目都必须建设，也不代表每项能力最终都需要独立
Skill。

### 7.2 Phase 1：Decision Review MVP

**目标：** 证明单一决策审视 Skill
能够在真实任务中改善决策依据和建议质量。

建设内容：

-   `decision-review` Skill；
-   精简的决策理论参考资料；
-   TOC/TP、循证分析和 Decision Analysis 的调用指导；
-   决策说明模板；
-   正例、反例和边界案例；
-   基础的调用、应用和质量评测记录。

暂不建设：

-   多个独立决策 Skill；
-   完整决策流程编排器；
-   复杂概率和效用建模平台；
-   企业级决策治理与审批平台；
-   新的决策数据库。

### 7.3 Phase 2：专业方法拆分

**触发条件：**
真实任务中某一方法被频繁、稳定、独立地调用，且其输入、输出和质量要求已经清晰。

可能拆分：

1.  `option-analysis`：专业方案比较；
2.  `risk-uncertainty-analysis`：风险与不确定性分析；
3.  `decision-framing`：复杂决策问题定义；
4.  `decision-quality-check`：决策质量专项检查。

拆分后，`decision-review` 仍作为综合审视入口。Agent 根据任务需要组合子
Skill，而不是每次加载全部能力。

### 7.4 Phase 3：Decision Retrospective 与双库联动

**目标：** 从"形成决策建议"走向"积累决策经验"。

建设内容：

-   记录当时的目标、依据、假设、预测和建议；
-   记录用户采纳、拒绝、暂缓及原因；
-   关联实际行动、时间和资源投入；
-   对照预期结果与实际结果；
-   区分判断错误、执行偏差和外部环境变化；
-   经过复核后更新假设库和策略库。

沉淀经验时必须保留适用条件、来源、时间和反例。不能因为一次行动成功，就将其提升为普遍规律。

### 7.5 Phase 4：决策组合与场景资产

当专业 Skill 和方法资产稳定后，可以将其组合为场景包，例如：

-   会员复购下降诊断与决策；
-   促销投入与优惠策略评估；
-   新业务投资与退出决策；
-   门店经营改善；
-   供应链约束与资源配置；
-   月度经营复盘与行动调整。

Scenario Bundle 负责场景目标、依赖、交付要求和推荐资产组合；Agent
仍然根据实际情况自主调整方法和执行顺序。

### 7.6 Phase 5：决策学习与组织智能

在个人工作台阶段验证后，再逐步扩展到团队和企业场景：

-   跨 Case 识别重复问题、约束和策略模式；
-   识别哪些假设在特定业务条件下更常成立；
-   记录组织目标、风险偏好和决策规则；
-   支持多角色证据审查、方案讨论和决策确认；
-   连接 Decision Graph、Decision Platform 和执行反馈；
-   在权限边界内复用团队与组织经验。

这是长期演进方向，不是首期建设范围。

## 8. Skill 的评测与持续改进

### 8.1 不能只评测"是否调用了 Skill"

评测需要区分三个层次：

  ---------------------------------------------------------------------------------------------------------------------------
  层次                    评测问题                                               观测方式
  ----------------------- ------------------------------------------------------ --------------------------------------------
  加载                    Agent 是否在适当任务中发现并加载了正确版本？           Skill 调用记录、版本记录

  应用                    Agent 是否真正使用了方法，而非只提到理论名称？         产物结构、推理轨迹、证据引用、方法应用记录

  质量                    应用方法后，决策说明是否更完整、准确、诚实且可验证？   案例评测、人工审核、回归测试
  ---------------------------------------------------------------------------------------------------------------------------

### 8.2 首期核心评测维度

1.  **问题框定：**
    是否识别真正要决定的事项，而不是把现象直接当作决策问题？
2.  **目标与约束：** 是否区分用户明确目标、Agent 推测和未知偏好？
3.  **证据纪律：** 是否保留来源、区分事实与假设、处理反证？
4.  **因果严谨性：** 是否避免将相关关系直接写成干预效果？
5.  **方案完整性：** 是否考虑合理替代方案、不行动、暂缓或试行？
6.  **不确定性表达：** 是否避免虚构概率、精确收益和效用权重？
7.  **取舍透明度：** 是否说明推荐方案的代价、风险和适用条件？
8.  **行动可验证性：** 是否提出与目标一致的观察和重新考虑条件？
9.  **用户决策边界：** 是否区分 Agent 建议与用户确认的决定？
10. **方法适配性：** 是否避免在简单任务中强行启动复杂方法？

### 8.3 首期测试案例

至少建立以下案例集：

  案例                             主要测试点
  -------------------------------- --------------------------------
  复购下降，是否发券               事实、因果、方案比较和目标取舍
  销售增长，但利润下降             指标目标错位、约束和二阶影响
  只有少量访谈，没有完整经营数据   定性证据、适用范围和不确定性
  两个方案收益相近，但风险不同     风险偏好和方案权衡
  管理者经验判断与数据趋势冲突     经验适用性、数据质量和反证
  决策期限临近，继续分析成本很高   有限理性、停止条件和信息价值
  证据不足且行动不可逆             证据门槛、延迟决策和风险控制
  用户只要求查询指标               不应误触发完整决策审视

### 8.4 与 Harness Optimizer 的关系

后续 Harness Optimizer 可以利用 Skill
的调用轨迹、失败案例和评测结果，提出：

-   Skill 描述与触发条件优化；
-   方法指导和输出要求优化；
-   参考资料组织优化；
-   示例和边界案例补充；
-   回归测试用例扩充。

但它只能提出候选修改和发布建议。正式 Skill
及专业方法资产仍由资产所有者审核、版本化和发布。Harness Optimizer
不直接修改正式业务资产，也不修改 pi-coding-agent SDK 内核。

## 9. 资产治理与版本管理

首期不需要建设复杂的资产治理平台，但应从一开始保留必要的规范。

### 9.1 每项方法资产建议记录

  字段                          含义
  ----------------------------- ---------------------------------------
  `asset_id`                    稳定资产标识
  `name`                        资产名称
  `asset_type`                  方法、Skill、模板、参考资料或工具指导
  `version`                     资产版本
  `status`                      草稿、测试、已发布、弃用
  `purpose`                     解决什么问题
  `applicable_context`          适用情境
  `limitations`                 局限和不适用条件
  `source`                      理论来源、参考文献或内部经验来源
  `owner`                       资产维护者
  `created_at` / `updated_at`   时间信息
  `evaluation`                  评测记录和适用结论

具体字段应与现有 Extension 资产规范对齐，避免另建一套目录和版本系统。

### 9.2 版本发布原则

-   已发布版本保持可追溯；
-   Skill 更新必须通过回归测试；
-   方法来源、适用边界发生变化时，应更新版本说明；
-   旧版本被新版本替代时保留历史引用；
-   Case 应记录当时使用的
    Skill/方法版本，避免后续无法解释当时的判断依据；
-   未经验证的经验只能作为候选假设或案例，不能直接升级为正式方法规则。

### 10.2 首期验收标准

**功能验收**

-   [ ] Agent 能识别适合决策审视的任务；
-   [ ] Agent 能在适当任务中加载 `decision-review`；
-   [ ] 简单查询和常规分析不会被强制套入完整决策流程；
-   [ ] Agent 能按任务需要调用 TOC/TP、循证分析和其他方法；
-   [ ] Agent 能输出结构化但可伸缩的决策说明；
-   [ ] 决策说明能与现有 Case/Project/Session 关联；
-   [ ] 能记录 Skill 和方法版本。

**质量验收**

-   [ ] 能区分事实、证据、假设、经验、偏好和未知；
-   [ ] 不把相关性直接当成因果结论；
-   [ ] 不虚构概率、收益、效用权重和用户偏好；
-   [ ] 能识别至少一个合理替代方案，或说明为何没有；
-   [ ] 能说明推荐方案的关键依据、代价和适用条件；
-   [ ] 能提出合理的验证或重新考虑条件；
-   [ ] 能区分 Agent 建议、用户决定和执行结果；
-   [ ] 证据不足时允许输出条件性建议或保持未决。

**架构验收**

-   [ ] 不新增独立决策 Agent；
-   [ ] 不修改 pi-coding-agent SDK 内核；
-   [ ] 不让 Host 编排 Agent 的内部分析步骤；
-   [ ] 不重复建设分析资产、IR 或 Decision Case 的既有能力；
-   [ ] 不要求所有决策任务都创建 Analysis IR；
-   [ ] 不因首期 Skill 建设而新增独立数据库或复杂治理平台。

## 11. 主要风险与设计约束

### 11.1 理论堆砌

**风险：** Skill 罗列大量理论名称，却不能帮助 Agent 完成具体任务。

**应对：**
以任务和方法为中心组织资产；每个方法都要说明适用条件、输入、应用方式、输出和局限。

### 11.2 固定流程化

**风险：** 把决策审视做成每次必须执行的长流程，增加简单任务成本。

**应对：** Skill 只提供方法选择和质量约束；Agent
根据问题复杂度自主组合、调整和停止。

### 11.3 虚假的精确性

**风险：** Agent 为了比较方案而自行编造概率、收益、权重和评分。

**应对：**
明确区分已知数据、估计、主观判断和未知；缺少依据时使用定性比较或区间/情景表达，并说明限制。

### 11.4 把价值判断伪装成客观结论

**风险：** Agent 擅自决定企业应该优先利润、增长、客户体验或员工稳定。

**应对：**
用户明确的目标与偏好优先；未明确时提出需要确认的价值取舍，不把 Agent
推测当成用户意图。

### 11.5 把经验当成规律

**风险：** 某次成功案例被直接沉淀为通用策略。

**应对：** 保留适用情境、来源、失败案例和复核状态；跨 Case
复用时重新检查条件。

### 11.6 只评价结果，不评价决策过程

**风险：**
偶然成功的决策被认定为优秀方法，合理但遇到外部冲击的决策被认定为失败。

**应对：**
分别评估决策过程质量、执行质量和业务结果；通过反馈持续修正，但不将三者混为一谈。

## 12. 最终产品建议与待确认事项

### 12.1 建议确立的首期产品决策

1.  决策理论正式纳入 OptraCall 分析资产模块，作为决策方法资产建设。
2.  首期明确建设一个官方内置 Skill：`decision-review`（决策审视）。
3.  首期不为有限理性、前景理论、Decision Analysis、Decision Quality
    等每个理论分别创建独立 Skill。
4.  首期复用既有
    TOC/TP、循证分析、因果推理等方法资产；缺少的通用方案比较和不确定性指导，以轻量方法补齐。
5.  Skill 运行在既有 pi-coding-agent Harness 中，不新增 Agent
    Runtime，不修改 SDK 内核。
6.  Agent 自主判断是否使用 Skill、选择何种方法和工具，不由 Host
    规定固定步骤。
7.  决策说明与 Decision Case
    关联，逐步连接假设库、策略库、用户决定、行动和结果反馈。
8.  后续 Skill
    拆分由真实任务复用频率、方法独立性和评测结果驱动，不以理论数量驱动。

### 12.2 后续需要在实施中确认的事项

-   `decision-review` 首期采用的 Skill 元数据和 Extension 资产登记格式；
-   决策说明是否直接使用现有 Case
    产物结构，还是在现有结构上增加轻量字段；
-   哪些方法参考资料应作为首期必备资源，哪些按需补充；
-   首期测试案例的业务领域和数量；
-   Skill 的调用轨迹、方法应用证据和版本记录如何进入现有评测链路。

这些是实施细节，不影响首期产品方向。

## 13. 参考理论与资料方向

以下资料用于建设参考资料目录。具体引用和摘要应在资产制作时核对原文、版本和适用范围。

1.  **Frederick W. Taylor --- *The Principles of Scientific
    Management***：科学管理、测量、标准化与工作改进。
2.  **Herbert A. Simon --- *Administrative
    Behavior***：有限理性、组织决策和满意解。
3.  **Daniel Kahneman & Amos Tversky --- Prospect
    Theory（1979）**：风险情境中的选择行为、参照点和损失框架。
4.  **Daniel Kahneman & Gary Klein --- Conditions for Intuitive
    Expertise（2009）**：专家直觉形成的环境条件与反馈要求。
5.  **Ronald A. Howard --- Decision
    Analysis（1980）**：决策分析、偏好、不确定性和系统分析。
6.  **Frank H. Knight --- *Risk, Uncertainty and
    Profit***：可度量风险与不确定性的区别。
7.  **Judea Pearl --- *Causality***：因果模型、干预与反事实推理。
8.  **Evidence-Based Management /
    CEBMa**：多来源证据、证据质量与循证决策。
9.  **Decision Quality / Strategic Decisions
    Group**：决策框架、备选方案、信息、价值、推理和承诺。
10. **Eliyahu M. Goldratt --- TOC / Thinking Processes
    相关著作**：约束聚焦、因果逻辑、冲突与系统改善。

理论摘要应服务于方法应用，不应把参考资料数量当作资产建设成果。

## 结语

OptraCall 要建设的不是一个"懂很多决策理论"的
Agent，而是一个能够在真实业务问题中正确使用决策方法的 Agent。

数据分析帮助我们认识事实，因果推理帮助我们理解机制，知识与经验帮助我们提出解释，决策理论帮助我们比较行动，目标与价值决定取舍，执行反馈则帮助我们修正认识。

首期的 `decision-review`
是这条能力链的入口。它不追求一次性覆盖所有理论，而是先让 Agent
在真实任务中做到：**说清楚要决定什么、依据是什么、哪些仍是假设、为什么这样取舍，以及什么情况下应该改变决定。**

这与 OptraCall 的长期产品理念一致：**持续做出更好的决策。**
