# 业务语义增强与独立核算 Agent 一期方案

用户已确认本方案并授权实施、本地检查、兼容迁移验证、联合回归、真实模型对照、独立复核和 Git／CI 后合并 main，合并前更新 main。复用现有 RAP／SAP／Case，只做必要增强，保留现有项目、会话和文件。运行服务采用不在本次授权内。原 [EC01–EC06 建议](extension-correctness-proposal.md)保留为历史讨论，由本方案取代其作为本期实施依据。

## 一 当前基线与一期目标

设计核对基线为工作树 `94a2/OptraCall`、`codex/engineering-reliability`、HEAD `66b36268d6b6d73a0be79d9f327c04994835597d`。它是源码核对身份，不表示运行服务已经采用该提交；实施前重新核对最新 main、WIP 和真实运行版本。

已有能力包括：

- RAP 需求实例、确认快照、不可变 0.2 发布物和显式送入；未确认框架可以探索，正式发布和正式送入沿用现有确认条件。
- SAP 0.2 指标定义、口径、场景、来源、人工审核发布和项目精确版本启用；SAP 提供定义，不执行指标计算。
- Case 关联现有项目，项目下设任务 Session；背景、判断、未知、行动及经验引用由现有 Case 结构承载。
- Pi 统一 Runtime、Interface v1、独立 owner、取消与观察恢复；Agent 已能用 bash／Python 等工具。
- 文件“保存并采用此版本”、来源摘要及操作回执。已有采用能力继续复用，不另建版本平台。

一期目标是：关键业务事实及未决内容实际到达 Agent；重要结论能由另一会话自主核对；差异、未知和版本关系可查看；现有工作原位可用。新增语义的收益和核算的收益分别验证。

## 三 RAP SAP Case 的职责与增强

### SV01 各自回答的问题

| 权威来源 | 负责内容 | 本期强化 | 不承担 |
| --- | --- | --- | --- |
| RAP | 本次决策目标、对象、范围、约束、事实／假设／未知、所需资料 | 生成时不靠凑澄清数量；把重要未决问题与风险内容送达，而不只显示数量；方法路径继续表示建议 | 企业全局指标库、强制执行计划或最终答案 |
| SAP | 指标、对象、维度、口径、适用范围、来源与版本 | 利用现有 definition、粒度、caliber_switches、type_params、provenance 及场景说明表达单位、分母、去重、退款、时间等 | 编排完整分析步骤、承包全部算法、替用户确认真实业务定义 |
| Case | 当前经营背景、判断与未知、关联项目、决策／行动／反馈及经验出处 | 区分事实、假设、建议、采用、执行和效果；引用经验时带适用背景及未知 | 复制全部 RAP／SAP，或把核算通过当成经营效果验证 |

上述为内容职责，不新增一套同名实体。普通项目可以不关联 Case；不为核算强制新建 Case。一个 Case 仍可关联多个原项目，一个原项目仍由原任务 Session 组成。

### SV02 具体改动和格式范围

1. 调整 RAP／SAP 起草及修订引导，让必要业务含义进入已有字段；信息不足可以保留未知，不凭模型猜测填成已确认。
2. RAP 消费摘要至少包含相关 openQuestions／risks 的实际内容及可定位全文，不仅是条目数量。摘要不包含全部企业资料。
3. SAP 延续“精确版本索引＋按需读取全文”；增强口径预览和引用提示，不把所有资产全文塞进每轮消息。
4. 补充经营材料优先放在现有项目文件，通过现有 Case／项目引用提供；不在自由文本备注里偷偷定义第二套机器协议。
5. 本期不改变 `rap:0.2`／`sap:0.2` 校验规则和发布字节。已有结构无法表达的独立需求列为后续格式变更，不临时扩字段。明确公式是业务定义，不等于固定分析路线。

### SV03 版本、冲突与实际消费

- 启动分析／核算前可展开查看来源、版本／指纹、确认状态和未决内容；来源仍指向原 RAP、SAP、Case 或文件，不成为新的语义权威库。
- 同名口径冲突并列呈现，不设“SAP 永远胜过 RAP”或“最新文本永远优先”。用户明确解决后，通过原业务流程修订、确认和发布；Agent 只能提出修订建议。
- 区分 Host 实际提供的材料、工具可见记录中实际读取的材料、Agent 声称采用的材料。无法观察的读取不编造证据。
- Case 复用现有 `task_context_prepare` 回执；新普通请求在现有 `optracall.run` JSONL 自定义记录路径追加可选的“本次提供上下文”元数据，记录选定 RAP／SAP 身份、实际提供摘要／指纹、未决内容及 Case operationId。仅对新运行追加，缺少原证据的旧记录不回填；不另建上下文库。
- SAP 索引当前在项目原生资源初始化时取得；RAP／Case 在每次消息准备时取得。记录必须反映各自实际来源，不能用当前启用 SAP 列表冒充存活会话收到的旧索引。提供回执不证明模型已读懂或业务已确认。
- 一期不做 SAP 热切换，也不自动重建作者会话。显示该资源实际初始化的 SAP 版本；需要新 SAP 时提示用户显式新建任务，使新 owner／资源重新取得索引。同 worker 的 `/new` 或 `reload` 不承诺刷新 SAP。SDK 有刷新能力，当前 Host 接线尚未提供可靠的 SAP 热切换；后者后置，不在旧提示上悄悄叠加冲突定义。
- 旧报告缺少原采用依据时显示“原输入／口径版本不详，本次按选定依据核对”。不把事后选定输入描述为复原了原分析条件。

## 四 独立核算的产品行为

### SV04 发起与最小 UI

原任务增加“核算关键结论”。用户选择：作者产物的具体文件版本、核算问题／范围、获准的源数据、RAP／SAP／Case 依据及模型。可以沿用可靠的原采用记录；缺少时明确确认本次选用依据。初次发起须原任务当前空闲且选定文件可稳定读取，避免把尚在生成的半成品当完成交付；不锁住整个项目的其他任务。

界面只增加局部发起面板和核算详情：选用依据、实际运行阶段、停止／重新观察、双方报告、差异与无法确认项。核算不占用或覆盖原任务 draft、lastRun、sessionFile，不成为新的普通任务。归档项目不允许新核算，沿用现有空闲准入。

不改变导航、Case／项目看板、四阶段需求工作台或分析／决策切换，不给报告盖“全部正确”绿章。若后续实现需要大幅改布局，先提供 UI Demo 再实施该部分。

### SV05 先独立计算 再对照作者

1. Host 稳定读取并保存本次选定数据、语义和作者目标产物，记录来源及摘要；复制过程中源文件变化、缺失或准备失败时停止，不悄悄省略。
2. 建立项目三目录之外的核算工作区。冷读阶段只提供原问题、选定 `020_clean` 输入副本、同版本必要业务事实及资产；不提供作者完整对话、脚本、结果、报告或其路径。
3. Case 冷读材料仅包含解题必要的事前背景与假设。待核算结论及由其生成的后验判断、经验不进入冷读输入；无法分离或已携带目标答案时明确标记知情条件。
4. 核算 Agent 自主选择方法、动态写代码并实际执行，保存关键数值、推断和不确定性。不要求形成统一计算步骤，不要求不同方法必须给出完全相同的估计量。
5. 第一次运行终态可证、初步依据已保存后，Host 才提供预先固定的作者产物；核算者在自己的会话中比较差异。重跑作者代码可以解释差异，但不当作首次独立核算。

这只是信息交付顺序，不是规定统计方法的工作流。Host 可以检查文件身份、保存、请求状态；不根据公式替 Agent 计算或裁决业务结论。

**独立性的限制：**独立会话不 fork 作者历史；独立 cwd 减少常规检索触达作者答案，但全工具、共享 skills／MCP 和软约束仍可能越界。记录实际注入内容、工具／资产来源和可见读取活动。发现提前接触答案时标为“知情复核”；证据不足时标为“独立性无法确认”，均不计入有效冷读样本。未观察到越界只支持捕获范围内的结论，不宣称 OS 级访问审计或安全隔离。本期不增加硬沙箱。

### SV06 统一接入与运行模型

沿用工程规范 IN01–IN07、Interface v1。Host 静态注册核算 profile，owner 绑定真实项目、任务及本次核算身份；profile 解析回真实 projectId，纳入项目／Provider 关闭和应用退出。业务仅使用 Host 注入的受限 port／Ref，不直接创建 SDK 或维护第二份 opening／busy／generation 台账。

初次核算建议用一个 operation lease 承载“独立核算→对照”两个业务 turn；底层工具调用与自主迭代仍由 Pi 管。只在前一阶段可证完成并保存依据后派发下一阶段；失败、取消或未知立即结束后续派发。

默认原任务绑定模型，用户可显式选择现有已配置模型；整个 operation 捕获并固定配置。首次对照验证使用同模型不同会话，异模型另列探索，不自动 fallback 或换模型。不复制凭据、不自动安装技能／MCP／依赖。

断线只恢复观察，不重新计算。取消只影响本次核算；旧请求迟到不能覆盖新结果。进程重启保留文件与记录，不能确认完成的操作记中断／未知，不自动续算。显式重试生成新的核算尝试，关联旧记录并保留失败现场，不复用旧冷读为新独立结果。

### SV07 分歧、修正与采用

核算报告逐项说明：核查范围、依据、数值或判断是否一致、具体差异、尚不能确认什么。分歧可以来自输入／版本、业务口径、计算、方法前提或报告解释；不强制翻译成统一统计断言语言。

- 计算一致但口径未确认时，明确保留业务未决；业务含义冲突不靠模型投票解决。
- “启动核算”不授权修改原稿。用户点击“将核算意见交给作者修正”后，作者在原任务另存修订版本，保留初稿及原采用副本。
- 一期单次核算最多关联一轮作者修正和一次复查，均由用户显式发起。复查已经见过作者材料，只称复查，不重新声称冷读独立。
- 原输入或业务口径改变，视为新的分析条件；旧记录继续可读，重新核算需显式新建尝试，不沿用旧“已核算”结论。
- 复查后仍有重要差异就结束并保留双方证据；不自动启动第三个裁判，不讨论到一致才停止。
- 核算结果不自动发布 SAP、更新 RAP、改写 Case 判断、采用报告或沉淀全局经验。用户采用沿用现有显式保存／关联流程；采用与业务执行、效果验证分开。

## 五 新增记录 兼容与 Extension

### SV08 仅新增核算附属记录

推荐结构为“一次核算一个记录目录”，属于现有项目任务，不建立新项目或普通任务，不放进第二套会话数据库。一个任务可有多次核算，每次固定一个选定作者交付集合；一个集合可以含多份文件。其他项目的资料须走现有显式授权／引用，不因 Case 关联就默认全量可读。

建议保存位置：记录与 Host 管理的快照在 `<dataRoot>/analysis-verifications/<projectId>/<taskId>/<verificationId>/`；模型可见工作区在 `<dataRoot>/verification-workspaces/<verificationId>/`。原生 JSONL 独立保存，不 fork 或改变作者路径。作者产物及内部关联记录不放进冷读 cwd；即使物理分开放置，仍不声称硬隔离。

确认以下逻辑字段组，不预建分析步骤或方法表：

| 逻辑组 | 意义、格式及缺失语义 |
| --- | --- |
| 身份与关联 | 格式版本 1；前端为一次明确核算意图生成 UUID verificationId，Host 校验项目／任务归属并原子接受后作为记录身份；UUID 不授予权限。创建时间为 UTC ISO 时间；显式重试的前次 ID 可缺省，表示首次。作者原 requestId 可未知，不编造历史关联 |
| 固定输入与来源 | 所选数据、语义和作者产物的来源、版本（若有）、SHA-256、复制字节、观察时间、确认／未知说明及副本引用；需要完整字节的源缺失时不启动。原历史采用依据缺失明确未知 |
| 执行证据 | 捕获配置的非敏感身份、运行模型、实际可取得的工具／资产版本、各阶段实际 requestId／native 路径、状态与安全诊断；尚未创建的会话／请求留空，不预填完成或费用 0 |
| 结果与后续 | 初步独立结果、对照报告、实际产物引用、独立性证据与限制、差异及未知；可选修订／复查关联。用户导出／采用动作沿用既有回执，不复制成另一权威状态 |

记录是业务证据，运行资源状态仍由公共会话实现权威管理。记录缺失／损坏要明确报错，不生成“通过”空记录。Host 在发送模型请求前保存 verificationId 和选择载荷的指纹；同 ID 同载荷的重复提交只返回原准备／运行／终态，不再派发，同 ID 异载荷拒绝。前端超时后先按原 ID 查询，不自行生成新 ID 重试；只有用户明确发起新核算／重试才使用新 ID。读取不产生模型请求；跨文件准备中断保留现场，不自动补做。

执行记录只表达“准备、运行、完成、失败、取消、中断或未知”及当前冷读／对照／复查阶段；完成表示请求结束并保存了可读结果，不表示内容正确。未创建会话时原生引用缺省；终态未知不能默认为完成。普通任务新增的可选上下文元数据仅复用上表“固定输入与来源”中适用内容，不另设业务 ID、审批状态或语义权威；旧 JSONL 不回写，新附加元数据的旧读取器兼容须验证。

保存遵循：原件先固定，新产物新增文件，不覆盖旧稿。模型普通写入由提示限定在自己的工作区；Host 的复制／导出使用受控路径、新文件名和摘要核对。软约束不是绝对写保护，发现原件非预期变化即验收失败。临时过程不保证每个瞬态文件都已捕获，明确列出实际保全范围。

兼容决定：不改 project schema1／2、原 SQLite 表列、原 ID、JSONL 父链、三目录、RAP／SAP 发布字节和指纹；旧对象没有核算记录仍正常读写。旧代码通常看不到新核算记录，但应能继续读原资料；回退不能用旧备份覆盖新增工作，活跃核算先显式停止再回退。新增目录不自动清理，清理仍需单独范围确认。

向用户导出核算报告时，仅新增到原项目 `060_reports`，与对应核算记录关联；关联 Case 时复用现有 Artifact／采用版本入口，不新增 Case 表列。项目归档及权限规则继续适用。

### SV09 Extension 接入规则

| 类型／方式 | 一期允许的作用 | 接入要求 |
| --- | --- | --- |
| 分析资产、Skill、Prompt | 提供业务定义、方法说明、适用条件、参考材料和可复用脚本 | 按需提供并记录来源；建议不变成强制计算步骤；参考示例与最终留出答案分开 |
| 场景组合 | 选择相关资产、资料和工具 | 复用现有组织方式；不增设调度平台，不要求所有任务采用同一流程 |
| 连接器、MCP | 访问获准数据和工具 | 带来源及错误，按既有权限与数据出口授权；MCP 是接入协议，Python 统计库是计算依赖，二者不混同 |
| 业务插件 | 提供实际需要的专业能力及业务交互 | 通过 Interface v1 取 Agent 能力；不自建 Runtime／会话管理，不修改宿主任务权威 |

一期不迁移全部历史资产，不自动安装库或技能，不新增统计函数全集。双方共享必要业务定义，但核算者不继承作者的方法选择和推理历史；记录双方使用的资产，防止把同一错误模板的一致结果视为独立证据。发现资产问题只形成修订建议，经原人工确认发布，不自动全局传播。

Codex 负责 Host／Agent 接入、保存、UI 薄挂载及联合回归；Qoder 负责适用的 RAP／SAP／Extension 引导与消费改动，分工不等于本轮已派发实现。最终工程复核者须独立于全部作者，产品核算 Agent 不能替代工程非作者复核。

## 六 对照验证和验收

### SV10 对照矩阵

本方案及模型试验已获用户确认；实际执行和成绩见[实施记录](../openspec/changes/business-semantics-verification/result.md)。使用合成资料，冻结题目、业务事实、数据字节、模型／版本、工具／依赖、权限、资产版本及评分依据；先建立独立参考答案，再运行产品。无法匹配的原生默认提示／工具差异原样披露。

| 组别 | 条件 | 用来判断 |
| --- | --- | --- |
| A 原生 Pi | 同版本 Pi、同模型、同问题／数据／必要业务事实和工具，独立新会话 | 原生条件的能力参照 |
| B OptraCall 最小接入 | 与 A 保留相同必要事实，记录接入差异 | 产品接入是否引入损失，不把缺失业务信息算成封装退化 |
| C1 语义组织 | 与 B 相同事实，采用增强后的 RAP／SAP／Case 呈现、引用与未决内容传递 | 组织和取得方式的收益／干扰 |
| C2 新增语义 | 另选确实依赖企业事实的题，仅增加已确认业务信息 | 新信息价值；缺信息组可合法澄清／保留未知，不逼它猜答案 |
| D 独立核算 | 复用 C1 已保存的同一批作者产物，先独立算后对照 | 检错、误报、净改善及成本；不重新跑作者后把改善都算给核算 |

一期固定 6 个留出任务，每题 A／B／C1 各 3 次独立试验；C2 只在其中 2 个任务各运行 3 次；D 对 C1 的 18 份产物核算。至少 3 题为未加入提示、skill 或参考示例的数据／业务条件变体。

题目覆盖数值与粒度、企业口径及变更、推断边界、Case 经验适用范围四类，不按统计方法穷举。另设受控核算集：6 份有重要问题的报告（至少三类问题，各两份）与 4 份正确对照，各 3 次核算；与自然错误结果分开报告。

预定规模为 60 份作者试验、48 次核算（18 次自然产物、30 次受控产物）。每次核算两阶段，共 156 个初始业务 turn；如对全部 48 次核算都显式进行一次作者修正和一次复查，最多再加 96 个，整套最多 252 个业务 turn。业务 turn 不是 Provider API 请求数或费用上限：Pi 内部工具迭代及原生重试另计并按原配置运行、记录，Host 不新增重试循环。失败或中止保留并计入预定尝试，不因结果不好无限补样本；额外试验需另列范围。实际耗时、usage 与可知费用分别交付。

参考答案、植入错误清单和评分规则只留在工程评估位置，不进入业务提示、全局 memory／skill 或可检索项目资料。发现提前读取作者答案或金标，该次不计独立有效样本，原失败保留；不自动追加直到凑够通过，需先说明失效与后续取证范围。运行顺序交错，主对照同模型不同会话，异模型试验另列。

### SV11 验收门槛

**工程门槛全部适用项通过：**

1. RAP／SAP／Case 来源、确切版本、重要未决内容能在真实 Host／SDK 请求及保存记录中核对；不混入新草稿、新版本或未选择的 Case。
2. 冷读前不由 Host 注入作者答案；首次依据先保存再开放作者材料；独立性受影响或证据不足可明确显示，不伪报通过。
3. owner／配置捕获／停止／关闭／迟到结果隔离正确；作者会话不被核算替换。断线仅恢复观察，失败和重启不自动重放或换模型。
4. 输入／目标文件变化、准备中断、导出／采用重复请求、记录损坏等路径明确保留失败／未知，不悄悄覆盖。
5. 兼容保全：旧项目、任务、草稿、JSONL／父链、原件、RAP／SAP 发布字节、SQLite 既有行不发生非预期变化。正常显式续聊／新增核算的合法追加与迁移性改写分开核对。
6. 联合回归覆盖 RAP 草稿／确认／发布／送入、SAP 发布／选用／精确升级、Case 多项目关系／经验引用／采用版本、普通聊天／上传下载、模型配置、归档，以及新核算保存／重开／取消／恢复。
7. 运行时与共享改动执行届时完整适用检查；固定候选完成非作者 Standards／Spec 复核。合成 Provider 能证明接线与状态，不替代真实模型质量结果。

**真实模型局部试用门槛（用户已确认的目标，实际成绩另记）：**

- 受控核算集的 18 次错误报告核算，至少 15 次正确指出重要问题；每份错误报告至少 2／3 次成功，并提供可核对依据，笼统说“有风险”不计检出。
- 12 次正确对照核算，重要误报最多 1 次；不得出现“原本正确→用户采用修订后出现重要错误”。模型建议了错误修订但未采用，也须单列记录。
- 自然全链路中，核算／显式修正后的重要结论净正确数不得低于原作者。若自然错误不足以判断收益，结论为证据不足，不用人工植入成绩替代真实收益。
- C1／C2 与 B 报告配对原始次数、正确／错误／合法未知及重复澄清。小样本升降不宣称显著；没有达到可解释的收益，只交观察结果，不宣称语义增强已验证有效。
- 同时报耗时、token／usage、可取得费用和人工介入；未知费用保持未知，不填 0。阈值只约束这份有限题集，不外推为任意分析准确率。

作者首次结果、核算检出／漏报／误报、修订后结果分别保留。评分按关键结论与原始数据依据判断，不以文风或“已生成报告”评分，不写一个能裁决全部业务的运行时判分器。工程评估使用有限参考答案／复算材料，与产品中的固定计算方法库不同。

工程通过而模型质量未达时，记录“技术接入通过、核算质量未达标”，保留失败，不宣称一期产品完整验收或默认开启核算，不继续补专用方法凑通过。语义和核算的部分成果可分开报告，是否采用未达目标的部分由用户决定。

### SV12 顺序与交付边界

建议按以下顺序推进，整包确认后在授权范围内连续实施，不按每个小步骤重复申请：

1. 固定既有资料与基线，补薄规格和合成验收资料；先做语义消费与版本可见性。
2. 接入一次“冷读核算→对照”的最小闭环，完成保存、取消和恢复，再增加显式作者修正／复查。
3. 完成 RAP＋SAP＋Case 联合回归和兼容保全；按固定矩阵运行真实模型合成试验，保留所有尝试。
4. 完整候选做工程非作者独立复核；获授权 Git／CI 交付时先更新 main、集成新增基线并重验，再以实际最终候选 CI 完成合并。
5. Git 合并、运行服务切换和用户验收分别报告；本方案不自动更新 Mac mini 服务、不操作 MacBook。

一期不增加 DuckDB、Semantica、本体平台、插件市场、多 Agent 调度台、通用 IR、固定计算／核验方法库、自动因果识别、自动业务执行或硬沙箱。不恢复退役 JuanerAI，不迁移其运行数据。DuckDB 下一项、Semantica 后置的既有安排不因本方案改变。

主要风险是：企业语义本身错误导致双方一致出错；软约束无法保证冷读；模型互审误报／漏报；额外延迟和费用；旧输入无法完整回溯。处理方式分别是保留业务确认、标注独立性限制、做正确对照及留出评测、默认显式发起并报告成本、缺失保留未知，不增加一套万能裁判。
