## 1 背景与问题

OptraCall 的正式分析报告目前以 Markdown 产出（`060_reports`）。实际经营汇报场景中，用户经常需要 PPTX 版本向管理层或业务方汇报。用户在实践中确认了两个独立的问题：

1. **生成**：从 md 报告到一份「结构清楚、视觉专业、数字可靠」的 PPTX，缺少一个可被产品 Agent（pi-coding-agent）直接调用的标准能力。目前各 Agent 自由发挥，产出质量不稳定。
2. **逐页精修**：Agent 生成的 PPT 几乎必然需要**逐页检查并修改**——这是用户实际用 Agent 做 PPT 最痛的点。通用聊天式修改「改一页等于重写全本」，缺乏针对单页的闭环修改工具。

参考仓库 reports-factory（MacBook `/Users/huangbo/Dev/Projects/reports-factory`，独立仓库，只读参考）已经验证了一条可行路径：材料 → 大纲提案 → Agent 写页面渲染代码 → 渲染自检 → **选中任意一页对话修改（自动重渲）** → 质检导出。其 2026-10 行业调研同时确认：逐页 AI 修改已是头部产品标配（WPS/Gemini/Gamma 为显式按钮级），而**导出后 AI 编辑断链是全行业通病**——保留可重渲的源链是差异化机会。

### 1.1 用户已确认要点（2026-11-01 反馈，v0.2）

1. **触发**：skill 生成候选版 PPTX 不由 Agent 自动触发；默认用户手动发起。唯一例外：分析需求中已显式声明需要 PPTX 报告。
2. **底本**：生成 skill 以 Anthropic 官方 pptx skill 为底本，吸收其他 skill 的优势项。
3. **流程边界**：分析流程到产出候选版 PPTX 即结束；逐页修改在 B 工具读取候选版 PPTX 后的独立对话中进行，不回原分析会话（在原会话里改 PPT 上下文会乱）。
4. **接入范围**：reports-factory 只有逐页修改工具作为业务插件开发接入 OptraCall，**不是整体接入**；严格遵守 OptraCall 接入规范，特别是统一 Agent Runtime 底座。
5. **md 报告锚点（v0.3 接受）**：精修会话只读携带 md 报告作为数字/事实锚点，内容级改动可对照原文；改动是否强制回流 md 报告仍为 D5 待讨论。
6. **编辑链路（D1，v0.4 确认）**：XML/ooxml 级编辑为主 + 底本工具单页重生成为辅，不引入自定义可重渲源工件；用户全程对话式修改，不接触 XML。
7. **D4–D8 整体确认（v0.5）**：精修会话接入形态、差异清单回流策略、首期只面向本产品产出、版本锁定沿用已验证模式、合成数据全链路验收——细则见 §6。

## 2 两部分方案总览

| | A：PPT 生成 skill | B：PPT 逐页精修插件 |
| --- | --- | --- |
| 归属 | 分析资产（`extensions/analysis-assets/`，**首个 skill**） | 业务插件（`extensions/business-plugins/`） |
| 形态 | Pi SDK skill（独立目录 + `skill.md`） | 带 UI 的业务插件（参照 decision-board / metric-factory 形态） |
| 使用者 | Agent（pi-coding-agent）执行生成；**用户手动触发**（需求显式声明 PPTX 除外） | 用户主导的交互闭环 |
| 输入 | `060_reports` 正式 md 报告（+ 按需的 020 资料） | A 产出的候选版 PPTX 及其源工件 |
| 输出 | 候选版 PPTX（原生可编辑） | 终版 PPTX（及可选 pdf/html） |
| 关键约束 | 内容守则进 skill 红线；不编造、数字逐字来自报告 | 经统一会话入口接 Agent，不自建 Runtime |
| 构建方式 | 以 **Anthropic 官方 pptx skill 为底本**，吸收其他 skill 优势（§3.2）；不抄 reports-factory | 仅其**逐页修改工具**按 OptraCall 规范开发为业务插件（非整体接入） |

**为什么分两部分而不是一个工具：**

- 生成环节嵌入 Agent 自主分析流程，skill 是最薄接入——无需新 UI、新会话管理，Agent 按适用条件选用；这与产品讨论稿 v0.2 对分析资产的定位一致（可检索和引用，不是强制步骤）。
- 精修环节是用户参与的交互工作流（选页、看图、对话改、锁定、版本回退），需要专门界面、会话与状态管理，天然是业务插件；两类能力生命周期和验收标准不同。

## 3 A：PPT 生成 skill（分析资产首个 skill）

### 3.1 定位与产出

- 触发方式（已确认）：正式 md 报告完成后，**默认由用户手动发起**「生成 PPTX 版本」，Agent 才调用该 skill 产出**候选版 PPTX**——多数报告没有 PPTX 需求，Agent 不自行猜测。唯一例外：分析需求中已显式声明 PPTX 需求时，报告完成后可直接进入生成。
- 候选版的含义：数字与结论可回溯到 md 报告、结构完整、版式达到「可直接进入逐页精修」的水准，不承诺零人工修正。
- 产物为纯 .pptx，不携带自定义源工件（D1 已确认）；整页级重构由 B 侧用底本工具单页重生成兜底。

### 3.2 构建参考（已确认：Anthropic 官方 pptx skill 为底本）

底本与优势吸收来源（2026-11-01 确认；调研为发现式记录，未安装）：

**社区标杆**
- `anthropics/skills@pptx`（skills.sh 246.5K 安装）：Anthropic 官方 pptx skill，创建/读取/编辑 .pptx 的完整方法论，事实上的行业标准参考。
- `minimax-ai/skills@pptx-generator`、`claude-office-skills@pptx-manipulation`：生成与既有文件操作两个方向的补充参考。

**Qoder 官方市场（相关性较高的候选）**
- 通用 PPTX（QoderWork，官方精选）：全场景 .pptx 读/写/编辑/合并拆分。
- QoderWork 演示文稿（官方）：14 种模板一键出可编辑 pptx。
- PowerPoint 演示文稿处理：版式/占位符/模板保真 + 视觉质量检查。
- 专业PPT生成器：风格提取、大纲、AI 配图、HTML 预览确认后导出可编辑 pptx。
- PPT演示标题（Marp 引擎）：**从研究报告一键生成演示文稿**，与本场景输入形态最接近。
- PPT 内容核对（linksass）：逐数字回源对账，与 OptraCall 数字红线高度契合，可作守则参考。
- PPT（Qoder 官方 plugin，含 1 skill + 1 MCP）：整体工作流参考。

用户还将另行提供数个优质 PPT 生成 skill 作参考。**底本已确认为 `anthropics/skills@pptx`**；上列候选与用户参考作为优势吸收来源（如模板体系、风格提取、数字回源核对、报告→演示的输入形态），逐项评估取舍，不做整包拼凑。版式层以底本方法论为框架，吸收 reports-factory 实测版式系统（色彩、字体栈、页型模板）作为视觉基线，视觉质量纳入 skill 验收（v0.6 已确认；用户反馈：候选版观感不得低于 reports-factory 一版 skill 的产出）。

### 3.3 内容守则（与 OptraCall 原则对齐）

reports-factory 的 skill 内容守则虽不照抄，但其红线与 OptraCall 已确认的分析原则同源，建议新 skill 明确继承以下原则（表述与实现重新设计）：

1. **真实性最高优先**：所有数字、事实、结论来自正式 md 报告；报告没有的明确留白标注，不编造。
2. **数字逐字**：引用报告数字照抄，不改写口径；图表数值同样受控（reports-factory 痛点矩阵指出图表数值缓存是幻觉重灾区）。
3. **每页单焦点**：headline 直接陈述该页结论；要点密度受控。
4. **克制视觉**：0 emoji、有限强调色、统一中文字体栈。
5. **推断明示**：推断与报告原话区分。

### 3.4 技术路线（D1 已定）

生成侧跟随 Anthropic pptx skill（html2pptx / ooxml 直出 .pptx），不引入其他渲染路线；整页重构所需的单页重生成由 B 侧使用同一底本工具实现。

## 4 B：PPT 逐页精修插件（业务插件）

### 4.1 定位

放在业务插件模块（暂名 `ppt-refiner`，名称待定）。解决「Agent 生成 PPT 后需要逐页检查并修改」的痛点，提供从候选版到终版的用户主导精修闭环。

**接入范围（已确认）**：只把 reports-factory 的**逐页修改工具**作为业务插件开发接入 OptraCall，不是整体接入——其会话宿主、Fastify 服务、材料摄取、预算账本、双机同步等均不进入 OptraCall。接入严格按 OptraCall 规范执行：统一 Agent Runtime 底座（不自建 Pi SDK 接入层或平行 Runtime）、统一会话入口 IN01–IN07、Host 注册与资源权限边界。

### 4.2 核心交互（以 reports-factory 已验证机制为基底）

- **页网格预览**：整 deck 缩略图总览，快速定位问题页。
- **选页对话修改**：选中任意一页，用自然语言描述修改意图 → Agent 执行该页修改（编辑链路见 D1；用户不接触 XML/代码）→ 自动重出页图 → 即时看效果；只动该页，不重写全本。
- **视觉自检**：渲染截图回传视觉模型检查遮挡/溢出/对比/字号（reports-factory look_page 实测：缺陷页召回 4/4，封面留白误报需按页型校准——校准经验直接继承）。
- **页锁定**：已确认的页锁定，后续修改不波及。
- **版本快照**：每轮修改自动存版本，可回退。
- **大纲联动提示**：章节增删后提示受影响页（可选，后置）。
- **导出**：终版 PPTX（原生可编辑），可选 pdf。

### 4.3 接入边界

- 遵守统一会话接入 IN01–IN07：经 Host 统一入口创建精修会话，不自建 Pi SDK 接入层或平行 Runtime；profile 声明真实差异（准入、模型、工作区）。
- 精修会话与原分析会话的关系（独立会话 / 附属资源）待讨论（§5 D4）。
- 材料边界：精修读取的是本产品产出的报告源工件；不扩大到原始数据目录。

## 5 与 OptraCall 分析流程的结合

```
分析需求 → Agent 分析 → 复核 → 正式报告（md → 060_reports）── 分析流程到此结束
                                        │
              用户手动发起（或分析需求中已显式声明 PPTX，报告完成后直接进入）
                        │
                        ▼
              A：PPT 生成 skill（独立触发生成）
              输入：正式 md 报告（+按需 020 资料）
              产出：候选版 PPTX（唯一工件，D1 已确认）
                        │
                        ▼
              B：逐页精修工具读取候选版 PPTX（独立对话）
              预览 → 选页对话改 → 视觉自检 → 锁定 → 版本
                        │
                        ▼
              终版 PPTX 导出（060_reports 同目录归档）
```

要点：

- **分析流程在候选版 PPTX 产出即结束（已确认）**：A 是用户显式触发的独立生成步骤；B 读取候选版 PPTX，在**独立对话**中逐页精修——不回原分析会话改 PPT，避免上下文污染。独立会话也与统一会话接入的任务隔离原则一致。
- **独立精修对话的锚点（已确认）**：精修会话只读携带 md 报告作为数字/事实锚点，使内容级改动可对照报告原文；改动是否要求回流 md 报告见 D5。
- **单一事实来源**：md 报告是内容权威；PPTX 是其呈现形态。
- **目录约定**：候选版与终版 PPTX 及源工件归档到 `060_reports`（与 md 报告同级），不进 `010_draw`/`020_clean`。

## 6 决策点与确认状态

**已确认（2026-11-01 用户反馈）**

- 触发方式（原 D3）：默认用户手动发起；仅分析需求中已显式声明 PPTX 需求时，报告完成后直接生成。
- skill 底本（原 D2）：Anthropic 官方 pptx skill 为底本，吸收其他 skill 优势项。
- 流程边界：分析流程到候选版 PPTX 产出即结束；逐页修改在 B 工具的独立对话中进行。
- 接入范围：仅 reports-factory 逐页修改工具作为业务插件接入，非整体接入；严格遵守 OptraCall 接入规范（统一 Agent Runtime 底座）。
- 编辑链路（原 D1，v0.4 确认）：**XML/ooxml 级编辑为主 + 底本工具单页重生成为辅，不引入自定义可重渲源工件**。对话式修改，用户不接触 XML；.pptx 是唯一事实工件（用户在 PowerPoint/WPS 手改后 AI 链仍成立）。P0 前置验证项随实施：(a) pptx→页图 渲染管线（页预览与视觉自检前提）、(b) html2pptx 单页重生成后拼回原 deck 的可行性。

**已确认（v0.5 用户整体确认）**

- **D4 精修会话设计**（v0.5 确认）：复用 requirements-elaboration / metric-factory 的接入形态——Host 静态注册 `ppt-refiner` 域与 profile，owner 绑定 projectId + 报告/deck 标识；精修入口从报告页显式打开候选版 PPTX。模型用项目绑定配置，需支持图像输入（视觉自检前提，不支持时降级并提示）。owner/profile、Interface 版本与接入规格按 IN01 在变更规格定义。
- **D5 内容修改回流**（v0.5 确认）：允许 PPTX 内直改数字/事实（不打断精修流程），由会话标记与 md 报告的出入，导出终版时生成差异清单；不自动改写 md 正式报告，回填由用户在报告侧另行处理。
- **D6 兼容范围**（v0.5 确认）：首期入口只面向本产品 A 产出的候选版；XML 机制天然不排斥外部 .pptx，但不做外部导入入口与兼容承诺，后续按需开放。
- **D7 版本与锁定策略**（v0.5 确认）：沿用 reports-factory 已验证模式——每轮修改自动存版本快照（文件副本 + 元数据），可回退任意版，首期不自动清理；锁定页在后续修改、单页重生成与批量操作中不被触碰，解锁需显式操作；锁定为编辑期元数据，不影响导出内容。
- **D8 首轮验收场景**（v0.5 确认）：选一个已有正式 md 报告的**合成数据**项目走通全链路（md → 手动触发生成候选版 → 逐页精修 → 终版导出）。验收标准：① 终版数字与 md 报告逐字一致（程序化核对）；② 单页修改完全隔离（未改页与锁定页字节不变）；③ 精修在独立会话进行，原分析会话不受污染；④ 版本回退可用；⑤ 页图预览与视觉自检可用。

**状态：全部决策点已确认（v0.5）。**变更已按工程规范创建：[ppt-report-extension 规格](../openspec/changes/ppt-report-extension/spec.md)（验收标识 PPT-01–PPT-11，含 P0 前置验证）与 [clickable UI 演示](../openspec/changes/ppt-report-extension/clickable/index.html)同步提交用户确认；确认后申请实施授权。实施与模型调用需另行授权。

## 7 边界与不做事项（当前讨论阶段）

- 本文仅为产品讨论，不构成实施授权；当前[固定版本与 MacBook 试用交付]授权不含新能力开发。
- **只有逐页修改工具作为业务插件开发接入，不是整体接入（用户明确）**：不整仓搬迁 reports-factory；其会话宿主、服务端、材料摄取、预算账本与数据不进入 OptraCall 仓库。逐页修改工具的移植按工程规范作为独立变更走 SDD/TDD 与独立复核，严格使用统一 Agent Runtime 底座与会话入口（IN01–IN07），不复用其自建 pi-agent-runtime 接入层。
- A 不直接抄 reports-factory 的 skill 文本；以 Anthropic 官方 pptx skill 为底本构建，原则性对齐见 §3.3。
- 不做插件市场、通用 PPT 编辑器、模板商店（首期）；不承诺与 Kimi/Gamma 级模板丰富度对齐。
- 数字红线继承 OptraCall 既有原则；PPT 场景的外发审批/隐私建议等治理项随 §6 决策点一并明确，不预设。
