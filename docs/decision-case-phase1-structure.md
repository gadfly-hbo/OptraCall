## 3. D01：存储、身份与权威来源

建议新增 `${dataRoot}/decision-cases.sqlite3`，默认是 `~/.optracall/decision-cases.sqlite3`；另有同目录 `decision-cases-store.json` 身份标记。隔离验证必须使用明确的测试 dataRoot／projectsRoot，不能使用真实默认目录。

| 信息 | 唯一权威来源 | Case 层如何使用 |
| --- | --- | --- |
| 项目 ID、名称、创建时间、配置、归档、任务与上传登记 | 原 `projects/<projectId>/project.json`，保持 schemaVersion=2 | 按 ID 读取，不复制为可编辑权威副本 |
| 项目工作状态、范围、承接人、下一步、业务修订／历史 | 新库 `project_work` 及项目事件流 | 所有 Case 与项目空间显示、修改同一份 |
| 原生消息、工具结果、fork／branch、运行历史 | 原 Pi JSONL | 复用原路径及 SDK，不重写消息库 |
| 三目录中的资料与报告 | 原项目文件空间 | 仅保存引用；不搬迁、不复制、不改名 |
| Case 当前值、关系、Case 历史与操作回执 | 新库 | Host 受控读写 |

`project_work` 是现有项目的物理字段扩展：主键只能是既有 Project ID，没有自己的项目 ID、名称、文件根、任务集合或运行时。API 组合返回同一个项目；不是另一种 Case Project。

SQLite 内建议用显式短事务、外键检查、`journal_mode=DELETE`、`synchronous=FULL`，参数化语句，关闭可加载扩展；不为一期增加 WAL、后台索引服务或图数据库。Host 仍是单写进程。连接配置须读回确认；锁忙／IO错误返回失败，不通过清库重试。

建议使用 Node 自带 `node:sqlite`，不新增原生第三方驱动。当前 Mini Node v25.9.0 只做了模块导入诊断，`DatabaseSync` 可用；尚未创建测试库或验证集成。官方此版本标注 release candidate，不能称为已完成稳定性验证；若实施前发现兼容缺口，记录后提出驱动替代，不静默增加依赖。依据：[Node v25 SQLite](https://nodejs.org/docs/latest-v25.x/api/sqlite.html)、[SQLite事务](https://www.sqlite.org/lang_transaction.html)、[PRAGMA](https://www.sqlite.org/pragma.html)。

库和身份标记为0600，所在数据目录沿用0700；使用受控普通文件，拒绝意外软链接／硬链接、身份不匹配及未知结构。权限保护不是加密；不保存密钥、不上传数据库。

## 4. D02–D06：逻辑记录与字段

以下是已批准、尚未实施的字段合同，不是已建立的表。SQLite 映射采用 TEXT／INTEGER；JSON 字段必须是经过白名单校验的结构。UUID 为小写标准字符串；时间为 Host 生成的 UTC ISO字符串（毫秒），显示时再本地化。名称允许重复，身份不从名称派生。

字符上限按 Unicode 码点计；名称去首尾空白、拒绝控制字符。自由文本保留换行，拒绝 NUL；空值规则按下表，不把“空”“未设置”“存储不可用”混为一谈。修订号为正整数；不存在的项目业务扩展通过只读视图返回 revision=0，不代表已写入。

### 4.1 `cases`：一行是一件业务事项

| 字段／组 | 格式、必填、默认与语义 |
| --- | --- |
| `id` | UUID主键，Host生成，稳定不变 |
| `title` | 必填，1–80字符；业务问题名称，不自动由模型扩写 |
| `description / judgement / next_step` | TEXT，默认空串；分别为问题背景、当前判断与未知、下一步／等待条件；前两项各≤20000，下一步≤5000字符 |
| `status` | 必填，默认 `pending`；允许 `pending / analyzing / awaiting_confirmation / observing / closed`，对应待处理／分析中／待确认／待观察／已结束 |
| `close_reason / closed_at` | 活动状态为NULL；结束时分别为1–1000字符原因和实际结束时间；重开清空当前关闭字段，历史保留旧值 |
| `revision` | 创建为1，每次实际提交递增；不因查看、项目草稿变化或重复请求递增 |
| `created_at / updated_at` | 创建／最后一次 Case 实际修改时间；追加说明及关联变更也更新；不把项目全局修改伪装为 Case 摘要修改 |

允许合理的非线性状态变化。`closed` 状态只读，允许查看历史和已有引用；继续该 Case、修改其内容／关联／反馈前，走明确的重开操作并指定一个活动状态。结束不要求 Objective、Decision、Action 或 Outcome，不触发项目操作。

### 4.2 `case_project_links`：一行是一条当前关联

| 字段／组 | 格式、必填、默认与语义 |
| --- | --- |
| `case_id / project_id` | 必填UUID，组合主键；前者外键指向Case，后者是原 Project ID；不存在第二套项目身份 |
| `linked_at` | 必填实际关联时间；来源与操作记录在 Case 事件中 |

一个 Case 可有0到多个项目，一个项目可关联0到多个 Case。首次关联要求原项目存在且可读取，允许关联已归档项目用于查阅。无任务项目也可关联；任务列表动态读取原项目，不需要 `project_sessions` 表。

解除关联删除当前关系行并追加事件，不删项目或任务。再次关联恢复同一对ID的当前关系并记录新时间，历史不覆盖。项目缺失时保留已有关系并显示失效，不自动重建或清除。

项目解绑后，已有产物引用保留为“历史引用／项目已解绑”，不再作为当前任务上下文候选；重新关联后可继续使用。Case 结束不移除任何关系。

### 4.3 `project_work`：现有项目的一组全局业务字段

| 字段／组 | 格式、必填、默认与语义 |
| --- | --- |
| `project_id` | 原 Project UUID主键，一项目最多一行；不是新的项目对象 |
| `work_status` | 可NULL，表示用户尚未设置；有效值为 `not_started / in_progress / awaiting_feedback / completed / cancelled`（待开始／进行中／待反馈／已完成／已取消） |
| `work_scope` | TEXT，默认空串，≤20000字符；工作问题与范围，不规定分析步骤 |
| `assignee` | 可NULL；非空为1–200字符的承接人文字；空输入规范为NULL，不是用户账号、权限或派工凭证 |
| `next_step` | TEXT，默认空串，≤5000字符；项目下一步／等待事项 |
| `status_reason` | 可NULL，非空≤1000字符；状态实际改变时默认清空旧原因，目标为取消须重新明确填写，目标为完成可显式补说明；同状态编辑保留已确认原因，旧原因始终保留在历史 |
| `status_changed_at` | 可NULL；首次设置或实际改变业务状态时写入，其他编辑不刷新 |
| `revision` | 首次明确保存为1，此后独立递增；Case A／B和项目空间都使用这一版本检查冲突 |
| `created_at / updated_at` | 首次保存业务扩展／最后实际修改时间；不是原项目创建时间 |

旧项目和尚未编辑业务字段的新项目均可没有扩展行：只读返回 `work_status=NULL`、其余默认值、revision=0和业务时间NULL，显示“未设置”。不批量生成扩展行，不根据任务数量、原项目时间、归档或运行结果推断业务状态。无变化的保存不产生一行空扩展、修订或事件。

清除工作状态允许设回NULL并保留历史。Case A修改全局字段后，Case B和项目空间读取同一结果；不会生成各Case专属项目状态。业务完成／取消与 `archivedAt` 独立；已归档项目须恢复后才能改这些字段。

### 4.4 `case_artifact_links`：一行是一个Case对项目内文件的引用

| 字段／组 | 格式、必填、默认与语义 |
| --- | --- |
| `id` | UUID主键，仅引用记录的身份 |
| `case_id / project_id` | 必填UUID；Case外键，项目为原ID；新增／修改时验证项目当前关联 |
| `relative_path` | 必填项目相对路径，仅允许原三目录，沿用既有路径／软硬链接验证；不接收任意绝对路径或外部URL |
| `task_id` | 可NULL；若填写必须属于该项目，表示用户关联的相关任务，不凭此宣称文件由该任务产出 |
| `upload_id` | 可NULL；只有原uploads存在对应登记时引用；不为原生Agent文件补造上传记录 |
| `role` | `file / analysis_result / report`，默认file；用户指定展示用途，不靠目录或文件名猜最终报告 |
| `display_name` | 可NULL，非空≤200字符；为空时动态显示文件名，不覆盖原文件名称 |
| `observed_sha256 / observed_bytes / observed_at` | 可NULL组；有可靠、同次观察才保存实际哈希、非负字节数和时间，否则全NULL；旧上传哈希不能冒充当前文件版本 |
| `created_at / updated_at / unlinked_at` | 关联创建／最后实际引用修改／解除时间；解除默认NULL，解除后保留记录和历史，不删文件 |

唯一约束为 `(case_id, project_id, relative_path)`；同一路径的重复关联不制造重复卡片。重新关联使用原引用ID，更新已确认的观察信息并保留变化历史。显式改指向应解除旧引用、建立新引用，不静默追随移动后的同名文件。

一期以人工选择项目文件为主。可只读观察用户明确选择的文件，流式计算哈希且核对读取期间文件身份／修改信息；不批量读取原件或自动发送内容。哈希只是某时刻观察，不保存文件快照；检查发现内容变化时提示“内容已变化”，不自动覆盖旧观察信息。没有版本信息时直接说明“引用当前文件，内容可能变化”。

可访问性、文件变化、项目归档和“来源项目已解绑”是读取时计算的状态，不作为永久有效事实存入表。已解绑项目的历史引用仍可经原项目只读入口查看／下载，但不能以此绕过Case重开或项目恢复规则。

### 4.5 `work_events`：一行是一次明确提交的业务变化

| 字段／组 | 格式、必填、默认与语义 |
| --- | --- |
| `id` | UUID主键 |
| `subject_type / subject_id` | `case / project`及原对象UUID；Case事件属于Case，项目业务事件只全局存一份 |
| `revision` | 提交后的对象修订；`(subject_type, subject_id, revision)`唯一，一次对象提交一条事件 |
| `event_type` | `case_created / case_updated / case_closed / case_reopened / project_linked / project_unlinked / artifact_linked / artifact_updated / artifact_unlinked / note_added / project_work_updated / project_work_note_added` |
| `operation_id` | 对应受控操作回执的UUID；写入前校验并在同一事务内建立 |
| `actor_kind / origin_case_id` | Host确定的 `user / host`；可选来源Case仅表达编辑入口，不成为项目所有权，不从前端接受伪造身份 |
| `changes_json` | 字段前后值的白名单结构；Case创建保存初始值，关系事件保存相关ID和必要引用；不复制会话或文件正文 |
| `note / feedback_source` | 可空说明≤10000字符；用户反馈来源可空≤1000字符，表示用户陈述的来源，未经核验不会升级为系统事实 |
| `occurred_at` | 实际提交时间，不回填成历史业务发生时间 |

当前摘要与历史不是两个竞争事实来源。用户提交新判断后旧值留在事件中；首次Case或项目业务保存建立完整初值，其后按修订记录差异。追加项目业务说明也走该项目修订；共享项目历史在各Case中标为“项目全局记录”，不复制入Case事件流。解除项目关联不删除它的历史，也不把全局变化自动写成Case已采纳／已执行／已验证。

事件仅覆盖本期Case和项目业务字段，不新建通用审计平台；原项目名称／归档／草稿／SDK运行不补造历史事件。当前无删除或批量清理入口，无自动保留期淘汰。

### 4.6 `operation_receipts`与存储身份：支持可靠保存，不是业务项目

| 字段／组 | 格式、必填、默认与语义 |
| --- | --- |
| `operation_id` | 客户端生成UUID主键；一个明确用户操作使用一个ID |
| `kind` | `case_create / case_update / case_close / case_reopen / case_note / project_link / project_unlink / project_work_save / project_work_note / artifact_save / artifact_unlink / project_create_link / task_context_prepare` |
| `request_sha256` | 白名单请求规范编码后的SHA-256，包含对象、预期修订与实际输入；同ID异内容返回冲突 |
| `case_id / project_id` | 可NULL，仅在该种操作适用时填写；新建并关联项目在副作用前保留Host生成的项目ID |
| `phase` | 普通库内操作与背景准备只提交completed；跨存储项目创建使用 `prepared / project_created / completed / needs_review` |
| `result_json` | 可NULL的白名单结果／恢复信息；completed必须有可重读结果；可含本次上下文快照及 `recoveredByOperationId`，不含密钥或文件正文 |
| `created_at / updated_at` | 回执建立／实际阶段更新的Host时间 |

库内另有单行 `store_metadata(store_id, initialized_at)`，其中store_id为UUID。数据库结构版本使用 `PRAGMA user_version=1`；单行身份和版本均须校验。

身份标记 `decision-cases-store.json` 仅含 `formatVersion=1`、同一 `storeId`、固定相对库文件名、`state=initializing或ready`及 `createdAt`。它用于区分“首次启用”与“已启用后数据库丢失”，不是另一份业务存储。

## 5. D07：事务、并发与部分成功

### 库内一致性

- Case内容、关系或引用变化：检查 `expectedCaseRevision`；在同一短事务提交Case当前值／revision、对应事件和completed回执。
- 项目业务变化：检查独立的 `expectedProjectWorkRevision`；提交全局业务当前值、项目事件及回执。不同Case窗口编辑同一项目也必须冲突检查。
- 同ID同内容重试返回已提交结果，不再次递增修订或写历史；不同ID重复建立同一关联返回已有关系，不制造第二条关系或无变化事件。重复结束／解除等无变化操作同样不制造历史。
- 修改对象必须提交完整预期版本；返回冲突后由用户核对，不静默合并。项目全局编辑携带来源Case时，还须验证该Case仍活动且仍关联该项目；项目空间独立编辑不受Case结束限制。
- 所有已存在Case引用采用不级联删除策略；项目／任务在外部JSON，不能声称有SQLite外键保证，须由Host重新验证。内部Case／回执外键和字段／枚举约束由数据库与入口共同校验。
- 索引只覆盖已知读取：Case状态＋更新时间、项目关联的反向Project ID、Case产物列表、事件对象＋修订唯一索引。标题／背景一期做本地查询，不建独立全文索引服务。

### 新建项目并关联：明确跨存储边界

原项目JSON和SQLite不具备共同原子提交，不能宣称两者总是同时成功。

1. 接收 `project_create_link` 操作ID和Case预期版本，先在SQLite记录prepared及保留的Project UUID；此时不创建文件、任务或模型请求。
2. 扩展现有项目创建入口，以该保留ID独占创建原项目。只有属于本操作、结构完整的同ID项目才可在恢复时复用；不覆盖未知目录／元数据。
3. 项目完成后记录project_created，再重新验证Case和预期修订，在事务中建立关联、Case事件和completed回执。此流程仍沿用现有项目配置要求，不绕过归档或配置检查。
4. 项目已创建而关联失败：原创建回执保留原Project ID及project_created阶段，明确返回“项目已创建、关联未完成”，项目可独立使用。同ID原请求只用于查回原结果或恢复未变的阶段，不修改其请求摘要／预期修订。
5. 若Case修订已变化，用户核对后使用**新的project_link操作ID＋原Project ID＋最新Case预期修订**关联，并携带原创建操作ID作为恢复来源。Host校验两操作指向同一Case／项目；在建立关系、Case事件和新回执的同一事务内，把原回执更新为completed，结果记录recoveredByOperationId，原request_sha256保持不变。原Case已结束时先重开，再使用新版本；不得重新发project_create_link来代替关联重试。若用户改为保留独立项目或关联其他Case，原回执仍如实保留该目标Case未完成关联的事实。
6. 响应丢失或中断后先查两份回执与原项目；新关联响应丢失用该project_link操作ID查回，不重复创建、不重复历史。若目录不完整、身份冲突或无法证明阶段，记录needs_review并保留现场，不自动清理、换ID重建或盲目重放。

创建Case、关联已有项目及任务导航不触发模型。现有新建项目／任务需要已保存的模型配置，但不要求模型在线或模型响应；一期不顺带重做这一既有创建前提。

## 6. D08：任务身份、上下文与请求记录

继续入口以原 `projectId + taskId` 打开任务。原生fork／branch仍属于同一个任务，不新建Case、项目或产品任务；需要定位特定历史时使用已有原生会话／条目引用，不把当前sessionFile当永久任务ID。

仅用户实际发送、且明确选择Case背景时准备上下文：

1. 展示本次Case、项目及修订；默认包含Case问题／判断与未知／下一步、项目工作范围／下一步、用户选择的可用材料引用。不默认附加全部历史、原始数据或其他Case背景。
2. 发送时在Host队列重新验证Case活动、项目仍关联、项目未归档、任务所属正确及预览修订。背景已变则提示刷新预览，不静默替换用户确认的内容。
3. 使用原消息requestId及原projectId/taskId建立 `task_context_prepare` 回执（SQLite全局operationId由这三项加固定操作名确定性派生UUID，SDK运行和原任务去重仍使用原requestId，允许不同任务各自使用相同requestId），其result保存 `caseId / caseRevision / projectId / projectWorkRevision / taskId / capturedAt / contextText / selectedReferenceIds / userPromptSha256 / composedPromptSha256`。该快照是本次请求证据，不是Case当前值副本。
4. 背景作为明确标识的任务数据进入现有prompt入口，不提高为可覆盖系统规则／权限的指令；本次Case来源和修订随原生请求记录保留，实际发送文本仍由SDK JSONL管理，不另存整段聊天。
5. 重试同requestId使用已固定背景；输入或背景不同须新操作，不能把新背景套在旧请求ID上。执行是否已接受继续依据原运行／去重机制；准备回执成功不代表模型已接受或分析成功。未知状态不自动重发。

打开页面、关联、存草稿、查看历史及项目字段保存均不自动发模型请求。普通项目入口新发送不自动加Case背景。**复用同一任务时，其原有历史可能已经含其他Case信息**；不能声称上下文隔离。用户需要独立上下文时，在原项目中新建任务，不清洗、改写或复制旧会话。

Case结束不会停止已经接受的任务；后台输出仍留在原任务／文件中，不自动更新Case判断或新增关联。以该Case再发起工作前需重开；从项目空间独立工作仍可进行。项目当前全局字段在其他入口发生的变化可正常显示，不因Case结束而冻结。

## 7. D09：入口、读模型与故障行为

| 入口合同 | 责任与约束 |
| --- | --- |
| Case列表／详情／历史读取 | 查新库并读取原项目摘要；不打开任务Runtime、不修改更新时间；项目缺失明确显示 |
| Case创建／编辑／结束／重开／说明 | 只经Host受控写入口，校验字段、活动状态、操作ID和Case修订 |
| 项目关联／解绑／新建并关联 | 接收原Project ID或受控创建请求；不搬移项目、任务和文件 |
| 项目业务字段读取／保存／说明 | 原项目API组合返回业务扩展；独立project业务修订与统一全局历史；不能每Case维护一份 |
| 产物读取／关联／解绑 | 沿用原项目路径访问验证；存在性不明确时不伪造，解除只改变引用 |
| 任务打开／新建／消息／命令／停止 | 复用现有入口；发送可选明确Case背景；命令、停止和原生UI仍按原任务生效 |

具体路由名称可在实现中依现有HTTP风格落地，以上数据与副作用合同不得变化。查询结果是组合视图：项目名称、文件、任务和归档动态读取原源；卡片项目数／状态汇总按当前关联计算，不写回Case状态，不持久保存“完成百分比”。

项目全局修改在不同Case和项目空间共用一个保存入口，成功后刷新对应视图；其他窗口在重新读取时获得新值，后续写入有修订检查。一期不承诺实时多人协作。Case自身更新时间与项目业务更新时间分开显示。

新库取得现有数据根进程锁后才打开；关闭数据库后再释放锁。业务字段编辑与项目归档／恢复／打开／发送在同一Host生命周期队列排序，入队后重新检查，不能只禁用前端按钮。SQLite事务保持短小，不跨模型调用、文件扫描或长IO。

Case库缺失、损坏、版本未知或身份不一致时，不新建空库掩盖错误。Case及项目业务字段入口明确不可用；如果原ProjectStore健康，原项目独立功能可继续，组合API须区分“业务扩展未设置”和“Case存储不可用”，不得用默认空值伪装读成功。Case背景发送拒绝，不能偷偷降为无背景请求。

## 8. D10：兼容启用与保全步骤

**实施验证先在隔离合成副本执行，实际Mini业务存储未自动启用。** 结构与最新UI Demo均已明确确认，按以下迁移与保全合同验证。MacBook部署、真实模型、业务资料与Git交付不从本结构确认自动取得额外授权。

1. **固定输入并静默清点。** 核对实际源码／运行版本、dataRoot／projectsRoot、项目状态及并发写入。通过授权的空闲／正常停止窗口建立基线；有活动任务先等待或交由用户停止，不自动杀进程。正式数据只记录结构、ID、路径、权限、数量、字节及流式哈希，不输出凭据或业务正文，不把这些清单提交公开仓库。
2. **覆盖全部保全对象。** 项目JSON（含tasks／配置引用／上传来源）、已有迁移备份、全部原生JSONL及父会话引用、三目录所有文件均记录原路径和字节摘要。核对过程中有写入则基线失效，不能以不一致清单宣布保全通过。
3. **识别既有格式。** 本增量的正常输入是合法schema2。若发现schema1，先单列执行既有已确认v1→v2规则及其备份／保全检查，再做Case启用；不把这一前置转换写成“所有JSON零变更”。未知／损坏／冲突元数据保留并报错，不自动重置或强行升级。
4. **显式初始化新存储。** 标记和库均不存在只是可初始化的条件，不能证明从未启用：两者同时丢失时，单靠这两个文件无法区分真正首次与整组丢失。普通Host启动报告“Case存储未初始化或缺失”，不自动造空库；本次获准启用应核对部署／备份记录后走明确的初始化步骤。随后先独占持久写入initializing标记及storeId，再以同storeId原子建立全套表／版本，最后将标记原子写成ready并同步目录。initializing中断时只允许核对后续接同一身份；发现已提交库则完成标记，未提交库则恢复同一初始化，不另造storeId。不另建第三套业务身份标记来声称解决整组丢失。
5. **已启用库只读校验。** ready标记下缺库、缺标记但库存在、身份不符、未知版本或完整性失败均保留报错；不以“首次运行”掩盖丢库。版本提升先做一致性备份，再事务迁移；失败保留原版本与日志，重复启动不产生半套结构。
6. **不批量改旧对象。** Case启用不创建默认Case、关系或project_work行，不改合法schema2项目JSON，不碰原会话路径／字节，不搬三目录。原始配置与凭据不导出、不重新导入。
7. **启用后回读。** 比对步骤2的保全基线，确认旧项目、任务、原生父链和文件可访问；再用隔离合成Case验证新功能。正常使用后产生的新草稿／历史不是迁移字节差异，必须分开记录。

缺少业务字段的项目始终显示“未设置”。首次用户保存才写project_work，不伪造其真实业务开始／完成时间。若旧版曾继续修改原项目，新版按原Project ID动态重新读取名称、任务和归档，不从Case缓存覆盖旧数据。

## 9. D11：备份、回退与保留

一期没有现成的产品备份中心，不能宣称已有。新增最小启用／升级前备份步骤：Host正常停机并关闭新库后，独占写入 `${dataRoot}/backups/decision-case/<UTC时间-UUID>/`，保留匹配的身份标记、数据库、原项目元数据／既有迁移备份及校验清单；只读核验副本，不覆盖旧备份。目录0700／文件0600，默认不复制凭据。

这一备份是结构恢复材料，**不是三目录和会话的完整灾备副本**。后者本轮不搬迁／改写，以保全清单验证；若用户需要完整灾备，应在明确范围下另作完整副本。不能仅凭元数据备份承诺可恢复被外部删除的文件。新库如需在线备份，应使用一致性备份机制；不得裸复制活动库或丢弃恢复日志。依据：[SQLite Backup API](https://www.sqlite.org/backup.html)。

| 阶段 | 允许的回退方式 | 数据影响与限制 |
| --- | --- | --- |
| 仅启用新库、没有新业务／上下文写入 | 停机保留新库／标记／备份，回到原兼容构建 | 原schema2／JSONL／文件未因Case启用变化；不要求删掉新库 |
| 已有Case、项目业务字段、关系或请求快照 | 保留全部新库，优先使用修复后的兼容构建；不得恢复旧空库覆盖 | 旧版可能仍能使用原项目功能，但看不到Case／业务字段；不称为功能等价回退 |
| 已产生原任务新消息、文件或原生fork | 同时保留最新JSON／JSONL／文件和新库 | 不用旧项目备份覆盖新任务／历史；代码回退不等于数据回退 |
| 损坏、未知结构、操作结果不明 | 保留原件、日志和副本，明确不可用／needs_review | 不自动重建、清理或重放；修复前核对最新写入与身份 |

备份和失败现场本期不自动清理，不设置隐含保留期限。任何后续删除按单独核定范围执行。不存在项目／文件引用也保留并提示，绝不通过重建空项目“修复”Case。

## 10. D12：验收与证据方案

验收先使用隔离dataRoot／projectsRoot、合成资料及合成Provider，不读取正式凭据／会话／业务文件，不自动调用真实供应商。下表定义验收目标；当前实际命令、候选和结果以本变更result记录为准，不从设计表预填PASS。

| 编号 | 关键场景与必须满足的断言 |
| --- | --- |
| AC-01 身份与多对多 | Case A关联原项目P／Q，Case B关联P；P的UUID、目录、任务及文件仍一份，没有Case Project或新任务归属层 |
| AC-02 低门槛／无模型响应 | 名称即可创建Case；无目标、未决或明确不行动可保存／结束；模型离线仍可管理Case、关联原项目和文件；不把“无配置新建项目”冒充既有能力 |
| AC-03 全局业务字段 | 从A、B及项目空间读到同一字段；旧项目显示未设置；两Case窗口编辑同项目的旧revision必须冲突；取消转完成不沿用旧取消原因，转取消须重新明确原因 |
| AC-04 状态独立 | 任务结束不完成项目，P完成不结束A；Case结束不停止任务、不归档项目；已结束Case继续前重开，项目独立入口仍能用 |
| AC-05 归档准入 | Case中可看归档项目与下载；保存业务字段、草稿、发消息／命令、新建任务不能绕过恢复；归档与写入竞态服务端有明确结果 |
| AC-06 关联入口范围 | 从任务建立Case明确关联整个项目；显示原任务集合，fork／branch保持原任务身份；解绑不删原对象 |
| AC-07 当前值与历史 | 判断修改、关闭原因、重开、用户反馈能追溯；原判断可查；项目全局历史不复制为多个Case事实；未变化保存不制造事件 |
| AC-08 引用与来源 | 真实文件有项目来源，未知来源任务为空；同路径不重复关联，解除不删文件；项目解绑后产物转历史引用；缺失／移动／变更有提示，不伪造版本或结果 |
| AC-09 上下文 | 发送前可见本次Case，版本变化须核对；固定背景／输入摘要可追溯，重试不静默换背景；普通项目发送不自动注入所有Case；旧任务历史不承诺隔离 |
| AC-10 并发／去重／事务 | 注入磁盘满、IO／提交失败；当前值与事件／completed回执共同成功或共同不提交；同ID重试不重复写，异内容同ID冲突；返回未知时先查结果 |
| AC-11 部分成功 | 新建项目成功而关联失败明确告知原Project ID；覆盖Case修订变化、结束后重开及关联响应丢失：用新project_link操作和原Project ID完成，原创建摘要不变，两回执可追溯，不新建第二项目；创建中断／目录冲突保全并needs_review，不自动删除 |
| AC-12 恢复与副作用 | 重启后Case、多对多关联、业务字段、引用及历史完整；列表／展开／关联／保存不触发模型或批量初始化Runtime；查看不刷新时间 |
| MIG-01 保全基线 | schema2启用前后项目JSON、所有JSONL／父链、既有备份、三目录路径／字节／权限符合保全清单；清点期间写入使基线失效 |
| MIG-02 旧格式／缺省 | schema1前置迁移与schema2增量分开验证；不猜旧状态，不自动生成Case／扩展行；未知格式／损坏保持原件报错 |
| MIG-03 初始化中断 | 标记前／标记后／建表中／提交后／ready前注入中断；续接同storeId，不出现重复结构；ready后缺库不能当全新启用；库与标记同时缺失时普通启动报未初始化或缺失，不静默造空库，只有核对后的显式初始化才新建 |
| MIG-04 锁／完整性 | 同根第二Host拒写；数据库身份、版本、外键、唯一性和完整性检查；错误时不伪装空看板，原项目健康时可独立使用 |
| MIG-05 备份／回退 | 对一致性副本核对storeId、版本、修订、历史和关联；测试新业务写入后的旧构建保留范围；旧快照不能覆盖新数据；不把结构备份称为完整灾备 |
| MIG-06 接受未知／故障恢复 | 发送前后断连、回执提交后响应丢失、跨存储阶段中断均保留真实已知／未知结果；不因Case库恢复而自动重放模型或业务动作 |
