## 1 产品方向与主要价值

OptraCall 是面向数据驱动决策者的分析与决策工作台。Agent 在获准环境内自主理解问题、查资料、计算、检查与解释；产品提供企业业务上下文、可复用的语义和经验、准确依据以及决策反馈环境，帮助用户把一次工作转化为以后可用的业务积累。

价值需要在实际工作中体现：减少反复解释口径、重复找资料和拼接关联，降低概念混淆与关键依据遗漏，让判断及其适用条件更容易核对。材料数量、图谱节点数、记忆命中或安装组件数量不能单独证明这些收益。

业务问题可以从数据、制度、流程、事件、用户陈述或历史案例开始。用户不必先准备完整 Case、RAP、SAP 或图谱；需要量化时，Agent 继续在原任务中使用获准数据计算。没有数据时可以形成有边界的判断与补证建议，不能把一般常识当成企业事实，也不能编造数值或效果。

### 四点产品原则

- **Host 管环境：**提供目标与材料、真实归属、权限、资源、交互、保存及可观察记录。
- **Agent 自主执行：**自主决定查什么、怎样计算、如何验证与纠错，形成专业判断和解释。
- **优先复用 Pi 已有能力：**会话、工具循环、原生历史、分支、恢复和压缩沿统一 Runtime；语义组件不另建分析循环。
- **减少人的操作：**正常路径是提出问题并发送；可选资料管理和依据查看不成为使用能力的前置步骤。

产品继续聚焦分析与决策，当前以个人工作台为范围。团队协作、企业权限、全套治理和真实业务执行由具体需求另行确定。沿用 JuanerAI 的有效资产和经验，新增复杂度需要证明价值，不重建完整旧蓝图。

## 2 业务内容、架构与责任

### 四库与双库表达什么

这些是业务内容的逻辑划分，不规定数据库、服务或页面的数量。同一内容可以互相关联，不要求复制多份。

| 内容 | 服务的问题 | 保留的含义 |
| --- | --- | --- |
| Data 数据 | 用哪份数据，一行代表什么？ | 原项目归属、固定版本、粒度、单位、字段说明及未知 |
| Ontology 本体／概念 | 术语和对象分别是什么，怎样区分和关联？ | 类型、身份、定义、别名、属性、范围、关系与有依据的约束；正式指标关联准确 SAP 发布版 |
| Knowledge 知识 | 有哪些制度、事实陈述、观点或方法可参考？ | 精确原文与来源性质；原文、整理、推断和已确认定义分别表达 |
| Memory 记忆 | 以前怎样判断，后来怎样，有什么可借鉴？ | 选择性经验、原场景、支持与反证、反馈和适用限制 |
| Hypothesis 假设 | 哪种解释可能成立，什么证据会改变判断？ | 主张、范围、机制、支持／反对依据及未知；不要求每次分析凑假设 |
| Strategy 策略 | 有什么选择，什么条件下适用，实际结果如何？ | 建议、人的选择、实际行动和观察效果分别记录 |

### 谁承担什么

| 部分 | 主要责任 | 边界 |
| --- | --- | --- |
| Host | 工作空间、上下文与工具供给、权限、资源生命周期、保存、日志和界面 | 不替 Agent 选择口径、裁决业务冲突、补计算或规定分析步骤 |
| Agent | 理解当前问题、取材、检查适用性、计算、推断、解释与修订 | 不扩大授权；引用、人的意见和图中关系不能直接当作已证实结论 |
| Pi Runtime | 原生会话、历史、分支、上下文管理、工具循环和统一运行接入 | 不建立第二份消息权威或平行会话恢复引擎 |
| Extension 与语义组件 | 提供分析资产、连接器、专业工具以及选定的语义组织／查询能力 | 共用产品接缝，明确额外模型调用和副作用，不接管任务权威 |

原业务 Store 继续保存各自权威：SAP 发布正式指标定义及可供参考的方法版本；企业资料保存原文修订；项目数据保存输入、说明和成果来源；Case／Board／Feedback 保存判断、取舍与实际反馈；Pi 原生记录保存工作历史。L2 的语义表示必须能回到这些来源，不能形成另一套可独立修改的正式公式、方法权威或历史事实。方法沿既有“先保存、后发布，发布后才可供后续任务参考”的规则，IR 与其他来源没有入图即参考的例外。

SQLite 承担现有业务记录与事务，文件保存正文和成果，DuckDB 是 Agent 可选的数据计算能力，Semantica 承担本版拟上线的语义处理能力。它们承担不同职责，不因“四库”名称而合库，也不要求同一任务全部使用。

工程接入继续沿当前 Pi1.4.0／Interface v3 与[统一会话规范](agent-session-integration.md)；本文不变更接口或逐 profile 的能力范围。Pi 原生历史可以长期持久存在，跨任务业务语义与经验则按来源和权限另行组织与提供。

## 3 当前 L1：让 Agent 取得并解释业务材料

### 已实现的供给方式

L1 已有正式定义、企业资料、数据说明、经验和准确引用的供给与追溯能力。它的主要方式是把相关内容交给模型，由模型结合当前任务理解、关联和判断。

| 环节 | 当前方式 |
| --- | --- |
| 当前工作上下文 | 恢复本任务的 Pi 会话，结合本次问题和实际选定的材料；不自动读取所有其他任务历史 |
| 初始材料入口 | 企业公共资料默认提供可自主查阅的目录路径；SAP 提供已启用资产的版本、名称与定义文件索引，完整定义按需读；本次选定的 RAP、Case、个人参考、反馈和数据说明按原合同交付 |
| 按需查读 | 普通项目任务可使用原文件工具、个人／Case 来源工具，以及 `read_semantic_context` 的 find／read／trace；分别查目录、读准确目标、展开一层显式引用 |
| 业务理解与计算 | 模型阅读定义和材料，判断范围、适用性及冲突，自主选择 Python、DuckDB 等可用工具分析 |
| 成果与回源 | 可选调用 `record_analysis_sources`，委托原 M2 保存成果与作者明确声明的准确来源；原回答旁可查看依据 |

这不是固定执行顺序。Agent 可以不查语义工具，也可以多次追溯引用；相关目标列出不等于已读，资料提供不等于已理解或采用，保存声明不证明计算正确。查询或可选保存失败时可以说明缺口并继续原分析，明确必要选材与权限仍按原合同执行。新语义工具目前不自动扩展到受管、独立核算、封闭文本和其他专用资源。

L1 的业务定义和关系并非全部是散文：SAP、数据映射、来源清单和 Case 引用已有结构。当前主要由模型在任务上下文中把这些材料综合起来，后台没有接入通用本体／知识图谱引擎。**本轮核对的 L1 尚未实现切片向量 RAG。**

`recordedBefore` 只筛具有可靠系统留存时间的记录，未知时间另列；业务时间保留原声明，不能据此声称完整历史快照或通用 as-of 查询。实现依据见[L1 规格与记录](../openspec/changes/fourbase-l1-semantic-trace/implementation.md)及[L2 接缝核对](../openspec/changes/fourbase-l2-temporal-projection/reuse-audit.md)。这里描述已核代码能力，不表示每次真实模型都会正确使用。

### L1 与 L2 共用的模型原理

模型在运行时处理用户问题、对话和工具结果形成的上下文，据此生成回答或工具调用；普通读资料不会自动训练或修改模型参数。L1 主要让模型从材料中理解和关联；拟议 L2 在模型之外增加可持续复用的业务语义组织和查询。两者最后仍由 Agent 结合当前情境分析，图查询结果也需要通过工具等获准入口进入模型上下文。

## 4 完整 L2：后台业务语义支撑

### 主要目标与能力

**完整 L2 的主要价值，是借助本体和知识图谱，让 Agent 更可靠地理解企业的概念、范围、规则及其关联，并在分析中正确使用。**来源、关系、时间和前端解释共同支撑这一目标，任何一项都不能代表完整 L2。

本体定义业务世界怎样表达：有哪些类型、属性和合法关系，概念如何区分、范围与约束来自哪里。知识图谱按这些定义组织具体对象、事实陈述、关系、来源和时间。明确规则的推导需要相应实现及成立前提；沿图查到关系、执行约束检查和分析经营原因是不同工作，不能混称为已证明的业务推理。

| 完整能力方向 | 对 Agent 的帮助 | 必须保留的边界 |
| --- | --- | --- |
| 概念与身份组织 | 区分同名不同义、同义不同名、业务对象、范围、粒度与单位 | 同一实体的合并需要身份和范围依据，不能只凭词相似 |
| 知识关系与语义检索 | 关联指标、制度、数据字段、业务对象及经验，按问题取得必要上下文 | 关系需要来源；图中缺边不证明现实没有关联，命中也不证明适用 |
| 规则约束与冲突核对 | 在选定且实际可执行的范围内发现不一致，把依据和未知交给 Agent | 结构合法不等于事实真实；相反声明不能被自动覆盖，图路径不证明因果 |
| 事实演变与历史 | 区分业务有效时间、系统留存时间和原稿引用，核对前提变化 | 不追改旧报告与人的选择；缺失的历史不能用当前内容代填 |
| 可复用与可维护 | 复用已有语义组织，支持更新、失效、回源及必要重建 | 原权威保留；派生内容仍受权限、数据出口和保留规则约束 |

### Semantica、Graphiti 和 Pi 的关系

Semantica 是本版拟上线的本体／知识图谱语义支撑系统。应围绕首个服饰零售 Case 选择必要的组织、建图、来源、约束及检索路径，完成固定版本能力验证和产品接入；上线目标不自动承诺所有模块、完整 OWL 推理、GraphRAG 或官网能力均已可用。必需能力存在实际阻碍时应明确差距并调整方案，不能以一份组件研究代替上线结果。

Graphiti 保留为具体缺口后的条件比较：当持续输入事件、实体对齐、事实更新／失效或历史状态查询存在明确需要时，针对同一问题验证。两者能力有重叠，不能机械划成“语义只归 Semantica、时间只归 Graphiti”，也不默认同时维护两个引擎。

Pi 继续承担 Agent Runtime。OptraCall 提供业务来源与身份映射、准入、最小工具接线和必要展示。组件自带的 LLM 抽取、检索整理或其他内部处理若被采用，应说明实际作用、运行归属、取消、成本与数据出口，不能隐藏为普通数据库读取，也不另造产品分析循环。

### 与文本 RAG 的关系，以及更准、更快的条件

文本 RAG 检索相关原文片段，图检索通过实体、关系与路径组织关联依据；RAG 是检索辅助生成的方式，知识图谱也可以成为其检索来源。两者可结合：用图找到相关制度、指标和字段，再读取原文及例外条件。简单原文定位未必需要图，跨材料关系也不能只靠相似片段保证完整。

预期的“快”来自减少重复找源、辨义和拼接；建图、更新、检索与模型使用仍有成本。预期的“准”来自有依据且及时维护的概念、身份和关系；错误抽取、合并或过时规则可能被反复复用。Agent 仍需判断当前问题、检查适用性、计算并解释，不能宣称图谱普遍更准、更快或替代所有推理。

例如，一个**虚构**场景同时存在两种“净销售额”：门店定义按退款登记月份扣减，某渠道定义按原订单月份归属。L1 由 Agent 读取定义、制度和数据说明后识别差异；L2 的目标是将两个定义及其范围、退款规则和字段关联提前组织，供 Agent 按需查询并回源核对。本例不是企业正式规则、标准答案或已选定试点，也不证明采用效果。

### 采用方案必须打通的内容

采用 Semantica 需要完整考虑业务语义如何形成、维护和被 Agent 使用，不能只完成 spec 和 UI。下表列出方案必须回答的问题，不是要求普通用户手工完成的操作清单，也不是产品固定分析步骤。

| 环节 | 需要明确什么 |
| --- | --- |
| 有限业务问题与本体 | 首个问题、概念与关系范围、定义来源、类型和适用约束；先复用已确认材料，实质歧义再由业务负责人取舍 |
| 材料与实体映射 | 哪些资料准入，如何保留原身份、版本、hash 和位置，何时视为同一实体，哪些关系是声明或推断 |
| 建图与检查 | 哪些现有结构可直接映射，是否需要抽取／对齐／模型，哪些约束路径真实可用，怎样保留冲突和未知 |
| 存储与维护 | 使用哪条原生保存路径，怎样更新、失效、重开和重建，谁负责维护，如何处理索引落后与访问变化 |
| 检索与 Agent 使用 | 哪些问题适合图查询或图与原文混合检索，返回什么依据，怎样沿现有 Pi 接缝提供并观察实际使用 |
| 效果与成本 | 相对 L1 改善什么错误或重复工作，首次整理、运行和持续维护成本是否可接受 |

工程负责环境、配置、映射和接入，优先复用组件已有入口；Agent 可以提出候选并按需查询、解释。业务负责人处理不能从既有依据确定的定义与取舍，不逐条审批普通读取，也不被要求先填满全企业语义资料。无需为所有组件设置制作用户页面或复制一套图谱管理平台。

固定发行与主要设置、原生入口、已知实现限制见[Semantica 使用链研究](../openspec/changes/fourbase-l2-temporal-projection/semantica-usage-research.md)。该研究只有静态证据，尚未完成安装、实际调用或嵌入式 Pi 兼容验证；图查询、SHACL 等约束检查及 OWL 推理分别核验，不能因为函数或文档存在就承诺完整规则能力。

### Semantica 与 Pi 的系统接入

OptraCall 在 Node／TypeScript 中使用 Pi，Semantica 核心运行于 Python 环境。拟沿现有工具接缝让 Agent 查询语义后台，保留原会话和模型／工具循环。图数据准备与运行时查询是两类工作：已建图但没有获准接口，或只接好接口而没有业务数据，都不足以支撑首 Case。

| 层次 | 在本产品中的作用 | 实施时必须核定 |
| --- | --- | --- |
| Python 环境与 Semantica 模块 | 执行选定的本体、建图、约束和检索操作 | 固定发行、兼容解释器、必要依赖和配置；不默认全量 extras 或新的外部模型 |
| MCP 或业务工具接口 | 公布工具与参数、接收调用、返回相关语义及来源 | 优先复用现成 MCP；若准确来源／准入／必要能力存在缺口，再沿现有 Host port 作薄适配，不默认叠两套机制 |
| Pi skills | 指导 Agent 理解何时、怎样使用相关能力 | skills 不等于已安装 Python 包、已连服务或已加载企业图；仅复用适用内容 |
| Pi 会话与工具结果 | Agent 自主生成参数，取得结果后继续回源、计算、判断与回答 | 重要定义和依据进入模型可见的工具 content；界面 metadata、调用成功和实际理解分别记录 |

现有普通任务已有显式 MCP 扩展装载和商圈／天气注册机制，也有 L1 的 semanticContext 业务端口。接入应先核这些机制与官方所需能力的匹配。CLI 的安装命令或 mcp.json 不能直接充当嵌入式接线证据；固定文本、冷读、独立核算及受管资源不因普通任务上线而自动扩权。

需要选定一个明确的语义数据装载、保存和刷新路径，保证建图、必要管理入口和 Pi 查询取得一致的可核版本。已核发行的 MCP、Explorer、REST 默认状态不天然共享；多个进程指向同一个 JSON 也不等于已证明同步或并发一致性。原生装载已支持的格式应先复用并做往返核验，不能仅因表示不同就新建通用转换平台。

官方 MCP 只暴露部分能力且包含写图工具，所需查询集合、读写归属和当前数据准入必须明确。模型可选的查询不等于任意写图资格。请求取消、丢弃迟到结果、关闭连接、终止 Python 进程和确认写入结果分别验证；组件若使用自己的 LLM／embedding 路径，应单独说明实际配置、成本和数据出口。详见[Semantica／Pi 接缝研究](../openspec/changes/fourbase-l2-temporal-projection/semantica-pi-integration-research.md)。

### 首个服饰零售场景的 SAP、本体与知识图谱建设

前一轮研究以“L1 已具备服饰零售指标体系、方法和背景”为题设说明操作方式。本版将首 Case 所需资产的实际建设纳入交付：实施时先盘点已有内容，复用准确发布版，补齐必要缺口，不能把研究题设当作现有材料已经齐全或上线已完成的证据。

| L1 来源 | 本场景需要完成的建设／映射 | 保留的区别 |
| --- | --- | --- |
| SAP 指标 | 明确本 Case 使用的定义、维度、粒度、单位、时间归属与适用范围，补齐并发布必要版本，关联数据说明 | 净销售额等概念与某一具体发布定义分开；原公式保持权威，同名指标不自动合并 |
| SAP 分析方法 | 复用或补齐可参考方法的用途、指标／数据需要、适用条件、局限及来源，沿原规则发布并核项目可用性 | 未发布版本不进入后续参考；方法步骤是知识，由 Agent 自主选择、调整和验证 |
| 企业背景／制度 | 选择本 Case 所需门店、渠道、款式／SKU、季节及相关制度／事件材料，保留准确修订与原文 | 对象身份与编码沿原业务依据；制度规定、实际行为、观点与待核声明分别表达 |
| 数据与说明 | 固定获准输入及说明版本，补充必要粒度、单位、时间归属和字段到指标／概念的映射，披露争议 | 原始明细继续由原文件及 Python／DuckDB 分析，不默认逐笔搬进图 |
| RAP | 明确本次业务问题、对象／时间、目标／约束、已知材料、假设和未决项 | 任务情景用于查询范围和分析背景，不把目标或假设升格为企业全局事实 |
| Case／经验 | 保留本次判断、反证、人的取舍、经授权行动及反馈；可参考原有经验并核适用性 | 经验被保留不证明有效，人的采纳不证明执行，观察改善不直接证明因果 |

具体建设按下列依赖关系推进，验收贯穿同一个 Case，不先完成多套孤立 CRUD：

1. **确定业务范围与准入材料。** 选定首个问题、责任人、对象／时间和观察安排，形成可定位的输入及来源集合；候选题面可用“直营门店销售下降，是否促销”，但真实企业、门店和问题尚待指认。
2. **完成所需 SAP 与背景资产。** 复用已有发布版、补齐必要指标／方法、背景与数据说明，沿现有发布和项目准入验证可读；不重复录入已有定义。
3. **形成小范围本体。** 表达业务类型、身份、范围、关系方向与必要约束；区分类型、具体指标／方法版本、企业对象和带源声明。可以用 Semantica 辅助生成候选，但不能把自动推断当已确认业务规则。
4. **构建带依据的图数据。** SAP、数据映射和显式引用优先确定性映射，背景原文再做有位置和不确定性的候选抽取；相反材料并存，名称相似不直接合并。每个必要关联都能回到原准确来源。
5. **检查语义与表示。** 分别核结构、业务含义和实际执行的约束。若采用 RDF／SHACL，需检查真实 target 命中与负例；通用 validator 的 valid 不自动证明完整 OWL 或业务正确。核保存、重开和查询后身份、关系、来源及时间是否保真。
6. **接入并采用可查询版本。** 在约定环境加载数据、连通 Pi，核更新／失效／刷新和失败继续；实际任务可取得相关定义、关系、方法条件与原文依据，组件停用后原 L1 和计算能力仍可用。
7. **用首 Case 检验并修订。** Agent 实际查读、分析和解释，真实反馈进入复盘；若暴露资产或映射错误，保留原结果，修订准确源或派生映射，再按各自发布／采用规则供后续使用。

上列是建设与验证路线，不是 Host 在每次分析中强制执行的流程。工程负责源映射、配置、进程和准入，Agent 自主提出抽取候选、查询、计算与判断；用户只处理不可由已有依据确定的业务歧义、必要授权和实际取舍。具体本体、后端、接口、字段、模型和维护责任在后续整体方案收敛，不在讨论稿冻结。操作依据见[服饰零售语义构建研究](../openspec/changes/fourbase-l2-temporal-projection/apparel-retail-semantic-build-research.md)。

## 5 工作台体验与决策经验闭环

### 原任务提问，关键解释直接进入回答

用户继续在项目任务中表达目标、给出材料或纠正背景。Case、RAP、SAP 按需关联，普通材料与计算可在同一主任务连续进行；不因采用 L2 切换分析模式或搬运对话。只有实质缺失影响判断或权限时，Agent 才针对性澄清，其余可说明假设与局限后继续。

| 位置 | 应承担的内容 | 用户操作 |
| --- | --- | --- |
| Agent 主回答 | 主动解释与本次结论有关的关键口径、范围、版本差异、实质冲突和重要未知，以及对判断的影响 | 正常提问和发送即可看到，不必打开详情 |
| 回答旁“查看依据” | 业务含义作为可选内容，查看准确原定义、版本、来源、关系和已知时间；区分原稿引用与今天回看 | 想深入核对时自愿展开 |
| 追问与纠正 | 在原任务继续提问或修正背景，必要时说明结论如何变化 | 用户正常发送；查看详情不自动重算或改资料 |
| 可选资产管理 | 查看、补充、修订或归档值得复用的内容，处理必要业务定义 | 不成为每次使用 Agent 的必经步骤 |

不增加独立“业务含义”页面、一级导航或必做查看步骤，正常新增必做操作为零。Agent 输出目标由其自主分析实现，Host 不强制每轮先查 L2、固定查询顺序或强制保存引用。无 Case、空语义资料、组件不可用或可选保存失败时，原 L1 和计算路径仍可继续；已明确必要的资料与访问权限不能静默放宽。

### 从分析走向经验复用

一次工作可以关联业务背景、判断、支持与反证、未知、备选策略、人的取舍、实际行动、预期与观察结果。信息逐步补充，不要求所有工作都形成完整决策闭环。

“Agent 建议”“用户采纳”“实际执行”“效果已验证”分别记录；人的选择不证明执行，一次业绩改善也不直接证明策略因果有效。没有反馈、失败和反证保留原状态，不能自动标记成功。

有复用价值的内容可以整理为候选，按现有产品入口选择保留、修订或归档。下一次工作由 Agent 检查范围、条件和反例，引用或拒用旧经验；更新语义表示不能把过去报告的依据换成最新版本。业务纠正、排除与归档沿既有入口，物理删除和遗忘须另核源、索引、历史及备份，不新增自动清理。

### 首个服饰零售分析决策闭环 Case

本版要求交付首个真实使用的分析决策闭环，不只完成一个预置 Demo、合成计算或报告导出。行业域确定为服饰零售；具体真实问题、企业／门店／渠道、时间窗、决策责任人、材料、模型配置及反馈安排，在下一份整体方案明确。业务问题不必为了适配图谱而改写成纯关系查询。

```mermaid
flowchart LR
  Q[真实问题与获准材料] --> A[Agent 查询语义、回源与分析]
  A --> R[结论、证据、备选与未知]
  R --> D[人作出明确取舍]
  D --> O[经授权的行动、补证或持续观察]
  O --> F[实际反馈与结果]
  F --> V[复盘、修订与经验保留]
```

这条链说明首 Case 需要形成的业务证据，不规定 Agent 的工具顺序，也不让 Host 承担业务判断。正常分析可在原主任务连续推进，必要的业务取舍和外部动作授权由相应责任人作出。

闭环至少留下：业务问题与范围；准确材料、SAP 和实际语义使用的依据；可复核计算及报告；支持／反证、限制和备选；人的决定及理由；真实行动或补证／观察的安排与实际后续；反馈、复盘结论和需修订／保留的内容。实际提供、作者声明引用与正确采用仍分别核对，不能只凭工具回执补造采用事实。

补证、暂缓或不行动可以是合理决策，但仍需对应的真实后续结果或观察和复盘，不能仅凭选中该选项就关闭 Case。尚未取得反馈时保留待反馈／开放状态；模拟行动与合成反馈只用于工程演练，不计真实闭环。闭环完成不要求经营结果必然改善，也不直接证明策略因果有效；失败或无改善同样需要如实复盘。

首 Case 的资产建设、上线和真实反馈有依赖关系，可以小步验证与修正。将来第二个 Case 的经验复用继续是产品价值方向，但不为完成本次首 Case 额外强制创建第二个真实 Case。

### 三项目标怎样判定完成

| 编号／对象 | 最低完成证据 | 仍需分别判断 |
| --- | --- | --- |

| V405 首 Case 闭环 | 人的明确决定、真实后续行动／补证／观察、对应结果和复盘已记录，需修订内容与保留经验有来源；失败或无改善同样如实记录 | 无反馈仍待反馈；合理不行动也须有实际后续观察和复盘；闭环不直接证明策略因果或经营增益 |
| V406 持续可用与保全 | 维护、更新、撤回与故障处理责任清楚；旧报告／Case／源版本保持，停用语义组件仍可沿 L1 分析和回源 | 新上线不改写旧成果、人的选择、FAIL／UNKNOWN；实际访问边界按已批准范围验收 |

| 效率与维护 | 分开记录首次整理／建图、更新维护、查询和回答耗时，以及模型／资源成本和人的负担 |
| 工程与持续可用 | 保存重开、更新失效、重建、取消、权限、历史保留及停用后回源，按具体实施范围核验 |
| 决策与经营效果 | 实际取舍、执行和反馈另有证据；不从工程通过或报告完成推断经营收益 |

同源对照固定共同业务材料、问题、模型实际配置、权限和预算；L2 的表示与检索方式是比较因素，最终上下文不必逐字相同。L2 建模所依据的新增业务定义或人工澄清同样向 L1 开放，不能把独占标准答案当成组件收益。新增整理工作和成本应单独记录，必要时区分“增加业务知识”的收益与“改变组织／检索方式”的收益。

同源比较可以使用首 Case 的固定获准材料核对语义质量与成本，不要求为了评分重复真实业务动作。首 Case 跑通只证明该问题、材料和配置下的可用性；普遍更准／更快、跨场景收益和经营因果效果需要后续证据，不能由一次闭环外推。

保留首次、重复、失败、无增益和新错误，不预写提升比例。图节点数、命中率、约束通过、工具成功、页面可打开及预置 Demo 回答均不能代替 Agent 正确使用的证据。非必要模块可以收缩或不用；若 Semantica 上线、场景资产或首 Case 核心目标不能满足，应记录未达目标及原因，调整整体方案，不能把收缩后的工程 POC 记作本版完成。正常主分析能力继续可用。

本地工程检查、真实模型质量、经营效果、Git／CI、运行采用和用户产品验收分别记录。既有专业 FAIL／UNKNOWN 与历史流程限制不由本稿或未来组件接入改写。

## 7 实施方式、整体确认项与来源

### 开发与权限边界

沿用 SDD／TDD、适用检查、非作者独立复核及精简 Git／CI；详细要求唯一维护在[工程规范](engineering-workflow.md)。纯讨论稿变更只做相称内容、一致性、引用和范围复核，不制造产品 RED 或运行无关产品测试。

Mac mini 负责产品方案、开发、工程验证和修复；MacBook 作为用户体验与问题回传端，不形成第二条开发线。Codex 负责 Host／Agent 与整体接入回归，Qoder 负责获分派的 Extension 本体；接缝与移交按工程规范执行。

此次仅更新讨论稿与必要文档记录，不修改产品源码、测试、依赖或业务持久结构，不安装 Semantica／Graphiti，不调用真实模型或读取真实业务根／凭据，不切换服务或操作 MacBook。既有 Git、设备及历史功能授权不自动扩为 L2 采用批准。

### 下一份方案需要收敛的决定

1. **首个真实 Case。** 确定服饰零售业务问题、企业／门店／渠道、时间范围、决策责任人及判断基准，明确行动／补证／观察、反馈来源与复盘安排。首个行业域不再待选，具体 Case 仍需指认。
2. **SAP 与 L1 材料。** 盘点已有准确发布版，确定首 Case 必需指标／方法、企业背景、数据说明和字段映射的缺口，明确内容建设、发布及项目准入责任；真实材料和模型范围沿有效授权。
3. **本体和知识图谱。** 收敛必要类型、身份、关系、范围、来源和约束，明确结构化映射、候选抽取及未知处理；实际持久结构、兼容与维护方式在验证现成能力后提出最小决定。
4. **上线环境与 Pi 接入。** 明确目标运行环境、实际组件与依赖、MCP／业务工具路径、装载刷新、权限／取消、必要模型处理及成本；将安装、产品接线、运行采用和设备影响写入具体授权范围。
5. **验证与完成。** 将 V401–V406 落到同一个首 Case 与相称工程验证，明确原 P1 哪些探针可复用、哪些范围需调整，分别核上线、资产、真实分析和真实反馈；同源对照不代替闭环结果。
6. **维护与停用。** 明确源更新／撤回、资产纠错、图过时、权限变化和组件失效的处理与责任，保留原 L1、旧依据和原成果；核心目标受阻时怎样修订方案。

下一份整体确认包应覆盖上线、场景资产建设与首 Case 闭环的完整范围，可按依赖关系分批实施和验证；不得仅提交来源／时间 POC 而把三项目标遗漏。已有依据能解决的问题由工程／Agent 继续收敛，普通用户无需替开发者选择技术参数。本稿不冻结数据库、API、字段、模型、后端或全部模块，也不以“上线目标”默认批准公开部署、自动业务执行或操作其他设备。
