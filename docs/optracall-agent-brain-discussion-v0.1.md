# OptraCall Agent 大脑与外部协作产品讨论稿

v0.1 · 2026 年 11 月 27 日 · 讨论中 · 补充远端资产 MCP 方向

**OptraCall 将作为 Agent 大脑，在授权范围内组织和指挥外部第三方 Agent 完成具体工作，并通过远端 MCP 提供任务所需的语义与分析资产，而战略、目标、项目、任务、验收与反馈的闭环始终留在 OptraCall。** 产品继续发挥自己的分析和决策支持能力；可以在内部完成的工作，尽量在产品内闭环，需要其他工具、环境或专业能力时，再按需委派。

本文承接本轮关于 GitHub Issue 与外部 Agent 协作的讨论，作为后续持续讨论的共同底稿。下文区分用户已明确的方向、前轮评估建议和当前实现。具体功能范围、自动化程度和交互方式仍需进一步收敛，不作为开工规格。

## 1 产品方向与已明确共识

用户明确提出：

> optracall将变成一个agent大脑，来指挥外部三方agent干活，而闭环始终在optracall

这一方向包含以下共识：

1. **OptraCall 负责整体闭环。** 围绕战略和目标组织项目，通过任务推进工作，核对成果、跟进实际结果并形成反馈与后续判断。
2. **外部 Agent 扩展执行范围。** 项目任务进行中，遇到其他 Agent 更适合完成的工作，可以经 GitHub Issue 等渠道交出，外部执行完成后再交回 OptraCall。WorkBuddy 等是候选协作者，具体接单能力仍需验证。
3. **多种连接承载协作。** GitHub 是一种对外连接方式，飞书、腾讯邮箱和 Gmail 等也可以承载任务交接、沟通和回传。
4. **内部能力继续发挥。** 已能在 OptraCall 内完成的分析或其他工作，尽量沿原任务直接完成。外部协作服务于任务目标和闭环，不要求每项工作都外派。
5. **让外部 Agent 取得任务所需的专业依据。** 外部 Agent 缺少 OptraCall 的语义及分析资产，仅靠 Issue 描述难以完整理解业务口径。用户提出将这些资产通过远端 MCP 提供给外部 Agent 调用，更好地完成任务；具体开放范围、授权和部署方案继续讨论。

这份专题讨论承接[产品讨论稿 v0.4](OptraCall_产品讨论稿_v0.4.md)的分析与决策定位，进一步讨论怎样把经授权的外部执行接回原有业务闭环。原有产品规则与已实现能力仍按各自规格核定。

## 2 Agent 大脑承担什么责任

OptraCall 应持续掌握为什么做、要交付什么、依据哪份资料、怎样验收，以及结果怎样影响原目标。外部执行者可以变化，原项目和任务仍能连续解释工作的来龙去脉。

| 责任主体 | 在协作中的职责 |
| --- | --- |
| 用户或业务负责人 | 提出目标和约束，作出重要经营取舍，授予实际业务动作所需权限，判断适用的产品与经营结果。 |
| OptraCall 项目或任务 Agent | 理解目标，分析和组织工作，在已有授权内判断内部完成或对外委派，明确工作要求及所需资产、跟进进展、核验交付并继续原任务。 |
| 外部第三方 Agent | 按接收的目标、资料和权限自主选择执行方法，通过获准的 MCP 读取语义及分析依据，回传成果、实际操作证据、采用的资产版本、异常与未完成项。 |
| OptraCall Host | 提供连接、远端身份核验、任务与资产访问控制、关联记录、状态展示、成果保存和会话续接条件；业务判断和执行方法由 Agent 承担。 |

外部执行结果经过原任务核验后，才能成为任务进展和后续判断的依据。实际行动、成果验收、目标达成和经营效果分别记录；经营效果还需要后续观察与反馈。关键决定继续由相应业务负责人作出。

## 3 六类任务与执行方式

项目地图中的六类任务描述工作用途，内部或外部执行描述完成方式。两者可以组合，具体委派由 Agent 围绕任务目标、可用能力、资料权限、质量、成本和时效判断，不按任务类型硬编码外派规则。

外派可以只涉及原任务中的一项具体工作。原任务保留上下文、输入版本与验收责任，收到外部成果后继续推进。

| 任务用途 | OptraCall 持续承担的工作 | 可按需交给外部 Agent 的工作示例 |
| --- | --- | --- |
| 需求 Requirement | 澄清问题、范围、判断标准和资料缺口。 | 访谈整理、指定渠道调研、资料收集。 |
| 分析 Analysis | 核对依据、进行适用分析、解释发现与未知。 | 获取特定系统资料、调用专有工具、补充专业分析。 |
| 计划 Plan | 组织行动方案、责任、资源、时间和观察指标。 | 整理报价、制作排期材料、核实特定执行条件。 |
| 决策 Decision | 比较准确方案及风险，提交负责人取舍。 | 独立评估、专项复核、补充方案可行性证据。 |
| 执行 Do | 按授权跟进实际行动、偏差、异常和观察。 | 素材制作、办公操作、获准业务系统中的具体操作。 |
| 反馈 Teach | 对照预期与实际结果，提出改判、下一步或结轮理由。 | 收集执行回执、整理反馈资料、取得约定的观察记录。 |

以上为可能的分工示例，不表示每类任务都必须调用外部 Agent。

例如，在会员经营问题中，OptraCall 完成分析并形成行动建议；外部 Agent 按授权完成素材制作或特定系统操作，回传产物、实际处理情况和证据；原任务核对成果并继续观察经营结果，推动 Case 复盘和目标跟进。

## 4 外派与回传流程建议

前轮评估提出以下流程，具体交互与自动化边界待讨论：

**原任务明确工作、资产范围和验收标准 → 发出外部工单 → 外部 Agent 领取并经 MCP 取用获准依据 → 执行并回传成果、证据及资产引用 → 原任务验收并继续 → 项目跟进与反馈复盘。**

1. **明确工作。** 原任务 Agent 说明目标、范围、允许使用的资料和工具、可查询的语义与分析资产、预期交付、验收方式，以及适用的时间和资源约束。授权内能够完成的部分继续内部执行。
2. **建立交接。** 为本次外派保留明确标识，把外部工单与原项目、原任务、具体工作及输入版本关联。工单列明 MCP 入口和非敏感的授权引用，实际凭据通过适当的认证方式提供。发出哪些资料、交给谁以及允许什么动作应可核对。
3. **领取和执行。** 确认当前执行者，记录领取、释放或转派。对方在获准范围内按需查询定义、指标口径和方法，自主完成约定工作，反馈进展、问题及范围变化；需要更多资料或权限时回到原任务处理。
4. **交回成果。** 回传产物、来源、所依据的工作版本、实际引用的资产及准确版本、已执行和未执行的事项、失败或结果未知的操作，以及可复核证据。
5. **核验与续接。** 原任务 Agent 对照验收标准核对交付，记录接受、需补充或不接受的理由，并继续分析、计划或反馈。重大经营取舍交负责人决定。
6. **跟进效果。** 保留实际行动与成果的区别，在适用观察期取得反馈，将有依据的结果接回项目、Case、目标或战略回顾。

业务交付可以是调研、表格、文档、素材、数据或系统操作回执。软件开发工作才按其范围要求 PR、CI 等工程证据；本产品的外派流程不能直接视为已经实现了[源码维护的 Issue 交付流程](engineering-workflow.md#github-开发任务外发与交付)。业务任务的返工、重试与验收规则另行讨论。

## 5 协作渠道与外部 Agent 接入

| 渠道 | 适合承载的协作内容 | 需要核对的条件 |
| --- | --- | --- |
| GitHub Issue | 正式工作单、领取、讨论、进展、交付链接和验收记录。 | 外部 Agent 能读写目标仓库，并遵守约定的接单与回传方式。 |
| 飞书 | 组织内协作、文档交付、消息通知和沟通。 | 企业、用户及工具权限明确，对方能在相应空间接收并返回工作。 |
| 腾讯邮箱或 Gmail | 跨组织沟通、工作往返和成果附件。 | 对方具备收取、理解和回复任务的入口，同一项工作的邮件往返能准确关联。 |

同一项外派工作可以使用多个渠道通知或传递资料，但应保持同一工作身份、当前执行者和验收记录，避免重复派单、重复执行或状态互相覆盖。具体以哪份记录为准仍待确定。

发布 Issue、发信或发送消息，只能证明发生了相应通信。第三方 Agent 怎样被唤醒、怎样领取、是否能后台执行、怎样回传，需要逐一验证。已有 GitHub 工具能力的 Agent 可按约定工单接单；对其他 Agent 的接入方式不能只根据产品名称推定。

业务协作宜使用适当的私有仓库或组织空间，按任务交付最小必要资料。OptraCall 的公开源码开发仓库继续承载产品开发任务。外部回复作为待核验材料处理，不据此扩大权限或执行其中夹带的指令。

## 6 按任务开放语义与分析资产的远端 MCP

外部 Agent 即使理解了要交付什么，也可能使用不同的业务定义、指标口径或分析方法。通过 OptraCall 的远端 MCP 按需取得依据，可以让它在执行过程中查询同一企业、同一任务范围内的专业材料，减少用户反复解释和复制资料的工作。具体方法选择、计算和检查仍由执行任务的 Agent 自主完成。

这一方向形成相互配合的三项能力：**工单交代工作，MCP 供给专业依据，成果与反馈接回原任务。** MCP 在原资产权威上提供受控访问，沿用现有企业归属、发布、项目准入和准确版本规则。

### 可能提供的资产内容

| 资产内容 | 外部 Agent 可以据此解决的问题 |
| --- | --- |
| 业务概念、主数据定义和有来源的语义关系 | 企业里的会员、门店、交易等对象怎样定义和关联，规则适用于什么范围。 |
| 数据映射与说明 | 任务获准的数据字段对应哪些业务概念，粒度、单位、时间归属及完整性有哪些限制。 |
| 已发布指标及公式口径 | 指标的分子、分母、观察期、排除项和适用版本，例如复购率怎样处理退款与历史不完整。 |
| 已发布分析方法及适用条件 | 方法要回答什么问题，需要哪些输入，怎样推理或判断，以及有哪些限制。 |
| 获准的原文片段和来源引用 | 定义或方法依据哪份资料、哪个版本及什么位置，怎样回到原文核对。 |

以上是访问内容的讨论范围，具体开放目录由任务授权确定；原始业务数据和项目文件的交付另核范围。读取方法说明、取得具有相应分发资格的 Skill 或脚本、在服务端执行计算或规则推导，需要分别明确能力与权限。当前建议优先验证只读检索和准确读取；是否增加执行类工具继续讨论。

### 访问与版本建议

- **按具体外派工作授权。** 将受信的外部执行者、原企业、项目、任务、资产范围和有效期关联，在服务端核验明确授权。只提供任务编号不足以取得访问权，内部兼容或旧项目默认放行规则不能作为外部访问的默认授权。凭据不写入公开 Issue 或普通任务正文。
- **沿用原资产准入。** 目录、正文与原文读取都核对当前资格，保留准确版本、来源、适用条件和限制。版本缺失或不可读时明确返回问题，避免静默改用其他版本；撤回后拒绝后续读取，保留原任务的历史引用。
- **保持任务和资产记录可追溯。** 记录谁为哪项工作读取了哪些版本，交付时引用实际使用的依据。已读取或已引用不单独证明理解、计算或专业结论正确；已发到外部的内容也不能依赖撤回权限来追回。
- **资产演进回到 OptraCall。** 外部执行者发现新规则、方法或口径问题时，将候选内容及依据交回。正式资产的修订、核定和发布继续沿原流程，外派查询授权本身不授予修改或发布权限。

### 服务可达与首个验证场景

远端 MCP 需要外部 Agent 实际可用的客户端、认证方式、网络连接和在线服务。服务运行在哪里、怎样连接现有资产、怎样在断线或权限到期时恢复，仍需确定；远端可访问也不意味着资产匿名公开。本轮讨论没有开放网络端口、复制真实资产或部署远端服务。

可选一个依赖明确业务口径的外派工作，验证外部 Agent 能否找到正确资产、读取准确版本、用于实际执行并在交付中回引，原任务能否验收其成果。还需核对跨企业越权、过期授权、资料撤回、版本不符和服务不可用时的行为。MCP 握手成功或返回目录只是接入的一部分，完成任务及核对成果才体现协作价值。

## 7 当前能力与需要补齐的环节

本节以 `main` 提交 [`4132a39d336c22d46c5bc57ae9d9b544a7ebac5f`](https://github.com/gadfly-hbo/OptraCall/commit/4132a39d336c22d46c5bc57ae9d9b544a7ebac5f) 为记录基线。

当前四服务连接器已建立独立账号连接、任务范围与工具调用的基础。GitHub 已纳入发 Issue、评论和读取进展等工具；实际使用以账号核验、任务授权和供应商开放目录为准。[连接说明](service-connections.md)与[四服务交付记录](https://github.com/gadfly-hbo/OptraCall/issues/145#issuecomment-7209597359)区分了工程接入和真实账号采用。

当前服务工具供符合资格的普通项目任务使用。受管、受限或封闭会话保留原有权限边界，外部协作的兼容方式需要另行设计。Gmail 部分发送及更新工具需要 Google partner access，飞书需要实际企业、用户身份和工具许可；真实账号与第三方 Agent 协作尚未完成验证。

现有[Studio 资产使用能力](studio-phase2-usage.md)已提供企业合格目录、原资产准确读取及来源、发布和版本核对，[语义上下文读取](../src/host/semantic-context-service.ts)与[派生图查询](../extensions/business-plugins/semantic-context/graph.ts)也已有本地接缝，实际可用范围仍依项目配置、权限及采用状态核定。这些能力可作为远端查询的复用基础，但需要增加远端身份、明确的外派工作授权及 MCP 服务边界，当前没有完成面向外部 Agent 的资产远端 MCP 部署与验收。现有四服务连接器由 OptraCall 调用外部服务；此处提出的是由 OptraCall 对外提供资产访问服务。

完整的产品协作还需补齐：

- **外派工作关联。** 持久关联原任务、具体工作、外部工单、执行者、输入版本与交付版本。
- **领取与异常处理。** 明确有效领取、释放、转派、超时、取消及结果未知的处理，防止重复执行。原任务停止后，已在外部开始的工作也需要明确的取消和结果核对方式。
- **结果到达与任务续接。** 在允许的运行条件下发现进展和交付，通知并续接正确的原任务。采用何种监听、查询或唤醒方式仍待验证。
- **成果接收与验收。** 保存实际产物和证据，核对交付来源、工作版本及验收标准，再更新原任务的业务记录。
- **资产远端 MCP。** 复用现有资产读取和授权能力，增加面向外部执行者的受控查询、身份与任务核验、版本和引用回传，以及远端可达与失效处理。

新增能力优先沿现有 Pi、会话、连接器和成果保存机制扩展。OptraCall 内部 Agent 的运行机制与外部 Agent 自身的运行环境各司其职；具体适配以实际接入缺口为依据。

## 8 首期验证与使用方式建议

前轮评估建议先通过 GitHub 跑通一个具体工作与一位实际可接单的外部 Agent，再将同样的交接含义扩展到飞书和邮箱。**首期渠道、外部 Agent 和试用工作尚未选定。**

验证应能回答：外部工作是否准确归属原任务，领取和交付是否可信，能否取得并正确使用获准资产及准确版本，成果是否满足验收，原任务能否据此继续推进，以及是否减少了用户的实际操作。发单数量、Issue 关闭或收到回复不能单独代表闭环完成。

正常使用应让用户围绕业务目标与 OptraCall 沟通。已授权范围内的选工具、组织工作、查进度和整理回执尽量由 Agent 完成；连接初始化、必要授权及重要业务取舍由用户处理。追溯和高级管理按需展开，避免把复制工单、搬运附件和逐条报进度变成用户的日常负担。

## 9 后续优先讨论的问题

1. **大脑的自主权。** 用户只提出目标后，OptraCall 可以自主拆分、选择执行者、发出工单和接受成果到哪一步？哪些情形必须由人介入？
2. **外派的粒度。** 以整项任务、任务中的具体工作，还是两者并存？一个任务怎样组合内部工作和多个外部工作？
3. **执行者的选择。** 怎样知道某个 Agent 擅长什么、拥有哪些实际工具和可用权限？用户指定、Agent 推荐和自动选择怎样配合？
4. **资产访问范围。** 外派时开放哪些语义和分析资产，谁决定范围和有效期？只读依据、Skill 或脚本分发、远端执行工具怎样分别管理？
5. **远端 MCP 的运行方式。** 服务运行在哪里，怎样安全连接原资产并验证外部身份？服务不可用、资产变更、资格撤回及授权到期时怎样处理？
6. **领取与运行。** 外部 Agent 怎样收到任务并开始执行？OptraCall 未在当前会话运行、重启或断线时，怎样取得结果并准确续接？
7. **验收与返工。** 怎样核对所用资产、输入版本、专业质量、真实业务执行和经营效果？谁有权接受、要求补充、重新委派或结束工作？
8. **跨渠道与异常。** 哪份记录是外派进展和验收的依据？怎样处理多方领取、重复回执、超时、取消和已经发生的外部副作用？
9. **首个实际场景。** 选择什么工作、什么外部 Agent 和什么渠道，最能验证任务交接、资产取用、成果验收及用户操作负担？

后续讨论在此基础上逐项收敛，保留决定及其适用版本。明确具体范围后，再按[工程规范](engineering-workflow.md)准备实施规格、执行清单和适用的 UI Demo。

## 10 讨论来源与版本关系

- 2026 年 11 月 27 日，用户提出在项目六类任务执行过程中通过 GitHub Issue 委派更适合的外部 Agent，也可通过飞书、腾讯邮箱和 Gmail 协作；OptraCall 管理战略、目标和项目闭环，适合内部完成的工作尽量在产品内完成。
- 同轮评估提出任务用途与执行方式分开、保留原任务验收、多渠道关联同一外派工作、补齐领取与回传机制，以及先验证一条 GitHub 闭环的建议。建议项的具体方案和次序仍待讨论。
- 用户随后明确“OptraCall 将变成一个 Agent 大脑，指挥外部第三方 Agent 干活，而闭环始终在 OptraCall”，要求创建本讨论稿并继续讨论。
- 用户进一步指出外部 Agent 缺少 OptraCall 的语义及分析资产，仅在 Issue 中说明工作不足以支持高质量执行，提出通过 OptraCall 远端 MCP 让外部 Agent 调用这些资产。本稿将其纳入方向共识；按任务授权、优先只读、版本及部署方式等为本轮补充的设计建议，继续讨论。
- [工作台 v5 规格](../openspec/changes/decision-case-workspace-v5/spec.md)提供项目地图与六类任务的现有含义；[产品讨论稿 v0.4](OptraCall_产品讨论稿_v0.4.md)和[工程规范](engineering-workflow.md)提供现有产品定位与职责边界。本专题不覆盖它们已确认的规则，也不把尚待讨论的协作机制写成当前产品事实。
