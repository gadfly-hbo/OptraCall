### 四点产品原则

本项目统一遵循：**Host 管环境、Agent 自主执行、优先复用 Pi 已有能力、减少人的操作**。以下职责及复用规则是详细来源；每次 spec／UI 设计、开发和验收均须实际检查，不能只在方案中重复原则口号。

### 产品 Agent 与工程 Agent

本项目遵循“Host 管环境，Agent 自主执行”的架构原则。Host 负责提供任务目标、业务上下文、资源与工具访问、权限边界、预算与取消控制，以及交互、状态展示、日志、成果持久化和决策学习环境；产品运行时的 Pi Agent 在授权范围内自主理解任务、选择方法与工具、安排分析步骤、检查结果并修正错误。Host 不通过硬编码分析流程、固定步骤、方法配额或无必要的确认门槛干涉 Agent 的内部运行，不替 Agent 作业务判断、补跑计算或编排其推理过程。这里的自主性不改变 Codex、Qoder 的 SDD/TDD 与独立复核责任。

Host 对越权、资源超限和破坏性操作实施必要约束，保护原始材料与历史成果；这些环境治理职责与 Agent 自主执行并存。校验失败应尽可能将具体问题反馈给 Agent 在授权范围内自主修正，不在 Host 中另造分析流程；业务适配器按已确认契约进行结构／格式校验、保存和回执，仍遵循下述 IN01–IN07。

整个 OptraCall 产品统一采用 **pi-coding-agent SDK** 承担 Agent Runtime，由 Codex 维护产品级 SDK 接入与运行管理入口。Extension 通过统一入口使用 Agent 能力，提供工具、skill、上下文及专业能力，不自建 Pi SDK 接入层、会话运行管理或平行 Runtime。

会话循环、工具调用、上下文管理、压缩、恢复与重试等能力优先复用既有 SDK／Runtime。仅在存在已验证的能力缺口时增加最小适配，并在变更规格中记录实际版本、验证证据、缺口及最小适配理由，不重复建设平行机制；恢复与重试仍须遵守原有取消、UNKNOWN 和副作用保全边界，不盲目重放请求。

统一底座允许按任务隔离会话与上下文。所需会话的创建、续接、停止及事件处理均经过统一入口；具体接口与并发方式随实际任务确定。宿主不直接组合 pi-agent-core + pi-ai 自建运行底座；SDK 内部的传递依赖不受此限制。实施时核对并锁定兼容版本，不能将“已声明同一依赖”当成实际共用 Runtime 的证明。

人的操作围绕表达目标、指定资料或偏好、纠正／排除，以及确需由人作出的授权和不可替代的业务取舍。正常使用优先让 Agent 在已有授权内完成查找、读取、方法选择和纠错；用户无需为享受能力先维护日记、搬运资料、逐条审批普通读取、填写机器身份或确认引用。可选管理与人工指定资料作为补充，默认沿已有当前工作和合理值，技术细节按需展开。减少点击不能以 Host 代作专业判断、暗中放宽权限、擅自丢弃用户明确选材或越过必要确认实现。

所有新增设计均须检查四点原则：是否属于环境与治理职责、是否侵入 Agent 自主执行、是否重复 Pi／既有 Runtime 能力、是否把可由 Agent／SDK 完成的工作推给用户。Pi 已支持的工具组合／嵌套、分支、上下文与重试方式优先沿用；权限或持久副作用确需收窄时记录实际缺口／风险依据，不能只为日志更整齐或新证明协议限制 Agent 的正常方法。职责越界、重复建设或非必要人工作业应先删减、合并或调整；确需例外时按第4节记录并批准，不将必要授权和保护误省。

### 官方 Pi SDK 来源与版本约束

1. **官方包保持原实现。** OptraCall 全产品统一采用官方发布的 pi-coding-agent SDK，经现有统一入口使用。不得直接改写官方包的源码或安装目录中的构建产物，不通过补丁、私有 fork、包别名／本地替代、模块加载替换等方式改变官方实现；也不得绕过官方公开契约改写 SDK 内部对象、方法或原型。使用官方公开配置、事件钩子、工具注册和扩展机制，或在 OptraCall 自有对象上包装调用，属于产品适配；不能仅因代码位于 Host／Extension 就认定原位改写 SDK 对象合规。用户指定版本后的标准包管理安装属于官方版本采用，不是手工改包。只读使用内部接口按下述例外管理，不等于获准修改它。
2. **版本由用户指定。** 保持当前已确认并锁定的官方版本。只有用户明确指定升级目标后，才能在相应授权范围更新到该官方发布的精确版本；记录用户指令与目标，不把 `latest`、浮动范围、安全提醒或自动依赖机器人当成版本决定。未经指定，不自动升级、替换或降级；可以主动提示官方新版本、变化和潜在影响。SDK 及其官方 Pi 依赖的替代／覆盖同样受此约束，不能借 `overrides`、别名或安装脚本绕过。第三方依赖覆盖若影响 SDK，另记录实际解析版本、理由和兼容证据。
3. **适配归 OptraCall。** 先核对目标版本的官方发布说明、变更及公开接口，优先在 Host、Extension 和必要薄适配层解决差异，逐项遵循四点产品原则，不重造 Runtime 或分析循环。确实无法通过官方公开接口、配置或扩展机制解决时，说明缺口、影响和可选产品安排，交用户决定；不能自行修改 SDK。内部接口确有必要时，按 IN06 记录路径／符号、公开能力缺口与证据、owner、精确版本约束、升级失效风险、替代／移除条件及独立复核结论；版本改变后重新核对适用性，不能自动继承旧例外。
4. **来源与实际采用分别证明。** 同时核对依赖声明、锁文件的官方 registry 来源／完整性、实际解析目录／版本及有关官方 Pi 依赖；必要时将安装包与该版本官方发布归档逐文件比对。包名、锁文件或统一入口检查通过，均不能单独证明安装包未改、运行时无不受支持的改写或正在运行的服务已采用新版本。版本提醒／模型目录刷新也不构成 SDK 升级授权。

### Semantica 官方组件来源与版本约束

Semantica 是业务语义支撑引擎，Pi SDK 是统一 Agent Runtime；两者职责不同，官方组件治理要求一致。本节为 Semantica 的长期规则来源，升级执行第3节的[验证与回退流程](#semantica-升级验证与回退)。

1. **使用官方原包。** 采用未经修改的 Semantica 官方发布包；不改源码或 `site-packages` 安装产物，不通过补丁、私有 fork、同名替包、模块替换或绕过公开契约的运行时改写改变其实现。通过官方公开 API、配置和扩展机制操作自有实例及业务图数据属于正常使用，不把合法图数据更新误当成改包；业务本体、图数据、来源映射和适配代码维护在 OptraCall 自身资产与代码中。
2. **版本由用户指定。** 保持已批准并锁定的版本。只有用户明确指定精确升级目标后，才按授权更新官方依赖与对应平台锁文件；不因 `latest`、安全提醒、依赖机器人、重装或依赖重解算自动升级、替换或降级 Semantica。可主动说明官方版本变化和影响，不能代替用户决定。关联 Python／传递依赖的变化须记录理由、实际锁定版本和兼容证据，不能借其绕过组件版本决定。
3. **适配在 OptraCall 完成。** 先核官方发布说明与变更，优先使用公开接口，在 Host、Extension 或必要薄适配层处理差异，遵守四点产品原则。Semantica 不成为第二套 Agent Runtime，也不接管 SAP／方法、企业资料、M2 或 Case 的来源与发布权威。确有必要只读依赖内部接口时，按 IN06 记录公开能力缺口、owner、路径／符号、精确版本、升级风险与替代条件，逐版重核；无法解决时说明影响交用户决策，不自行修改官方实现。
4. **核对来源及实际安装。** 检查官方发行来源、精确版本、平台锁文件与 wheel 完整性、实际私有解释器／导入目录／分发版本及依赖闭包，必要时逐文件对照官方归档。相同版本号或安装命令成功不能单独证明原包完整，也不能证明运行服务已采用；工程核验不放入每次产品启动或日常查询中增加用户操作。

### 统一会话接入规范（当前Interface v3，兼容v1/v2业务子集）

以下IN01–IN07适用于Codex、Qoder及其他开发者。准确类型及Interface版本以`src/host/agent-sessions.ts`为准；最小使用方式、业务差异和验证示例见[接入说明](agent-session-integration.md)。本节是强制规则唯一来源，AGENTS及工具专属项目入口仅放同源指针。

当前v3落实用户已确认的[生命周期补充A边界](../openspec/changes/automatic-verification-revision/lifecycle-supplement-proposal.md)：仅显式开启自动核算的受信新任务，从首次普通执行前托管工具资源；允许任务内后台与并行计算，正常交接先等待计算自然结束，显式停止才强制收回。Host只管理材料、权限、资源归属及实际收尾，不决定Agent公式、工具选择、专业意见或是否改稿。未开启的普通任务保持原策略；旧任务及重启后缺可信起点的资源不因JSONL标记、关闭driver或读取历史而升级为受管。v3候选的检查与非作者复核结论另记，接口存在不等于专业验证或运行采用完成。

| 标识 | 必须遵守的接入规则 |
| --- | --- |
| IN01 开发前必读 | 新增/修改Agent交互、SDK接入、会话启停/恢复、模型配置或插件接入前，读取本节及接入说明；本变更规格记录规则/Interface版本、owner/profile、修改范围、业务差异和验收。旧任务授权不替代当前范围。 |
| IN02 Host注册与注入 | Host静态注册域/profile并注入能力受限的port及绑定owner的Ref；业务前端保留自身入口。域构造、跨owner管理留在Host，插件只取得自己的会话资格，不接收可自行注册域或清理全局会话的管理对象。 |
| IN03 共用生命周期 | 启动、占用、取消、关闭及订阅经公共入口；业务层不直接创建SDK会话、new ProjectAgent或另写opening/operation/代际Map、配置监听及全局清理。公共实现创建多个隔离实例属于正常复用，业务Store和业务集合仍各自维护；同一资源只有一处权威生命周期状态。 |
| IN04 保留业务差异 | profile仅声明真实差异：准入、模型选择、工作区/工具和续接参数。业务上下文、RAP/SAP/Case校验、保存/回执、事件投影及有限修正留在业务适配器。多turn明确结束与取消条件；公共层按技术能力工作，不按业务名加入流程分支。 |
| IN05 Host资源权限 | 凭据解析、原生资源创建和跨owner清理由核准Host路径负责。插件只使用非敏感引用及获准能力，不通过消息中的任意workspace/sessionFile、密钥或Provider绕过配置；事件与日志继续脱敏，会话port不扩大数据或经营动作授权。 |
| IN06 契约共同维护 | 新能力先补契约、消费者适配与验收。Codex 负责 Host／Agent 集成与主链路，Extension 实施者交付接入说明及证据。涉及另一方职责的契约变更由双方协商并记录。不兼容变化或范围扩大先补适用决定。底层导入例外的新增或变更须说明理由并独立复核。 |
| IN07 交付验证 | 交付覆盖正常路径、取消、配置变化、迟到结果、保存/恢复与兼容范围；公共改动复测现有消费者及第三合成接入。导入约束加入`npm run check`及CI，合规样例通过、受控绕过样例失败、恢复合规后通过；不能靠跳过检查、删除断言或扩大白名单制造通过。 |

### 会话策略与兼容边界

Interface v3 兼容已确认的 v1／v2 业务子集；各消费者沿用其已核定子集。v2 的 Host-only `execution/owns` 和 lease 的 `quiesce/reopen/onCancel` 由公共入口管理，资格绑定真实 owner 与当前 operation；业务 port 不取得资格创建或 owner 证明能力，不从 JSON、任意 workspace 或旧 lease 恢复资格。公共层在同一占用内确认旧资源终止后受控重开。具体历史增量及其原验证范围见[历史索引](engineering-workflow-history.md#会话接缝历史候选与兼容记录)。

原任务与核算仍各持原owner权威，自动链只关联实际请求。可信SDK驱动唯一写原native；所有Agent可控的文件/代码/codemode/间接工具均须跨受限执行边界，不得在驱动内留下动态执行后门。工具执行器不是另一位分析Agent，不能改变专业意见、选择方法或补计算；普通分析及旧封闭文本资源保留其原工具合同。具体保护可行性、局限及实际完成范围记录在当前变更，不将合成探针扩大成完整产品验收。

父取消先撤后续派发，再等匹配子操作和本资源安全停止；阶段间也不能提前idle。子停止/资源关闭失败时隔离原owner、保留UNKNOWN，显式close可重试失败清理，不能自动重放请求。按Provider/project/owner关闭只等待匹配资源与子停止，不受无关operation影响。IN07验证须覆盖这一增量及所有旧消费者，详见同源接入说明；历史v1实施记录仍保留原事实。

两类策略继续保留：项目任务使用绑定配置和已保存sessionFile；需求梳理在operation开始捕获当前配置，生成与最多一次修正期间固定，重建沿用原新建native策略。各owner的原生会话、上下文、配置快照与占用独立；Host只持域管理引用，协调明确的Provider/真实项目/退出范围，不另建资源台账或全局Agent运行队列。需求的目标项目不是需求会话归属。SDK原生历史读取及固定连接探针只由检查中列明的路径承担，不能借例外接管业务会话。

迁移采用原位换接线；原统一会话迁移不新增会话库、业务ID、持久代际或需求续接指针；后续变更按其已确认规格核对。旧资料保全与正常追加分开验：迁移不改写既有内容，显式续聊及原有证据校正仍可产生合法更新；回退兼容代码读取最新资料，不恢复旧副本覆盖新增工作。未知结果保留UNKNOWN/中断，不自动重放或换模型。共享代码与同进程资源仍有共同故障风险，逻辑隔离不等于进程/安全隔离。

执行工具入口／规范采用核验时，分别记录当时Codex/Qoder版本、实际项目入口及读取证据；文件存在或加载器支持某文件名不等于任务已读取。未实际验证的工具项记NOT_RUN，不能宣称固化全部通过；不得为凑通过改全局配置、调用未获准模型或启动MacBook开发。静态导入检查只覆盖已知绕过形式，仍需实际调用链、行为回归及非作者复核。

独立核算沿用Interface v1，由Host的核算适配器静态注册profile；owner包含真实projectId/taskId/verificationId，原任务资源和结果权威保持原位。按已确认SV05先固定独立结果再提供作者产物；核算、显式作者修订、一次复查和用户采用分开，不从completed推断专业正确或经营效果。固定输入、快照、原生指针归属与普通文件完整性由Host核对，不承担统计计算裁判。`SessionTurn.providedContext`是向后兼容的可选交付回执，新JSONL自定义记录可保存实际来源，旧记录不回填；SAP记录资源实际初始化索引，不使用当前启用列表伪造历史采用。详细技术与可观察限制见[核算接入说明](verification-agent-integration.md)。Codex/Qoder及其他开发者修改此接缝均先读本节与该说明；不建立平行Runtime、全局运行队列或固定方法注册中心。

已确认的修订出稿使用Host静态`verification-author-draft`附属profile和`fixed-draft`能力策略，由同一Interface v1管理。固定全文由Host读入，创建时不注册可执行工具，不自动加载技能、上下文文件、MCP或扩展；只允许产品可信脱敏扩展，不向业务Ref暴露SDK管理对象或原生命令。不得仅隐藏工具名、临时修改原分析会话后依赖finally恢复，或在材料过大时回落全工具。新native归本记录的revision-native，原项目会话指针/父链/历史保持原位，原普通分析及独立核算的既有工具策略不变。接入必须覆盖实际工具拒绝、动态/间接调用、取消/关闭/重开和原件字节保全；空工具不代表内容正确或OS沙箱。

## 3. 连续 SDD 与 TDD

每项非平凡变更在 `openspec/changes/<change-id>/` 维护简洁规格及结果记录，首次实际变更时再创建目录。必要设计与证据用链接关联。简单、范围闭合的纠错可沿用原记录，写清复现、修正、验证及适用性；复杂改动须维护简洁规格，不能以“修复”绕过重要合同、权限、持久化或 UI 设计决定。

规格至少写明完整可观察结果、需求／验收标识、范围与不做事项、允许修改路径、关键边界、适用检查和未决问题。开发顺序为：目标及验收 → 确认并固定设计输入 → 适用 TDD 与最小可运行切片 → 持续修正和受影响检查 → 第 4 节完整候选独立复核 → 适用的 PR 前用户确认 → 第 5、6 节 Git／CI 交付。

### 设计确认与四原则前置检查

新增或实质调整用户界面／关键交互时，先提交 spec、任务清单和可点击 UI Demo，说明关键路径、状态、现状差异与演示边界，取得用户对具体版本的明确确认后再实施受影响产品代码。Demo 可使用虚构资料及内存状态。简单文字／按钮调整可以免另做 Demo；纯后端或无界面影响的任务说明不适用依据。是否需要按实际影响判断。

提交确认前，沿正常、失败与恢复路径检查：Host／Agent 职责；实际 Pi 版本及已有原语；新增适配的能力缺口及证据；用户必须执行的动作及其必要性；合理默认、已有当前工作、合并操作和按需展开能否减少负担。记录 spec 条款、UI 动作／原型或不适用依据及反例。产品运行时验证另记。

已确认且未变化的设计沿用原决定。确需实质调整时，仅补受影响决定并同步规格、Demo 和任务要求，保留原版本及差异；不能事后改 Demo 迁就偏离的实现。此处的前置设计确认与第 4 节 PR 前真实产品截图确认分别执行。

### TDD 与真实路径验证

- 确定性行为：实现前有能检出目标行为错误的测试；修复前保留失败测试或因果复现，再做最小 GREEN 修复及必要重构，留下永久回归。保留关键正向、反向、边界、失败和禁止副作用断言。
- 探索与模型质量：先明确任务、预期及观察条件，保留真实试验与失败，不伪造确定性 RED。单次成功只证明该场景及其输入、模型、工具、配置。
- 纯重构：保留修改前后 GREEN 及相关等价证据。
- 文档及规范：做相称的一致性、引用、范围复核；CI 选择按第 5 节执行。

测试从需求与验收导出，不照着实现重述；fixture、环境、导入和定位器失败不算产品 RED，后补测试不伪造历史失败。测试修改或删除应解释覆盖如何保留，不能通过削弱断言把失败改成成功。

从首个可运行切片起，走用户正常入口、实际配置、代表输入及真实工具，覆盖适用的保存／重开、失败、取消与恢复。模型、数据和外部副作用按有效授权执行，缺授权时明确未验证范围；Mock、结构或导入通过不证明真实分析成功。

真实模型评估不能仅凭模型名称相同认定配置等价。冻结并用实际SDK核对Provider/协议/线路、reasoning、thinking level、contextWindow、maxTokens、compat及相关输入限制；中继或自定义Provider可能触发通用模型默认值，必须先核对实际注册模型和请求参数。隔离测试的内存凭据替身仅替换获准配置的密钥，保留原配置校验、版本与公共生命周期；只用于评估，不作为Extension或生产接线范式。实际原配置、诊断替身、合成Provider和供应商结算费用分别报告，不能混用成绩或将SDK费用估计0写成免费。

同一责任方持续诊断、修复及回归，复用有效规格与授权，不因每次编辑重建文档套件、全量回归或审批。新增产品行为、重要契约／持久化、数据权限或外部影响先补适用决定。

### 领取方的冻结 UI Demo 阅读与开发要求

以下适用于绑定了已确认 UI Demo 的受影响实现，包括首次领取、返工和 PM 接手修正；纯无 UI 影响的工作按第4节记录不适用理由，不要求启动产品或浏览器。本节不增加简单改动另做 Demo 的要求。

1. **固定并实际查看设计输入，先于受影响 UI 编码。** 读取 Issue 绑定的冻结 Demo、spec、任务清单及用户后续明确决定，记录版本与文件摘要。执行开发的 Agent 必须用真实浏览器渲染 Demo，亲自查看画面和截图，并操作受影响页面、导航、页签、弹窗、默认选择及关键状态。只下载文件、校验 hash、运行原型脚本、读文字说明、生成但未查看截图，均不能声明“已读 Demo”。单文件过大时可分段读取或提取相关结构，不得以体积或上下文限制跳过视觉阅读。
2. **记录视觉与交互骨架，建立实现映射。** 结合渲染画面读取相关 DOM 和 CSS，提取页面／弹窗形态、主次区域与组件层级、导航／滚动边界、控件及默认范围、关键交互，以及间距、字号、颜色等设计令牌和响应式约束。按受影响页面记录「冻结页面/状态 → 视觉与交互要求 → 现有差异 → 拟修改的生产组件/样式与真实数据接线」。不要求复制相同 DOM/CSS 或逐字搬入原型源码，但须落实已确认的布局、信息层级及行为；设计差异不能以已有组件复用为由省略。
3. **正确理解旧代码与模拟设施边界。** spec 列出允许修改的既有文件，表示改动范围，不表示旧页面框架、弹窗结构或样式必须保留。禁止搬入 Demo 的虚构人物、固定推荐、模拟回复、独立数据或 sessionStorage 等生产规则，不免除实现其已冻结的视觉和交互。以真实 Host/API、原业务权威及已有 Runtime 接线；若 Demo 已确认整页重排，就按其骨架调整视图，不能只往旧页面叠字段、改标题、加按钮。确需实质偏离已确认设计时，沿本节前述设计变更流程取得用户决定，不自行取舍。
4. **分切片与返工对照实际产品。** 完成受影响页面或交互后，在相同视口和可比较状态下，截图冻结 Demo 与实际产品并实际查看、并排核对，逐项检查布局、层级、导航、默认状态、数据范围和交互。覆盖确认规格或冻结 Demo 要求的视口（如 Issue #149 的1440／1024／390）；未指定时，按受影响页面适用的桌面／窄屏范围选取并记录依据，同时记录页面、状态、版本、入口、视口和截图时间。真实数据、权限和空状态造成的内容差异如实解释，不伪造 Demo 对话或业务事实；截图不能单独证明交互与归属正确，仍须实际操作和相称行为验证。
5. **文字断言不能代替视觉验收。** `innerText`、控件存在、接口成功、功能测试、原型检查和 CI 各自只证明所测范围。页面出现相同文字，不代表整页／弹窗形态、左右分区、组件层级、样式或操作路径一致；这些检查不得作为冻结 UI 一致性的唯一证据。返工须回到原冻结基准核对，不能只照退回报告的文字补丁判断完成。
6. **阅读与验证缺失须如实阻断。** 浏览器、Demo 或截图查看不可用时，记录具体阻塞和未覆盖项，可继续不依赖该设计的安全工作；不得依靠文字臆测实施受影响 UI 并报为“已读／一致／通过”。交回时提供开工阅读记录、截图、DOM/CSS骨架与实现映射、Demo／实际产品对照、已处理和未解决差异。PM须核对这些证据，缺失时不得通过相应 UI 验收；图像文件存在也不等于作者或复核者已经查看。

### 任务目标执行清单与范围管理

准备 spec 及适用 Demo 时，一并准备目标执行清单，随同提交用户确认。清单写明任务目标、预期交付、阶段任务、完成条件及验收标识，可放在 spec 或现有任务记录中；允许简化规格的任务沿用原确认安排。

**冻结验收要求，持续记录进度。** 固定的是用户确认的目标、范围、任务要求及完成标准，保留其确认版本／提交／摘要。执行中可在同一文件更新完成状态、实际结果和证据链接，无需另建清单；条目沿原标识追溯到确认版本。纯进度更新不构成范围变更或自动触发重新确认。目标、行为、范围或完成标准实质变化时，先取得相应决定，保留新旧对应关系并更新受影响设计。

每项达到完成条件后标记完成并关联证据；受阻项保持未完成，记录原因，继续不依赖阻塞的工作。新增发现按下列规则处理：

1. 对照原目标及验收判断影响，排查中发现的其他问题也按同一依据判断。
2. 在现有授权内最小修复本次引入的回归及直接阻塞，验证后回到清单；扩大权限、改变公共契约或新增独立功能时，先交具体阻塞及选项供用户决定。
3. 范围外问题在现有记录留下线索、复现及影响，继续原任务；同文件或改动小不足以纳入。发现数据损坏或越权风险时暂停受影响操作、保留现场并继续安全部分。
4. 收尾按冻结要求逐项检查；额外修改须对应回归、直接阻塞或获准范围变更，不能只抽查作者已标完成项。

### Pi SDK 升级流程

用户指定目标后，由 Codex 维护统一 SDK 接入，Qoder 配合其 Extension 适配；已明确的版本与授权沿用，不重复索取相同确认。升级按以下顺序实施：

1. **固定目标和基线。** 记录用户指定的精确官方版本、升级前依赖／锁文件／实际解析版本、官方发布说明与变更来源；核对运行环境、内部接口清单、依赖覆盖、各 owner/profile 及现有 Extension。界面无实质变化时注明 UI Demo 不适用，避免无关人工步骤。
2. **隔离候选并适配。** 保全项目、原生历史／fork 指针、配置、文件和已有 FAIL／UNKNOWN；在隔离工程环境先更新官方依赖及锁文件，不共用或改写正在服务的依赖安装目录，不改官方包实现。对 OptraCall 适配先保留兼容性失败，再按适用 SDD/TDD 修正；公开接口优先，内部接口及第三方覆盖逐项重核，不能删除保护或跳过断言换取通过。升级候选安装与正式运行采用分开，不自动更新其他设备或正在运行的服务。
3. **验证受影响能力。** SDK 为共享底座，执行完整适用检查、真实 SDK 的隔离集成路径及非作者独立复核；按下表在规格中固定关键项、通过标准和证据，逐项记录 PASS／FAIL／NOT_RUN／UNKNOWN，不把测试文件存在或旧版本 PASS 当成新版本证据。

| 能力 | 升级回归至少核对 |
| --- | --- |
| 来源与依赖 | 用户目标、官方发布／锁文件完整性、实际解析及 SDK 导出版本一致；无包改写；官方 Pi 传递依赖、Node 要求和第三方 overrides 兼容 |
| 会话与历史 | 新建、恢复、重启、空会话首次追加、原生版本／header／fork／branch、保存重开；原项目及会话文件／指针保全、owner／配置隔离 |
| 工具与取消 | 原生及自定义工具、嵌套调用、codemode、错误回执、停止／关闭／drain、迟到事件和已有权限／原件保护；不代 Agent 选分析步骤 |
| MCP | 官方配置加载、连接、工具发现／调用、错误与取消；普通可用范围及受管／封闭 profile 原有拒绝边界分开核对 |
| 模型接入 | 已配置 Provider／协议／线路、模型注册与流式事件、工具协议、thinking／reasoning／上下文和输入限制；配置保存、切换及恢复 |
| 上下文管理 | 系统／业务上下文、资源加载、压缩、分支恢复、嵌套执行上下文及当前运行资格；不串任务或退回未经核定的旧上下文 |

| 现有 Extension | 按实际影响覆盖已接入的 skill、连接器和业务插件及第三合成消费者，保留当前 Interface／owner／profile 合同和历史成果 |

工程验证默认使用隔离合成 Provider／MCP、合成资料及获准的兼容历史副本；真实模型、业务材料与凭据访问继续核对相应授权，不因升级自动启动。关键能力若缺授权而未验证，也必须保留未验证状态，不能以模拟成功代替。既有已接受的能力限制单列保留，不自动标成新版本已支持。

4. **交付及采用。** 交付说明列升级前后版本、来源及实际版本证据、OptraCall 适配／内部接口与依赖覆盖变化、测试与独立复核、数据／历史兼容、未解决风险和回退方式。关键验证未通过或仍待验证时，升级不能标记完成，也不能直接投入使用。Git／CI、安装／服务采用、其他设备更新与用户产品验收按既有范围分别执行和记录。回退需使用用户指定或已明确批准的目标及触发条件，不自行降级；保留升级后新增数据，不用旧快照覆盖新成果，无法兼容时维持隔离并提交用户决策。已有明确回退授权不重复确认。

### Semantica 升级验证与回退

Semantica 升级沿用上节[Pi SDK 升级流程](#pi-sdk-升级流程)的用户目标、固定基线、隔离候选、自有适配、SDD/TDD、独立复核及交付门槛；按其实际能力执行下表，不照搬 Pi 专属会话实现。本节补充语义引擎、既有资产及环境回退的验证要求。

| 范围 | 升级至少验证 |

## 4. 独立复核与工程完成

日常自检、接口互查和作者测试不能替代最终独立复核。复核者须独立于完整候选的全部作者，包括参与实现的 PM；使用独立、聚焦且不继承作者会话历史的上下文。两位作者互查不构成完整候选独立复核。

收尾固定完整候选、规格、输入与证据，包含 staged、unstaged 和新增文件；提供候选提交或文件清单及摘要、验收依据、检查权限、现有结果、失败和缺口。复核者先从验收基准导出关键预期，再独立检查实现、真实路径及作者测试。

复核保持源码、测试、规格及固定证据只读，临时文件、缓存和报告写入指定隔离位置。记录范围、命令、结果、发现及结论。作者修复后重验受影响范围，失效的旧复核与 CI 结论不得沿用。

### 冻结基准逐项复核与 PR 前截图确认

以下为 2026-11-28 用户明确要求的交付门禁，适用于 PM、领取方及独立复核者。它约束工程交付，不在产品正常使用流程中新增审批步骤。

1. **固定三个验收基准。** 固定用户已确认的 Demo、spec、任务清单及后续决定的提交／版本／文件摘要，并固定完整候选。未提交候选须补 staged、unstaged、新增文件清单与摘要；不能仅报 HEAD。独立复核者先读三个基准，再检查实际产品与实现，不能只照作者摘要、测试断言或总 PASS 复核。按第 3 节允许简化的任务使用原验收记录；Demo 不适用必须写明理由并由独立复核核定。
2. **逐项形成可追溯矩阵。** 对每条 spec、每项任务及 Demo 的页面、布局、导航、状态和关键交互逐项映射，字段至少为「基准版本与条目 → 预期 → 实际代码及真实产品入口／状态 → 截图或实跑证据 → 差异 → 结论」。复核者须独立用浏览器查看冻结 Demo 与实际产品，按[领取方阅读与开发要求](#领取方的冻结-ui-demo-阅读与开发要求)核同视口截图、布局与交互骨架，不能只看作者的文字总结或图片清单。核对信息层级、主次区域、控件与默认选择、关联数据范围、正常／失败／恢复路径及适用视口；截图不能单独证明交互和数据正确。条目可以共享证据，但不得漏项或以测试数量替代覆盖。结论区分通过、不通过、待验证、有依据的不适用。后续 PR CI、合并与结案任务未到执行阶段时如实记待执行；开 PR 的必需前置项未完成则阻断。
3. **截图必须来自实际运行产品。** 在真实产品入口运行候选，记录源码完整 SHA／未提交摘要、构建与实际运行身份、环境、配置范围、合成或获准公开的数据场景、页面／状态、视口和截图时间，保留可访问原图与复现步骤。不得用冻结 Demo、独立静态仿制页面、历史截图或注入样式的临时效果冒充产品。可以在隔离环境使用合成业务数据，但必须走实际产品组件和适用服务路径，明确模拟模型等验证边界；不能借验收操作未获授权的业务数据或设备。截图覆盖全部受影响页面和关键状态，不只选择最好看的一个画面。
4. **开 PR 前由用户确认。** PM 汇总独立复核矩阵、真实产品截图及已知差异，实际向用户展示截图，取得针对该候选的明确确认，并记录展示位置、确认原意、时间与候选身份。仅生成截图、给一个尚未展示的路径、曾确认设计 Demo、作者自测、独立复核 PASS 或 CI 成功均不能替代这一步。待确认、被拒绝或证据缺失时，不得创建 PR（含 draft），也不得通过接管／转为 ready 规避；继续已授权的安全修复。领取方可以在有效 Git 授权内提交、推送、交接；PM 对开 PR 门禁负责。
5. **变更后重核有效性。** 确认后的修复、整合 main、构建／配置／输入变化如影响已确认的界面或交互，标明受影响的旧截图确认和复核结论失效，补受影响截图、独立复核及用户明确确认后再推进 PR／合并。无影响须留下核对依据，不能自动沿用旧 PASS。若已有 PR，门禁缺失或失效时暂停后续交付和合并，不因 PR 已存在而跳过。
6. **无 UI 影响与其他验收分别记录。** 纯文档、纯后端等确无用户可见影响时，记录影响分析和截图不适用理由，由独立复核核定；不能按文件目录、免 Demo 或“只改后端”推断无界面影响。实际产品截图确认仅覆盖所展示候选及范围，不替代功能／集成检查、独立复核、实际 head CI、完整产品体验或设备运行采用。失败、未验证及用户接受的差异保留各自结论，不改写为复核 PASS。

纯进度、结果记录或证据索引更新仍纳入最终差异及内容复核。只有在说明其未改变验收要求、产品代码、构建、配置和输入，并经适用复核核定无运行影响后，才可引用原产品验证及截图确认；记录原受验候选与最终交付候选的对应关系，不将新文件摘要冒充原受验身份。涉及产品行为或证据结论实质变化时，按上款重验，不能将“文档更新”作为一律免验的理由。

### 工程完成条件

1. 已确认范围内的实现／维护完成，规格、任务要求及结果一致；额外改动有明确归属。
2. 适用目标测试、回归、质量检查和真实路径验证完成，失败、跳过、未知及限制均有记录。
3. 本节规定的完整候选独立复核、逐项矩阵、适用 UI 门禁以及职责／复用检查齐备、有效，发现已处理。获准例外单列，不写成检查通过。
4. 第 5、6 节要求的实际候选 CI、获授权合并及工程结案完成，并完成适用 OpenSpec 归档。未到执行阶段的工作如实标记待完成，不提前记通过。
5. 交付说明给出版本、证据、风险、后续点及适用回退方式和数据影响。

独立复核不可用时，继续安全且已授权的工作，明确缺口；不得用作者自评替代或宣称完整工程验收。工程检查、复核、CI、Git、安装／运行采用及用户对明确候选的产品验收分别报告，互不替代。

### Host 与 Agent 职责边界及复用检查

本项与最终独立复核一并完成，范围限于本次变更及受影响接缝。基于实际代码、调用链和必要运行记录检查：

- Host 承担环境、目标与业务上下文交付、权限、资源控制、交互、状态与日志展示、成果持久化和决策学习环境等职责；Agent 在授权范围内自主选择方法、工具、执行顺序及纠错方式。Host 不通过硬编码分析流程、固定步骤、方法配额或无必要的确认门槛干涉 Agent 内部运行，不代作业务判断、补计算或编排推理。
- 会话循环、工具调用、上下文管理、压缩、恢复与重试等能力优先复用既有 SDK／Runtime；新增机制须有已验证的能力缺口、证据及最小适配理由，不能以包装或统一入口掩盖平行机制。
- 必要的权限、安全、预算、取消和原件保护措施属于环境治理，应核对其实际边界，不将其误判为干涉 Agent 自主执行；已确认的业务输入输出契约与普通分析内部步骤分别检查。
- 人的操作沿本次实际 spec／UI 与运行路径核对：正常使用无需额外维护／普通读取审批，新增必做动作有目的和必要性证据；已考虑当前工作快捷路径、合理默认、合并操作与渐进披露。不能只凭“已自动化”文案通过，也不能以省操作为由替人作未授权的业务取舍。

涉及 SDK、依赖或 SDK 适配的变更，专项最终检查还须核对本规范的官方包不可修改、用户版本决定、公开接口优先、内部接口例外及上述升级回归／交付要求。源码补丁、运行时改写、来源／实际版本不一致或关键未验证不得被统一入口 PASS 掩盖；既有风险的“已登记”不等于“已修复”。

验收记录须列明本次检查范围、候选身份、证据位置、发现的问题，以及“通过／不通过／待验证”结论；不能仅凭设计声明或测试全绿判定通过。检查范围以本次变更及受影响接缝为准，不据此宣称未检查的既有实现已合规。

存在职责越界、重复建设、无合理必要性的人工作业或关键证据缺失时，本项保持不通过／待验证。先修正并复核；确需限范围例外时，说明范围、理由、风险和退出条件，按下款取得适用决定，保留原结论及未解决项。

### 例外批准权限

对四原则和职责／复用检查的限范围例外，由用户明确批准。PM 负责提交依据、记录决定、限定适用任务及核对有效性；有效授权内的普通技术选择、诊断和修复由责任 Agent 自主推进，无需逐项请求例外。

此类例外不用于绕过官方 SDK 原包约束、用户指定精确版本、前置设计确认、适用的 PR 前真实产品截图确认或独立复核，也不扩大数据、模型、Git、安装、设备和运行采用权限。确需改变这些既有规则时，由用户另作明确决定并更新适用规范，不能借一般例外条款推定放行。

## 5. Git 与 CI 的精简节奏

### Git

`main` 为集成基线，远端为 `https://github.com/gadfly-hbo/OptraCall.git`。一般功能、修复及维护使用独立任务分支／工作目录，例如 `codex/<slug>` 或工单指定分支；同一分支同一时刻只有一个写入者。

分支操作前核对工作树状态、占用、跟踪关系及进行中的合并／变基；保留 WIP，不重置、清理、强切、改写历史或覆盖他人工作。在有效授权内按需提交、推送任务分支，内部修正无需每次创建 PR、独立复核或打包。完整变更集中交付，创建 PR（含 draft）前须满足第 4 节适用门禁；不要求尚未创建的 PR 先有 CI，也不以门禁为由阻止已获授权的分支提交和交接。

提交前核对实际暂存清单、差异、身份和公开内容，只纳入本任务文件。合并前整合最新 main，检查受影响兼容性和失效证据；获授权后 squash 合并，安全快进本地 main，核对该合并提交的 main push CI。已有 PR 更新触发的检查正常完成，不能通过隐藏更新规避。推送或合并不自动更新运行服务及其他设备，本项目不建立双开发端同步流程。

### CI

[Check 工作流](../.github/workflows/check.yml)检查 PR 的实际 head 和每次 `main` push 的实际提交。整份差异仅编辑 `AGENTS.md`、`README.md`、本规范或 `docs/macbook-trial.md` 时，CI 检查差异格式和 UTF-8 编码，内容一致性、引用、范围及适用独立复核按下表完成。其他变更、无法可靠判断范围或手动触发时，在 Ubuntu／Node 25.9.0 按锁文件安装依赖，运行 `npm run check` 和高危级别依赖审计。CI 无真实凭据、模型或业务数据。本地检查与 CI 结果分别记录，浏览器／macOS 真实模型及产品验收另行记录。交付须核对检查范围、结果和提交身份。

| 修改范围 | 验证选择 |
| --- | --- |
| 纯非运行时文档 | 差异、内容一致性、引用、范围和适用独立复核；不安装无关产品依赖 |
| 已知消费者且影响闭合 | 使用有证据的影响映射运行对应检查，并报告遗漏范围 |
| 运行时、安全/权限、持久化、公共接口、共享依赖、构建/CI 自身或影响不明 | 运行届时定义的完整适用检查及受影响真实路径；平台专有验收另行报告 |

混合变更只有全部对象被可靠覆盖时才能采用定向检查；否则采用完整适用检查。检查选择逻辑不能批准自己降级。每次报告实际选择、结果和未跑项，局部 PASS 不表述为全量通过。保留失败日志，先解释原因再重试；无解释的绿色重跑不关闭原始失败。

## 6. Extension 接入与版本交付

Extension 实施者交付任务与输入输出、版本依赖、权限和数据出口、测试、限制、接入与停用说明。Codex 核对统一 Runtime 的真实调用路径、接口兼容及受影响主链路，验证插件没有绕过权限、另建 Runtime 或破坏宿主会话。按实际接入建立必要契约测试，不从一次维护任务推导新建插件协议或调度平台的授权。

MacBook 收到可识别版本后以用户身份体验。记录设备运行采用时，给出源码提交、构建和实际运行版本、模型及关键配置、入口与必要启动方式、体验步骤和已知缺口。MacBook 使用独立浅克隆的 `main` 和本机安装的依赖，代码和持久业务数据分离，试用副本只单向接收上游版本。三个入口分别启动、停止、显式更新并启动。更新前先停机，更新入口核对干净的 `main`、`origin` 和目标提交的成功 CI 后仅快进，遇本地变更时停止并保留现场。准备副本和安装按相应授权执行。

目标 `main` 提交的 push CI 通过后，用户自行切换 Mac mini 和 MacBook 的运行服务并体验产品。Mac mini 使用正式服务的桌面入口，MacBook 使用试用副本根目录的入口。每台设备先用「停止」入口停止服务，再双击「更新并启动 OptraCall.command」。正式产品验收以用户对明确候选的结论为准。

### GitHub Issues 问题收件与结案

新产品／新功能及上线后试用修正以 `gadfly-hbo/OptraCall` 的正式 Issue 发单、领取、交接和结案。发单与验收列工程交付项；设备更新、服务切换、运行采用及完整产品体验由用户另行安排。第 4 节的 PR 前截图确认属于工程交付门禁。

#### 新产品、新功能开发

#### 上线后体验反馈与修正迭代

用户／试用 Agent 可直接交报告给 PM，或用[反馈表单](https://github.com/gadfly-hbo/OptraCall/issues/new?template=trial-feedback.yml)提交整份报告，提供已知的实际运行版本、环境、复现、预期、实际结果及可公开证据；未知如实标记，私有材料按第 7 节保留。

PM 核对实际版本、复现和最新 origin/main，确认范围并查重，按授权发布正式开发 Issue；已有正式工单时补充原单。原反馈与开发单双向关联；整份报告可拆为有验收条件的清单，独立事项分别跟踪。规格／Demo 适用性按第 3 节判断，后续按共享流程交付。同一问题复发时重开原反馈或修正 Issue，补新版本和证据，保留旧结论。

#### 工程维护任务入口

规范／文档维护、纯重构、构建／CI 维护等工程任务复用同一开发任务 Issue 与共享交付流程，在工单说明任务性质和适用检查；已有对应正式工单时继续原单。是否需要新规格、Demo、产品运行或截图，按实际影响及第 3、4 节确定，不新增一套审批流程。CI 选择按第 5 节执行。

用户直接授权的只读调查和仓库外草案可先完成，不为准备建议而强行发单；进入实际仓库修改和交付时按已确认入口办理。

#### GitHub 开发任务外发与交付

旧专项移交模式已停用；其兼容锚点仅定位本共享流程，原文及停用说明见[历史记录](engineering-workflow-history.md#已停用的-extension-专项移交模式)。历史工单仍按其当时确认件解释，不因旧链接定位到本节而改写原授权或写入归属。

发布账号须为仓库所有者或其公开指定的发单维护者。Issue 写明实际 PM Agent／实例及代任安排；共用账号仍记录实际执行者。范围变更、转派及用户对设计／发布的决定，由有资格的账号记录在发单 Issue。仅已获授权、范围明确的正式工单可领取。

1. **PM 发单。** 写明目标、范围、授权、可修改模块／接缝、可开工阶段、基线、规格或等价正文、冻结输入版本、验收和交付物。验收引用第 3、4 节的适用要求。接缝按 IN01–IN07，官方组件按第 2、3 节处理；公开材料使用脱敏示例。
2. **领取。** 读取根 AGENTS、本规范及 Issue 最新正文和评论；确认 Open、可领取、权限和工作树占用，核对最新 origin/main。在 Issue 留言“领取 · 实际 Agent／实例 · 任务分支 · 基线完整 SHA”并回读；最早且未释放的有效领取生效，同时领取按评论 ID 排序。首次实现从核实的 main 基线建立独立分支／工作目录；返工与接手按第 4 步的候选继续。
3. **实施与验证。** 按确认规格、任务要求及适用 Demo 执行第 2–4 节，记录进度、实际结果、失败和限制。涉及冻结 Demo 时，UI 编码前在 Issue 留下实际浏览器阅读回执，链接版本、截图、DOM/CSS 骨架及生产实现映射；开发和返工保留对照。实质设计变化由 PM 组织用户确认，只影响相应部分。
4. **推送及交接。** 只将本任务的完整交付候选和适用记录纳入交接提交，推送并回读远端完整 SHA，按下表回执。原执行者交回后停止写入。任务分支交接不等待尚未取得的截图确认，PR 仍受第 4 节门禁约束。

   | 回执字段 | 内容 |
   | --- | --- |
   | 身份和续接起点 | Issue、实际 Agent／实例、原基线、远端分支及候选完整 SHA，返工／接手从该候选继续 |
   | 写入归属 | 原执行者已停止写入、下一位写入者及原工作树处理方式。沿用同一分支时先安全释放占用；也可经记录由接手方从同一候选另建分支，保留原分支和 WIP |
   | 完成与缺口 | 逐项验收结果、变更范围、已处理／剩余事项、规格／Demo／矩阵及结果链接 |
   | UI 与验证 | 开工阅读、实现映射、同视口对照、真实产品入口及运行身份、适用检查和失败／跳过／未知；用户截图确认已取得／待展示或有依据的不适用 |
   | 证据与风险 | 第 8 节的证据位置及接收方访问结果、兼容／回退方式、限制及原始失败保全位置 |

   返工或接手方先核对该候选与差异，沿用或记录新分支后续修；不机械地按首次开工步骤从最新 main 重做。需要整合 main 时保留续接起点，再整合并重验受影响范围。原写入者及工作树未释放时不强制抢占，先明确归属并继续安全工作。

5. **PM 审核。** 从 origin 核对回执 SHA 及实际差异。首次发现问题，在同一 Issue 记录证据、返工范围、退回候选和负责方，退回一次并释放首次领取，按第 2–4 步续修、重新回执。二审为领取交付的终审；二审或后续集成、验证、独立复核发现问题，PM 接收当前候选，在同一 Issue 明确写入归属并在已授权范围内修复，不再安排第三次领取。PM 参与实现后，最终复核须独立于包括 PM 在内的全部作者。
6. **集成与交付。** 整合最新 main、重验受影响路径，按第 4 节完成独立复核及适用用户确认，再创建／接管关联 PR。核对实际交付 head CI，通过且获授权后 squash 合并；安全快进本地 main，确认合并提交的 main push CI，通过后回填并按下款关闭工程 Issue。关联原反馈的全部适用修复完成后再关闭原反馈。

#### 工程关闭条件

PM 关闭前核对第 4 节工程完成条件和本节实际交付结果。必需验证、复核或适用用户确认失败、缺失、待完成时保持 Open。PR 实际交付 head 和合并提交的 main push CI 均须通过，未发生的步骤保持待执行。

结案评论给出目标和交付摘要、版本／提交、PR、两类 CI、逐项验收矩阵、复核与适用用户确认记录、证据链接及限制。公开材料按第 7 节脱敏，证据访问按第 8 节核对。PR 与提交使用 `Refs #编号` 或普通链接，避免 `Fixes`、`Closes`、`Resolves` 及合并自动关单设置；待 main push CI 和结案回执齐备后关闭。

关闭 Issue 表示本次工程交付完成，不代表设备运行采用或用户产品验收。重复、撤回或不修复等结案按用户实际决定及原因记录。

本仓库公开。凭据、客户数据、私有经营资料、原始会话和运行日志保留在授权本地位置；公开样例使用合成或明确获准公开的材料。审查模型请求、工具结果、日志和报告的实际数据出口，不能从“本地计算”推导“零数据外传”。`.gitignore` 不替代内容审查。

## 8. 证据与进度

源码、长期测试、规格、正式决定及验收结论进入仓库适用位置。原始输出、日志、候选清单和诊断现场留在任务指定、获准访问的持久位置；初检可用忽略目录 `.local/`，临时位置不能成为应保留证据的唯一副本。数据范围按第 7 节。

**在现有任务记录维护证据索引。** 写明证据位置、保管责任 Agent／交接后责任方、关联候选和检查范围，以及接收方如何获准访问。使用已有获准资源，不因本条自动创建新服务、扩大共享或上传私有材料；缺少可用位置时明确阻塞及未完成保全范围。

交接前，接收方按索引实际读取必要证据并记录可访问／缺失／权限不足。只给发送方机器上的路径、文件名或摘要不足以证明可复核。敏感原始材料留在获准私有位置，公开位置仅放脱敏索引和结论，不为追求访问方便扩大数据出口。

任务结束、归档或销毁云端临时环境前，责任方确认应保留证据已有持久副本，核对身份和必要内容，接收方能够访问；证据保全未完成时保留现场并如实记录缺口，不能销毁唯一副本或将移交写成完成。没有清理授权时，本条不授权删除任何工作树或历史材料。正式记录不以临时路径作为唯一长期引用。

记录候选及输入身份、实际命令与退出结果、环境／配置、复核范围和失败／未知。重要结论须能追溯到可访问证据，不只交摘要／hash。进度说明验收推进、结果、缺口和下一步，普通里程碑不新增审批点；用户明确停止时停止相应任务，保留现场与返回点。UI 证据内容按第 4 节统一维护，索引直接引用，不另填一份相同矩阵。

原始 FAIL、UNKNOWN、NOT_RUN、NOT_PROVED、取消及已接受限制保留。严重事故及重复反馈写入持久记录和 Agent 入口，落实同源规则；保留旧错误结论的候选、范围与后续更正，不删除或追溯改写旧 PASS。规则建立、规则复核、实际修复及用户确认分别报告。
