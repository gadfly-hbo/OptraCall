### Qoder → Codex 移交交付模式

这是既有分工的一条可选交付路径，适用于 Qoder 完成全链路开发后，由 Codex 接管至合并。采用本模式时，在当前变更规格记录安排与范围；Codex 自始开发等其他交付方式继续沿用原流程。

1. **Qoder 开发。** 在 `qoder/<slug>` 分支的独立工作树实施 Extension。Host／Agent 接缝由 Codex 实施；仅在用户对本变更直接指定 Qoder 实施接缝时，Qoder 才可承担该部分，并按 IN06 在规格记录例外的范围、理由及后续维护回归 Codex 的安排。先例、一般“开工”指令或自行填写 IN06 记录均不构成该指定。完成规格、适用 SDD/TDD、`npm run check`、隔离环境端到端及浏览器点验，保留失败与未验证项。变更目录提供候选文件清单与哈希、结果和证据索引，以及包含接缝互查导引、非作者复核任务书和移交声明的移交包。
2. **分支移交。** 在有效 Git 授权内将全部候选与移交包固定为单一交接提交，推送 origin；原工作树切为游离状态释放该分支，并停止写入。交接提交、基线、原工作树及候选身份须可核对。移交即分支所有权转移，此后唯一写入者为 Codex，Qoder 保持只读。
3. **Codex 接管至合并。** fetch 后在自己的独立工作树检出该分支，先核对提交与清单哈希，再完成接缝互查、直接修复、提交和受影响检查；修复持续由 Codex 承担。固定修正后的完整候选，以全新、干净上下文的非作者子 Agent 完成第4节独立复核，处理发现并请其重验。按当前用户授权执行第5节 Git/CI 交付：需要授权时由 Codex 申请，集成最新 main 并重验受影响部分，集中单 PR、实际 head CI，获用户合并确认后 squash 合并并安全快进本地 main；更新规格/结果并完成适用 OpenSpec 归档。

移交前后同一分支同一时刻仅有一个写入者。独立复核者须未参与候选任何部分的创作，且不继承作者会话历史；接口互查与作者测试仍按第4节单独报告。本模式不改变 IN01–IN07、职责边界及复用检查、独立复核的强制要求，也不扩大模型、数据、设备、安装或运行采用授权。

未经上述直接指定实施接缝时，在结果记录保留流程偏差、实际范围及用户后续决定；事后知情接受、保留实现或 Codex 互查兜底不追溯改写为原流程合规。

### 四点产品原则

本项目统一遵循：**Host 管环境、Agent 自主执行、优先复用 Pi 已有能力、减少人的操作**。以下职责及复用规则是详细来源；每次 spec／UI 设计、开发和验收均须实际检查，不能只在方案中重复原则口号。

### 产品 Agent 与工程 Agent

本项目遵循“Host 管环境，Agent 自主执行”的架构原则。Host 负责提供任务目标、业务上下文、资源与工具访问、权限边界、预算与取消控制，以及交互、状态展示、日志、成果持久化和决策学习环境；产品运行时的 Pi Agent 在授权范围内自主理解任务、选择方法与工具、安排分析步骤、检查结果并修正错误。Host 不通过硬编码分析流程、固定步骤、方法配额或无必要的确认门槛干涉 Agent 的内部运行，不替 Agent 作业务判断、补跑计算或编排其推理过程。这里的自主性不改变 Codex、Qoder 的 SDD/TDD 与独立复核责任。

Host 对越权、资源超限和破坏性操作实施必要约束，保护原始材料与历史成果；这些环境治理职责与 Agent 自主执行并存。校验失败应尽可能将具体问题反馈给 Agent 在授权范围内自主修正，不在 Host 中另造分析流程；业务适配器按已确认契约进行结构／格式校验、保存和回执，仍遵循下述 IN01–IN07。

整个 OptraCall 产品统一采用 **pi-coding-agent SDK** 承担 Agent Runtime，由 Codex 维护产品级 SDK 接入与运行管理入口。Extension 通过统一入口使用 Agent 能力，提供工具、skill、上下文及专业能力，不自建 Pi SDK 接入层、会话运行管理或平行 Runtime。

会话循环、工具调用、上下文管理、压缩、恢复与重试等能力优先复用既有 SDK／Runtime。仅在存在已验证的能力缺口时增加最小适配，并在变更规格中记录实际版本、验证证据、缺口及最小适配理由，不重复建设平行机制；恢复与重试仍须遵守原有取消、UNKNOWN 和副作用保全边界，不盲目重放请求。

统一底座允许按任务隔离会话与上下文。所需会话的创建、续接、停止及事件处理均经过统一入口；具体接口与并发方式随实际任务确定。宿主不直接组合 pi-agent-core + pi-ai 自建运行底座；SDK 内部的传递依赖不受此限制。实施时核对并锁定兼容版本，不能将“已声明同一依赖”当成实际共用 Runtime 的证明。

人的操作围绕表达目标、指定资料或偏好、纠正／排除，以及确需由人作出的授权和不可替代的业务取舍。正常使用优先让 Agent 在已有授权内完成查找、读取、方法选择和纠错；用户无需为享受能力先维护日记、搬运资料、逐条审批普通读取、填写机器身份或确认引用。可选管理与人工指定资料作为补充，默认沿已有当前工作和合理值，技术细节按需展开。减少点击不能以 Host 代作专业判断、暗中放宽权限、擅自丢弃用户明确选材或越过必要确认实现。

所有新增设计均须检查四点原则：是否属于环境与治理职责、是否侵入 Agent 自主执行、是否重复 Pi／既有 Runtime 能力、是否把可由 Agent／SDK 完成的工作推给用户。Pi 已支持的工具组合／嵌套、分支、上下文与重试方式优先沿用；权限或持久副作用确需收窄时记录实际缺口／风险依据，不能只为日志更整齐或新证明协议限制 Agent 的正常方法。职责越界、重复建设或非必要人工作业应先删减、合并或调整；确需例外时按第4节记录并批准，不将必要授权和保护误省。

3. **适配归 OptraCall。** 先核对目标版本的官方发布说明、变更及公开接口，优先在 Host、Extension 和必要薄适配层解决差异，逐项遵循四点产品原则，不重造 Runtime 或分析循环。确实无法通过官方公开接口、配置或扩展机制解决时，说明缺口、影响和可选产品安排，交用户决定；不能自行修改 SDK。内部接口确有必要时，按 IN06 记录路径／符号、公开能力缺口与证据、owner、精确版本约束、升级失效风险、替代／移除条件及独立复核结论；版本改变后重新核对适用性，不能自动继承旧例外。
4. **来源与实际采用分别证明。** 同时核对依赖声明、锁文件的官方 registry 来源／完整性、实际解析目录／版本及有关官方 Pi 依赖；必要时将安装包与该版本官方发布归档逐文件比对。包名、锁文件或统一入口检查通过，均不能单独证明安装包未改、运行时无不受支持的改写或正在运行的服务已采用新版本。版本提醒／模型目录刷新也不构成 SDK 升级授权。

### Semantica 官方组件来源与版本约束

Semantica 是业务语义支撑引擎，Pi SDK 是统一 Agent Runtime；两者职责不同，官方组件治理要求一致。本节为 Semantica 的长期规则来源，升级执行第3节的[验证与回退流程](#semantica-升级验证与回退)。

1. **使用官方原包。** 采用未经修改的 Semantica 官方发布包；不改源码或 `site-packages` 安装产物，不通过补丁、私有 fork、同名替包、模块替换或绕过公开契约的运行时改写改变其实现。通过官方公开 API、配置和扩展机制操作自有实例及业务图数据属于正常使用，不把合法图数据更新误当成改包；业务本体、图数据、来源映射和适配代码维护在 OptraCall 自身资产与代码中。
2. **版本由用户指定。** 保持已批准并锁定的版本。只有用户明确指定精确升级目标后，才按授权更新官方依赖与对应平台锁文件；不因 `latest`、安全提醒、依赖机器人、重装或依赖重解算自动升级、替换或降级 Semantica。可主动说明官方版本变化和影响，不能代替用户决定。关联 Python／传递依赖的变化须记录理由、实际锁定版本和兼容证据，不能借其绕过组件版本决定。
3. **适配在 OptraCall 完成。** 先核官方发布说明与变更，优先使用公开接口，在 Host、Extension 或必要薄适配层处理差异，遵守四点产品原则。Semantica 不成为第二套 Agent Runtime，也不接管 SAP／方法、企业资料、M2 或 Case 的来源与发布权威。确有必要只读依赖内部接口时，按 IN06 记录公开能力缺口、owner、路径／符号、精确版本、升级风险与替代条件，逐版重核；无法解决时说明影响交用户决策，不自行修改官方实现。
4. **核对来源及实际安装。** 检查官方发行来源、精确版本、平台锁文件与 wheel 完整性、实际私有解释器／导入目录／分发版本及依赖闭包，必要时逐文件对照官方归档。相同版本号或安装命令成功不能单独证明原包完整，也不能证明运行服务已采用；工程核验不放入每次产品启动或日常查询中增加用户操作。

### 统一会话接入规范（当前Interface v3，兼容v1/v2业务子集）

以下IN01–IN07适用于Codex、Qoder及其他开发者。准确类型及Interface版本以`src/host/agent-sessions.ts`为准；最小使用方式、业务差异和验证示例见[接入说明](agent-session-integration.md)。本节是强制规则唯一来源，AGENTS及工具专属项目入口仅放同源指针。

当前v3落实用户已确认的[生命周期补充A边界](../openspec/changes/automatic-verification-revision/lifecycle-supplement-proposal.md)：仅显式开启自动核算的受信新任务，从首次普通执行前托管工具资源；允许任务内后台与并行计算，正常交接先等待计算自然结束，显式停止才强制收回。Host只管理材料、权限、资源归属及实际收尾，不决定Agent公式、工具选择、专业意见或是否改稿。未开启的普通任务保持原策略；旧任务及重启后缺可信起点的资源不因JSONL标记、关闭driver或读取历史而升级为受管。v3候选的检查与非作者复核结论另记，接口存在不等于专业验证或运行采用完成。

**2026-11-01会话接缝初始v2增量（历史候选）：** [自动核算与主Agent修订](../openspec/changes/automatic-verification-revision/spec.md)及其[九项结构合同](../openspec/changes/automatic-verification-revision/structure-decisions.md)已由用户确认。当前Interface v2兼容原v1调用子集，增加Host-only `execution/owns`和lease的`quiesce/reopen/onCancel`；不向业务port暴露执行资格创建/owner证明。资格绑定真实owner和当前operation，不能从JSON、任意workspace或旧lease恢复。公共层在同一占用内确认旧资源终止后受控重开，不由业务层另建busy/代际/运行队列或平行Runtime。

原任务与核算仍各持原owner权威，自动链只关联实际请求。可信SDK驱动唯一写原native；所有Agent可控的文件/代码/codemode/间接工具均须跨受限执行边界，不得在驱动内留下动态执行后门。工具执行器不是另一位分析Agent，不能改变专业意见、选择方法或补计算；普通分析及旧封闭文本资源保留其原工具合同。具体保护可行性、局限及实际完成范围记录在当前变更，不将合成探针扩大成完整产品验收。

父取消先撤后续派发，再等匹配子操作和本资源安全停止；阶段间也不能提前idle。子停止/资源关闭失败时隔离原owner、保留UNKNOWN，显式close可重试失败清理，不能自动重放请求。按Provider/project/owner关闭只等待匹配资源与子停止，不受无关operation影响。IN07验证须覆盖这一增量及所有旧消费者，详见同源接入说明；历史v1实施记录仍保留原事实。

两类策略继续保留：项目任务使用绑定配置和已保存sessionFile；需求梳理在operation开始捕获当前配置，生成与最多一次修正期间固定，重建沿用原新建native策略。各owner的原生会话、上下文、配置快照与占用独立；Host只持域管理引用，协调明确的Provider/真实项目/退出范围，不另建资源台账或全局Agent运行队列。需求的目标项目不是需求会话归属。SDK原生历史读取及固定连接探针只由检查中列明的路径承担，不能借例外接管业务会话。

迁移采用原位换接线；本期不新增会话库、业务ID、持久代际或需求续接指针。旧资料保全与正常追加分开验：迁移不改写既有内容，显式续聊及原有证据校正仍可产生合法更新；回退兼容代码读取最新资料，不恢复旧副本覆盖新增工作。未知结果保留UNKNOWN/中断，不自动重放或换模型。共享代码与同进程资源仍有共同故障风险，逻辑隔离不等于进程/安全隔离。

规范完成验收须分别记录当前Codex/Qoder版本、实际项目入口及读取证据；文件存在或加载器支持某文件名不等于任务已读取。未实际验证的工具项记NOT_RUN，不能宣称固化全部通过；不得为凑通过改全局配置、调用未获准模型或启动MacBook开发。静态导入检查只覆盖已知绕过形式，仍需实际调用链、行为回归及非作者复核。

独立核算沿用Interface v1，由Host的核算适配器静态注册profile；owner包含真实projectId/taskId/verificationId，原任务资源和结果权威保持原位。按已确认SV05先固定独立结果再提供作者产物；核算、显式作者修订、一次复查和用户采用分开，不从completed推断专业正确或经营效果。固定输入、快照、原生指针归属与普通文件完整性由Host核对，不承担统计计算裁判。`SessionTurn.providedContext`是向后兼容的可选交付回执，新JSONL自定义记录可保存实际来源，旧记录不回填；SAP记录资源实际初始化索引，不使用当前启用列表伪造历史采用。详细技术与可观察限制见[核算接入说明](verification-agent-integration.md)。Codex/Qoder及其他开发者修改此接缝均先读本节与该说明；不建立平行Runtime、全局运行队列或固定方法注册中心。

已确认的修订出稿使用Host静态`verification-author-draft`附属profile和`fixed-draft`能力策略，由同一Interface v1管理。固定全文由Host读入，创建时不注册可执行工具，不自动加载技能、上下文文件、MCP或扩展；只允许产品可信脱敏扩展，不向业务Ref暴露SDK管理对象或原生命令。不得仅隐藏工具名、临时修改原分析会话后依赖finally恢复，或在材料过大时回落全工具。新native归本记录的revision-native，原项目会话指针/父链/历史保持原位，原普通分析及独立核算的既有工具策略不变。接入必须覆盖实际工具拒绝、动态/间接调用、取消/关闭/重开和原件字节保全；空工具不代表内容正确或OS沙箱。

## 3. 连续 SDD 与 TDD

每项非平凡变更在 `openspec/changes/<change-id>/` 维护一份简洁规格和现有结果记录；首次实际变更时再创建目录。必要设计和证据用链接关联，普通纠错更新原记录。最少写清：完整可观察结果、需求/验收标识、范围与不做事项、允许修改路径、关键边界、适用检查和未决问题。

**按复杂度选择规格与UI Demo（2026-11-03用户明确）：** 简单、范围闭合的修复可不另建spec，在适用原记录中留下复现、修正及验证即可；跨模块、重要契约／权限／持久化或其他复杂改动须维护简洁spec。涉及较明显的前端布局、导航或交互流程变化时，先提供可查看的UI Demo供用户审核，记录明确审核结果后再实施正式UI变更。很简单的文字修改、按钮调整等可不另出Demo，仍完成相称验证。spec和Demo是否需要按实际影响判断，不把所有修复一律升级为文档／审批套件，也不以“修复”名义绕过复杂变更的必要规格或UI审核。

工作顺序：明确目标与验收 → 维护规格并实施适用 TDD → 最小可运行切片与真实路径反馈 → 同一责任方持续修正和受影响检查 → 完整候选集中复核与验证 → 适用验收及获授权 Git 交付。

**spec 与 UI 的四原则前置检查：** 提交确认前，沿普通用户的实际目标走一遍正常、失败与恢复路径，记录：Host／Agent 各自负责什么；采用的 Pi 实际版本／原语、已存在能力和新增适配的缺口证据；用户完成目标必须做的操作、相对已有路径新增的记忆／配置／确认动作，以及可删除／合并／默认完成的步骤。区分正常提问／发送、用户自愿管理、必要权限确认和技术异常处置；新增必做的人工作业须给出不能由 Agent／SDK 完成的理由。提供可体验的最简正常路径，管理／追溯／高级范围按需展开，不能让可选管理成为实际默认必经流程。审查必须包含 spec 条款、UI 动作／可点击原型或不适用理由与反例；设计阶段与产品运行的验证结论分别记录。

**界面与交互的开工确认：** 新增或实质调整用户界面／关键交互时，先提交对应spec与可点击UI Demo，写明关键路径、状态和现有实现差异，由用户确认后再实施受影响的产品代码。Demo可用虚构资料与内存状态，明确其演示边界；实现后的截图、测试或独立复核不能替代用户的前置UI确认。现状盘点、纯后端变更或无界面影响的普通纠错，在spec说明不适用原因即可，不补造Demo。已确认且未变化的事项沿用原决定；出现实质变化时只补受影响部分。确认记录保留具体版本／摘要与用户决定；用户明确选择暂不对齐的差异另列保留，不改写为已一致。

- **确定性行为**：实现前有能检出目标行为错误的测试；修复前保留失败测试或因果复现，再做最小 GREEN 修复和必要重构，留下永久回归。保留关键正向、反向、边界、失败和禁止副作用断言。
- **探索与模型质量**：先明确实际任务、预期和观察条件，保留真实试验与失败；不伪造确定性 RED。单次成功只证明该场景及其输入、模型、工具和配置条件。
- **纯重构**：保留修改前后 GREEN 与相关等价证据。
- **文档和规范变更**：做相称的一致性、引用和范围复核，不制造产品 RED 或无意义的占位测试。

测试从需求和验收导出，不照着实现重述。环境、导入、定位器或 fixture 失败不算产品 RED；后补测试不能伪造历史失败。测试修改或删除应解释覆盖如何保留，不能通过削弱断言把失败改成成功。

从首个可运行切片起，尽早走用户正常入口、实际配置、代表输入、真实工具及适用的保存/重开、失败、取消和恢复路径。需要模型、数据或外部副作用的检查，沿用有效任务授权；缺少授权时明确未验证范围。Mock、结构校验或 SDK 导入通过不能证明真实分析成功。

真实模型评估不能仅凭模型名称相同认定配置等价。冻结并用实际SDK核对Provider/协议/线路、reasoning、thinking level、contextWindow、maxTokens、compat及相关输入限制；中继或自定义Provider可能触发通用模型默认值，必须先核对实际注册模型和请求参数。隔离测试的内存凭据替身仅替换获准配置的密钥，保留原配置校验、版本与公共生命周期；只用于评估，不作为Extension或生产接线范式。实际原配置、诊断替身、合成Provider和供应商结算费用分别报告，不能混用成绩或将SDK费用估计0写成免费。

同一责任方持续完成诊断、修复和回归。普通修正复用有效规格与授权，不为每次编辑重建文档套件、全量回归或独立审批；新增产品行为、重要契约/持久化结构、数据权限或外部影响边界，先补齐必要决定再实施受影响部分。

### Pi SDK 升级流程

用户指定目标后，由 Codex 维护统一 SDK 接入，Qoder 配合其 Extension 适配；已明确的版本与授权沿用，不重复索取相同确认。升级按以下顺序实施：

1. **固定目标和基线。** 记录用户指定的精确官方版本、升级前依赖／锁文件／实际解析版本、官方发布说明与变更来源；核对运行环境、内部接口清单、依赖覆盖、各 owner/profile 及现有 Extension。界面无实质变化时注明 UI Demo 不适用，避免无关人工步骤。
2. **隔离候选并适配。** 保全项目、原生历史／fork 指针、配置、文件和已有 FAIL／UNKNOWN；在隔离工程环境先更新官方依赖及锁文件，不共用或改写正在服务的依赖安装目录，不改官方包实现。对 OptraCall 适配先保留兼容性失败，再按适用 SDD/TDD 修正；公开接口优先，内部接口及第三方覆盖逐项重核，不能删除保护或跳过断言换取通过。升级候选安装与正式运行采用分开，不自动更新其他设备或正在运行的服务。
3. **验证受影响能力。** SDK 为共享底座，执行完整适用检查、真实 SDK 的隔离集成路径及非作者独立复核；按下表在规格中固定关键项、通过标准和证据，逐项记录 PASS／FAIL／NOT_RUN／UNKNOWN，不把测试文件存在或旧版本 PASS 当成新版本证据。

## 4. 独立复核与工程完成

日常自检、Codex/Qoder 接口互查和作者测试不能替代最终独立复核。复核者不得是该候选任一部分的作者；两位作者互相看代码，不自动构成完整候选的独立复核。

完整结果收尾时固定候选、规格、输入与证据，覆盖 staged、unstaged 和新增文件。提供候选提交或文件清单与摘要、验收依据、允许检查、现有结果、失败和缺口；复核上下文独立，先从验收导出关键预期，再检查实现和作者测试。

复核保持源文件、测试、规格和固定证据只读；获准检查需要的临时文件、缓存或报告只能写入明确的隔离位置。复核者独立检查关键路径与失败路径，记录检查范围、命令/结果、发现与结论；作者修复后重验受影响范围。候选变化导致的旧 PASS 失效应明确记录，不能沿用不适用的复核或 CI。

工程完成至少具备：

1. 当前规格与已确认验收一致，实际修改在授权范围内。
2. 适用目标测试、回归与质量检查完成，真实集成路径和结果有证据。
3. 独立复核完成，发现已处理；必要的用户风险接受单独记录，不写成复核 PASS。
4. 必要 CI 对应实际交付候选；变更到位后更新规格及结果记录，并完成适用 OpenSpec 归档。局部检查不代表完整交付；原四项批次的延后Git／CI安排已完成，不再作为当前例外。
5. 交付说明给出版本、验证、失败/未验证项、风险与后续点；涉及更新时说明回退方式及其数据影响。
6. 下述职责边界及复用专项最终检查已通过，或已有负责人批准且仍有效的限范围例外；批准例外不记为检查通过。

独立复核不可用时，明确未完成的复核及其影响；可继续安全、已授权的实现，但不得用作者自评代替要求的复核或宣称完整工程验收。

产品验收由用户对固定候选的适用体验和结果作出。工程检查、独立复核、CI、Git 推送、产品验收、安装与发布分别报告；任何一项不自动代替另一项。尚未运行、失败、跳过及未知结果如实保留。

### Host 与 Agent 职责边界及复用检查

开发流程的最终验收须包含本项检查，与本节要求的最终独立复核一并完成。合并或发布前，基于本次变更的实际代码、调用链及必要运行记录，按第2节通用原则确认：

- Host 承担环境、目标与业务上下文交付、权限、资源控制、交互、状态与日志展示、成果持久化和决策学习环境等职责；Agent 在授权范围内自主选择方法、工具、执行顺序及纠错方式。Host 不通过硬编码分析流程、固定步骤、方法配额或无必要的确认门槛干涉 Agent 内部运行，不代作业务判断、补计算或编排推理。
- 会话循环、工具调用、上下文管理、压缩、恢复与重试等能力优先复用既有 SDK／Runtime；新增机制须有已验证的能力缺口、证据及最小适配理由，不能以包装或统一入口掩盖平行机制。
- 必要的权限、安全、预算、取消和原件保护措施属于环境治理，应核对其实际边界，不将其误判为干涉 Agent 自主执行；已确认的业务输入输出契约与普通分析内部步骤分别检查。
- 人的操作沿本次实际 spec／UI 与运行路径核对：正常使用无需额外维护／普通读取审批，新增必做动作有目的和必要性证据；已考虑当前工作快捷路径、合理默认、合并操作与渐进披露。不能只凭“已自动化”文案通过，也不能以省操作为由替人作未授权的业务取舍。

涉及 SDK、依赖或 SDK 适配的变更，专项最终检查还须核对本规范的官方包不可修改、用户版本决定、公开接口优先、内部接口例外及上述升级回归／交付要求。源码补丁、运行时改写、来源／实际版本不一致或关键未验证不得被统一入口 PASS 掩盖；既有风险的“已登记”不等于“已修复”。

验收记录须列明本次检查范围、候选身份、证据位置、发现的问题，以及“通过／不通过／待验证”结论；不能仅凭设计声明或测试全绿判定通过。检查范围以本次变更及受影响接缝为准，不据此宣称未检查的既有实现已合规。

存在职责越界、重复建设、无合理必要性的新增人工作业或关键证据缺失时，不得标记本项验收完成。应修正并复核，或提交写明范围、理由、风险和退出条件的例外供负责人批准；未通过且未经批准例外，不得进入合并或发布。批准例外须与原“不通过／待验证”结论及未解决问题分别记录，不得改写为检查通过；例外不扩大其他任务、数据、模型、Git、安装或运行采用授权。

## 5. Git 与 CI 的精简节奏

**长期产品试用与修正分支（2026-11-03用户确认）：** `Test-And-Repair` 长期承接“MacBook用户试用 → 试用报告回传Mac mini → Mac mini诊断、修正与迭代”。MacBook负责产品体验和反馈，Mac mini在本分支开展相应修正；同一时刻保持一个明确写入者。每轮依据实际试用版本、复现步骤、预期与实际及可安全提供的证据处理，保留原FAIL／UNKNOWN、项目、会话和文件，按第3、4节及本节完成适用验证和交付。`main`继续作为集成基线；本分支不随单轮修复完成或合并而删除，后续迭代基于已核对的最新集成基线继续，不重置或改写历史。分支用途不改变MacBook现有只接收`main`的更新入口，也不自动切换设备运行版本；具体更新按相应交付授权执行。

**长期 Host／Agent／Extension 协调分支（2026-11-03用户确认）：** `codex/Host-Agent-Extension` 由 Codex 承接 Agent、Host 与 Extension 之间的协调接缝、能力核查及必要接线；Qoder 的 skill／Extension 本体继续在其明确归属的分支实施。同一分支同一时刻一个明确写入者；本分支长期保留，不因单轮任务完成或合并而删除。每轮仍按实际规格、适用检查、非作者复核及 Git/CI 授权交付，合并前核对最新 `main` 并重验受影响部分；分支定位不自动授权模型调用、网络收费、设备更新或服务切换。首个任务见[任务 Agent 能力规格](../openspec/changes/task-agent-capabilities/spec.md)。
