# 作者修订保全收尾建议

2026-10-31 · 待用户确认，仅方案，不实施权限或流程调整

## 为什么需要补充决定

正式合成测试的60份作者结果和48次初始核算均技术完成。进入作者修订后，模型在明确收到“保留原件、另存新稿”指令的情况下，两次覆写选定原稿，一次删除自己的合成项目目录。冻结副本仍在不等于原件保留成功。完整SV11已失败；原真实项目、配置、会话和文件逐项复核未变，事故现场保留，不合并main。

事故包含三层问题：模型越过保留指令；“固定目标路径”容易被理解为编辑目标；工程失败归因及关闭链还需准确、完整。后两项在原授权内补确定性测试和最小修正，不声称修复了原件保护。单纯再加强提示词不能作为保全保证。

## 推荐方向：修订出稿不授予写删能力

原任务仍可发起修订、查看核算意见与新稿。修订 Agent 只读取固定材料并返回新稿全文，由 Host 使用新文件名保存；不让它在原项目中执行改写、删除或目录清理。需要新增计算时，在固定输入副本侧另行完成，不能为方便临时放回原项目写删能力。原普通分析的工具权限不在本决定内改变。

继续用现有 Pi 和统一会话接口，不建另一套调度平台，不建 IR、固定计算方法库或第三裁判循环，不加操作系统硬沙箱。保留原项目、原任务标识、原会话与父链、原稿及原核算记录；只关联新稿，不自动采用，不更新 RAP/SAP/Case 判断。

**需要确认的取舍**：修订这一步不再拥有原普通分析的完整 macOS 执行能力。它只负责出稿，不能一边修改正文一边任意运行命令。若安装版 SDK 无法可靠地在原资源上临时收窄能力，应使用同一公共生命周期管理的附属只读出稿资源，不能替换原任务的会话指针或改写历史；实现前固定该接缝与兼容验证，不绕过统一入口。

## 必须证明的边界

SDK 1.4.0 有活动工具与可调用工具的区分。仅从展示名单移除工具，不等于撤销执行能力；历史恢复、codemode/deferred、扩展和 MCP 都须核对。后续实现必须用确定性调用证明修订资源不能执行 write/edit/bash、间接写删或重新开放权限，不能只检查工具名称。若做不到，先采用无执行工具出稿；材料放不下就明确缩小范围，不猜测结果。

完成、失败、取消、配置变化、迟到结果、关闭和重开均须覆盖。不得把临时工具选择污染原普通分析配置或下一轮会话；恢复失败关闭该资源，旧操作的清理不能修改新资源。原件哈希、原 native 前缀及项目目录逐项前后比对，新稿必须新增。模型给出的错误内容、漏报和误报仍需单列；收窄文件能力不等于保证专业正确或 OS 安全隔离。

真实复测采用另行固定的小范围合成样本，保留本次失败，不恢复旧现场后重新计为通过，也不无限补跑。通过本地、兼容、联合回归、真实行为和非作者复核后，重新评估 Git/CI 合并资格；当前草稿和 CI 不代替这一门槛。

## 更小的范围替代

若优先交付可用部分，可先关闭新“交作者工具修订”入口，保留业务语义增强、独立核算建议与现有人工保存/采用。代价是本期不具备自动修订/复查完整闭环，必须重新确认收缩范围，不能宣称原SV07和完整一期已完成。

本建议不授权新权限策略、额外真实模型、恢复/清理事故数据、合并或运行服务切换。当前验证与失败见[实施记录](../openspec/changes/business-semantics-verification/result.md)。
