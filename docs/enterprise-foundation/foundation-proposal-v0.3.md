## 1. 本版决定及原因

建议在首批企业基础层正式建设及共享规则执行用途发布前，先补齐“规则定义—候选验证—准确发布—普通 Agent 调用—修订与历史”的最小工具闭环。资料盘点、业务定义和候选整理无需等待全企业图或完整 OWL 建模。这里约定后续先后关系，本轮不实际推进这些工作。

历史接入优先解决原资产、准确来源、派生图、版本与使用。早期[有限快照范围](../../openspec/changes/fourbase-l2-rollout/s3-structure-addendum.md#4-单一构建与原生保存布局)明确不启用 OWL reasoner；后续三类资产增量保持正文权威、图可选。现有记录不能证明已经充分评估并排除了官方规则推理器。当前工具能够保存规则定义、关联指标和字段，却尚未提供将核定规则交给官方 Reasoner 执行的普通工具合同。

本版补足这条使用主线，不将“Agent 自主”理解为排斥确定性工具。Host 管归属、权限、资源与回执；Agent 自主选择读什么、何时调用工具、如何计算和解释；SDK 执行规则；人提供资料并处理必要业务取舍与发布决定。

## 2. 首批范围与两条路线

首批仍为“运动鞋服共享经营骨架＋会员运营核心”：经营范围及共同维度、门店渠道、商品 SKU、交易／退货／退款、会员身份、计划与资格、会员交易关联、实际参与及权益。指标体系与主数据、本体同步建设；不绑定某一道首购复购问题。

- 行业路线：运动鞋服行业 → Nike 企业公开参考 → 目标企业。
- 领域路线：会员运营领域 → Nike 会员运营公开业务域参考 → 目标企业会员运营。

每站都含主数据、指标体系、本体。四模板 v0.2 继续作为输入；本轮不改写模板或将标杆公开规则当作目标政策。共享对象沿一致身份，记录采用／修改／排除／新增及企业依据。行业与标杆参考不构成第三个企业正式层。

企业基础层提前供同企业合格项目任务使用；任务演进层将实际资料、政策或共享缺陷形成贡献，核定后修订基础层。创建企业、关联项目及旧资产都不能自动认领未归属合成内容。

## 3. 三类资产与规则的关系

| 资产 | 原建设内容 | 本版增加的可执行关联 | 保留边界 |
| --- | --- | --- | --- |
| 主数据模型与字典 | 对象、属性、键、值域、粒度、身份与有效时间 | 在所选用途核必需关系／类型约束；向规则提供准确主体、状态和时间事实 | 不自动生成黄金记录，不以相似字段／设备推断同人，不改原系统主记录 |
| 数据分析指标体系 | 主题、指标族、定义、公式、维度、资格、场景及方法 | 指标引用准确资格／有效性规则及事实条件；规则派生结果可作为计算输入，保留完整性限制 | 准确公式仍归原 SAP；聚合、金额、比例与复杂日期处理使用原获准计算工具，不建第二计算引擎 |
| 本体及业务规则 | 概念、属性、关系、事件、适用条件和出处 | 部分定义明确的规则具有声明式执行表示，关联原 item、数据 Binding、核验及版本 | 自然语言知识继续保存；不要求所有规则可执行，不将执行成功等同企业政策正确 |

可读定义与执行表示绑定在同一原规则修订，执行表示是准确源稿的投影。引用跨主数据、指标、本体的 item、来源、版本和字段；不单独建立可编辑规则主库。

## 4. 最小推理范围及官方复用

先在当前获准官方 Semantica 0.7.0 实际安装上核对公开接口与边界。官方源码可见 Reasoner 的规则／事实接口及结论、规则、前提返回，OntologyEngine 提供 SHACL 校验。它们是否与本机 wheel 完全相符、哪些输入可稳定支持，仍列为未来 I01 实证，不用网页代码代替本机验证。[官方 Reasoner](https://github.com/semantica-agi/semantica/blob/v0.7.0/semantica/reasoning/reasoner.py) · [官方 OntologyEngine](https://github.com/semantica-agi/semantica/blob/v0.7.0/semantica/ontology/engine.py)

首切片限定有限事实上的无环、正向合取规则，适合“已入会＋明确状态＋已核时间事实 → 对某用途资格成立”一类判断。否定即失败、递归闭包、聚合、任意函数／回调、自动冲突裁决及经营动作不纳入。规则中的不符合结论必须有显式前提；未推出不等于不符合。

日期／数值比较按实际能力由原获准工具形成带输入和依据的事实，不能靠适配器猜资格。状态缺失、覆盖不足、相互矛盾、不支持或执行中断分别显示；不能补成零、false 或隐式降级为“已通过”。推理结论不改写主记录或正式源。

复用原 Studio、SAP、Binding、准确源读取、预览、发布、任务工具及公共 Pi 生命周期。OptraCall 仅补可执行规则投影、事实绑定、官方调用、结果／版本证据及必要 UI；不改造官方 SDK，不默认升级，不新建 Runtime、通用推理器、规则语言或发布中心。官方能力无法覆盖时缩小支持范围并显式返回限制，实质扩范围另核。

规则调用可直接使用同一准确源投影的规则和事实，无需先建完整企业图；现有图及旧快照仍可读。图遍历、约束校验、规则推导和 LLM 业务判断分别留证，不互相替代。

## 5. 完整建设与使用主线

| 环节 | Agent 与工具 | 用户看到／决定什么 |
| --- | --- | --- |
| 提供范围和资料 | 建设 Agent 沿原任务读取四模板、获准企业资料、现有指标／字典和样本，整理范围与差异 | 一次表达自然语言目标，提供已有资料；无需先填规则表或选择固定专家团队 |
| 三类并行内化 | 同步核对象、度量和规则；识别适合执行化的共享判断；关联实际字段与事实条件 | 查看三类成果及关联、来源与缺口；只集中处理材料不能裁定的业务问题 |
| 候选验证 | 建设者可对自己的候选及获准样本试推演；规则语义、事实绑定、官方执行和指标计算分别核查 | 查看正常、明确不符合、缺事实、冲突及时间边界，不以一次执行成功代表整体业务正确 |
| 准确发布 | Agent 准备原预览，冻结规则、模型／SAP组合、用途和检查证据；Host 资格校验及分项回执 | 必要正式决定；关键 FAIL／UNKNOWN限制受影响用途，独立定义可单独发布 |
| 普通分析与决策 | 普通 Pi 自主发现正式目录、读取准确原文，按需调用规则工具、计算及解释；不接建设会话或预期答案 | 直接提问；按需查看结论使用了哪些版本、事实、派生及限制，无需逐条选规则 |
| 贡献与修订 | 实际任务反馈形成贡献候选；核三类影响、试验修订、新版发布；新任务使用新版 | 必要企业范围及政策决定；原报告固定原规则、SAP及输入，运行中任务不静默换版 |

普通执行工具只返回获准范围的结果和证据；消费资格不附带建设／发布写权。调用失败时 Agent 可以说明限制、选择其他获准方法继续独立分析，但替代判断不能冒充该引擎的成功证据。

## 6. 原权威、状态及回执

企业业务资料仍保存制度和业务依据；Studio 保存主数据／本体／规则及关联；SAP 保存公式、场景和方法；Binding／数据说明保存实际映射。执行回执沿原任务成果和准确来源记录，不产生第二份可编辑规则或事实真相库。

每次执行至少可追溯：企业／用途、真实项目任务与请求、规则准确修订和哈希、谓词与对象身份、事实输入版本及覆盖／截止、所用 Binding／关联 SAP、官方组件与适配版本、结论／前提、缺口及实际完成状态。官方返回的规则和前提补充原 SourceRef 关联，不能把 SDK 置信字段当专业正确概率。

沿原四项状态记录定义、映射、当前可计算、实际使用；规则支持范围及执行证据纳入原检查与证据，候选／正式另列。作者声明、工具执行事实、独立核验与用户验收分别记录。没有真实模型业务实验或目标企业资料的通过结论。

## 7. 资料与人工操作

沿[原资料清单](batch1-confirmation-v0.1.md#5-需要用户提供的资料清单)分批：先经营范围、会员制度、当前指标／报表和系统字典，再补可关联样本，历史覆盖依所选指标补充。本版尤其需要制度生效时间、状态历史、身份关联依据及已知例外；Agent 从现有材料提取，用户不用重填结构化规则。

用户后续在 OptraCall 界面操作，Codex 提供逐步引导；产品 Agent 实际建模。当前审核包既不登记企业，也不入库目标企业资料或启动任务。

## 8. 验证、顺序与停止点

1. 本轮：方案、spec、Demo、任务清单一致性及独立原型走验；提交用户审核后停止。
2. 后续明确实施授权后：核实际官方版本，以合成资料完成最小工具与 UI、兼容、来源／权限、取消、版本及普通 Pi 使用验证。原失败和未知保留，真实模型／配置／预算按届时范围固定。
3. 工具所需验证完成、用户提供获准资料并确认启动后：沿原 M01–M05 建设目标企业。首次满足限定范围可发布，不为凑流程制造错误或政策变化。
4. 第二家企业验证仍独立：复用流程、检查和方法骨架，重新核规则、映射、来源和正式身份。

全部 Demo 为虚构预置状态。接口原型或点击成功不等于规则引擎实跑、真实模型专业质量或企业产品验收；未来 Git／CI、main、服务及设备采用另按明确授权核定。原三个 Mini 桌面功能不变。
