# 企业基础层三类资产建设：调整思路与工具评估

版本 v0.1 · 2026-11-12 · 待用户确认，暂不开发

本稿补充用户提出的数据分析指标体系，依据四组参考模板、两条建设路线及当前实现评估最小调整。四份模板 v0.1 与原批准方案保留。本轮仅形成讨论文档；未改产品、SDK、正式资产或目标执行清单，未读取目标企业资料或运行模型。

## 1. 建设目标修正

企业基础层同步建设三类成果：

| 成果 | 主要解决的问题 | 与其他成果的关系 |
| --- | --- | --- |
| 主数据模型与字典 | 业务对象是什么、标识和粒度是什么、属性与值域怎样定义 | 为指标的统计对象与维度、本体的概念和关联提供一致身份 |
| 数据分析指标体系 | 企业及领域需要怎样度量，指标如何组织、定义、分解和使用 | 帮助发现需要哪些对象、事件、维度、时间及资格规则，也接受本体与数据映射约束 |
| 本体 | 对象、属性、关系、事件和规则具有怎样的业务含义 | 把主数据、指标测量对象与业务条件连接起来，发现歧义、遗漏及不一致 |

这三类内容在同一建设范围内同步起草、查证和迭代。指标体系进入基础层完成标准，不留到某一道分析题出现后再补。基础对象和关系也可因企业经营本身需要而保留，不以是否已被某个指标引用作为存在条件。

例如，会员规模指标会要求区分主体、账号与入会关系；权益使用指标会要求区分资格、授予、领取与使用；商品销售指标会要求说明商品变体、订单行、支付和退款。具体公式、统计范围及企业政策随目标企业资料核定。

三类资产是建设内容，企业基础层与任务演进层仍是原两层产品结构；行业／标杆参考是建设输入。

## 2. 两条路线与四份模板怎样调整

两条路线保持：

- 运动鞋服行业 → 标杆企业 Nike 公开参考 → 目标企业。
- 会员运营领域 → Nike 会员运营公开参考 → 目标企业会员运营。

每一站统一包含主数据、指标体系、本体和三者关联，目标企业两条线共享企业、品牌、商品、门店、账号等准确身份。

| 模板 | 下一版增补的指标体系范围（候选） | 边界 |
| --- | --- | --- |
| T01 通用运动鞋服行业 | 商品、销售、库存、渠道门店、供应履约及经营价值等指标主题；相应维度、粒度和业务事件 | 范围由经营模式核定，不将每个指标族强制启用 |
| T02 通用会员运营领域 | 会员规模与发展、参与活跃、权益、购买、留存与价值、服务等指标主题 | 等级、积分、付费等按企业实际选用；不预设天数、阈值或单一首购复购口径 |
| T03 Nike 企业公开参考 | 公开资料明确披露的指标及其报告范围；其他参考结构作为建模建议分列 | 公开财报度量不自动等于经营分析口径；未披露内部指标不补成 Nike 事实 |
| T04 Nike 会员运营公开参考 | 公开体验与规则所启发的测量结构和数据要求 | 内部会员 KPI、公式、分层与阈值无依据时保持未知；通用建议不冠以 Nike 已采用 |

四份模板的增补属于后续待审核版本范围，本稿没有将这些指标主题记为模板中已完成的指标定义。

## 3. 指标体系不止一份指标清单

建议统一描述以下内容，资料不足时留待核项：

| 部分 | 最少内容 |
| --- | --- |
| 体系组织 | 业务目标或用途、主题／指标族、覆盖范围、核心及可选项 |
| 指标定义 | 稳定身份、业务含义、统计对象、公式或测量定义、单位、去重及资格条件 |
| 分析条件 | 业务粒度、维度及层级、时间归属、窗口及截止、适用范围、空值与异常处理 |
| 指标关系 | 公式依赖、统计分解、维度分组、分析用途关联分别表达；分解须注明是否可加与互斥完备条件，驱动用途不构成因果证明 |
| 数据与语义关联 | 所需主数据、事件与属性、本体概念／规则、实际 Binding、来源和数据覆盖 |
| 治理与使用 | owner、参考及企业依据、版本、检查、已定义／待核／当前可计算等分项状态 |

正式指标定义和公式继续保存在 SAP 原主库。指标体系索引、主数据和本体以准确 SAP 包版本及指标名引用它，不另维护可独立修改的公式副本。

SAP 包及 scenarios 已有的用途、指标角色、方法引用等内容也以原资产为准，体系总览按引用展示；Studio 只补当前缺少的跨包组织、三类关联及内化信息。

## 4. 当前工具能力评估

结论：现有能力能承接文稿与源资产形态的第一轮 Agent 建设，也已有正式发布与普通任务使用底座。面向可持续复用的企业基础层，关键缺口是三类资产逐项结构化表达、内化差异及联合业务核验。

| 能力 | 当前可以复用的实现 | 仍需补齐 |
| --- | --- | --- |
| 资料与建设会话 | 企业资料、原项目文件、统一 Pi 会话、Studio 建设任务及工作项 | 基础层建设引导应明确支持行业／领域范围和多个指标主题，减少单题导向措辞 |
| 主数据与本体源稿 | 概念、规则、本体、Binding 等候选保存正文、范围、来源、依赖、检查和版本 | 实体、属性、键、值域、关系、事件与规则缺少统一逐项结构化契约；当前主要为正文编辑 |
| SAP 指标及场景 | 多指标包、维度、时间粒度、简单／比率／派生／累计指标、组合引用；决策目的、结果／驱动／约束角色、方法和证据要求 | 企业主题与目标结构、跨包关系及逐项语义映射尚不完整；不应重建指标库 |
| 字段与数据映射 | M2 字段观察、语义声明、概念及 SAP 引用、来源与争议；Binding 源稿及现有 Python／bash 核查 | 需明确对象／维度／事件到实际数据的关联及业务核验依据，不能把字段名对应当身份关联、粒度或单位正确 |
| 参考与内化 | 模板来源和版本、Studio sources/dependencies、采用／修改／排除／新增工作表 | 缺少参考 item 到目标 item 的稳定映射与受管差异记录；首轮可沿已有资料路径输入 |
| 发布与资格 | 准确预览和指纹、正式指针、SAP 分模块回执、普通读取递归核依赖资格 | 需要在这些机制上补三类资产的联合业务一致性与适用版本组合核验，不重建发布中心 |
| 图及使用演进 | Semantica 候选抽取、正式图投影、普通 Agent 按需查读、任务贡献与历史保全 | 当前图以来源陈述／关系为主；明确类型与逐项关联后才能更可靠地检查影响和覆盖 |

SAP 已允许在 definition、caliber_switches、provenance.note 表达单位、业务粒度、退款去重和时间归属。它们目前主要由 Agent 与人理解，不是全部已结构化强校验。

当前 SAP 校验检查结构及部分包内引用。type_params 整体可省略；expr 是文本，现有验证不能证明表达式、量纲、依赖环、聚合可加性或观察资格正确。此事实是本次评估边界，不在本轮顺手修改产品。

## 5. 建议的最小工具增量

### 5.1 沿现有源资产补结构化内容契约

优先复用 Studio save-asset／catalog／read 与候选、正式版本模型，定义可验证的内容形状：主数据对象／属性／键；指标体系主题、关系和准确 SAP 指标引用；本体对象／事件／关系／规则引用。原文与文字资产继续可读。

现有工具已经能保存和读取约定 JSON，真正要补的是内容语义、逐项引用和可靠验证。先用代表性模型片段检验原工具的表达能力；需要新增代码时明确其实际缺口，不预设必须新增一套读写工具。

先用现有业务源资产承载体系索引与关联说明。只有必须由工具稳定保存、读取和核验的内容，才补最小结构契约；不要求把每一段经营知识都形式化。SAP 0.2 严格拒绝未知字段，不能把新字段直接塞入现有包；需要演进 SAP 时另核定版本兼容方案。

### 5.2 补逐项关联与内化记录

最少记录：参考准确版本及 item 标识、目标项、采用／修改／排除／新增、差异理由、企业证据与适用范围。指标引用包含原权威 SourceRef 与 metricName／项定位，不编造新的 SAP 身份。

现有 SourceRef.locator 可作为项定位的复用候选；先核对实际读源及校验语义是否足够，再决定是否需要扩展内容约定或合同。

三类资产联合对照表最少包含：对象／标识与业务粒度 → SAP 指标及维度 → 业务事件／时间／资格 → 本体关系／规则 → 实际 Binding → 来源／缺口／核验结果。它是对原资产的关联，不是第二套主库。

### 5.3 在现有检查和发布预览上补联合核验

- Host 承担结构、身份、引用是否存在、版本、权限、来源资格及指纹校验。
- Agent 回源判断企业事实、口径一致性、计算与样本结果，自主使用原 Python／bash 及专业工具；人集中裁定证据无法决定的实质业务选择。
- 检查统计对象与维度是否一致、时间及资格是否清楚、Binding 是否支持所需事件与粒度；记录缺口和影响，修订回到相应原资产。
- 复用准确预览记录相关正式版本组合及分项实际回执。某模块失败或 UNKNOWN 时限制依赖它的用途，独立可用部分继续；不新增全库原子事务发布机制。

联合核验指核对有关资产是否相容，不等于 Host 自动证明全部业务语义正确，也不要求所有参考指标已经具有可计算数据。

### 5.4 在原 Studio 增加按需查看

建议优先增加三类成果的体系总览、关联对照、内化差异、检查缺口与修订影响；指标内容继续在原 SAP 专业区编辑。使用侧沿原 catalog/read 提供准确结构和资格，让普通 Agent 按需选用；不要求用户逐资产勾选。

先评估现有列表、正文详情和发布预览能否承载这些内容，只有缺少必要关联操作或无法清楚审阅时，再增加对应视图与交互。

是否需要独立视图与新增交互由后续 spec／UI Demo 核定，当前不开发。拖拽画布、完整 MDM 黄金记录治理、新计算引擎或新的 Agent Runtime 不列为本次基础层前提。图按用途可选，不以图完成阻断独立可用 SAP 和语义源。

## 6. 建设与验收流程建议

1. 先确认三类成果的建设范围、两条路线和参考对象。
2. 四组模板各自同步起草主数据、指标体系与本体，检查相互关联、来源和未知项；用户审核业务覆盖及模板结构。
3. 用户提供目标企业获准资料；Agent 并行比对三类内容，整理差异、映射和材料缺口，集中提交必要业务裁定。
4. 对有数据支持的部分核查样本与边界；对缺资料部分分别标记定义待核、数据未映射、当前不可计算等状态。定义发布与计算可用分别核定。
5. 经必要正式决定发布准确源版本；普通独立任务实际读取并使用相关模型、指标和语义，分别核验计算与业务解释。
6. 任务发现共享变化后形成贡献，核对三类资产影响，修订原资产并由新任务验证，保留历史依据。

这描述成果流转，Agent 内部工具选择和迭代顺序自主。基础层的“完成”按约定范围核定三类定义、相互关联、来源和未决项；不以文档数、图节点数或全部字段非空代替完成。实际计算与分析使用另有对应证据。

后续若确认产品增量方向，再整理最小资产契约、spec、适用可点击 UI Demo 和目标执行清单，经确认进入实施。本稿不启动这些产品变更。
