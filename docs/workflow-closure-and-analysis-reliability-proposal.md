## 1. 先回答：1–7是否已经完整？

**还不能称为完整的分析—决策—经验复用闭环。1–6的主要功能路径已有，第7步已有人工任务和反馈记录，但反馈进入下一次需求／分析的产品衔接仍缺。** 功能存在、链路可操作、专业结果正确、真实经营有效，分别判断。

上一条说明把“已实现的反馈保存”与“期望的后续经验复用”接成了完整流程，表述过满；这里按实际代码纠正。

| 步骤 | 当前已有 | 当前边界／缺口 |
| --- | --- | --- |
| 1 准备背景与数据 | 企业业务资料及修订、SAP指标资产、Case背景／本案补充、项目文件 | 来源可用不等于已读或理解；并非所有资料类型／连接器均已接入。 |
| 2 梳理需求 | 需求提案、用户编辑采纳、确认／RAP发布、显式送入项目任务 | 用户仍需确认业务事实；可直接提问，不要求所有分析先有RAP。 |
| 3 提供上下文 | 按本轮选择提供RAP／Case／企业资料，初始化SAP索引；原生记录与来源回执 | 不自动装入所有资料；提供与采用不同，旧记录不足仍未知。 |
| 4 Agent分析 | 自主阅读、工具／代码执行、过程产物及报告保存、原任务续聊 | 可完成任务但报告仍有方向、边界、归纳和依据错误；不是专业质量已解决。 |
| 5 独立核算 | 用户选定输入；先独立计算保存首次依据，再揭示作者产物；另存修订、一次显式知情复查／导出 | 选材不足会不可核；核算有漏报和自身新增错误，不能作为真值裁判。 |
| 6 决策看板 | 显式抽取建议、原文依据、采纳／驳回、负责人／日期／任务状态 | 采纳不等于实际执行；BoardItem尚无明确Case归属，不能由共享项目自动猜Case。 |
| 7 执行反馈与再分析 | 人工更新todo／doing／done，回录执行、结果、指标变化、复盘和评分，保存后可重开 | 没有业务系统派发或自动取数；反馈当前值更新会覆盖旧反馈；缺少来源固定、明确关联Case及送入下一轮的专门入口。 |

第7步更准确地分为三部分：

- **有：**人工执行跟进和结果回录。看板任务状态只表示记录，反馈是用户陈述，不是独立测得的经营事实。
- **不足：**围绕原决策依据、实际数据、适用条件做效果复盘，并保留当时供复盘的反馈版本。
- **缺少专门衔接：**从某项反馈发起下一次分析／需求，并能回读到底带入了什么。当前可手工复制反馈或保存普通资料文件后选用，但不应算作产品闭环已经完整。

Case已有历史／追加说明，不代表这些历史会自动提供给Agent。现有任务上下文只取Case当前字段、项目业务信息和用户选定产物引用；不自动包含全部Case事件或看板反馈。一个项目可关联多个Case，反馈复用时必须由用户明确选择适用Case，或保持无Case。

## 2. 大白话要点

1. **现在能记“做了什么、结果怎样”，但还缺“拿这次结果继续分析”的顺手入口。** 先补这段，不重做前六步。
2. **先把手工闭环做完整。** 人执行、回填、选资料，Agent复盘，再由人决定下一轮。自动经营执行和自动归因都不是前提。
3. **旧反馈不能跟着新编辑悄悄变掉。** 送去复盘时保存当时那份内容、来源和条件；以后能解释当时为什么这样判断。
4. **报告要把话说对，而不只是表算对。** 多／少、以上／以下、等于是否触发、相同订单数是否代表结构相同，这些也会改变决策。
5. **核算要看得到相关材料，也要对自己的新结论负责。** 没拿到的材料写不可核；别用一百条数字一致来代替全文判断。
6. **Host负责把资料和记录交清楚，Agent自己决定怎么算、怎么查。** 不加宿主计算器，不要求每题走同样步骤，不无限加审查Agent。

## 3. 建议顺序和“完整”的最小定义

先实施A“反馈回流与复盘”，用一个新合成案例证明首尾连通，再实施B“分析可靠性”和C“核算覆盖／检错”。这是研发优先级，不是产品中强制用户按A/B/C通关。

本阶段链路完整的定义是：**原需求及背景 → 分析报告 → 用户选定建议 → 人工行动／反馈 → 基于固定反馈和资料的自主复盘 → 用户明确保存经验或提出下一轮需求 → 下一轮Agent实际读取并正确处理该经验。** 可以通过普通任务实现，不要求每次新建RAP或Case，也不要求结果一定正向。

不以自动业务执行、实时指标同步、因果引擎、推荐策略自动学习、经验自动发布或复杂知识库作为补齐前提。不能据此宣称所有业务场景完整、所有结论可信或经营效果已被因果证明。

## 4. A：先补齐第7步，复用现有页面、文件和普通任务

### 4.1 用户看到的最小衔接

在现有决策任务／反馈附近增加“基于此反馈复盘”入口，进入轻量预览，展示：

- 原项目、建议、任务、当前反馈及时间；没有反馈也可明确以“未取得反馈”发起追问，不补造成功。
- 建议对应的报告／抽取身份、用户能取得的采用理由、核算分歧及相关RAP／SAP来源。原记录没有的理由或历史版本标未记录，不事后补造。
- 用户补充的实际观察期、对象范围、执行说明、结果资料和仍未知的影响因素；直接沿用项目上传／文件引用。只有业务确有需要才填，不把完整效果表设为启动条件。
- 可选择本项目关联的某个Case，也可以无Case；多个候选不自动挑选。Case选择不扩大文件或经营动作权限。

用户审核后创建**本项目内一个新的普通复盘任务草稿**，附上可读的来源材料。复用现有任务创建、草稿编辑、模型选择和显式发送；创建／预览不自动发模型。原分析任务、报告和看板反馈保持原位。

Agent在普通任务内自主决定：比较哪些基线、读取哪些获准文件、是否需要计算／澄清、能否评价效果、还缺什么。可以得出“无效果”“证据不足”“仅观察到共现”“旧建议不适用”，也可以提出下一步；Host不替它判定。

### 4.2 保留反馈修订，并固定当时带入的材料

建议在原看板反馈同一业务域内增加轻量修订保留：用户更新反馈时保留旧值，当前页面展示最新值；每次已保存修订可定位，不另建经验库或第二套反馈权威。历史只从新能力启用时开始，旧记录只有当前值时将其标为首个已知版本，不伪造此前修订。具体持久结构在实施前决定包中确认。

交接时，再将用户确认的那一版反馈及材料保存为项目`020_clean`中的普通、来源明确的复盘资料副本，复用原文件读写、来源回执及Case产物引用。新生成副本使用新身份，不覆盖旧副本；原看板修订是反馈来源，项目副本是某次分析实际取得的交接材料，两者用途不同。

固定内容至少能定位：来自哪项建议／任务、何时／哪版反馈、原报告已知身份、哪些观察为用户回录、实际或模拟性质、哪些附件本次明确选入、哪些原始依据缺失。资料正文不提升为系统指令。技术身份／字节由Host保存，业务解释由Agent承担。

后续反馈编辑既不删除已有修订，也不会追改已发送的复盘副本。旧反馈在此前被覆盖而无副本时，明确不可恢复，不从当前值生成“旧版本”。无需保存未提交的每次输入、全局审计平台或完整项目备份。

这里的“固定”是交接时实际使用的正文／明确片段及身份可回读，不是宣称`020_clean`普通文件不可修改或具有沙箱保护。普通副本或Case采用副本仍可能被外部编辑；再次送入前稳定读取并核对身份／字节，变化时保留原交接记录并要求重新确认，不自动重建或覆盖原采用。若附件只固定了路径和观察信息，应标“仅固定引用，未固定当时全文”；不能据此承诺完整复算。已发送正文／片段的历史保留方式，在实施结构包中明确，不能只留指向可变文件的路径就宣称旧内容已保全。

历史报告变化时，不把当前报告当作原决策报告。若保存的抽取材料只有片段或原文件缺失，展示能取得的范围；用户可以继续受限复盘或补充原件，Host不自动用最新版替代。原经营数据集不默认整份复制；确需固定复算输入时由用户明确选取。

### 4.3 复盘之后怎样回到下一轮

复盘报告仍保存`060_reports`，支持三种显式去向：

1. **继续研究：**在原复盘任务追问，沿用普通会话能力。
2. **形成下一轮需求：**“基于复盘梳理新需求”打开既有需求创建入口，预填可编辑的问题和有来源的反馈摘要／文件位置；用户按原流程生成、审核、确认和发布RAP，不自动将反馈认定为事实或发布需求。具体文件读取须服从需求profile现有能力：当前需求会话无执行工具，Host仅提供用户选定的可读正文／明确范围，不假称该Agent会自行读取路径。
3. **沉淀到Case：**用户选择Case并通过既有产物关联／采用或当前判断更新保存。下一次任务仍要明确选用相应资料／引用；只写Case追加说明不能算已送入Agent。不自动升级为企业公共资料、SAP或通用经营规则。

如果复盘形成可复用业务事实／规则，另经用户在原企业业务资料或SAP维护入口审核修订；保留适用时间和条件。一次结果改善不能直接变成“这类策略一定有效”。

### 4.4 最小验收，先证实链路连通

| 验收 | 可观察结果 |
| --- | --- |
| A01 人工闭环 | 从报告建议到逐项采用、任务、反馈，再创建普通复盘任务并显式发送；保存／刷新／重启后关联和正文一致。 |
| A02 版本保全 | 连续两次保存反馈可查看两份已保存修订；交接后修改原反馈，原请求仍回读交接时内容。旧缺历史如实未知，报告变更／失效／片段范围不被隐去。 |
| A03 不猜Case | 一个项目关联两个Case，用户选择其中一个或不选；其他Case的特殊规则不混入。 |
| A04 未知可用 | 未执行、执行但效果未知、负效果、观察期不足均可记录并进入复盘；不因done或评分高自动标记效果已验证。 |
| A05 自主复盘 | 用新合成事后数据让Agent实际计算并指出旧建议适用或不适用；Host不计算效果、不决定因果。 |
| A06 下一轮实际使用 | 将一条经用户确认的经验选入下一次需求或任务，记录实际提供／读取与回答如何变化；再给一个条件不相同的案例，Agent应保留边界而非照搬结论。 |
| A07 安全与兼容 | 预览／建草稿不发模型；重复点击不重复创建或发送；取消、失败、配置变化、归档、跨任务／项目、旧记录和原文件保全按原合同验证。 |

仅保存反馈到数据库，或只把文件关联到Case，都不能代替A06。真实经营效果尚未发生时，使用合成观察验证功能，不称真实业务收益。

## 5. B：分析结论专业可靠性的具体改进

### 5.1 已有能力与剩余原因

已有完整工具／Python、SAP／RAP／Case／企业资料、过程文件和来源记录；也已有共享`OUTPUT_EVIDENCE_GUIDANCE`，提醒合计、排序、分母、范围与全称断言。这一轮**不再把重复添加“认真检查”提示词作为主要修复**。现有评估显示正确主表仍可伴随相反的正文、严格边界误判、订单数相同推断结构稳定，以及无依据的权限断言。

能够观察到的是“数值产物到最终判断的约束不足”；不能仅据此断言模型内部为何出错。需要分别验证材料表达、可选专业能力、最终解释及模型适配的贡献。

### 5.2 从已有结果形成可回读的判断依据

建议围绕用户问题中**会改变建议的论断**，让Agent按需保留简短依据，例如“采用的定义／条件、涉及的数据或结果文件、由结果支持到哪一步、何处仍是推断”。载体可以是计算脚本输出、表格、普通Markdown或报告引用，由Agent选择，不强制结论JSON、章节、条数或通用IR。

优先利用Agent已经生成的结果来写正文：它可以自主使用结果驱动表格／段落、计算临界值或反例、复读最终报告并核对解释；不要求Host识别论断、解析报表、算出正确答案后再改写。需要重新计算时由普通分析Agent在授权工具中完成，不能让封闭文本修订资源偷偷回落到全工具。

### 5.3 可选专业能力，针对实际失败类型

复用现有分析资源的短证据指导及用户已安装的原生skill机制，提供可按需读取的专业参考／工具使用示例。例如使用既有Python标准库`decimal`／`fractions`演示精确边界，使用明细／总计和并列值的通用样例演示反例验证，并提供从已有结果文件生成数值段落的普通脚本范例。范例不内置企业公式、列映射、评估题真值或固定报告模板；Agent可以读取、运行、修改或用自己的方法替代，不由Host自动执行。是否采用、采用几项及先后由Agent决定。首轮不建设新的方法平台或强制skill安装器，也不将方法指令伪装成企业业务事实。

| 能力主题 | 具体帮助 | 预期表现 |
| --- | --- | --- |
| 方向、等线与触发 | 提供精确数值与展示数值分开、`<`和`≤`不同、上调／下调条件的通用示例；示例不含评估题答案 | Agent自主选精确计算／边界反例，正文方向、等线值和触发条件一致。 |
| 粒度、合计与并列 | 提供明细／小计／总计混合数据、加权比率、零基期和并列排名的常见陷阱 | 不把区域加总再加企业总计，不把排序位置当不等名次，不把金额率写成订单率。 |
| 证据支持程度 | 提供计数不证明结构一致、共现不证明因果、用户回录不等于独立验证的反例 | 重要推断明确前提，缺少SKU／客户／反事实时缩小结论，不补造事实。 |
| 业务行动与权限 | 复用RAP目标／约束、Case例外、企业制度来源 | 区分“建议提请复核”和“已有取数／预算／执行权限”，不把复核线变成经营授权。 |

通用示例放专业参考材料；企业口径及例外继续由SAP／企业资料／Case维护，不能在参考里另建一份业务真值。尚未明确的制度含义由用户确认，Host不解释规则胜负。

### 5.4 用小实验选择有效增量

用同一份业务输入先做三个独立实验臂：R0为现有指导基线；R1仅增加可选的结果引用／数值段落生成样例；R2仅增加上述专业反例和工具范例。逐一与R0比较后才试R3组合，不把组合进步归因给某一项。各臂不追加题目事实或评分答案，也不强制Agent执行示例。需要比较已获准模型时固定各自实际配置并单列结果，不静默换模型兜底；若仅某模型适配有问题，先给局部结论。

实验范围和候选先写入后续获准的适用规格，证实收益后才将有效资产纳入产品能力；若无收益，删去无效指导／额外产物要求，不能以报告变长或检查条数增加当收益。用户仍可普通直接提问，简单描述性任务无需补齐所有参考主题。

## 6. C：独立核算覆盖及检错能力的具体改进

### 6.1 先解决材料覆盖，复用现有两类选材

当前已支持`dataFiles`与`authorFiles`，不需要重建核算入口：

- 原始数据、原始字典及选定的事前业务语义作为独立计算依据；不能把作者计算出的结果表冒充原始数据喂给冷读。
- 完整作者报告、被报告引用的结果表、检查摘要和相关计算脚本可由用户选为作者产物，固定后**冷稿保存完成才揭示**。作者脚本可供阅读或明确的复现用途，执行与否及验证方法由核算Agent在原授权范围内决定；重跑不等于独立计算。
- 选材页提示“本次实际选了什么、报告提及但尚未选入哪些资料”，优先由用户选择，或由原分析Agent在原报告中列出所引用的产物供用户核对。不让本次核算会话为了选材先读作者报告、过程结果或后验摘要；不为选材默认新增第三Agent。作者候选清单及其结论也不提前交给冷读，冷读所见清单只涉及获准的原始数据和事前语义来源。Host不自动递归抓全项目、扫描全盘或决定专业相关性。新增一键建议选材不得自动确认或扩大权限。
- 来源缺失、文件过大／不可解码或后续变更按技术事实提示；没有提供的材料写不可核，不要求为出结论而猜测。主体报告和只读过程产物分别列范围。

本轮实测的退款诊断小计错误位于未提供给产品核算的作者过程文件。改善选材能让它进入可核范围，但不保证模型一定检出；验证时将“有材料却漏报”和“材料未提供不可核”分开。

### 6.2 两个既有turn，保留独立性并扩大专业对照

继续原`withSession`／lease和owner，不加固定第三Agent或递归审查：

1. **首次依据：**保持只给固定数据和事前语义，由Agent自主形成计算、关键判断和不能确认项，保存后才开放作者产物。反馈、当前Case判断和本轮作者意见均是后验内容，不能混入冷读。
2. **对照：**核算Agent可读取完整作者产物，判断哪些重要结论得到核对、哪些存在差异、哪些材料不足或尚未核到。范围可用自然语言或表格解释，不要求逐句建全量论断库，也不以固定检查数量为目标。

现有对照提示只嵌入报告短摘要并提供完整副本位置。拟明确“摘要可能不完整、全文和引用产物在哪里、实际读了哪些范围”，由Agent决定如何阅读和核验；未读全文不能在结果里宣称全文核查。Host只展示实际提供范围、可观察活动与Agent声明，无法证明理解或专业覆盖率。

### 6.3 对照稿的新结论同样需要依据

核算Agent对新增合计、排序、敏感度、取舍建议和采信内容采用与作者相同的专业标准，自主核对或缩小表述。不能“发现作者错一项”就认定其余新增内容正确，也不能把措辞改进建议统计成实质检错。

优先复用B的可选参考及可读计算结果，检查真正影响决策的正文／建议，特别是“建议合并作者某项结论”是否沿用了作者未解决的边界。对照结果可说明：确有错误、可改进表达、结论一致、资料不足或未覆盖；这些是专业意见，不变成Host审批状态或强制格式。

检查行数、不同命题数、检出问题数不是同一件事。由Agent据真实产物表达范围；工程侧再独立核验，不能由Host统计“检查了216行”后盖专业通过章。

### 6.4 修订与后续使用保持原保护

继续现有显式修订、另存、一次显式知情复查和导出，不覆盖原稿／任务指针／native历史。文本修订缺少新增计算能力时应保留未知；要新增数据／计算，用户明确发起普通分析或新核算。知情复查不改称新冷读，报告／输入变化不能沿用旧范围。

核算记录及分歧可作为用户下一轮分析／看板判断的材料；不自动阻止普通分析或强制用户接受核算意见，不自动采纳、重算、换模型或循环到通过。

## 8. 怎样验证真实收益

### 8.1 功能连通先单独验收

按A01–A07验证真实UI／HTTP、原生任务、来源交付、保存重开和正常取消／失败。用一个正反馈、一个负反馈、一个未知反馈及多Case共享项目场景；至少一次展示经验改变下一次分析，同时在条件变化时不照搬。模型自行计算；测试侧可离线有答案，不能把答案放入产品上下文。

### 8.2 专业质量用固定任务和未见变体比较

建议初轮12类、每类2个变体，共24个任务：方向、严格阈值／舍入、混合明细总计、加权分母、零基期、并列排名、样本结构、因果边界、政策／例外时效、资料／执行权限、未决事项条件情景、缺失或矛盾证据。纳入已有失败类型并更换数值、单位、对象和表述；至少加入其他业务情境，避免只记住同一商贸题。

每类一个用于开发验证，另一个由非作者保留为冻结盲测。当前基线和候选在相同问题、输入、实际模型／协议／thinking／工具条件下，各取首次结果；对预先选定的4类关键问题各做3次固定重复（包括首次，共3次），保留全部，不选择最好一次。先保持现有两类选材内容不变比较专业增量，再对“仅报告／报告＋过程产物”做单独范围实验，避免把新增事实收益误当方法收益。A/B/C尽量一次只变一个因素。

核算能力实验固定**同一作者稿、同一组过程产物、同一份数据／语义和可核问题分母**，包含正确稿与有问题的稿；不能让新作者稿恰好更容易就算核算进步。材料范围实验只改变是否提供相关作者过程产物，原始事实、报告和专业能力保持不变，并单列可核范围增加。完整端到端实验再允许作者稿随B变化，其收益单列，不反推为C单项检错提升。

一旦盲测结果被用于定位和修正，该题就转为已见回归；修正后的候选使用新的未见变体验收，不能反复调试同一盲题后仍称盲测通过。预先约定的重复用于衡量稳定性，不是失败后临时加跑直到通过；全部首次结果、失败及人工介入保留。

| 评价对象 | 真正需要计量的结果 |
| --- | --- |
| 作者稿 | 首次完成率、全文重要决策依据错误率、方向／边界／范围／权限错误、未支持推断、依据可回读比例。核心表数值单列。 |
| 核算冷稿 | 计算和解释正确性、未知是否如实、独立性实际可观察范围；作者未揭示前不算漏报。 |
| 核算对照 | 对实际可核重要问题的检出／漏报／误报，错误定位与严重度；未提供或不可读材料单列不可核，不算检出或漏报。 |
| 核算新增内容 | 自己新增的数字、排名、解释及采信建议错误率；不能只复用作者的正确主表评分。 |
| 看板／反馈 | 来源忠实、采用理由和范围可回读、原报告错误是否被继续传播；人工记录与真实效果分别评价。 |
| 成本与介入 | 全部人工编辑／补资料／修订次数、耗时、可得token／费用及未知范围，不把SDK估算当供应商结算。 |

工程评估者根据固定全文独立标注重要论断及实际可核范围，给出分母；产品Host不抽取固定论断IR或计算专业覆盖率。新增错误和误报由非作者核对，不能只用同一模型给自己评分。

### 8.3 通过标准与停止线

- A的连通验收通过，可以称“人工反馈回流的最小闭环补齐”，仍不宣称专业可靠或真实经营增益。
- B/C的冻结重要错误集应无未关闭的重要错误／可核漏报／重要误报及核算新增重要错误；作者首次正确交付率、核算检出能力应比基线改善，同时报告全部分项与样本数。达不到则保留PARTIAL／FAIL，不能用总平均掩盖关键退化。
- 正确报告及无结论任务是必要负例：核算应允许一致、无需新增和不可核；不能为了证明价值凑错误。核查变广导致不可核分类变化时说明原因。
- 零观察错误只支持本次固定样本，不保证普遍正确。历史失败保留，不恢复或重放旧事故，不循环跑到偶然通过。
- 取消／恢复／原件／owner／配置／旧记录兼容及自主性边界先按受影响测试验证；最终适用完整check、非作者复核与实际head CI按未来实施范围执行。任何一项不替代用户产品验收。
