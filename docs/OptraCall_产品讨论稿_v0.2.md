# OptraCall 产品讨论稿

版本 v0.2 · 2026 年 10 月 28 日 · 根据用户补充确认修订

状态：产品原则、工程分工及开发方式已确认；本次授权限于仓库初始化、文档与规范更新、首次提交及推送，产品功能开发尚未启动。原始 v0.1 原样保留。

品牌主张：持续做出更好的决策

## 1 产品方向与讨论边界

OptraCall 是面向数据驱动决策者的分析与决策工作台。它让成熟 Agent 自主完成分析，由宿主提供业务上下文、交互环境和决策经验沉淀，帮助用户把一次分析转化为可采取的行动，并在反馈中改进下一次判断。

本稿记录已确认方向和首轮验证重点，不是完整白皮书或固定技术蓝图。本次初始化不包含产品功能开发。后续以用户明确的真实任务、小步实现和实际验收推进；新增模块必须说明解决了什么问题，不以架构完整度替代用户价值。

### 已确认的建设原则

- 品牌名称为 OptraCall，名称寓意为 Optima 最优、tra 迭代、call 决策；沿用「持续做出更好的决策」。
- 技术结构采用 Host + Agent + Extension。Host 管环境，不管分析步骤；pi-coding-agent SDK 统一承接全产品 Agent Runtime；Extension 包含分析资产、连接器和业务插件，共用产品统一运行入口，不自建 Pi SDK 接入层或独立 Runtime。
- 产品体验参考 WorkBuddy，但服务分析与决策，不扩张为通用办公平台。
- 吸取 JuanerAI 的资产和经验，不先建立宏大的白皮书与蓝图；重点提炼有效的开发流程和规范。
- Mac mini 全权负责产品方案、开发、工程测试及修复迭代；MacBook 仅以用户身份体验产品、整理问题并回传。Codex 负责 Host、Agent 与整体接入回归，Qoder 负责 Extension。
- 延续 JuanerAI 的 SDD + TDD、独立复核和必要验证，采用精简 Git/CI 节奏；具体执行以[工程规范](engineering-workflow.md)为准。

### 为什么重新开始

用户报告 JuanerAI 全链路反复调试失败，而 Pi 或 WorkBuddy 配合分析 skill 能完成任务。这说明新增复杂度需要证明价值，不能因设计更完整就认定产品更好。

当日早先针对 JuanerAI main `72570c7` 的只读核查显示：该快照的主分析循环已经由 Pi 自主运行，但仍存在回合后的宿主补计算及报告、审查交接；实际使用版本与近期失败根因尚未确认。因此，重启并不以「旧系统完全是固定状态机」为前提，而是主动收缩自建编排责任。

**证据标记：**品牌、Host + Agent + Extension、统一 Runtime、工程师与机器分工、SDD/TDD 与独立复核为用户已确认方向；以下未明确确认为原则的体验、具体边界实现和推进安排仍为讨论建议。OptraCall 尚未经过真实任务验证，不能把本文方案视为已实现能力。

## 2 技术结构与责任边界

目标是让 Host 为 Agent 提供可用的业务环境，而不是形成另一个逐步指挥分析的系统。业务分析方法优先由 Agent、skill 和分析资产表达，资源访问与副作用由可执行的边界控制。这里描述产品运行时 Agent 的自主性；Codex、Qoder 的工程开发仍遵守 SDD/TDD 与独立复核。

| 部分 | 主要责任 | 不承担的责任 |
| --- | --- | --- |
| Host | UI、工作空间、任务入口、业务上下文、结果保存、决策经验环境 | 不指定每一步分析，不替 Agent 补跑计算，不另建分析循环 |
| Agent | 理解问题、查资料、探索、选方法、写代码、执行、自修复、验证与解释 | 不自行扩大授权，不把建议自动当成批准或实际执行 |
| Extension | 提供分析资产、数据接入与专业业务能力；通过产品统一入口使用 Agent 能力 | 不自建 Pi SDK 接入层或平行 Runtime，不绕过资源权限，不占有宿主任务权威 |

### Host 与 Agent 如何协作

Host 将问题、已知业务背景、获准使用的数据与工具交给 Agent。Agent 可以自主检索、澄清、执行和修正。Host 展示实际进展、响应必要输入、执行权限边界并保存产物；不以固定阶段切断每一轮分析。

需要区分「不能访问资源」与「结果还不合格」：前者在调用前阻止，后者给出具体检查反馈，让 Agent 在当前上下文继续修正。校验可以可靠，分析路线仍应灵活。恢复也不应把未知执行结果当成成功，或盲目重放有副作用的操作。

### 采用成熟的 Pi SDK

已确认直接采用 pi-coding-agent SDK，接受部分自定义自由度的减少；不再直接组合 pi-agent-core 与 pi-ai 自建运行底座。这里改变的是自己的接入与维护责任，不要求 SDK 内部移除这些依赖。

官方 SDK 文档已确认：Pi 可嵌入 Node.js 或 Bun 进程，并提供会话、工具、模型和事件等程序化接口。当前官方文档展示的包名为 @earendil-works/pi-coding-agent；实施时应核对并锁定兼容版本，不照抄历史包名或默认跟随 latest。[1]

pi-coding-agent SDK 是整个 OptraCall 产品的统一 Agent Runtime。Codex 维护产品级 SDK 接入、会话生命周期、事件传递及运行管理入口；Qoder 开发的 Extension 通过这一入口使用 Agent 能力，提供工具、skill、上下文和专业能力，不再自建 Pi SDK 接入层、会话运行管理或独立 Runtime。

统一底座下可以按任务隔离会话与上下文，具体接口和并发方式随实际任务确定。集成验证既检查依赖，也检查真实调用、会话创建与停止路径，不能仅凭包版本相同就认定共用运行底座。

产品接入优先薄适配：任务与会话关联、UI 事件展示、上下文和工具提供、结果保存。会话循环、上下文压缩等先复用 SDK 已有能力；具体可用性仍需针对选定版本验证。

### 三核心不再作为强制结构

业务语义、必要计算校验和执行安全仍有价值，但不要求恢复 JuanerAI 原有模块形态。SCR、IR、Harness 相关代码只有在解决具体问题且收益明确时才复用；不把完整 IR 或多阶段交接设为所有分析的入口条件。

## 3 业务上下文环境与权限边界

Host 的首要增益是让 Agent 理解「这家企业、这次问题和当前条件」。上下文不是一次性填满的大表单，也不是把整个企业资料库塞入提示词，而是按需提供有来源、可更新、能处理冲突的信息。

### 最小上下文内容

- 目标与约束：要支持什么决策、比较哪些选择、时间范围、资源限制和不能做什么。
- 业务语义：指标口径、字段含义、单位、时间归属、对象与关联关系；保留已确认、推断和未知的区别。
- 经营背景：促销、缺货、组织变化、渠道调整等影响判断的事实，并记录时间与来源。
- 可用材料：数据文件、文档、连接器及授权范围，避免把可见误认为可任意使用。
- 历史经验：相关假设、曾采用的策略、实际结果与适用条件，不强行套用其他情境的结论。

### 怎样让上下文真正可用

建议先提供简单的查看、补充和纠错入口。Agent 按需检索并引用所采用的口径；重要冲突向用户澄清，不能悄悄覆盖。用户确认过的信息可复用，但仍要检查时间、业务范围和版本是否适合当前任务。

运行会话的短期记忆由 SDK 承担；跨任务业务知识和决策经验由产品保存并按需提供。两者相关但不能等同。首期无需为此预建复杂本体平台、多个物理库或大量必填字段。

### 不干涉分析与安全控制并存

建议把硬边界放在真实资源与副作用上：允许读取的文件和数据、写入位置、原件保护、外部服务访问、数据外传、破坏性操作、预算与取消。能力限制应落实在工具、执行环境和连接器中，而非仅依赖提示词。

在已授权的工作区内，Agent 的普通读取、代码迭代和临时产物生成不需要逐步确认。授权范围变化、敏感内容外传、覆盖原件或执行真实业务动作时，才触发相应确认与阻止机制。对高风险工具保留最小权限，不把「自主分析」变成无边界访问。

本地计算不自动等于数据不出本地：模型请求、工具结果、样例行、日志和报告均可能携带业务信息。首期必须明确可发送的字段与内容、目标服务及用户确认方式；不能提前宣称零数据外传。

## 4 核心体验与决策经验闭环

### 一个主入口和按需展开的工作区

建议采用对话为主的工作台：用户提出问题、选择资料、补充业务背景；侧边或展开区查看上下文、产物和历史。过程显示真实活动、当前阻塞与待确认事项，不展示与实际执行脱节的固定阶段进度条。

结果首先回答「判断是什么、依据是什么、还不知道什么、下一步有哪些选择」。代码、计算、证据和过程按需查看。用户可以继续追问、纠正口径、要求反证、调整目标或停止，而不是被迫沿固定向导完成分析。

### 一个示例任务

以「某门店销售下降，要不要促销」作为体验示例，首轮试点是否采用此场景仍待确认。

1. 用户给出问题和销售资料。Host 提供已知口径、门店背景及可用历史；Agent 判断哪些信息仍缺失。
2. Agent 自主探索销售、客流、转化、价格或缺货等线索，提出候选解释，寻找支持与反证；方法可调整，不固定为某个公式。
3. Agent 生成可核对的分析结果与备选行动，说明不确定性和风险。发现计算错误时在原会话中修正，而非由宿主代做。
4. 用户决定是否采纳。首期建议以人工执行和结果回填为主，不默认自动操作业务系统。
5. 后续记录实际行动与效果。下一次相似问题可检索这段经验，但仍需核对条件是否相同。

### 沉淀的最小内容

建议以一条简洁的决策记录关联：业务背景、判断与证据、反证和未知、备选策略、采纳理由、实际行动、预期效果、实际结果及修正意见。信息可逐步补全，不要求每次分析都先填写完整记录。

「Agent 建议」「用户已采纳」「实际已执行」「效果已验证」必须区分。没有回填不等于没有效果，更不能自动标记成功；一次业绩改善也不能直接证明策略有因果作用。未排除其他因素时，保留关联观察与解释边界。

只有有复用价值的结论与经验才进入长期资产；保留来源、适用条件、时间、冲突与失效机制。允许纠错、撤销和遗忘，避免把全部对话和错误判断永久灌入后续上下文。首期验收应展示：一条经过反馈修正的经验，怎样实际改变下一次分析，而不只是证明「写入数据库成功」。

## 5 扩展体系与小步验证

Extension 按三类组织，但不先做插件市场或统一安装平台。优先接入真实任务需要的能力，并验证无扩展时主分析仍可工作。

| 类型 | 主要内容 | 首期原则 |
| --- | --- | --- |
| 分析资产 | 指标口径、业务知识、skill、方法、假设、策略与模板 | 可检索和引用，按适用条件使用；不是强制执行步骤 |
| 连接器 | 文件、数据库、业务系统及外部数据接口 | 返回来源与错误，遵守读取和外传授权 |
| 业务插件 | 专业计算、分析工具、报告编审等工作流与界面 | 按清楚的输入输出接入，复用统一 Agent 底座 |

这里的 Extension 是产品分类，不意味着三类对象都实现为 Pi 的同一种技术扩展。具体映射按 SDK 能力和实际任务选择。场景组合可先以资产和依赖配置表达，不急于增设第四套子系统。

### 建议的验证顺序

**先证明基础分析可用。**选一个已有 Pi + skill 成功基线的真实任务，完成提问、数据访问、计算、纠错、结果交付与停止恢复。对照数据、问题、模型和工具条件；有差异就记录。正确交付率、人工介入、耗时和恢复表现不能仅凭一次演示判断。

**再证明上下文有增益。**在同类任务中提供已确认业务口径和背景，观察重复解释是否减少、错误口径是否减少、结果是否更贴近决策。上下文的价值要在被实际使用的证据中体现。

**再证明经验能改善判断。**记录一项行动及反馈，在后续任务中正确召回并保留适用边界。必要时推翻旧经验，而非只展示记忆命中。

**扩展跟随已验证需求。**某项能力反复需要且无法由现有 Agent、工具或资产充分解决，再引入相应插件。每次增加能力，同时复测最初的基础任务，防止功能越多、主链路越难用。

这些是可调整的验证顺序，不是必须层层审批的研发阶段。小步交付可并行；每个迭代只需明确目标、不做什么、如何验收和结果证据，不以长文档作为启动前提。

### 当前不作为首期前提

完整三核心重建、企业级全套治理、多 Agent 调度平台、自动业务执行、动态插件市场、所有历史插件迁移，以及完整本体与知识图谱建设，均不作为本讨论稿的首期依赖。

## 6 开发方式与待确认事项

### 从 JuanerAI 选择性继承

产品资料保留为经验来源，不要求逐章映射到 OptraCall。指标口径、方法、可复用插件、测试样例和踩坑记录逐项评估；保留能证明价值的部分，不整仓搬迁，也不因重启而无差别重写。

开发规范明确延续 JuanerAI 的 SDD + TDD、独立复核、独立变更分支、明确修改范围、适用测试、真实集成验证、证据与缺口说明，以及适用的版本和回退要求。采用连续工程和精简 Git/CI 节奏：日常运行受影响检查与主路径，完整候选集中完成独立复核、适用回归和必要 CI；必要安全要求与质量标准保留。详细流程、完成条件与固定继承来源见[工程规范](engineering-workflow.md)，不整套迁入旧产品蓝图与双端开发流程。

Mac mini 全权负责产品方案、开发、工程测试、诊断与修复迭代。MacBook 仅以用户身份使用产品、总结问题和修改建议并回传；Mac mini 修复后再提供可识别版本复测。体验前标明源码提交、构建与实际运行版本、模型和关键配置。MacBook 不承担工程修复，不形成第二条开发线；用户体验反馈与正式产品验收分别记录。

工程师分工已确认：Codex 负责 Host、Agent，并承担整体接入、主链路集成和回归；Qoder 负责 Extension，提供适用规格、测试、接入说明和证据。两者共同遵守工程规范；最终独立复核者须独立于候选的全部作者，作者之间互查不能自动替代独立复核。分工确认不等于已派发具体功能任务。

2026 年 10 月 28 日初始化前再次核实：本地仅有 v0.1 讨论稿，尚无 Git 仓库；GitHub 的 gadfly-hbo/OptraCall 为公开空仓库。用户随后明确批准初始化仓库、更新讨论稿及开发规范、首次提交并推送 GitHub，暂不启动产品功能开发。首次交付的提交与远端结果以实际 Git 回读为准。

公开仓库不能直接承接凭据、客户数据或私有经营资料。旧项目只读工程规范参考不等于源码、Runtime、插件或数据迁移；模型调用、安装、发布和其他机器操作保持各自授权边界。

### 建议优先确认的五个问题

1. 首轮真实任务选什么，谁提供数据和结果判断基准？建议优先采用已经用 Pi + skill 跑通的任务。
2. 首期产品载体是什么？先验证最小工作台，再确定浏览器、本地应用或桌面封装，不在此提前冻结。
3. 什么业务内容允许进入外部模型？谁可确认，如何检查工具输出与日志的数据出口？
4. 哪些上下文和经验必须先保存？建议从少量高频口径与一条可回访决策开始，不先追求全面建库。
5. 首轮需要复用哪些具体旧资产？开发流程的继承原则和人员分工已经确认；具体指标、skill、插件和样例仍需按实际内容评估，并核对公开与私有边界。

### 本稿的使用方式

本次先完成已授权的仓库与文档基线。后续用户明确启动功能任务时，选择一个真实任务形成最小需求与验收样例，再按工程规范推进。上述业务与产品问题不阻塞本次纯仓库初始化；首轮功能开发前补齐适用决定。暂不补齐全量模块清单、长期路线图或详细接口设计；遇到真实缺口再补充，并保留调整和删除设计的空间。
