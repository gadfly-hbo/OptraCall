# 交付契约：建议类型与载体分开

本Skill执行本次项目已有的范围、整体方法、资料及权限。用户无需额外填写技术模式表；下列声明由Agent根据真实约定放入待校内容，供有限结构检查使用。

| 维度 | 取值与实际要求 |
| --- | --- |
| 分析意图 | 直答、诊断/归因、正式汇报或项目综合。归因未证实就保留诊断与待核线索；项目综合引用准确子成果并处理分歧 |
| 建议类型 | `诊断建议`可给建议角色、试点、建议期限和待确认条件；`正式行动计划`须有真实确认的责任/时限/授权与必要资源/跟踪依据。缺确认先交诊断或标明草案，不写成已授权 |
| 交付载体 | `完整报告`按适用六段及完整依据交付；`聊天摘要`简述结论、关键依据/限制、下一步及准确成果入口。明确要求在聊天交全文时按约定交，不强制文件永远只是副本 |

## 检查声明

待校内容开头400字符内分别声明：

```text
交付形态：完整报告
建议类型：诊断建议
```

或使用`交付形态：聊天摘要`、`建议类型：正式行动计划`。单指标直答沿旧`输出形态：直答`。完整报告和对应摘要分别校验；多个交付或建议声明冲突时先修正声明，不能借此选择较松规则。旧报告没有这些新声明时仍沿旧六段/行动检查，旧历史不回填为新契约已采用。

适用六段的末段可用“诊断建议与跟踪指标”或“行动建议与跟踪指标”。诊断建议可以有待确认的人选/日期/资源；脚本不把待确认变成真实安排。正式计划每条使用可核字段：

```text
- 核对具体对象；责任人：真实已确认的承担人/角色；时限：已确认时间；授权依据：准确确认记录及范围；跟踪指标：真实衡量依据。
```

字段完整只说明呈现，不证明原话、授权、事实或效果真实。授权记录、准确报告版本、实际发生及成熟效果分别回原权威核查，Agent不能靠模板填词作经营取舍。

## 完整成果与摘要

成果为文件时，先按本次许可写入真实项目位置并读回，取得准确文件/版本入口，再在聊天摘要引用。保存失败或可能已写保持真实失败/UNKNOWN并查原结果，不换名重写掩盖未知。原报告及实质修订分别保留。

摘要不需要复制完整六段或正式计划全部字段；声明正式计划的摘要若未呈现行动段，检查器会提示未检查完整计划，必须另核准确原计划及确认。摘要中实际写出的行动段仍按其声明类型检查。摘要PASS不能当完整报告/计划通过。

## 保留的专业检查

数值、期间、分母、样本、相关/因果、缺失、异常及已选方法的检查沿SKILL及方法库完成。聊天简短不减少分析实际应做的检查，也不要求直答硬套全部不适用方法。资料不足可交有依据的阶段结果，明确尚缺对象/期间/字段及其影响。无异常或不适用项保留实际核查范围，不编造方法已运行。

`quality_check.py`只处理有限Markdown结构和文本规则、CSV确定性疑点；不证明内容专业正确、真实方法采用、文件存在、项目完成或经营有效。候选的模型激活/增益/误触发和专业正确性留待独立测评。
