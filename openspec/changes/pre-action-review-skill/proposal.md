# 行动前审查（Pre-Action Review）最小方案与验证设计

版本 v0.1 · 2026-11-09 · 仅方案文档，不编写 Skill、不跑测评、不调用真实 Provider。原 decision-review `bda5f47` 已按「无效」结案，历史记录与方法资产保留。

## 0. 定位与唯一验证目标

**定位**：在具体行动即将拍板或执行时，检查原 Agent 是否遗漏了足以改变该行动的证据缺口或授权缺口。

**唯一验证目标**：面对即将执行的行动提案，加载本 Skill 的 Agent 能发现原 Agent 遗漏的、且足以改变行动（放行→拦下、拦下→放行、调整范围）的缺口。

**不做**：不替代原分析、不重复完整决策审视、不做事后复盘、不替有权人审批。原 decision-review 的失败教训——轻量决策审视无法在常规任务中稳定产出可操作的差距——是本方案从"审视决策"收窄到"行动前最后检查"的直接原因。

## 1. 触发条件与交付

### 1.1 触发条件

| 条件 | 说明 |
| --- | --- |
| 已有具体行动提案 | 提案中有明确拟采取的行动（签约、投放、扩围、追加投入、上线、采购等） |
| 临近批准或执行 | 已到审议或执行环节（非早期探索） |
| 错判成本明显 | 至少满足一项：金额大、影响范围广、不可逆或难撤回、涉及外部合同 |

由 Agent 判断是否需要审查——满足上述条件的提案进入审查，不满足的沿用原流程。纯查数、常规比较和低风险的明确交办不触发。

### 1.2 最小输入

| 输入项 | 来源 | 缺项处理 |
| --- | --- | --- |
| 拟采取行动 | 提案正文 | 必需；缺则回问 |
| 目标或关键约束 | 提案或项目上下文 | 缺则按对行动的影响标注 |
| 现有依据 | 提案引用的证据、数据、测算 | 缺则列为待核项 |
| 批准状态与范围 | 提案或 Host 审批记录 | 缺则标注"授权未确认" |

优先使用当前已授权材料（项目 `020_clean`、Case 关联产物、审批记录）。不额外索要，不替用户补造。

### 1.3 默认输出

**结构只需便于用户采取下一步**，不套固定模板：

- **现在可以做什么**：一句话（含可推进范围边界）。
- **最可能改变行动的缺口**：哪条证据或授权缺口（如果有），为什么足以改变行动。
- **谁用什么材料核实**：责任人＋材料＋预期时间。
- **核实后如何调整**：不同核实结果对应的行动变化。

证据充分时：简短确认可推进的范围（一句话＋关键依据出处）。

能部分推进时：分开写清可做事项与待核事项。

## 2. 按产品四原则划清职责

| 原则 | 本方案中的落实 |
| --- | --- |
| **Host 管环境** | 沿用现有 Case 材料、权限、隔离与留痕。审批与执行由 Host 的权限机制和有权人负责——Skill 不审批、不拦截执行、不绕过权限 |
| **Agent 自主执行** | 自主选择审查重点（证据 vs 授权 vs 口径）、方法和工具。工具报错在授权范围内换法。证据仍不足时仅将受影响判断标待核，其余有依据的结论照常交付 |
| **优先复用 SDK** | 沿用现有 Pi 沙箱与可用工具（Python/计算器/read 等）。决策方法资产（TOC/TP、循证、DA）按需参考不强制加载。计算交给现有工具或计算专项 skill |
| **减少人类操作** | 优先从已授权材料自行核查。只有缺口会改变行动且无法从授权材料核实时，才向用户提一个聚焦问题（不连环追问） |

## 3. 验证设计（小规模真实提案）

### 3.1 提案选取

4 份脱敏真实提案，覆盖四种情形：

| # | 情形 | 设计意图 |
| --- | --- | --- |
| A | 关键证据缺口 | 提案依赖的关键数据或因果判断有缺口，原 Agent 可能遗漏——期望新 Skill 发现并拦下或条件化 |
| B | 授权范围缺口 | 提案超出已批准范围（如扩围、延长期限），原 Agent 可能未察觉——期望新 Skill 发现并标注须另行授权 |
| C | 证据充分且已批准 | 提案材料齐备、在批准范围内——期望新 Skill 简短确认可推进，不引入新误拦 |
| D | 低风险无需审查 | 常规明确交办，不满足触发条件——期望不加载 Skill，直接完成 |

### 3.2 事前准备

1. **脱敏**：去除真实业务标识、金额可保留相对关系、人名用角色替代。
2. **预写关键事实**：依据原材料和授权记录，由未参与 Skill 编写的审阅者独立写下——每份提案的可核验关键事实、应允许的行动、应拦下（或条件化）的行动。这些构成评分基准。
3. **冻结基准**：预写事实与评分标准在实验前冻结，不因实验结果回改。

### 3.3 实验流程

| 步骤 | 说明 |
| --- | --- |
| 1 | 同一模型、同一材料、同一工具环境 |
| 2 | 每份提案分两轮：原 Agent（不装新 Skill）处理一次 → 加载新 Skill 的 Agent 处理一次 |
| 3 | 匿名：审阅者不看两轮的标签，只看输出内容 |
| 4 | 对照冻结基准核验：是否发现关键缺口、是否允许了应允许的行动、是否拦下了应拦下的行动 |
| 5 | 记录指标：漏检数（应发现而未发现）、误拦数（不应拦而拦下）、用户追问次数、耗时 |

### 3.4 继续投入条件（判定标准）

**满足以下全部条件才建议继续开发**：

1. 提案 A（证据缺口）与提案 B（授权缺口）各出现**至少一项基线遗漏**（原 Agent 未发现但新 Skill 发现），且该发现**经核实会改变行动**。
2. 提案 C（已批准）**保留已获批范围内可做的动作**——新 Skill 不引入新的误拦。
3. 提案 D（低风险）**正常直办**——新 Skill 未被误触发。

**出现以下任一情况则建议不继续**：

- A/B 两例新 Skill 均未发现基线遗漏的缺口。
- C 例出现新的误拦（已获批动作被拦下）。
- D 例被误触发（加载了 Skill 导致流程变重）。

四例只用于判断是否值得继续开发，不作为产品验收。

### 3.5 审阅者要求

- 未参与 Skill 编写。
- 独立阅读原材料与审批记录，不受实验输出影响。
- 匿名对照两轮输出，逐项核对冻结基准。

## 4. 本方案不做的事

- 不编写或修改 Skill 文件。
- 不跑测评（v4 或其他）。
- 不调用真实 Provider。
- 不修改评估器或 Host 代码。
- 不处置原 decision-review 的历史记录与方法资产。

## 5. 后续步骤

用户确认方案后：

1. 准备 4 份脱敏提案与预写基准。
2. 获准后在指定环境执行实验。
3. 由独立审阅者出结果报告。
4. 据继续投入条件判定是否进入 Skill 编写阶段。
