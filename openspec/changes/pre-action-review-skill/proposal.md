# 行动前审查（Pre-Action Review）最小方案与验证设计

版本 v0.2 · 2026-11-09 · 仅方案文档，不编写 Skill、不跑测评、不调用真实 Provider。原 decision-review `bda5f47` 已按「无效」结案，历史记录、原评测记录与决策方法资产保留。

## 0. 定位与唯一验证目标

**定位**：在具体行动即将拍板或执行时，检查原 Agent 是否遗漏了足以改变该行动的证据缺口或授权缺口。

**唯一验证目标**：面对即将执行的行动提案，可发现本 Skill 的 Agent 能发现原 Agent 遗漏的、且足以改变行动（放行→拦下、拦下→放行、调整范围、调整时点、调整前提）的缺口。

**不做**：不替代原分析、不重复完整决策审视、不做事后复盘、不替有权人审批。原 decision-review 的失败教训——轻量决策审视无法在常规任务中稳定产出可操作的差距——是本方案从"审视决策"收窄到"行动前最后检查"的直接原因。

## 1. 触发条件与交付

### 1.1 触发条件

| 条件 | 说明 |
| --- | --- |
| 已有具体行动提案 | 提案中有明确拟采取的行动（签约、投放、扩围、追加投入、上线、采购等） |
| 临近批准或执行 | 已到审议或执行环节（非早期探索） |
| 错判后果明显 | 至少满足一项：金额大、影响范围广、不可逆或难撤回 |

涉及外部合同也按实际后果判断，不因"涉及合同"单独触发。普通任务缺少具体行动时继续原流程。由 Agent 判断是否需要审查；纯查数、常规比较和低风险的明确交办不触发。

**追问条件**：只有用户明确要求审查、关键缺项会改变行动、且从已授权材料无法自行核实时，才问一个聚焦问题。不连环追问。

### 1.2 最小输入

| 输入项 | 来源 | 缺项处理 |
| --- | --- | --- |
| 拟采取行动 | 提案正文 | 按 §1.1 追问规则处理 |
| 目标或关键约束 | 提案或项目上下文 | 缺则按对行动的影响标注 |
| 现有依据 | 提案引用的证据、数据、测算 | 缺则列为待核项 |
| 批准状态与范围 | 提案或 Host 审批记录 | 提案自述「已批准」须对照可核验的授权记录确认适用范围与条件 |

缺项一律按 §1.1 追问条件处理——只有用户明确要求审查、缺项会改变行动、且 Agent 无法从已授权材料自行核实时，才问一个聚焦问题。普通任务缺少具体行动时继续原流程。优先使用当前已授权材料（项目 `020_clean`、Case 关联产物、审批记录）。不额外索要，不替用户补造。

### 1.3 默认输出与建议用语

**结构只需便于用户采取下一步**，不套固定模板：

- **现在可以做什么**：一句话（含可推进范围边界）。
- **最可能改变行动的缺口**：哪条证据或授权缺口（如果有），为什么足以改变行动。
- **谁用什么材料核实**：责任人＋材料＋预期时间。
- **核实后如何调整**：不同核实结果对应的行动变化。

证据充分时：简短确认可推进的范围（一句话＋关键依据出处）。能部分推进时：分开写清可做事项与待核事项。

**建议用语**（三档，不代行审批）：
- **建议按授权范围推进**——材料齐备且在批准范围内
- **建议暂缓或附条件推进**——有缺口须核实或补授权后行动
- **建议调整范围**——提案超出已批准范围或须修改行动参数

## 2. 按产品四原则划清职责

| 原则 | 本方案中的落实 |
| --- | --- |
| **Host 管环境** | 沿用现有 Case 材料、权限、隔离与留痕。实际批准与执行由有权人和现有权限机制负责——Skill 不审批、不拦截执行、不绕过权限 |
| **Agent 自主执行** | 自主选择审查重点（证据 vs 授权 vs 口径）、方法和工具。工具报错在授权范围内换法。仍无法核实时只降级受影响的判断为待核，其余有依据的结论照常交付 |
| **优先复用 SDK** | 沿用当前 Pi 和现有工具（Python/计算器/read 等）。决策方法资产（TOC/TP、循证、DA）按需参考不强制加载。计算交给现有工具或计算专项。SDK 修改或升级须另行授权 |
| **减少人类操作** | 优先从已授权材料自行核查。只有缺口会改变行动且无法从授权材料核实时，才向用户提一个聚焦问题 |

**授权边界**：提案自述「已批准」须对照可核验的授权记录确认适用范围和条件；无法确认时只把受影响的动作标为「授权未确认」，已获批部分仍可建议推进。四案均在隔离环境内验证建议与交付，不触发真实业务操作。

## 3. 验证设计（小规模真实提案盲评）

### 3.1 提案选取

4 份脱敏真实提案，覆盖四种情形：

| # | 情形 | 设计意图 |
| --- | --- | --- |
| A | 关键证据缺口 | 提案依赖的关键数据或因果判断有缺口——期望新 Skill 发现并拦下或条件化 |
| B | 授权范围缺口 | 提案超出已批准范围——期望新 Skill 发现并标注须另行授权 |
| C | 证据充分且已批准 | 提案材料齐备、在批准范围内——期望新 Skill 简短确认可推进，不引入新误拦 |
| D | 低风险交办 | 常规明确交办，不满足触发条件——期望不加载 Skill，直接完成 |

### 3.2 先冻结再验证

后续获准后按以下顺序执行，**不可跳步**：

1. **准备四份脱敏真实提案与事前判据**。脱敏去除真实业务标识、金额保留相对关系、人名用角色替代。由未参与编写 Skill 的审阅者独立依据原材料和授权记录，逐案写下可核验的关键事实、应允许的行动、应拦下（或条件化）的行动、增量发现的认定标准。
2. **冻结全部输入与候选**。纳入冻结哈希清单的内容：四份脱敏原提案、各自的原行动建议、所用材料与授权记录、实验版 Skill 完整文件、运行配置（模型、工具、上下文）、逐案判据与评分标准。记录冻结哈希后不因实验结果回改。
3. **执行对照**（见 3.3）。执行前先核对哈希，确认两侧使用同一份冻结输入。

### 3.3 同起点盲评

| 要素 | 说明 |
| --- | --- |
| 会话 | 每案两侧各开一个**新会话**（不继承历史），使用相同请求文本、模型、上下文和工具环境 |
| 唯一差异 | 新 Skill 是否可用——候选侧只把实验版**注册为可发现的 Skill**，由 Agent 自主决定是否读取；基线侧不提供该 Skill |
| 共同输入 | 原提案作为两侧共同输入；基线是原 Agent 在同等条件下独立审查的结果 |
| 匿名 | 打乱两侧输出顺序，审阅者不看标签只看内容 |
| 盲评 | 由未参与编写 Skill 的审阅者按冻结判据逐案核验 |

**D 案触发判定**：候选侧 Agent 一旦**实际读取 Skill 正文**（含 read 与 shell 路径），即记为**误触发**并停止推进。目录列举与输出自述均不算读取证据。轨迹不足时标「证据不足」。耗时单列记录，不作为触发判据。

### 3.4 计入与不计入

**A、B 两案只计入同时满足以下三条件的发现**：
1. **基线遗漏**——原 Agent（基线侧）未发现；
2. **可追溯**——能追溯到原始证据或授权记录（不是推测）；
3. **改变行动**——具体改变行动范围、时点或前提（不是抽象风险提示）。

不计入：基线已发现的（非增量）、无法追溯的推测、不改变行动的泛风险提示。

### 3.5 继续投入与停止条件

**建议进入下一步小规模验证——须同时满足以下全部**：

1. A（证据缺口）与 B（授权缺口）**各有至少一项**经核实且会改变行动的**增量发现**。
2. C（已批准）**保留已获批范围内可做的动作**，未引入新误拦。
3. D（低风险）**正常直办**，且**内容读取轨迹确认未触发**。
4. 四案均**无新增错误放行或误拦**。

**部分结果**：
- A、B **仅一例有增量**发现：保留单例证据，**暂缓投入**——不继续开发但保留证据供后续评估。
- A、B **两例均无增量**：按「未观察到增益」收尾。

**停止条件**（任一即停止推进）：
- 任何一例出现**新增错误放行**（应拦下而建议推进）。
- 任何一例出现**新增误拦**（应允许而建议暂缓）。
- D 案**候选侧实际读取了 Skill 正文**——即误触发（见 §3.3 判定规则）。

**证据不足处理**：运行或证据不完整时标「证据不足」，保留原记录，不据此判定通过或不通过。

四案只回答**是否值得继续投入**，不作为产品验收。

### 3.6 审阅者要求

- 未参与 Skill 编写。
- 事前独立阅读原材料与审批记录，逐案写下判据（在实验前冻结）。
- 匿名对照两侧输出（打乱顺序），逐项核对冻结判据。
- 保留漏检、误拦、用户追问次数与耗时。

## 4. 本方案不做的事

- 不编写或修改 Skill 文件。
- 不跑测评（v4 或其他）。
- 不调用真实 Provider。
- 不修改评估器或 Host 代码。
- 不处置原 decision-review 的「无效」结案、原评测记录或方法资产。

## 5. 后续步骤

用户确认方案后：

1. 准备 4 份脱敏提案与事前判据（审阅者独立完成）。
2. 冻结最小实验版 Skill 及运行配置。
3. 获准后执行同起点盲评。
4. 由独立审阅者出结果报告。
5. 按继续投入与停止条件判定是否进入下一阶段。
