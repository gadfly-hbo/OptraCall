# 企业业务资料：实施结构与兼容决策包

2026-10-31 · **五项 A 已整体确认**。用户明确回复“整体确认，按五项 A 继续实施”。用户此前已批准功能 spec、UI 和开始实施；五项均已实施，验证证据见 [result.md](result.md)；本文只补 spec「结构与兼容合同的停止线」留下的五项，不重开产品方向讨论。分类页真实入口调整可独立实施。

## 固定原则与证据

- Host 保存原文、来源身份、版本和实际提供记录；Agent 自主理解、检索、读资料、选字段、计算和表达。未关联 Case、零勾选也能读取已授权公共资料。
- 复用 Interface v1、`project-tasks` 域与现有 projectId/taskId。资料维护不创建 Agent、会话库或运行队列。
- `src/host/case-types.ts` 的 CaseArtifactRecord 只表示项目路径；企业公共资料不能伪装成这种记录。
- `src/host/case-store.ts` 严格校验 SQLite schema v1，新增表也会破坏旧版读取。因此推荐不迁移该数据库。
- `src/agent/project-runtime.ts` 的 ProvidedContextInput 只有 RAP/Case；`project-session.ts` 还需显式接入新可选字段。`project-history.ts` 可读取 v1 的可选子字段，不必改为 v2 或回写旧历史。
- SAP 的不可变发布物与轻索引可以借鉴保存方式；不能把企业原文塞入 SAP/RAP 0.2 的严格字段。

## 第 1 项：公共资料的身份、原文与修订

**我的建议 A：** 在现有 Host `dataRoot` 下新增独立 `enterprise-business-materials/`，使用版本化 JSON 轻索引、普通 UTF-8 正文和显式上传的原文件。默认仍随 Host 数据根，测试全部使用隔离根。单 Host 写入、原子替换，不引入数据库或搜索服务。

**原因：** 可以用现有原生 read/grep/find 直接发现正文；不改旧项目、会话或 SAP/RAP。修订独立保存，旧引用不会随编辑漂移。

**替代 B：** 给现有 Case SQLite 增表并升级版本。代价是旧版拒读且公共资料不应归 Case 所有，故不推荐。

已确认的逻辑合同（字段名与下列含义一一对应，不把 Demo 对象照搬成生产协议）：

| 对象／字段组 | 粒度、格式及含义 |
| --- | --- |
| 库身份 | `schemaVersion: 1`；`storeId` 为首次初始化生成并保留的 UUID，防止不同数据根的同名资料被误认 |
| 资料身份 | `materialId` 为 Host 生成 UUID；一个资料有一个可编辑工作稿、零到多个不可变修订；标题不是身份 |
| 工作稿 | 标题必需；正文或有效来源文件至少其一才可启用。类别、来源说明、维护人、适用范围、生效时间说明均为可选用户文本；正文仅因已有有效来源文件而为空时明确标「正文未取得」。未知用空值并在 UI 标未知，不猜测日期、事实或确认情况 |
| 修订 | `revisionId` 为 UUID，另有资料内递增展示序号；保存启用时固定标题、类别、正文、上述来源字段、创建时间与正文 SHA-256，以及当时来源文件的身份、字节数、SHA-256 和位置；序号不表达业务优先级 |
| 来源文件 | 可选；只能由用户显式上传的字节进入新根，记录 Host 文件身份、原名、字节数、SHA-256、保存时间。文件只追加不覆盖，工作稿换文件不改变旧修订原件。UTF-8 文本可明确导入正文；其他格式仅登记原件并标「正文未取得」，不伪造解析成功 |
| 可用状态 | 当前启用修订可为空；显式启用新修订更新当前指针。启用资料允许用户显式选择所有保留修订，不只最新版。停用阻止新选择，不删除历史；可重新启用一个明确修订 |
| 技术时间 | Host ISO 8601 时间；与用户填写的业务生效时间说明分开。编辑工作稿不改变已启用修订 |

受控写入口为 Host 资料 API；浏览器不能提交任意磁盘源路径或决定存储路径。请求严格校验对象身份、工作稿版本和路径；并发旧编辑返回冲突，不覆盖新稿。文件写入先落独立新文件，再原子更新索引；失败不把未完整保存的修订设为启用。未知 schema／损坏记录保留并报错，不重置。

首期已确认技术上限：正文 UTF-8 1 MiB、每个显式上传文件 10 MiB；超限给出可读错误，不裁剪后冒称全文。限制用于保存与请求大小，不判断业务前提是否充分。

## 第 2 项：Case 引用与本案补充

**我的建议 A：** 公共资料根内新增按 CaseId 管理的版本化 sidecar；不改 Case SQLite、项目 JSON schema 或原有 Artifact 类型。保存前 Host 核对 Case 存在和当前版本。

**原因：** 公共资料是跨项目资源，关联归 Case 所有；sidecar 可以原位增量接入，同时让旧版继续读取原 Case 数据。

**替代 B：** 公共资料复制到每个项目再伪装为项目文件。会产生多份权威和版本漂移，故不推荐。真正的本案文件继续走现有项目文件引用。

| 对象／字段组 | 关系与生命周期 |
| --- | --- |
| Case 关联文档 | schema 1、新资料库 storeId、现有 CaseStore 的 caseStoreId、caseId、自身递增 revision、更新时间；读取时同时核对两库身份。不存在表示「尚无本增量记录」，不是损坏或需要迁移；Case 库更换后身份不匹配时报错，不自动重新绑定 |
| 公共引用列表 | 零到多个 `{storeId, materialId, revisionId}`；同一明确修订不重复。只接受已存在、可供新选择的修订；原引用停用后仍保留且可读 |
| 本案短说明 | 零到多个有 UUID 的补充项：正文、来源、适用范围、确认情况说明、创建／更新时间。后三者允许未知；文本不形成自动裁决字段 |
| 项目特殊文件 | 继续使用现有 Case Artifact，只能来自该 Case 已关联项目；新增选择界面优先展示 `020_clean`，不建立任意路径引用 |
| 取消关联 | 从当前候选列表移除，不删除公共原文、项目文件或过去消息已固定的来源 |
| 历史时点 | 消息准备时捕获 Case 版本、sidecar 版本、所选公共修订与本案补充快照；之后修改不追改已发送内容 |

本案补充不自动发布为公共资料。共享项目的文件仍共享，不声称 Case 文件物理隔离。Case 状态和项目运行准入沿用现有规则；sidecar 不引入新的分析阶段。

## 第 3 项：任务选择与实际提供回执

**我的建议 A：** 任务材料选择保留在前端按 projectId/taskId 区分的状态中；只在显式发送时提交明确资料修订。扩展现有消息请求和 `ProvidedContextInput` 的**可选**企业资料字段，worker 在现有 `optracall.run` custom entry 保存 v1 提供回执；不另建消息库。

**原因：** 选择和一次请求绑定，历史由原生会话保存；旧请求没有新字段时仍走原去重、ACK 和未知结果语义。刷新后无需虚构旧选择已经生效。

**替代 B：** 给项目任务 schema 增加长期默认资料集合。首期没有这个必要，会增加迁移与隐式随每轮发送的风险，故暂缓。

可选回执字段组明确包含：库／资料／修订身份、资料标题、正文 SHA-256、原文位置、实际提供时间、实际正文范围，以及「仅来源定位／全文／片段」的提供种类。记录实际交付的片段文本或可回读的不可变修订与精确范围；目录指针单列，不能冒称全文。

发送前预览准确显示正文大小与提供范围。用户显式选择全文、文本范围或仅来源定位；片段使用 JavaScript UTF-16 半开区间 `[start, end)`，以不可变修订正文为基准，界面同时展示实际片段。一次主动附带正文总量建议不超过 20,000 个 UTF-16 字符：全文或所选范围超限准确报错，不能静默改成片段；可调整范围、减少选择或改为仅来源定位。用户原问题和普通分析入口仍可发送，不以长资料构成业务门槛。Host 不生成语义摘要、不挑选业务重点；回执保存实际区间与内容身份，可精确复现。

新请求指纹纳入排序确定的资料修订、范围、正文指纹及本案快照；同 requestId 内容变化返回冲突。没有新材料的 legacy 请求维持原逻辑。请求取消、配置变化、迟到结果仍用公共生命周期和 context.isCurrent，不重放或创建第二套 busy Map。

旧历史没有新字段显示「未记录／未知」，不回填当前修订。未来未知可选字段不导致旧消息丢失；无法读取的具体来源单独报缺失。

## 第 4 项：自主发现、全文读取与读取证据

**我的建议 A：** Host 维护明确标为业务资料的可读目录索引和不可变正文文件。普通项目任务从现有环境／每轮资源位置提示获得目录；Agent 使用现有 read/grep/find/bash 自主检索。每轮目录位置可见与材料正文主动附带分别记载。

**原因：** 复用普通分析工具，未勾选或没有 Case 也能发现资料；不新增模型、检索 Agent、固定方法匹配或 Host 分析循环。活会话可以在下一次显式消息看到目录位置，不隐式重建或重发。

**替代 B：** 只给勾选文件临时读取白名单。直接违背已确认自主性要求，不采用。

索引展示身份、标题、类别、范围、可用修订及正文位置，不带业务优先级或自动可信评分。停用资料从新选择／当前可用索引移除，但旧明确修订仍可回读。正文与原文件的 UI 下载由 Host 验证身份和路径；客户端不能任意读取 Host 文件。

资料内容是带来源的输入材料，不升格为系统指令。普通分析完整原生工具和用户安装资源保持原规则；该目录不注入 `fixed-draft` 附属出稿资源，不扩大冷读核算材料。

原生工具日志可观察到的读取保留在 SDK 历史；若只能证明调用或拿到片段，则如实显示这一层，**不新增「全部读取已审计」承诺**。读取不等于理解或采用；Agent 引用和用户显式采用报告仍按现有独立语义展示。公共资料也不冒充 SAP 初始化版本已热切换。

## 第 5 项：保留、兼容与回退

**我的建议 A：** 保留全部本增量明确保存的公共原文、修订、来源文件和必要引用；首期无物理删除／自动清理。**不自动复制项目数据集**，也不承诺历史完整复算。

**原因：** 满足修订回读且不扩大数据保留范围、磁盘副作用或访问权限。项目数据是否另存仍由用户和 Agent 在当前任务中按原授权决定。

**替代 B：** 每次发送复制全部项目输入。会扩大保留和磁盘使用，且本次未要求完整审计备份，故不采用。

只新增本增量根；启动不迁移／回写旧 Case SQLite、项目 JSON、RAP/SAP 发布物或 SDK 历史。旧版本源码仍可读原对象，但不会展示新库和 sidecar；回退保留新增根，重新使用兼容代码后可恢复新功能。不用旧数据副本覆盖现有数据，不接管活 worker。

受影响既有来源继续记录实际身份；文件已变、旧字节不在或来源原本未知时明确说明，不能拿最新版替代。测试只在隔离合成根创建资料，保留当前真实项目、任务、会话、父链、文件和旧 FAIL/UNKNOWN。
