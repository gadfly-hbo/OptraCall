## 要解决什么

现在Agent准确读到一条人工保留经验时，往往需要再读其来源，才知道来源候选后来被纠正或排除。最小增量是：读取这条经验时，把直接来源候选的当前治理提醒一并交付，让Agent自主判断适用性；经验正文、版本和自身治理仍独立。

## 最小范围与原能力复用

1. 仅增强准确 `retained + kind=experience + part=content` 的读口，包括准确片段／正文续页，以及走同一实现的显式选材 `prepare`。没有直接候选来源时沿原输出；knowledge、目录find、source/corrections和裸Enterprise来源不扩展。来源只检查准确经验决定的直接agent-candidate引用，不递归来源树、不猜同名或最新对象。
2. `personal-context-reader` 已拿到准确decision/sourceRefs；`PersonalRetentionStore.readItem` 已只读准确正文与hash，不展开来源，无需新Store模式。复用 `AgentCandidateControls.getRecords()`（原2MiB限额）的一份只读快照和 `candidateControlState`。不调用 candidateReader/sourceReader 为提醒读取native、候选标题、正文或摘要，不新增Runtime／记忆框架／后台模型／事务或重试引擎。
3. 新来源治理附注与经验自身 `governance`、正文及corrections分开。Host核准确引用、权限、预算和状态；Agent自主判断经验是否继续可用。来源被排除不自动改写、归档或使经验级联失效，也不自行解除排除。

## 返回什么

- 未排除且治理可核：原sourceIndex、治理状态、最新人工纠正的允许片段；标明来源、注记操作身份、片段／截短，不冒充经验原文。
- 已排除：仅排除状态和是否存在纠正／其操作身份，不带候选标题、正文、摘要或纠正自由文本（自由文本可能引用被排除正文）。
- 治理账无记录：明确“无已记录的排除／纠正控制”；不等于候选存在、正文可读、事实可靠。治理账损坏／不可读、准确occurrence对应hash冲突：UNKNOWN，不回退成“未排除”。
- 所有附注明确“本次未核来源正文可用性”；治理可核与正文可用性是两件事。
- 附注进入模型可见content，并带有界的可选receipt元信息。准确经验target／版本／body hash和UTF-16正文范围不变；新增字段不冒充经验自身治理。旧receipt缺字段保留未提供／UNKNOWN，不查今天状态回填当时交付。

## 已确认预算与续页

- 每次read／一次prepare operation读取一份治理账快照，最多检查 **8个不同准确候选ref**（含expected hash）；重复ref复用状态。全份实际附注最多 **4096 UTF-16**，包含状态、索引、纠正片段及截短说明，并仍受原32,768文字／256KiB传输上限约束。这些预算随v0.1方案已获用户确认。
- 来源数量没有小上限；超出的引用只输出聚合“未检查数量＋UNKNOWN”，数量按原引用条数计，重复准确ref复用核对结果，不逐项输出无界数组。来源身份复用本次准确经验target＋有界代表sourceIndex，不逐项复制可能很长的完整ExactCandidateRef，不创建反向索引。
- prepare按原选择顺序共享8-ref／4Ki额度；先为所有符合范围的经验预留最短关键状态／未核提示，再把余量分给纠正片段。后项也明确未核／partial，不暗示全来源已核，不能让首项注记吃完预算后漏掉后项提醒。
- 先缩短附注而非丢失关键排除／纠正状态。普通read在原预算内沿既有continuation分片，正文原件、精确范围与后续字节不丢。显式固定选材不得静默截正文或省略材料。
- **精确满载边界**：不能承诺新增提醒绝不导致原本满载的选材超限。若缩至最短关键提醒后仍放不下用户的固定选材，沿现有超限流程明确失败并保留草稿／选择；不扩大预算、不伪称已附提醒。此边界随本方案一并确认，不以“正文优先”掩盖不可同时满足的容量要求。
- 正文续页签名加入实际已检查的准确来源、相关治理／注记身份及实际片段；相关变化用原409 continuation_changed拒绝旧续页，无关候选变化不失效。相同正文的独立新read重新查当前快照，不续旧状态；不建持久快照库，不宣称跨Store原子。
