## 1. 目标与本轮授权

**实施授权更新：** 用户已通过本spec及UI，要求开始A、保留原看板全部功能、项目／会话／文件并完成检查与非作者复核；随后整体确认[结构决定包](structure-decisions.md)七项A。下列原型阶段“暂不开发／待评审”保留为历史范围记录；现可在已确认结构内实施与验证A，B/C仍后置。不自动Git交付／部署／切运行服务或操作MacBook。

用户已确认[完整方案](../../../docs/workflow-closure-and-analysis-reliability-proposal.md)，当前仅细化A“补齐第7步反馈闭环”，输出本spec和[可点击UI Demo](../../../docs/prototypes/decision-feedback-loop-ui-demo.html)，暂不开发。B“分析结论专业可靠性”、C“独立核算覆盖及检错”均后置，不在本期顺带实施。

目标：在现有决策看板中保存反馈修订，明确选择来源与Case，生成原项目中的普通复盘任务草稿；用户显式发送后由Agent自主复盘，再由用户决定形成新需求或保存Case材料，并能说明下一轮实际取得了什么。

**最小闭环：报告建议 → 用户采纳／人工行动 → 人工反馈 → 自主复盘 → 用户选择进入下一轮需求／分析。** 不要求每次都有Case或RAP，不自动操作业务系统，不根据任务完成或评分推断经营有效。

本轮允许文件：本变更`spec.md`、`result.md`，独立HTML Demo，以及原方案确认状态／链接的小幅更新。原型只用合成数据、浏览器内存，不访问API、真实文件、模型、凭据或业务存储；不使用localStorage／IndexedDB，不修改产品`src/`、`extensions/`、测试、依赖／锁文件、SQLite、JSONL或项目目录；不提交、推送、合并、部署、切运行服务或操作其他设备。现有项目、任务、会话、文件和失败证据保留。

## 5. 交互流程与界面

### UI00 原型披露、外壳和范围

独立HTML，保持OptraCall中性白灰、紫色主操作、原侧栏四大类及“分析｜决策”工作区。根目录无`DESIGN.md`，本次采用中央SaaS UI标准作补充，既有产品样式优先；不趁此改版或新增设计系统文件。

页面持续展示“UI Demo · 合成资料 · 仅本页内存，刷新重置”。新建、保存、发送、回执和后续结果均明示模拟；预置回复不得显示成真实模型推理或经营成效。没有API／网络依赖、业务文件读取、数据库、浏览器持久存储、模型或真正保存／恢复。原型不要求启动产品Host或读取用户项目。

### UI01 决策看板上的行动和反馈

保留三泳道“判断建议／行动跟进／结果复盘”，本期增量从任务卡片进入。主要动作是“基于此反馈复盘”；“更新反馈”“反馈历史”作为次要动作，不把功能挂到侧栏树。

任务卡区分负责人／状态与用户回录；结果未提供时显示“效果未知”，仍可提出复盘问题。资料性质“实际回录／合成演练／未标明”描述来源，不表示核实。原有评分保持反馈字段含义，UI不据此标“已验证”。

### UI02 更新反馈与历史

沿用现有反馈内容的业务含义，增加已保存版本列表／详情；效果判断、来源性质、执行记录和未填写评分按原型表达为本期新增／放宽的界面语义，确切持久表示和旧数据兼容在结构包中确认，不能假称旧boolean和必填score已支持全部未知状态。明确的“是否按建议执行”继续是／否；尚不能回答时可不保存反馈而以“未取得反馈”直接追问，不默认为false或补造修订。其他观察、指标和评分允许未提供，不能默认为零／无效／成功。

保存按钮说明“保存新修订”；关闭／取消保留未提交编辑，直到用户明确放弃或保存。用户可返回再编辑。不要将未提交内容列为版本。

已知旧反馈只展示首个已知版本与原有可得时间；无法得知谁确认／此前如何变化时直接说明。查看旧版不改变当前最新版本。选择某旧版用于复盘后，有新版仅提示差异，不自动切换。

### UI03 交接准备与Case选择

使用独立宽内容页承载较多材料，避免把复杂流程塞进窄对话框。顶部保留“返回决策看板”和问题／草稿，不用强制多步分析进度条。

展示来源任务、所选反馈版本；问题可编辑。Case默认“无Case”，候选仅限与来源项目已关联且用户可用的Case；说明本次选哪个，不修改建议或任务的全局归属。已结束／不可用Case说明原因并提供现有重开／返回路径；本原型仅模拟边界，不真实重开。

观察对象／期间、资料性质、实际执行说明和仍未知因素可补充，均不要求凑齐。不能因为没有效果值、反馈或Case阻止创建普通任务；项目归属、正常任务标题和真实资源权限按原合同核验。

### UI04 本轮材料预览和变化

列表中勾选反馈正文、原建议／报告、复盘资料及可用来源。每项可展开本次可读内容，标注“全文／片段范围／仅引用／未取得”。业务页面优先显示可懂的版本与时间，路径／SHA／技术回执折叠查看。

原报告与抽取身份不一致时，显示“原稿已变化”；可查看已有固定抽取片段及其范围，不将当前报告冒充原稿。附件缺失／不可读时保留提示，用户可取消、仅引用或明确按受限材料继续。仅引用不称已固定全文。所选可变正文变化后重新预览，原输入不清空。

按钮“创建复盘草稿”说明不会发送模型。成功后给目标任务链接；处理中防止重复点击；失败／未知有原意图查询入口，不用成功toast掩盖未完成的部分。原型用预置场景模拟这些状态，不接API。

### UI05 普通复盘任务

进入原项目的新任务，预填可编辑问题和明确选择的材料；不追加到原作者会话。创建任务、查看材料和切换页面不发送消息。用户点击原发送动作才启动普通分析。

取消所有主动材料仍可发送普通问题，来源关联可以保留为历史导航，但不能把已取消正文重新注入。会话中查看本轮提供内容；Agent读取和采用只能按可观察证据／声明分别展示。

原型的发送动作写“模拟发送（不调用模型）”，结果显式标“预置复盘示例”，不假装保存到060或真实工具已执行。预置示例应保留未知、来源条件和方法自主性，而不是展示Host自动计算／打分。

### UI06 历史回读

在已模拟发送的请求中可查看当时反馈版本／正文、所选Case、正文范围和仅引用附件。修改看板当前反馈或返回其他视图不改变此回执。恢复演示通过浏览器本页内存返回／切换表达，**不宣称刷新后真实持久化**。

普通任务、反馈修订、业务采用和效果验证为不同状态；原模型／项目配置不在原型中真实设置。Demo支持“重置本页示例”，只重置自身合成内存。

### UI07 从复盘到新需求

用户选择一份明确的复盘回复／报告，点击“基于复盘梳理新需求”，进入需求草稿视图。标题／背景可编辑，提供的复盘正文／片段可查看；仅路径不能支持需求Agent理解文件内容，未提供全文要显示范围。

新草稿保持未确认、未发布；生成提案、采纳、确认及发布仍为原需求操作，不在本期自动串联。Demo最多模拟草稿创建和来源展示，不冒称RAP已发布或模型已梳理。

### UI08 保存Case材料，随后显式选用

从选定复盘报告打开短操作：选Case，分别选择“关联复盘报告／采用副本”或“编辑当前判断”；必要时提供来源和适用条件。使用各自现有显式操作，不把一个按钮做成全部自动采纳。当前判断编辑预览原值和新值，用户确认后才更新。

Case历史可保留追加说明，但只有当前字段和明确选择的资料按现有装配规则进入后续任务。UI明确“关联完成不代表下次已提供／已读”。报告／采用副本变化仍要识别，不能因为采用过就宣称不可变或效果已核实。

### UI09 下一轮经验使用

从原Case／项目继续，选择相应复盘资料，查看本轮选择／来源预览后发送。原型展示预置的适用条件对照及模拟回执；不同条件例子应允许“旧经验不足以支持当前结论”。不自动广播经验、不发布企业资料、不改变SAP或旧RAP。

### UI10 可访问性与响应式

亮／暗主题一致；桌面使用现有侧栏和内容栏，390px窄屏导航可收起、表单单列、工具栏换行、正文无横向溢出。按钮有可访问名称和可见焦点；原生表单标签／错误关联，状态用文字而非仅颜色。对话框支持初始焦点、Tab约束、Escape、关闭后返回触发控件；大流程采用页面而非多层模态。

| 对象／关系 | 推荐语义及约束 |
| --- | --- |
| 已保存反馈修订 | 权威仍在原看板业务域。一个原Board任务对应一组已保存修订，当前视图取最新；每次显式保存有可定位身份、提交意图、来源和可得时间。旧修订追加保留，旧无历史记录只给首个已知起点。 |
| 原建议／报告身份 | 沿用原projectId、itemId、reportId、extractionId和已知source fingerprint。不能把当前目录观察覆盖原抽取来源，也不把执行回录追记成最初分析的事前事实。 |
| 一次反馈交接 | 绑定来源项目／Board任务及明确选择的反馈修订；尚无反馈时修订可空，记录“未取得反馈”，不凭空创建修订。所选Case及版本可空，保存这一次用户问题、选材、身份及范围；同反馈可有多个显式交接，不形成全局唯一Case归属。 |
| 实际交付材料 | 正文或明确片段在交接／发送记录中保留历史，项目020普通资料供后续自主读取；只保留附件引用时如实标记。二者不构成两个反馈权威，不把普通文件宣称不可变。 |
| 目标任务／需求 | 沿用原projectId＋taskId或原需求instanceId；源关联不代替真实目标owner，不新建复盘Runtime或第二套会话生命周期。 |
| 操作意图／部分成功 | 创建任务、保存资料、关联Case和创建需求可能跨既有业务存储；结果可读、去重／冲突可验证，未知不自动重放。部分成功逐项保留，不删目标／文件“回滚”。具体恢复边界在实施合同中明确。 |
| Case写入 | 用原Case revision和显式选择核对冲突，产物关联／采用与当前判断更新分开；已结束先重开、归档只读；不改共享项目的其他Case。 |
| 保留与兼容 | 不重写旧JSONL／sessionFile／父链或历史发布物；新增材料和修订不自动清理。回退只能用兼容代码读取，不用旧备份覆盖本期写入；无法读取的新记录保留并明确提示。 |

待该决定包明确：物理落点、身份／修订键、事务与唯一性、只读历史保留、正文和附件的大小／解码／截取规则、来源变化冲突、业务操作幂等、旧数据兼容及跨存储部分成功恢复。均不影响本轮spec／Demo完成；未确认前不提前建表、实现API或迁移。

## 8. 评审要点与大白话

评审主要看：反馈更新会不会丢历史；用户能否清楚选哪个Case和哪版材料；创建草稿是否误触发模型；能否从复盘回到下一轮；过去没拿到的资料是否仍被如实标未知；是否保持普通任务自由提问。

大白话：**先把“这次做了什么、反馈哪一版、下次带什么继续问”接起来。Host负责材料和记录，Agent自己复盘；用户决定用不用，不强迫每次填完效果表，也不自动替用户做经营动作。**
