## 3. 内容与来源的最少合同（BC01–BC05）

### BC01 范围与方法输入

Agent 根据自然语言范围和获准资料自主安排盘点，不按六问或八步强制串行。用户不必填36格、逐条归类、批准每个坐标例外、维护图或先完成资料清单。普通动作优先沿已有企业／建设项目，只有实质企业归属或资料授权不明时才澄清。

方法输入保留准确 `SourceRef`、版本及来源可提供的 hash；没有 hash 时明确未提供，不虚构。原稿可保留在学习目录，实际任务沿已有获准项目资料／企业资料或 SAP 方法路径获得可读版本；需要受管快照时保存版本对应，不能把副本当另一可编辑权威，不自动搬走原稿、访问个人绝对路径或把私有资料提交公开仓库。仅在 spec 写一个 MacBook 路径不算已供给。

方法版本不可读、已失权或实际未读取时如实显示；Agent 可说明限制并沿其他获准资料继续，不能声明已经按该方法完成盘点。

### BC02 报告载体与兼容

最小候选为既有 **business 类型 Studio 源资产**的 body，识别字段使用 `reportProfile: "studio-coverage/1"`，而非 `contentProfile`。它是盘点派生报告，不是第四类业务定义或新规则／事实库。原资产 revision／hash／sources／dependencies／候选和正式机制继续作为保存、版本及供给权威。

`studio-foundation/1`、`/2`、SAP 0.2、SourceRef、现有七类资产不加 latticeCell；不向旧严格白名单悄悄塞字段。没有本格式的旧正文按原方式保存、读和显示。旧版本保留；新盘点保存新 revision，不覆盖已保存的报告或原生使用依据。

报告最少逻辑字段如下；这是未来实施的待审合同，本轮不实现解析器：

| 字段 | 约束及语义 |
| --- | --- |
| `reportProfile` | 精确 `studio-coverage/1`，不与原 foundation profile 混用 |
| `scope` | 企业／体系／主题、用途、纳入／排除范围与适用期间；企业必须与原体系归属一致，不用报告创建归属 |
| `methodRefs` | 本次实际采用的方法准确引用；可以为空并说明，不能伪造已读 |
| `basisRefs` | 本次据以盘点的准确原来源；内容内部 itemId／metricName／片段定位单列，不篡改 SourceRef.locator 含义 |
| `focusCells` | 0–36 个关注格；默认可用14格，允许调整，关注不是必须填写；未纳入与不适用不同 |
| `observations` | 每项有局部稳定 id、对象／范围／说明、0或多个格注记及理由、准确证据与资料判断；不是复制业务定义或公式 |
| `questions` | 观察项引用、缺资料／待核矛盾／用途依赖／业务决定、影响与所需证据；可关联原 workItemId，不含 issue／发布操作指令 |
| `limitations` | 未调查、无法读取、未核与方法边界；空白不能被解释成企业不存在相应内容 |

本候选上限为原 body 上限以内且最多256KiB，256观察项、128个去重来源引用、128问题；每项最多36格。解析与原引用检查须有界，无脚本、HTML执行或任意路径读取。未知报告版本仅显示原文及“不支持结构视图”；损坏显式报告给出具体格式问题，不伪造覆盖结论，不影响其他资产和普通分析。

最少字段类型固定如下：`scope`含原enterpriseId／systemId／topicId、purpose文本、included／excluded文本数组及可选validFrom／validTo；未知范围放limitations，不自造企业身份。`focusCells`是`{row:1…6,column:六列枚举}`数组。观察项含`id`、`description`、`subjectLabel`、`annotations:[{cell,reason}]`、`evidenceRefs`和`evidenceStatus`（not-reviewed／located／partial／missing／not-applicable）；可选`sourceSelection:{sourceRef,itemId?,metricName?,fragmentLocator?}`作内容内定位，不能替换原authority locator；not-applicable必须有reason。问题项含`id`、`observationIds`、`kind`（missing／possible-conflict／dependency／business-decision）、`detail`、`impact`、`evidenceRefs`及可选原workItemId。id在本报告内唯一，引用的观察项必须存在；不允许HTML、代码或执行动作作为结构字段。

同格的多个观察项和问题可并行，不把一个观察项的资料状态当作整格单态。资料类型不能替代准确SourceRef；所有method／basis／evidence／sourceSelection引用沿原精确读者核定，且须纳入原asset sources／dependencies的引用闭包，不能只藏在body绕过发布。复用现有内嵌引用提取与必需依赖校验接缝，缺失时给Agent可修正错误，不要求人重复填引用。来源不提供hash时保留原版本身份与未知hash，不能用虚构hash过检。

### BC03 多视角注记及范围判断

格编码 row=1…6，column=What／How／Where／Who／When／Why。14格（R1/R2全列＋R3 What/Why）只是首批默认视图，不是唯一合法枚举或发布门槛。业务对象、身份、责任、事件、时间、公式按其实际语义判断，不能用 item kind 强制唯一落格；复合材料按片段或断言可关联多格、保留理由，也允许未标注。

不管理技术部署不妨碍引用实际表／字段或运行记录的证据。第5行不笼统当作真实实例，第6行可关联实例证据；本轮不建设企业技术架构管理模块或运行数字孪生。

### BC04 状态保持独立

每个视角可同时存在：已见资料、未调查／未见资料、待补、待核矛盾、不适用（必须有范围理由），以及多个候选／正式／历史来源。它们不是互斥的单一五态。

候选／正式身份、四维作者声明（定义、映射、可计算、实际使用）与原实际使用／独立核验回执分别显示，不由格坐标或数量相互推导。报告里复述状态须标为原准确版本上的作者记录／实际证据；它不批准定义、不赋予正式资格，也不把正式转换为业务通过。

### BC05 版本及失效提示

报告在原精确修订中冻结所用 refs 和观察。来源有新版本、资格撤回或准确 ref/hash 失配时，当前视图提示依据变化／不可当前供给，保留旧报告与其当时依据；由 Agent 另存新修订，不在后台重写。单纯工作项进度或体系无关修改不使所有报告失效；如记 systemRevision 仅作上下文，不将保存报告自身导致的 revision 变化误判为过期。

正文、投影和历史的访问始终受原权限与来源资格约束。过期历史不是当前适用证明；不可读内容不能从缓存或旧投影越权泄露。

不另存“当前覆盖报告”全局指针：在当前企业／体系的原资产集合中发现可读报告，按准确资产与修订打开；多个范围的报告并列，不推断某一份代表整个企业，也不跨报告累加完成率。建设者沿原workspace读取获准候选，普通任务沿原正式来源读取。投影只来自该次实际读取的准确body；前端不得自行读文件、拼路径或跨owner取另一份源稿。

## 4. 核查、发布与实际使用（BC06–BC09）

### BC06 两类一致性核查

- 纵向：按本次用途核“参考与企业依据 → 目标定义／规则／指标 → 必需映射或计算条件 → 样本与实际使用证据”能否接上。定义参考用途无需一律有 Binding；指标计算／规则执行按各自已有依赖闭合，不改原门禁。
- 横向：核对象、过程、职责、时间与规则的业务相容，以及跨路线准确身份引用；同名不自动判同物，不同 id 不直接判矛盾。Host 复用原结构／引用检查，Agent 核语义和证据。
- 同对象、范围、期间和含义重叠而矛盾才列待核；地区／渠道／历史版本可合法并存。先沿原 question/gap/review 记录依据与影响。标格、报告生成或“发现可能矛盾”均不得调用 `mark-issue`、撤回正式源或自动改供给。

只有后续获得证据核定正式源确有错误，才由有原权限的维护者沿既有治理处理；本增量不新造冲突裁判器或自动政策合并。

### BC07 原发布机制不扩权

盘点报告默认候选。建设者可读自己有权限的候选；普通任务不能因存在报告、坐标或引用而读取候选。报告若需共享，仍沿原预览与人必要的发布决定，按原来源资格与依赖闭包核准确组合；含未获供给资格的输入时不能借发布报告绕过原检查。

报告发表仅代表该修订按其用途获准，不使报告中提到的定义／指标／规则全部正式或可执行。格坐标缺省、关注格未满、方法没有选用，均不成为其他资产发布或普通调用的新增门槛。

**报告专属薄适配必须显式接入原闭包。** 当前无`contentProfile`的正文按legacy处理，原foundation检查不会自动理解`reportProfile`；未来实现必须为此报告增加app-owned解析／引用收集，并在原保存校验、发布预览／指纹／确认、当前企业目录供给及准确read-source时调用同一资格逻辑。不能仅渲染UI或在保存时校验一次就宣称接入完成。

`methodRefs`、`basisRefs`、每个`evidenceRefs`及`sourceSelection.sourceRef`均为本报告当前适用所需的依据。按原身份元组（authority、id、version、projectId、taskId、locator及来源实际提供的hash）去重；原外层sources／dependencies必须覆盖这些必需引用，缺失／冲突／多出的身份解释由原校验回报Agent修正，不能只藏在body、伪造hash或以标题折叠不同版本。sourceSelection的item／metric／片段存在性经原准确读者核，不由前端猜字段。

原task／case回执、旧使用声明和独立核验只能在原授权上下文的使用详情／历史中按原路径查看；本报告格式不新增一组“仅审计refs”来绕过闭包。若它们被显式作为本报告依据，同样须通过原当前读者／发布资格，不支持或跨项目不可读时报告共享用途受限，不能借报告替调用者取得任务／Case内容权限。历史元数据可见不意味着可以解引用其正文。

必需依据失权／不可读／hash不符时，报告不得作为当前合格报告供给，也不能继续从旧结构缓存输出已核当前覆盖；原历史是否可读另沿原历史资格核定。生成新候选报告只新增候选，不创建正式指针、不恢复失效报告、不发布或修复其输入。原本仍合格的正式r1可以继续使用；原本无正式报告或已失效的场景依然无合格报告，普通分析可沿其他获准源继续。

### BC08 普通 Agent 使用主线

Host 仅提供原企业目录、可选方法／报告索引与获准资源；Pi 1.4.0 沿现有 Interface v3 的普通只读 profile 自主选择 `catalog/read/read-source/reason` 和获准计算工具，不建会话／推理循环或固定“先盘点再分析”。

正式合格的报告可作为普通准确来源读取，其范围／缺口只是上下文；实际口径、公式、规则及 Binding 仍回原权威。Agent 无报告、只有候选报告或没有格坐标时仍可分析；受影响结论说明限制，不必先补齐格子。原 declare-use/任务回执记录真正采用的准确版本，目录命中不当作使用证明。

UI 的普通使用详情按需显示本次实际采用的报告／原资产版本和相关限制，不整表强塞提示词，不给普通用户增加选格或方法维护动作。

### BC09 演进和历史

新任务发现缺资料、政策变化或共享错误，继续原贡献／维护机制。新盘点修订准备、核查、发布和原业务资产修订各自有据，不自动同步换版。旧任务／原报告保持原准确依据，新任务按原准入使用当前合格版本。无覆盖报告时原使用链路不受影响。

## 5. UI 合同（BC10）

沿已有企业基础资产页增加按需的“范围与资料”查看入口，默认六问＋重点缺口，不增加新顶级工作台。详细抽屉显示片段、准确出处、范围、并存版本、四项作者状态及独立使用证据。高级矩阵折叠，36格可查看、14默认关注，不显示填满率／健康分／建成率。

原关联核验中显示两类检查提示与工作项入口；“待核”不变成正式问题。普通任务沿原界面发送，使用详情只在确有消费时显示报告引用；无报告、候选不可供给、方法读取失败也有可继续的普通路径。

必须覆盖空报告、只候选、不可读方法、依据变化、缺必需映射、合法范围差异、待核矛盾、过滤无结果、加载／读取错误和历史等状态。失败信息不替代原资产权威。亮暗、390px、键盘、Esc／焦点恢复与容器内表格滚动相称点验。Demo 将加载／失败作为显式评审情景，所有数据为合成内存。

## 6. 职责、实施范围及验收（BC11–BC12）

### BC11 四原则与允许路径

Host 管归属、准确资源、格式／引用／权限、生命周期、保存和展示；Agent 自主盘点、分类、核口径、选工具和修订；人提供获准资料及不可替代的业务取舍／必要发布。正常新增必做操作为零，不要求逐资产分类、审批普通读取或确认每个例外。

本轮只写新目录：`docs/enterprise-foundation/studio-business-coverage-v0.2/`、`docs/prototypes/studio-business-coverage-v0.1/`、本 change；私人保全及检查留 `.local/studio-business-coverage-review-20261113/`。D3是待应用补丁，不直接修改既有模板README，原八稿与旧批准spec／Demo不变。
