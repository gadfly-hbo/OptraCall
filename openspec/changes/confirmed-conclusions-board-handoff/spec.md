# 报告结论确认与决策看板交接

v0.1 · 评审稿。[可点击 UI Demo](../../../docs/prototypes/confirmed-conclusions-board-handoff-ui-demo.html)以合成资料演示审查结果、用户确认、入板和失败恢复。本增量承接[结论与建议审查](../conclusion-recommendation-review/spec.md)及[决策看板](../decision-board/spec.md)，沿用其发起、审查与经营决策入口。

## 1. 用户路径

**CBH01｜确认的是可用于决策的具体结论。** 在「审查结论与建议」的已返回结果上显示本次所审报告版本、逐条意见、证据和适用前提。用户选择本轮要作为决策依据的结论，点击一次「确认并带入看板」。支持部分确认。「证据支持」和「有条件支持」的条目可供选择，后者随结论带上适用条件。证据不足、冲突或未核查的主张可留待补证，或用原「带回分析」入口交原主 Agent 核实。审查意见提供判断依据，是否确认由用户决定。报告审查的完成、停止或失败本身都没有入板副作用。[审查判据与原回交](../conclusion-recommendation-review/spec.md#3-证据判据与交付)

**CBH02｜结论与行动建议在看板各有去处。** 在现有「项目报告」的报告行增加可展开的决策依据，显示已确认的结论及来源。可选的行动建议须关联所选结论，且该建议自身在本版审查中获证据支持或有条件支持。用户同时明确选中时，把该建议及其适用条件写入既有待采纳列表。只有结论时亦可确认。行动建议保留现有 `suggested → adopted / dismissed` 及负责人、任务、反馈路径。该确认动作完成的是结论和来源交接，采纳建议、建任务及实际行动各自沿原显式操作。[看板状态规则](../decision-board/spec.md#关键规则借-decision-platform-g10g11-语义) · [行动反馈](../decision-feedback-loop/spec.md)

**CBH03｜直接使用已确认内容。** Host 从可信审查记录取得确切主张、条件及所选建议，完成身份与权限核验后直接写入现有看板能力。复用原报告列表和建议状态，不为这次交接重新抽取建议或发起模型请求。原「抽取建议」、人工补充、旧报告、既有建议、任务和反馈可按原入口使用。来源区分「报告确认交接」「模型抽取」与「人工补充」。当前人工条目固定为 `manual` 和「经验假设」，交接须保留真实出处。审查判据保留原含义，不自动换算成看板证据等级或置信度。[看板存储](../../../extensions/business-plugins/decision-board/storage/store.ts#L312) · [现有看板页面](../../../extensions/business-plugins/decision-board/ui/DecisionBoardPage.tsx#L118)

## 2. 版本、写入与回读

**CBH04｜固定报告与审查。** 确认记录保存项目与任务身份、看板报告身份、所审报告准确版本或字节摘要、审查记录与条目身份、确定的结论文本及条件、依据定位、所选建议关系、确认人及时间。客户端传所见身份和选择，Host 从实际记录重读文本。提交时在既有看板写入口重核报告归属、版本、条目来源、用户当前写权限及归档状态。尚未抽取过的报告通过同一 Store 完成确定性登记，交接无需先抽取。报告当前观测摘要来自实际当前文件，固定审查摘要另存于原版本关联。更换当前报告版本时，旧审查或旧确认继续指向原版本，进入新版确认前要先取得对应版本的审查。历史回看优先打开可读的原审查固定稿，若旧字节不可回读则展示实际保留的文本或摘要并说明限制。撤权后的正文和来源按当前权限限制回读。

**CBH05｜一致提交与去重。** 同一确认请求的结论记录和所选建议关联原子提交，一项写入失败则整组回滚，已选内容供显式重试。同一提交重放回读原回执，同一请求身份带不同选择时报冲突。重复确认同一报告版本、同一来源条目不重复入板。后续补选新条目只增加实际新增内容，原采纳或任务状态不受影响。回执未知时先按请求身份只读核实，能核实未提交时再允许明确重试。历史可按版本回读，未有确认记录的旧条目保持原来源。

## 3. UI 与接入

| 场景 | 可见结果 |
| --- | --- |
| 已返回审查 | 显示报告版本、可选的结论及关联建议、证据和条件。用户可选择部分条目；未选结论时确认动作不可用。 |
| 提交与成功 | 显示实际写入状态。成功后可查看对应报告在看板的详情，能分辨已确认结论和待采纳建议。 |
| 失败或状态未知 | 保留用户选择和原报告。失败说明可继续的动作；状态未知先回读原提交。 |
| 当前报告换版 | 明示已审版本与当前版本，旧版记录可在历史查看。新版按现有审查入口明确发起，随后确认本版。 |
| 看板继续决策 | 纯结论作为报告依据，行动建议沿原采纳与后续任务流转。 |

**四原则与实现范围。** Host 负责身份、版本、权限、写入、去重与可读回执。独立 Agent 沿原只读审查提出意见，主 Agent 自主复查，用户确认可采用的决策依据及后续行动。复用官方 Pi 1.4.0 与 Interface v3 下既有 `independent-verification` 的 `projectId/taskId/verificationId` owner/profile。确认与入板属于确定性操作，沿看板 Store 和正常路由，无新增 Agent 会话。正常路径合并确认与入板为一次提交，已有看板采纳动作继续承担经营决策。未来改动限原审查结果面板、看板报告详情和来源展示、两侧薄适配、现有看板持久化的最小兼容增量及对应检查。沿[工程规范 v1.9 IN01–IN07](../../../docs/engineering-workflow.md#统一会话接入规范当前interface-v3兼容v1v2业务子集)核对接缝。

## 4. 后续验收

| 标识 | 可观察判据 |
| --- | --- |
| CBH-A1 | 在尚未抽取过的所审报告上只选一条结论可入板，条件和出处可回读，待采纳建议与任务计数保持原值。审查返回、停止、失败均无自动入板。 |
| CBH-A2 | 同时选一条获支持的关联行动建议时，新增带真实来源和适用条件的待采纳建议。事实结论有依据但行动效果证据不足时，结论可入板，建议留待补证。只有后续明确采纳才具备建任务资格，确认阶段模型请求数为零。 |
| CBH-A3 | 并发换版、撤权、归档、跨任务身份和伪造条目均按原权限与版本处理，已确认历史只指向其实际版本。 |
| CBH-A4 | 重复点击、回执丢失、并发同一选择和部分写入失败均验证去重、一致性和原回执回读。失败保留选择。 |
| CBH-A5 | 既有抽取、人工建议、采纳、任务与反馈可继续使用。新旧来源可识别，条件或未知不会被换算成固定置信度。 |

评审检查覆盖只带入结论、同时带入有条件建议、失败保留选择、重复提交、单独采纳及新版确认。Chrome 桌面及 390 像素布局通过。非作者复核发现的建议证据、未登记报告和历史回看问题已纳入规格。检查限合成原型，实际持久化、权限和业务采用待后续工程验收。
