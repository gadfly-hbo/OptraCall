# 改前评估：四原则与运行稳定性

2026-11-06。对象为整改方案v0.1，并据评估形成[待确认v0.2](spec.md)。基线`main@4298db98e879cff0a73f7a131d633e2cc48d7667`，官方SDK1.4.0、undici8.12.2、Interface v3不变。本次仅静态核查和方案文档，不是实施或运行验收。

## 结论与发现

**整改目标符合四原则，但原v0.1不宜整包直接实施并采用。** R1应只替换已有调用资格保护的承载位置，保持SDK执行权与原启用范围；不能为消除原位改写扩建另一套Runtime。实现尚不存在，动态工具和取消的等价性、性能与内存均待验证，不能承诺零回归。

两位未参与方案创作的独立评估者分别审查职责原则和稳定性，均指出应先收窄设计。发现是设计缺口或失效条件，不是新运行事故，也没有事故概率或真实旧会话数量的证据。

| 发现 | 原方案问题及影响 | v0.2处理 |
| --- | --- | --- |
| F01／P2：旧历史兼容取舍未明示 | SDK原来可能自动迁移后续聊；全路径增加旧格式拒开会让这类历史无法续聊，不能同时称正常操作不变 | 正式拒开／迁移策略从本包拆出；仅做合成验证和只读工程诊断。原风险仍开放；未来采用前核定获准目标兼容，未知或需迁移且无决定的目标不采用 |
| F02／P2：新包装范围和失败域不够明确 | 若所有会话都装动态视图，或把可选资料失败变成会话前置，普通分析会承担额外故障面及不必要步骤 | 严格保持原启用谓词与source-reader例外；原排除会话不装适配；可选能力失败继续落在相应工具，Agent仍可用原工具自主执行 |
| F03／P2：窄差异复核补充的清理状态边界 | R2若把打开失败写成必然释放opening，清理失败／未知时可能错误转idle，违背原生命周期隔离 | 仅确认无残留或实际清理成功才释放；失败／UNKNOWN保留原owner隔离及busy／UNKNOWN，只按原资格显式close重试，不重放或另改生命周期 |

原稿两项设计缺口及窄差异复核补充均已在v0.2中收窄，不等于实现、运行或产品验收通过。此前准备复核PASS只适用于其静态准备范围，原报告与本次相反意见一并保留。

## 逐项核对四原则

| 原则 | 本次合理职责与保留能力 | 违反原则的条件与后续判据 |
| --- | --- | --- |
| Host管环境 | 校验真实owner／会话／调用存续期、取消及结果交付；保护文件和既有数据 | 若Host决定分析步骤、强迫先调用可选上下文工具或代做计算就越界；v0.2不增加这些行为 |
| Agent自主执行 | Pi继续自主选择工具／方法、直接及多层嵌套、并行与原有合法后台能力 | finally仅撤销已结束调用保存的ctx资格；不得顺带停止其他合法资源。合法／过期调用须配对验收，不能只测拒绝成功 |
| 优先复用Pi | 延用统一factory／runtime及公开加载／扩展入口；SDK仍唯一维护注册、选择、执行和会话生命周期 | 自有视图仅投影SDK注册记录；若必须新建第二注册表、调度器或大量补偿状态才能成立，就停止该候选并报告，不继续扩建 |
| 减少人的操作 | 正常v3路径目标为零新增必做动作；不增加普通工具审批、技术参数填写或资料维护 | 这是待验证目标。旧历史拒开会改变原操作能力，因此已拆出；不能用没有新按钮证明人的工作未增加 |

上述基于工程规范第2节及专项最终检查。必要资源和调用资格保护属于Host环境职责，但不能借保护名义缩小已有合法Pi组合能力。现有保护的finally失效并非本次新增；评估关注替换后保持等价。

### R1最容易遗漏的细节

1. SDK会写返回的Extension、commands及RegisteredTool的sourceInfo。投影记录须稳定且自有；晚注册闭包仍引用原Extension，不能把其初始synthetic来源当最终来源。需同时验证首次、晚注册与reload的真实来源。
2. 同名注册、MCP hidden重注册和下线必须反映新记录。保留全部定义／描述符、receiver、参数准备、hook及SDK原覆盖顺序；不能将扩展全转成customTools。Map的公开类型不等于任意可变Map替代已获证明。
3. 调用资格绑定真实run／session／manager／signal及该次调用活跃位。相同toolCallId或新signal不能续命旧ctx；并行B不能续命已完成A，A结束也不能终止合法B。复用原delegate和公共关闭流程，不造新调度。
4. 缓存随原资源代际释放；不在每次调用做全表复制、哈希、联网或模型调用。同规模合成工具比较首次、晚注册、重注册、多轮reload的耗时与释放情况；当前性能UNKNOWN。

### R2与R4不能过度承诺的地方

OptraCall普通打开目前会请求MCP loader；官方SDK公开入口自身也静态依赖MCP配置。仅将OptraCall内部路径改为惰性导入，不能保证SDK文件缺失时Host、历史页或无MCP会话仍可运行。

只读snapshot对v3的既有限制不等于所有续聊路径原本拒绝旧格式。SDK首开以及其runtime的switch、fork、import／恢复可能在重绑之前打开文件；未来若改正式策略，须按本产品实际可达入口核定，不能只查首次打开。该问题在v0.2保留为未解决风险；本包验证不读取正式原件，未来采用另设目标兼容前提。
