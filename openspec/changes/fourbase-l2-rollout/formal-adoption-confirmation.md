## 3. 最小接入差额与正常使用

### 3.1 已有能力与缺口

[正式启动链](../../../scripts/trial-launcher.mjs)经`start-host.mjs`／`host-entry.mjs`进入[main.runHost](../../../src/host/main.ts)，已有端口、业务根、instance与构建身份核验，但目前没有L2启动配置，也未向`createHost`传入`semanticGraph`。原[Host](../../../src/host/server.ts)已支持`semanticGraph.bindingFor(projectId, taskId)`和图服务／来源准入。缺口在正式入口的配置与投影，不在Agent引擎。

[startSemanticTrialHost](../../../src/host/semantic-trial-host.ts)只绑定其创建的任务为空项目的首task，后续／已有task不覆盖；它继续留作工程helper，不改造成正式部署器。原D16 operator、评分、冻结和导出脚本不进入日常运行。

### 3.2 拟新增的薄接线

- 由原launcher透传**一个显式的Host-only语义配置文件路径**，经现有启动参数链到`runHost`。未配置时保持现有L1行为；明确disabled时不启动图／L2解释器；显式配置损坏或启用配置的路径失效时明确报错，不静默当作L2已开启。格式采用单个小JSON，不建配置中心、Registry或热更新服务。
- 配置拟放在原dataRoot的`semantic-graph.json`，只含schema版本、enabled、准确L2解释器及获准项目到`{runRoot, snapshotId}`的映射；codeRoot来自当前受检运行代码。配置无密钥、模型参数或业务结论。路径／版本和根隔离校验复用现有边界，拒绝不明或越界配置。
- Host读取并固定配置后，沿已有`bindingFor`投影给该获准项目的真实task；未知项目无图绑定。已有任务、后续新任务和原Feedback创建的新普通复盘任务沿同一项目规则，无需用户逐task填ID或路径。仍须原Host核实际任务归属，插件／其他owner不能据此取图或扩权。
- 配置仅在正常重启后生效。换图、更新依赖或停用先沿原stop／close完成匹配资源收尾，再启新资源；不把改配置文件当成在途调用已撤权。来源停用／撤回仍由原authority每次查询核当前准入。
- graph-off采用同一配置的明确停用状态或启动时不传绑定。保持普通已授权工具与资料，不伪造ready；细节见回退安排。
- 沿已有`/api/health`运行信息补最少的**配置采用摘要**：enabled／配置hash／选定资产身份；与当前commit／instance一起回读。该摘要只证明装载了哪份配置，不能命名成业务ready或模型已采用，不新建状态中心／查询守护服务。

可复用的低层`SemanticGraphBinding`仍为`{runRoot,snapshotId,python,codeRoot}`；不新增Pi接口版本、Agent profile、会话ID或运行队列。未来允许差额集中在上述launcher／Host启动参数、一个小配置解析模块、原健康信息及相应已有测试；另允许为固定L2依赖补必要清单，并按第4节补一个有限资产维护入口及相应非空Store／冲突／保全测试；不新建通用安装器、迁移器或后台调度框架。

### 3.3 用户路径与权限

普通用户继续在原产品中选择项目、表达目标和使用资料；Agent自主决定查图、回源、计算、复核并复用结果。启用项目及维护图由工程维护人一次安排，**新增普通用户必做步骤0、前端差额0**；不新增L2开关页、本体管理页或独立业务含义页。原Demo继续保留，不另造UI原型。

现有非托管普通任务可用原L1目录／来源声明及Case／经验工具；托管普通主任务仅沿原资格获图只读能力，不能因此获得L1目录、来源写入、Case草案、跨Case经验或候选工具。旧任务也不因图绑定、重启或GET获得managed可信起点。Board、人的选择、行动与反馈继续原人工入口；绑定图不授权经营动作。

## 4. 首次资产采用与维护责任

首轮只选**一个新的SC-01S合成项目**接图，采用3指标＋1方法和对应小本体／带源图。其他现有项目先保持原模式；不扫描历史项目、不全局自动建图，也不读取原企业工作簿或真实经营资料。

[prepareSemanticTrialAssets](../../../src/host/semantic-trial-assets.ts)目前明确要求项目／指标／方法／企业资料Store全空，**不能直接在现有正式根执行，也不删除或绕过该guard**。正式采用的第二个确证缺口是非空Store下的有限资产准备。最小补法是复用该helper所用的原SAP／方法／企业资料／M2公开保存、发布和冻结调用，补一个一次性维护适配，仅处理本包明确的合成资产与新项目；不搬库、不造第二套Store，不将试验helper泛化成部署器。

该适配须先验证目标／版本与准确hash：已有同键同版本且hash一致的资产准确复用，冲突则停止并保留现场，不覆写、自动升版或默默改选其他版本；新项目／新资产沿原Store新增，部分成功回读原已生成Ref后显式处理，不能盲重跑制造重复。目标项目模型配置只引用原产品公开的configuration id／revision，核其可用性，不继承S5假配置、不更换Provider或导出密钥；原Host仍通过原配置路径解析本机凭据，不为准备资产发模型请求。

随后沿原[build_scene](../../../scripts/fourbase_l2/build_sc01s.py)，用目标Store生成／核准的真实Ref、新项目ID和新图UUID构图，不能复制D16整个dataRoot／study／auth／native或沿用旧项目绑定。原研究目录不作为资产发行目录；本轮合成输入内容及准确hash在候选清单单列，旧金标准、评分和模型执行记录不作为经营材料导入。合成项目和来源在原记录中明示性质。

目标根的资产写入／建图纳入**获准采用窗口**，在旧实例正常停止、匹配资源确认关闭后执行，避免离线Store与运行Host并写。先在**已有其他项目／资产的隔离合成根**验证这个有限适配、同版冲突、部分成功保全及旧版本兼容性；只有准确源、输入和新图校验通过，才将新绑定交给新Host。失败保留新建记录，不覆盖旧资产／历史或靠重放旧operator补齐。

| 责任 | 推荐首轮安排 |
| --- | --- |
| 工程维护／接线／固定版本／依赖／切换与回退执行 | Codex沿本项目规范承担；用户明确授权具体运行操作后执行。没有新设常驻值班或自动运维Agent |
| 服务采用决定、业务范围与不可替代的口径确认 | 用户／项目负责人；可指定其他接收人，未指定前不写成已经移交给外部维护人 |
| 指标／方法／企业资料／数据说明的业务权威 | 原各Store的准确发布和治理规则；Codex整理和投影，需业务确认的含义由用户确认，图不成为第二SAP／方法库 |

日常更新沿原Store保存／发布或撤回，停止匹配资源后离线构建新UUID并明确选择新代；不原位编辑旧图。坏图、错版、撤回源保持失败／partial／UNKNOWN，不能靠显示ready或保留旧快照绕过资格。

## 5. 分层回退

| 情况 | 回退／处理方式 | 必须保持 |
| --- | --- | --- |
| 图／解释器／绑定不可用，产品其余能力可用 | 先原stop／close核实资源终止，停用图并以同一正式候选正常重启；继续原模式已获准资料及工具 | 非托管任务保留原L1入口；托管任务仅继续其原资料／Python／bash等资格，不能借“回L1”增授目录、Case或写入工具 |
| 新候选启动或兼容失败 | 首回退目标为本次已核的旧release `model-pack-4298db9`、commit `695b9f10…`及匹配构建／Node／lock；沿原入口正常重启 | 切换前重新冻结该旧组合、核新记录对旧代码兼容；现场若已变更必须刷新目标。D16研究候选不是正式回退点 |
| 图更新／来源撤回 | 保留旧图及准确源，先确认新源治理，再构新UUID／选择新绑定；被撤回来源不因回退旧图而恢复准入 | 报告、Case、Feedback、原native、新资产和FAIL记录不删；不拿旧业务库／会话备份覆盖新增工作 |

沿现有launcher切换时，必须先**用旧代码根停止属于旧根的实例**，核关闭并清除旧启动控制记录，再从新根接同stateRoot／端口／业务根。现有`currentInstance`会拒绝其他root，不能从新根直接接管或强停旧实例。回退代码不回退业务数据；兼容性未证实时先停止采用，不强行恢复旧数据凑可运行。
