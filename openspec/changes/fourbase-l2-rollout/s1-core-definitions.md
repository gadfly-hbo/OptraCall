## 2. 核心定义语义卡

### C02 终端成交额

- 含义：范围内订单退款前的成交金额；本样本以有效支付订单金额代表，按原订单支付日期、门店和拟议直营范围筛选汇总。
- 输入：`orders`每条记录的`gross_amount_yuan`；归属用该记录的`payment_time`，门店用`store_id`。
- 本体角色：指标概念与其正式包内版本分开，金额／时间／范围／来源可追溯；不因与GMV叙述接近而合并。
- 边界：本例无取消、冲正、跨币种；实际渠道／一次性业务特例尚未由样本解决。simple是资产表达候选，不是对源指标类别的改判。

### C03 零售退款额

- 含义：退款金额为正、净额计算时扣减。源包含未发货仅退款、退货退款、已发货仅退款、拒收退款、额外退款等分类，不能遗漏分类范围或以样本未造类别推定现实为零。
- 输入：`refunds`每条`refund_amount_yuan`。先用`order_id`关联唯一原订单，再按**原订单支付日期和原门店**归属；`refund_time`仅核事件／截止及跨期，不替代支付归属。
- 本例约定：只造前两类，不重复、不过付，支付后7日内已入截止快照；这些是合成设定而非企业政策。
- 边界：源的回补／截数／实际成熟度仍未知。按事件金额聚合时可计划simple表达输入总量，同时在定义／方法保留其分类与依赖，不把它当无条件原子指标。

### C04 零售额

- 含义：同一范围、单位、税口径、时间及可加总粒度下，终端成交额减零售退款额；别称“零售金额／净销额”只用于发现，不跨范围自动合并。
- 本例计算：每门店、每支付期间的C02−C03；两期变化为`ΔC02−ΔC03`，Δ取B−A。退款增加对应净额负向金额影响。
- 输入定位：没有可冒充净额原始值的直接主输入指针；其来源是两组构成项。`synthetic_net_controls`仅为同批合成控制数，不映成真实独立净额报表。
- 边界：只报告金额构成，不能证明经营根因／策略因果；净变化为零或抵消时不强算贡献比例。derived／expr只声明含义，不让Host自动执行公式。

## 3. MTH-01参考方法正文草案

本次由定义与分析需要整理，非原字典已有完整方法。以下四组对应现有普通字符串字段；未来保存为other／manual来源、未发布草案，UUID／整数版本由原Store产生。现阶段不调用保存或发布。

**conditions**

适用于核对同一匿名直营可比门店集合两个已结束、等长窗口的金额变化。需要可读的固定订单／退款输入、准确的C02／C03／C04定义、币种／单位／税口径、支付时间归属和截止／回补／观察条件。SC-01S仅按其已声明合成条件演练；7日观察不推广为企业规则。必要条件未知时说明影响，可先做不依赖它的核查。

**logic**

Agent自主决定取材、工具和核查顺序。可参考：核范围和字段；按原订单支付时间归集成交及关联退款；比较两期C02、C03、C04及`ΔC04＝ΔC02−ΔC03`。可按门店检查变化及抵消，核退款跨期、类型／重复与截止。有独立业务净额时回源核对；本样本的同批控制数只作工程检查，同式零残差不证明源正确。取用何种方法与工具不由Host固定。

**judgment**

区分是否下降、成交项变化和退款项金额影响。整体下降不表示所有门店下降；退款增加也不自行证明其原因。可根据证据提出先核交易、退款、补证或观察等备选，解释支持、反证和未知；人的选择、实际核查、结果与复盘分别记录，不预写优先方向或决定。

**limits**

本例全为合成交易，未覆盖现实晚退款、全部类型／特例、小数舍入、取消／冲正和币种／税处理。源特例及实际业务条件未由样本解决。金额恒等分解不证明根因、因果或经营效果。工程参考结果不得作为被评估Agent输入；没有真实行动／反馈不记真实Case闭环。正式使用沿原保存、发布与准确查读策略。

## 4. 可逐项核查的字段映射

输入固定为[SC-01S input.json](data/sc01-synthetic-v0.1/input.json)，SHA-256 `ec996f92bed8c18b5a9809760827a59ddde85d115ad905df96a3dfac7f63372d`；[field-map.design.json](data/sc01-synthetic-v0.1/field-map.design.json)展开32条订单和16条退款的全部字段及原订单关联，还列明范围／期间和8组控制数位置。

| 角色 | 固定映射设计 |
| --- | --- |
| 范围／单位／截止 | `/scope/channel`、`/scope/store_ids`、`/scope/currency`、`/scope/amount_unit`、`/scope/tax_basis`、`/scope/data_cutoff`、`/scope/timezone` |
| 两期窗口 | `/periods/0/...`为A、`/periods/1/...`为B，设计清单给出每个确切字段指针；28天是筛选窗口，不新增SAP时间粒度枚举 |
| C02 | 从`/orders/0/gross_amount_yuan`等32个实际金额位置，结合各记录支付时间／门店／渠道；不把`orders[].…`存成指针 |
| C03 | 从`/refunds/0/refund_amount_yuan`等16个实际位置，经`order_id`匹配原订单的准确索引；原订单的支付时间／门店用于归组 |
| 事件时间 | 退款`refund_time`用于截数／回补证据，不替代业务归属 |
| C04／控制 | C04为计算关系而非直接字段；8组同批控制数单列为工程用途，不与原始净额来源混同 |

JSON Pointer只能定位，不能表达通配、join、分组或汇总。清单内每个指针均针对这份固定输入，实际关联与金额核对由本轮静态检查证明，不声称M2已经验证或执行。

## 5. 沿M2材料化的确定方式

复用[现有类型](../../../src/host/project-data-context-types.ts)与原保存入口，不扩Ref类型：

- `DataContextFieldLocation`沿`kind:'json-pointer',pointer`，后续只保存实际展开的合法位置。现校验主要核格式，不证明目标存在或join／计算正确。
- `DataContextMapping`要求非空真实`conceptRefs`或`sapRefs`；此刻没有实际project／dataset／input版本、SAP发布Ref，不制造看似可提交的保存请求。
- 指标Ref需实际`packageId/version/metricName/publishedHash`；其中publishedHash字段沿既有合同可为null，方法semantic Ref的hash可省略或取null。有实际hash时固定并核对，未知不编造或新增统一非空门槛，缺失限制保持。概念Ref仍是企业资料准确修订的`storeId/materialId/revisionId`，不能塞任意本体节点或材料代号；L2关系另沿获准语义表示维护。
- 字段含义、支付归属与合成限制可沿现有statements的`row-meaning/business-time/field/source-and-limitations`表达。工程整理采用现有`agent-inference`，不新增`synthetic` provenance枚举；合成性质写明正文，不因方案确认而伪填业务confirmed。
- 实际输入冻结、说明保存、准确Ref解析、UUID生成及发布均在后续获准阶段完成；S1定稿仅关闭设计不清的问题，不伪造实际写入回执。
