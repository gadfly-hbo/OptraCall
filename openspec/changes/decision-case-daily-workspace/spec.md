# Decision Case 日常工作台实施规格

v1.0 · 2026-11-27 · 用户确认交互的固化版，供外发开发

## 1. 目标、确认和基线

让用户围绕一件持续推进的事，准确地回到当前事项和本轮进展，找到具体项目／任务，保留新输入，并将取舍、行动和真实反馈接回原记录。Decision Case 是日常核心入口，战略选择、目标管理、语义资产、分析资产为其提供基础，也从 Case 的累积中持续完善。四项建设不成为开始工作的门槛。

用户已分别确认 Case 当前工作布局、事项与轮次保留、列表／树状图、两辅助页默认事项范围、统一 **Decision Case** 一级 Tab、Case 总览／全部项目，以及 v0.6 首页待处理和轻量新建／继续。用户在了解轻输入用于“先记下想法、找到归属”的辅助定位后，再次确认该版 Demo，随后要求固化 Demo／spec／任务清单并创建外发 Issue。

## 2. 范围与允许修改

本单交付统一日常入口、Case 当前工作、事项关系小图、准确范围与来源、完整全局项目入口、首页来源明确的待处理、统一创建／继续及输入保护，并补齐实现这些行为必需的最小持久数据和业务接缝。

允许修改的范围：

- UI：`src/host/ui/App.tsx`、`WorkspaceHome.tsx`、`CaseBoard.tsx`、`CaseIssuePanel.tsx`、Case 相关局部组件、`ProjectBoard.tsx`、`ProjectSpace.tsx` 及对应导航、表单、client、样式、首页投影 hooks／model。
- 业务：`src/host/case-*.ts` 的相关类型、校验、Store、业务服务及路由；与请求回应直接相关的 `decision-feedback-*` 和 `extensions/business-plugins/decision-board/` 原行动／反馈接口、存储与 UI；原目标采纳／准确绑定的既有业务 API 适配。
- Agent 薄适配：原 Case、目标草稿／业务讨论工具及 Host 注入，限于本单上下文读取、候选、明确请求／关系声明和保存回执。涉及 Host／Agent 技术接入由 **Codex** 承担；其他领取 Agent 与 PM 先明确该部分文件归属，Codex 领取时可整单负责。
- 必要 Host 接线限 `server.ts`、`business-role-conversations.ts`、`business-role-types.ts`、`strategy-discussion-host.ts`／对应类型、`src/agent/strategy-discussion.ts` 和 `src/agent/case-decisions.ts` 的相应只读工具／声明保存适配；`project-runtime.ts` 如确需仅做对应类型接线，不改 SDK／会话循环。
- 本目录、相关文档、必要迁移及永久回归测试。新增文件放在上述职责邻近位置，不泛化成全平台重构。

不改 SDK 原实现、依赖／锁文件、公共 Runtime 或会话权威；不新增模型重试循环、六步任务流水线、平行消息库／待办完成库／目标权威。设备更新、运行服务切换、真实业务数据、凭据和付费真实模型调用不由本工单自动授权。

开放的[目标管理修正 #148](https://github.com/gadfly-hbo/OptraCall/issues/148)与本单共享目标 Store／辅助 UI 边界。本单优先消费现有目标接口，不修改该单的 GSA 承接、实绩可比性、阈值或发布核对算法。确需共享字段／接缝修改，先由 PM 在两个 Issue 记录接口与唯一写入归属；分支在集成时重验，不覆盖对方 WIP 或历史结论。

## 4. 必要业务合同

### 4.1 对象、G/S 和当前工作

Case 显式关联原项目，多对多关系保留；任务只属于原项目，可带原 Case 事项绑定。项目共用文件、状态、约定和阶段不按入口复制。旧 Case↔Case `supports/follows_up` 等关系仍可达，与新增 Case 内事项承接边分开。

正式 G/S 引用原 `GoalRef{goalId,version} + 该版具体策略字符串`，沿既有采纳和 `CaseGoalBinding` 合同；不新增独立策略 ID／版本或 bundle 权威。它与 Case 内方案记录的 `strategyRef` 是不同原对象。Demo 的 bundle 仅帮助展示准确身份，不能成为新产品表。

“第几轮”沿原选择链、复盘与准确授权身份投影，不用 UI 自增数字代替业务权威。原判断、后来复盘、取舍、授权、观察、目标结果和经验有效性分别表达。当前摘要为原记录投影；Agent 综合内容另标来源，不覆盖旧正式内容。

目标结果优先使用既有 `goalIntentEvidence/goalCheckEvidence` 及原 `checkCaseBasis`。不可按同 goalId 的最新检查任取结果，不重做实绩填报、跨 Case 求和、趋势或贡献计算。现有目标修订及旧 Case 历史绑定保持原合同。

### 4.2 事项关系的真实写入口

当前 `CaseDecisionIssue` 没有持久关系字段，Demo 的固定边不是实际已有数据。需补最小、归属原 Case 的显式有向承接记录，具有稳定边身份、两端准确事项、关系说明、声明来源、修订／操作回执。支持 `A→C、B→C`，不能压成单 `parentId`。

写入口沿原 Case 事项正常对话和原业务工具：用户明确声明／修订／解除关系时，由 Agent 按该声明保存并引用准确原用户消息；Agent 自己提出的关系先作候选，明确采纳后才保存。Host 核归属、版本及结构，不从文本关键词猜关系。若无需 Agent 的现有明确声明保存入口可复用，同样保留原声明来源。

不新增强制关系填表、关系 Agent 或自动推断器。没有声明的旧数据保持无边，不导入示例边。图中的回指／重复引用应安全展示，不将显示为“树”解释为业务必须单父、无环或顺序执行；不扩大到跨 Case 事项关系。保留修改／解除的历史与并发冲突回执。

### 4.3 首页待处理的真实请求与回应

当前代码有方案来源、选择、授权、反馈及原操作身份，但没有通用“请求某人回应”的业务收件记录。该缺口必须在本单补齐最小来源合同，不能只调整首页计数。

首版围绕已展示的两类动作：**作取舍**与**补原始观察**。请求属于原 Case 事项或原 Board 行动 owner，至少有：稳定请求身份／修订、请求原文及其来源、请求人／实际承担人的声明来源、提出时间、回应类型、准确目标和轮次／选择链或行动授权身份。仅存在原期限时才显示到期；缺日期不判逾期。

明确请求的写入口沿原事项／行动对话：用户明确要求由谁回应什么，或明确将自己的一项取舍／观察留待处理时，原 Agent 工具在同 owner 的原业务记录保存请求元数据及原消息引用。Agent 建议的下一步不自动成为正式请求；原记录尚未表达承担人或请求意图时先保留候选／继续工作，不由 Host 认定。该增量不新增跨账号派单、自动提醒、团队认领或后台生成请求。

| 请求类型 | 准确目标与回应依据 |
| --- | --- |
| 取舍 | 原 `caseStoreId/caseId/issueId/strategyRef/expectedPreviousChoiceId` 或等价原选择链版本；由原 `chooseStrategy` 成功回执带准确请求引用回应。 |
| 观察 | 原 `projectId/itemId/taskId`、选择／授权身份、原反馈修订基线；由原 `saveFeedback` 带准确请求引用及 CAS 成功回执回应。 |

Agent 来源沿原 `requestId/sessionId/toolCallId` 与 native reply；UI 明确保存用原 owner 的 `operationId`，不伪造 Pi 请求 ID。回应引用是原业务结果的一部分，首页按该关联派生，不另存一份 complete/dismiss 权威。

打开不回应；普通 choice／feedback、别轮或别授权下的回应不消解。换轮、请求被准确修订／撤回、来源暂不可读或撤权分别显示替代／失效／待核，不能假装已处理。相同请求重试沿原 operationId 核回执，写冲突保留输入。

项目承接人、目标 responsible、Board owner 是业务文字，`actorKind:'user'` 不是具名登录账号。无可靠身份映射时使用“待处理事项”，逐条显示原承担人及其来源，不能称“待你确认”，也不取当前焦点项目负责人来填收件人。无承担人或来源不足的材料进入继续工作／待核说明，不伪造个人义务。Demo 人物与两条请求不得作为生产初始数据。

`pendingInput`、UI pending、无 choice／feedback、`Case.status=awaiting_confirmation` 均不单独证明业务请求。原 `pendingOperations` 可提供“原操作待核”分组，保留其真实含义，不混作经营取舍请求。报告、行动进展和外部等待有独立入口。

### 4.4 轻输入、创建前辅助与采纳

轻输入是辅助入口，日常已知工作从待处理／继续工作直接进入，不要求先走整理。整理不创建 Case、不采纳目标、不写入已有对话。推荐须依据本次获准可读的 Case／事项摘要，提供准确引用和简短理由，可返回无匹配；不得采用 Demo 的固定会员复购推荐、Host 关键词规则或仅最近打开 Case 来决定归属。最终继续位置由用户明确选择；原事项无可选身份时保留输入并提供建立事项入口，不默造事项。

已核可复用创建前 owner `{role:'goal-draft',draftId,scope}`：`BusinessRoleConversation` → `/api/business-role` → `business-role-discussion` 域／`goal-draft` 工具配置，`propose-goal` 返回可编辑候选及准确原生来源。每份准备草稿独立、可恢复的 draftId；不沿同 scope 共用一份准备身份。候选交原目标权威保存／采纳，带入前和保存时沿 `GoalRoleSuggestionRef` 重核 owner、discussion/session/entry、hash 与 scope。人工路径及采纳丢回执恢复优先抽取原 `CaseGoalPicker`，不取消其业务校验。

`GoalPlanAssistance` 是已具准确 G/S 的 A 行建议，不能直接当创建前 G/S 入口。Case Agent 仍需真实已有 Case／事项 owner。当前缺口是 `goal-draft` 尚无获准 Case 目录检索／推荐接缝，文字搜索不等于语义推荐；Codex 补有界只读目录／准备上下文，交真实可见候选及引用供 Agent 解释，不向模型开放任意 Case 数据。技术盘点记录权限、工具、原生历史及取消策略；优先沿现 profile，只有证实仍缺必要表达能力才最小补 variant/profile，不另写 opening／重试／恢复循环。

无配置、用户不愿调用模型、失败或取消时，手填／选已有 G/S 正常可用，原输入和候选保留。实际模型请求必须由用户在产品里主动触发，沿既有配置和数据出口权限；开发验收不自动调用真实 Provider。

三个创建分支沿同一可恢复准备意图实现：准确已采纳 G/S 无 Case → 创建；新候选 → 明确采纳并创建；已有准确 G/S 的 Case → 明确继续，保留输入。已结束 Case 先查看原记录，不自动重开；需要重开沿原明确操作，实质改 G/S 则沿原修订／采纳规则，不靠换标题绕过去重。

一个 UI 按钮可集中表达“采纳 G/S 并创建 Case”，但实际保存／采纳／创建分别有原回执。已采纳 G/S 不再次采纳；目标已有更新时重核准确引用，不暗取 latest。创建第一件事项如 Demo 所示明确告知，不自动新增项目任务或授权。

### 4.5 持久草稿、幂等和部分成功

业务准备草稿记录用户原输入、编辑内容、选定准确 G/S、已有采纳／创建回执及目标位置；待带入片段记录原文、来处、目标 Case／事项与追加状态。草稿是工作输入的持久数据，不能成为第二份原生对话历史。沿现有草稿设施；必要最小增量按业务 owner 分离，不搬 Demo sessionStorage 作正式持久化。

继续保留新名称、背景和正文；已有输入不被候选切换、示例插入、导航或恢复静默替换。追加须明确，重复追加一次有效，原文可回读；发送仍经过原会话发送入口。单纯打开、返回、选择浏览范围不发模型请求。

为创建／采纳／关系／请求保存保留稳定操作意图和准确回执。确定失败可修正后续办；丢响应或 UNKNOWN 先查询原操作，不盲目重写。部分成功后放弃草稿不撤销已保存目标或 Case。并发、跨版本、迟到事件和重开恢复不能串写；不承诺未经验证的跨 Store 原子事务或全局恰好一次。

### 4.6 全局项目与权限

全局项目能力完整保留，不能将全部项目按钮简单跳到当前 Case 的局部项目页。共享项目一个身份，多个 Case 只引用；关联项目不使其中全部资料自动关联 Case。解绑一侧保留项目、任务、文件和另一侧关联。

归档沿原项目空闲准入：运行、打开或待回应等已有阻塞条件仍有效，不隐式停止；竞态时原服务端准入决定结果。归档各写入口受限、既有历史可读，恢复不重开 Case、不启动任务、不恢复原本独立归档任务。

个人／部门／企业范围沿原目标／资产身份，不从名称推断。既有“资产企业范围”不冒充统一权限或 Case 归属选择。所有读取、图节点和来源均服从原资格，403 清掉失权内容，筛选不扩大权限。家庭可作为现有个人管理中的问题场景，本单不新增家庭实体、成员或权限体系。

## 5. 接入责任与四原则

| 原则 | 本单实现与验证约束 |
| --- | --- |
| Host 管环境 | 管准确 owner、来源、权限、版本／CAS、业务保存、导航及输入保全；不补目标实绩、猜归属／关系或决定业务优先级。 |
| Agent 自主执行 | 可自主查获准资料、整理候选、解释理由、按明确用户声明保存请求／关系；六类任务不约束内部方法。必要用户取舍／采纳与普通分析迭代分开。 |
| 优先复用 Pi | Pi1.4.0／Interface v3、现有目标／Case／项目业务权威及公共生命周期。新增 profile 的实际缺口、owner、公开能力、最小适配及回退在实现记录中列明；不改官方包或建平行 Runtime。 |
| 减少人的操作 | 已知 Case 直接继续；首页不另维护完成；输入不搬运；已有 G/S 不再采纳；基础建设不作准入。关系可由明确对话声明记录，不要求先填图。必要采纳／创建可同屏集中，管理与追溯按需展开。 |

正常最短路径：已知工作 → 点击继续 → 原事项直接讨论；明确请求 → 打开原事项 → 原保存动作回应；全新问题 → 一句话准备 → 核对必要 G/S → 明确采纳／创建。人工路径不依赖模型。

工程实施先记录 IN01–IN07 的真实 owner/profile。Case 事项沿现有业务讨论域的 `{role:'case',caseId,itemId}` owner；创建前辅助沿 `{role:'goal-draft',draftId,scope}`，不在没有 Case 时伪造 Case 身份。Host 接入由 Codex 维护，插件／业务层只获得相应 port/ref。公共契约若必须调整先补契约与消费者适配，保持原 Interface v3 子集和第三合成消费者回归。

## 6. 验证与工程交付

按 [tasks.md](tasks.md) 逐项交付。确定性行为先保留可检出目标错误的测试／因果复现，再最小实现和永久回归，不以 fixture 失败冒充产品 RED。

必需验收包括：

1. 真实 Store／HTTP：目标精确版本和三分支创建、部分成功／确定丢响应、请求精确回应、关系多前驱／修订、草稿保存重开、归档竞态及旧数据保全。
2. 真实官方 Pi＋隔离合成 Provider：原 Case、目标辅助与可能最小新 profile 的正常／取消／配置变化／迟到／owner 隔离、工具保存与原回执；UI 推荐的有效性依据与内容质量分别记录。不用固定 Demo 或 import 成功替代接入。
3. 实际产品浏览器：主页→请求→原记录→返回、三个创建分支、非空草稿追加、关系视图、全局项目往返；1440／1024／390、键盘和焦点、深浅主题如原产品适用；来源、结果未知、403／503／部分读取、旧快照与文字转义。
4. 适用完整 `npm run check`、原边界检查及最终固定候选非作者独立复核／四原则终检；当前原型浏览器未验证不能被用户确认或 Node VM 成绩抹去。生产验收需补实际运行证据。

最终交付在同一外发 Issue 回执分支、完整基线／候选 SHA、DW01–18 完成情况、规格／测试／结果链接、真实命令／结果、失败／跳过／UNKNOWN／未测、兼容回退与保全。交回后停止写入，PM 依工程规范审核、组织 PR／准确 head CI、获授权合并和 main push CI 后工程结案。设备更新／服务切换／用户实际体验不列为工单工程关闭条件。

## 7. 未决与后续

本单没有阻塞已确认范围开工的产品问题。新目标结果聚合／趋势／因果贡献、家庭实体／多人权限、自动派单提醒、跨事项成果采用、全局图形全量重设计、更广自动化留待后续。需要实质改动已确认 UI、目标权威或权限的发现，只补受影响决定，不由领取方自行扩大。

事项边、请求来源和创建前会话是已确认交互所需的真实最小实现缺口，按本 spec 补齐，不把这些技术工作写成“后端已有”。具体接口／迁移布局由领取方据真实代码细化并在原 Issue 留据，不能以此静默改变上述业务规则。
