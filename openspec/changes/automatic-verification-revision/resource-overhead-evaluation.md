# 托管执行资源开销评估

2026-11-01（Asia/Shanghai）。状态：18次正式运行完成，非作者独立复算及结果复核PASS_WITH_SCOPE，657项字段／数值比对一致、无未解决finding。仅评估，不修改产品代码、永久测试或运行服务。

## 结论和大白话

当前托管机制有可见开销，**频繁小工具调用是主要问题**。单次较长CPU计算的额外影响较小；后台并行能够正常完成，但耗时和资源增加。不能再笼统称监督资源“几乎没有成本”。

大白话：现在每叫一次工具，会新起一组执行和监督资源；工具做完后，一部分资源仍保留到整个阶段收尾。60次调用会积累60位监督程序和60个已退出、保留身份待回收的进程。它们不是120个都在忙算，但会占内存和进程名额；每次重新启动工具执行器，也明显拖慢小操作。阶段结束后本轮均释放，没有观察到完成后的持续残留。

## 对照方法与范围

- 同一候选5、同一实际Host/Pi SDK/原生工具入口，关闭自动核算与开启后的ordinary托管对照。产品252份源码／永久测试摘要前后保持一致。
- Apple M4，10核，16GiB；macOS26.3.1、Node25.9.0、Pi SDK1.4.0、Python3.14.4。
- 三类场景各三组交错配对，共18次正式运行；固定顺序，不丢弃结果、不按结果重跑。预跑另存，不进入正式统计。
- 长计算：同一脚本、固定286,123,113次迭代哈希，校准目标约60秒，不按固定运行时长替代固定工作量。
- 频繁调用：48次read同一短文件、12次简单bash，共60次；之后保持30秒无新工具的等待窗口，观察资源留存与空闲CPU。
- 后台并行：4个相同固定工作量Python任务，每个校准约8秒，主请求期间另做8次read，最后相同工具等待全部结果。两边均核对后台实际退出，不能用关闭自动时提前返回来制造速度优势。
- 使用本地固定流式Provider排除模型思考、网络和供应商抖动，实际计算／工具进程是真实执行。444次本地SDK传输、426次实际工具调用；真实模型请求0，核算／返修请求0。指定核算报告保持缺失，只隔离测主Agent阶段托管，不把额外分析业务算成监督成本。

Python版本均为3.14.4，但负载`sys.executable`记录的入口不同：关闭路径为Framework的`bin/python3.14`，受管路径为`Resources/Python.app/Contents/MacOS/Python`，入口文件inode和SHA不同。它们是当前产品实际开关下的环境选择；本轮没有统一入口做纯guardian单变量微基准，也未把入口元数据直接当作最终kernel-exec身份。因此小幅长计算／CPU差异不能全部归于监督。频繁read／简单bash场景不依赖Python计算负载；完整路径与摘要见[入口记录](/Users/bendandebaba/.codex/worktrees/4727/OptraCall/.local/managed-execution-resource-evaluation/python-entrypoints.json)。

## 正式结果

下表为各条件三次结果的中位数。主请求耗时从发起到同一请求完成且Host空闲；频繁场景包含双方相同的30秒等待。CPU是整个隔离Host生命周期累计CPU秒，含启动／配置／关闭及已回收后代；后台孤儿家族另核并单列补入，不能把全部CPU增量都归给guardian。

| 场景 | 主请求秒：关→开 | 累计CPU秒：关→开 | 活进程footprint峰值MiB：关→开 | 产品进程采样峰值：关→开 |
| --- | ---: | ---: | ---: | ---: |
| 约60秒单次计算 | 59.06→59.71 | 60.06→60.32 | 307.9→433.7 | 3→5 |
| 60次频繁工具＋30秒等待 | 31.30→53.40 | 2.56→31.72 | 436.6→1002.8 | 2→122 |
| 4路后台并行 | 9.61→11.49 | 35.74→44.38 | 382.1→593.9 | 8→28 |

CPU秒不是墙钟秒：四核各忙一秒约为4CPU秒。并行场景中，Host及已回收后代自身的CPU中位数是1.64→8.35秒；上表额外加入已证明为PPID1、已退出的后台master及其已等待子任务CPU，避免遗漏或父子重复计数。该家族自报值在写结果之后仍可能有极小的解释器退出成本未计入。

同组配对的耗时增加范围：长计算0.64–1.90秒，频繁调用21.79–22.25秒，后台并行1.27–2.39秒。长计算工具段差异为−0.19至+1.04秒，存在运行波动，不能宣称纯计算本体稳定慢了某个固定比例。表中各条件中位数之差与“配对差的中位数”是不同统计量。

RSS合计峰值另报：长计算387.2→555.5MiB；频繁调用495.5→1570.7MiB；后台并行510.0→837.0MiB。RSS会重复计入共享页，不能把它当作整机实际新增物理内存；footprint是活进程系统记账之和，也不等于整机净增RAM。

### 频繁调用的具体成本

排除共同30秒等待后，工具执行往返段中位数为**0.360→21.664秒**。同组配对该段增加21.30–21.45秒。

| 工具 | 关闭：p50 / p95毫秒 | 托管：p50 / p95毫秒 |
| --- | ---: | ---: |
| read短文件 | 4.94 / 7.02 | 359.14 / 369.60 |
| bash简单输出 | 8.07 / 9.28 | 365.04 / 376.14 |

这里是本地Provider发出单个调用至收到对应工具回复的SDK往返，包含执行、序列化和本地传输，排除模型推理；每组先算p50/p95，再取三组中位数。不能据此声称真实模型完整分析也会慢约60倍。

三次托管均达到60个guardian和60个Z状态进程。Z已退出，不是仍在计算；当前为防PID/PGID重用保留身份，到阶段收尾才回收。各类峰值可能出现在不同时刻，不能将活跃峰值和Z峰值直接相加当总峰值。

30秒等待窗口内，整个产品树CPU约2.69%→4.21%单核，60个guardian自身合计约2.08%单核；100%表示一个逻辑核。guardian自身活进程footprint约567MiB，约9.45MiB/位。总等待footprint还受SDK堆和GC影响。CPU大头不是等待时的监督循环，而是每次调用创建／初始化／执行／保护检查等组合成本；本轮未做函数级CPU剖析，不能把29秒CPU增量全部归因于轮询。

### 完成、并行及释放

18次主请求全部completed，全部工具无错误；六次长计算摘要相同，六次并行中24个子任务摘要相同。后台确实跨工具调用运行，两边均在同一工作完成边界比较，没有禁止并行或把后台任务提前杀掉。

所有隔离Host正常关闭，关闭后样本的产品进程均为0。开启路径为交接关闭执行环境；关闭自动的普通路径在请求结束后仍会缓存SDK，直到测试Host关闭。因此阶段结束后的内存差不能简单解释成guardian泄漏或托管永久更省内存。

## 优化建议（本轮不实施）

1. **优先减少每次工具调用的重复创建和初始化。** 评估每个任务阶段复用无模型工具执行器及监督资源，使进程数量取决于阶段／实际并行作业，而非累计工具次数。它应同时改善几百毫秒的单次启动成本及资源积累。
2. **对已证明无后台工作的调用及时释放。** 可以考虑异步核定自然结束后回收，不必全部留到阶段末尾；仍在后台工作的调用继续保留。单做这项主要改善内存／进程，不能消除每次重新启动执行器的延迟。
3. **再定位重复导入、初始化和目录检查。** 本轮短文件小目录已经观察到成本；大型项目的逐调用目录遍历尚未测，先补测再决定缓存或变更检测方案。单纯降低监督等待频率，只针对约2%单核的次要部分，解决不了当前主要延迟和内存留存。

这些优化只改变Host的资源实现，不增加专业计算工具、分析参考或固定分析步骤。工具次数、分析方法、并行和跨调用后台能力继续由Agent自主安排。任何复用／提前回收方案都须保持原件保护、可信SDK独占native写入、owner/lease、同阶段权限、停止、UNKNOWN和真实组身份收尾证明，不能以省资源牺牲这些合同。

优化后应复跑同一固定18次对照及原生命周期失败路径，并补小时级留驻、大目录、内存型数据和多项目并发；目标是消除“每累计一次调用又多留一组资源”的增长，并显著降低小工具新增延迟。当前没有用户确认的生产SLA，本报告不自造性能通过门槛。

## 测量限制及证据

采样周期200毫秒，计时wrapper按精确PID从产品指标中排除；采样器／Provider／控制器在目标树外。临时采样器及ps自身约占单核11.6%–23.8%，已单列且未计进产品CPU／内存／进程，但仍可能产生系统调度扰动。状态查询500毫秒一次，双方一致，包含在被测Host工作中。小幅长计算差异不应被过度解释。

内存／进程采样从配置完成后开始，不覆盖Host启动前段峰值；短命进程及瞬时内存峰值可能漏采。libproc活进程footprint覆盖不足时保留未知，不把Z读取失败填成完整总量。CPU自身计数按本机Mach timebase125/3转换，并通过独立忙循环与resource验证；[Apple XNU实现](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/task.c)为单位核对参考。

本次n=3，报告中位数和实测范围，不是总体置信区间；没有真实模型自主策略、小时级、多项目或大数据内存压力结论。本次资源与执行结果测试不改变此前专业验证FAIL，也不等于Git/CI、运行采用或产品验收。
