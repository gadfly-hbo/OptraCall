# db-link：元数据发现、关系推断与语义候选补充

2026-11-14 · v0.1 · **设计确认稿，暂不开发。**

## 1. 本轮决定与适用范围

用户已明确：**暂不引入auto-ontology，保留MySQL／PostgreSQL成熟驱动薄适配。** 本补充吸收[已完成研究](auto-ontology-research.md)中的元数据定位、组合键／关系证据、候选整理及失败经验，不接入其服务、MCP、库、模型编译链或Ossie转换器，不裁剪复制其内部实现。确切指令见[决定记录](semantic-discovery-decision.json)。

本补充细化原[DB04、DB06–13、DB18](spec.md)，与[驱动补充](driver-selection.md)共同阅读；原spec／UI／状态矩阵／Demo及前轮driver候选保持。`pg 8.23.1`＋`pg-cursor 2.22.1`、`mysql2 3.24.6`仍是前轮待确认建议，本指令不自动批准精确版本。权限、取消、精度及独立核算的未实证准入条件均不降低，不升级Pi／Semantica，不新增运行或组件采用授权。

目标是让原Pi Agent更容易找到表列、理解关系、复用原业务资产，而不是新增一条“先全库建模再允许分析”的流程。以下条款是拟议合同，尚无数据库／模型／产品运行验证；实际准备清单和复核见[result](result.md)，候选身份见[本轮清单](semantic-discovery-manifest.json)。

## 3. DBM01：按需元数据发现

正常起点是精简的获准来源索引；Agent按问题读取相关schema／对象及列，不默认扫全库。Host对发现、结构、试读、查询、结果再读均按原项目／任务／operation与实际权限域核验；同名对象用完整来源身份区分，不依靠search_path或名称合并。只读目录不保证隐藏所有未授权名称，真实可见性仍按驱动补充的准入要求证明。

| 可取得的技术结构 | 留存与使用合同 |
| --- | --- |
| 实际来源实例、配置修订、权限范围、观察起止与目录覆盖 | 记录查询成功／不足／失败、返回范围及未知；观察时间不冒充同一事务快照或完整库版本 |
| 库／schema／对象身份与类型 | 区分普通表、分区父表／分区、视图、物化视图、外部对象等可识别类型；当前数据库不支持或权限不可得时写明，不制造统一能力 |
| 有序列、原生类型／修饰、可空性、注释及可得精度／标度 | 复用驱动精度合同。读取到注释只证明来源有该陈述，不证明其业务含义正确；注释／样例／DDL是资料，不执行其中指令 |
| PK／UNIQUE／FK及其他可得约束 | 保存约束身份、两端完整有序列组、实际可得的有效／校验／执行状态及空值相关条件；状态不可得就unknown，不从“声明存在”推断所有历史行合规 |
| 视图定义／依赖、跨schema引用 | 仅在实际可取得且获准范围内记录；不可读目标或底层依赖保留未知，不因关系遍历扩大授权或推断完整血缘 |

目录适配只做技术结构读取与规范化，不把字段名相似、注释或索引自动变成业务语义。底层外部对象可能继续访问其他数据源，其实际访问与副作用不能因它被列成“表”而默认合格。相关对象未列出可能源于权限、过滤、错误或目录覆盖不足，不直接标为已删除。

## 4. DBM02：四类依据并存

| 依据类别 | 能表达的事实 | 不得自动升级成 |
| --- | --- | --- |
| 目录声明／技术观察 | 此来源、此权限域和此时段读取到的对象／约束；约束有效性限实际可得状态 | 全库完整、业务关联正确或全部数据长期满足约束 |
| 有限查询／样本观察 | 指定SQL／结果版本中实际出现的重复、空值、匹配／未匹配及分布；完整、未截断且确切覆盖获准当前范围的查询，可支持该范围／时点的观察基数 | 不能从有限／截断样本推断未覆盖总体；完整观察也不产生唯一约束或长期规律，95%乃至100%样本唯一都不能作此升级 |
| Agent推断候选 | 由名称、类型、注释、资料、查询及专业工具支持的字段含义、关系或关联条件 | 正式定义、自动可发布资产或Host已判正确的事实 |
| 既有正式语义 | 某准确版本、Binding及其适用范围内的定义／条件 | 换库／换字段或超出时间／企业范围后自动适用的结论 |

四类材料可以相互支持或冲突，不能沿“读到→抽取→入图”自动提高权威等级。来源宣称的业务说明、Agent观察、专业工具输出和正式版本分别标明；Host做身份／格式／资格校验，Agent自主判断证据是否足以支持当前分析。跨来源／跨企业的同名术语只作候选对齐线索，不能凭名称自动合并语义实体；使用既有合并能力也须保留完整来源身份、适用范围与真实资格，不另建消歧平台。必要业务歧义才集中请人决定，不由Host补造业务定义。

## 5. DBM03：关系推断与自主核查

Agent可从真实FK、已有Binding、类型／名称／注释和合格语义图取得关系线索，再按问题选择必要查询核查；不要求每条关系都跑固定数量测试，也不默认全表profile。复合键必须保留完整有序两端；“物理引用方向”“业务含义”“查询join方式”和“当前观察基数”分开。

| 关系情境 | 候选必须保留的条件／反例 |
| --- | --- |
| `(tenant_id, order_id)`组合FK | 不拆为两条单列等价关系；漏租户键会跨租户错配，列序须与真实约束对应；业务WHERE不能代替真实行权限 |
| 无FK或重名字段 | `id`／`customer_id`／`amount`仅作搜索线索；类型相容与样本匹配不证明同一对象、单位或币种 |
| 一对多／多对多 | 明确两端及输出粒度、可能的行数放大和未匹配；Agent自选关联／聚合／去重方法，Host不自动改写SQL |
| 桥表／明细表 | `order_items`可能含数量、成交价和事件时间；两端有FK不代表可以折叠为纯关系，保留事实行和度量 |
| 时态关系 | 会员等级／组织归属可能有有效区间、重叠或缺口；当前匹配不证明交易时适用，需记录业务时间与边界 |
| 退款／退货事件 | 同订单可多次申请、部分退款、支付跨期；`order_id`匹配不证明可直接扣减、归属期或退款已成熟 |
| 视图／跨schema对象 | 保留视图本身粒度与完整对象身份；同名旧表不自动沿用，底层依赖不可得时不假称完整读取图 |
| 与正式定义冲突 | 新观察、旧定义、准确版本及差异并列；只修本次能独立完成的结果，需要演进的源资产走原贡献／建设路径 |

“候选可信”不新建百分制或自动放行评分。可表达“当前范围有依据／待核验／不适用”及原因，并保留反例／未覆盖范围；适用范围的判断由Agent作出，不作为绕过权限或专业验收的Host通行证。

## 6. DBM04：有限采样与模型出口

结构足以回答时不必采样；确有需要时由Agent自主选择字段、时间／对象范围、样本或聚合观察、上限与核查方法。少量LIMIT不证明低执行成本或总体代表性，相关预算／取消／单值／字节限制仍沿驱动合同。Host不固定“每表读1000行、提top5、算唯一率、全库embedding”的流水线，不添加新embedding／模型服务。

样例值、SQL／参数、DDL／注释和结构都可能包含业务信息，按项目已授权的内容与目标模型出口提供；只获得结构资格不自动获得样例行、跨会话SQL或历史查询资格。**首批不默认摄取pg_stat_activity／全库查询历史**。已获准的项目资料、原报告或明确提供的SQL可供Agent按资料规则读取；未来若要新增活库历史采集，须另定明确范围，不借本补充自动开放。

有限样本的结果沿原文件／证据及结果版本保存，标实际覆盖、截断与错误；取样时间不变成可重现数据库快照。统计观察由数据库／Agent自主选用的工具完成，Host只管理环境与确切材料，不新增业务统计辅助器或强制检验方法库。

## 7. DBM05：候选的最小信息与准确留存

复用原数据说明修订、结构／结果回执、任务贡献／Studio候选及Binding，不建独立关系注册平台。每项按实际需要表达以下信息，不能由Host猜缺失字段：

- **命题及类别：** 字段含义、映射、关系或表达式；目录声明、有限观察、Agent推断或正式版本引用分开。
- **位置与条件：** 来源实例／配置修订、库／schema／对象／有序列组，两端粒度／方向／基数及必要租户、时间、过滤、空值条件；未知明确保留。
- **依据与限制：** 原结构观察、固定查询结果、数据说明及正式资产准确版本；观察范围、完整／截断、支持证据、冲突／反例及未覆盖，不重复复制另一套manifest。
- **沿革与适用性：** 原项目／任务／请求、提出者、修订／基础版本、替代或冲突关系，以及当前范围判断和原因；权限状态与业务适用判断分开。

探索时不强制先持久化整个目录；Agent声明某结构／关系被报告采用，或保存说明／候选时，Host固定其实际引用的准确观察与内容，沿原项目输入版本留存。标准JSON材料及摘要可复用驱动补充的文件能力；本节不冻结新数据库schema、API精确名称或另一套全域版本平台。

**最小新增接缝：** 原数据说明的文件位置增加数据库对象／查询表达式的可选定位及来源回执引用；旧文件位置与历史兼容。Agent保存复用原Store，补同一真实owner／权限下的受管调用；不能因已有HTTP保存路由就声称Agent工具已经接通。结构／关系输入送入现有Semantica候选提取／Studio时，补其原始位置和准确输入版本映射，不复制一份资产权威。具体字段与适用测试在获授权实施前按IN01–IN07记录。

## 8. DBM06：数据说明、Studio与Semantica连续承接

正常路径是：**连接配置与项目授权一次 → 直接提业务问题 → Agent按需读结构／正式资产、自主取数与核查 → 将本次必要说明和依据关联报告。** 有复用价值时再沿原资格准备任务贡献／建设候选，正式发布、项目采用和图刷新按原合同分别发生。箭头表达可发生的衔接，不是每个请求必须走完的阶段。

1. 普通分析可直接使用获准结构和原合格资产；Agent可准备说明及候选内容。持有现有合格owner／grant时才执行相应保存／贡献／建设动作，db-link不自动扩大普通Studio只读grant。
2. 项目内的观察、推断和临时约定先按原资料／数据说明保存。可复用贡献或源资产缺陷沿原Studio贡献／建设资格处理；无明确企业、目标或写资格时保留本任务草稿／缺口，不默认认领其他企业或暗开建设工具。
3. 原Agent准备准确候选、来源差异与发布预览；正式发布仍需原有效授权。已有自动化可完成的准备不推给用户逐字段维护，也不要求在两套系统重复认证。
4. Semantica按需要消费获准准确输入，复用现有抽取／构建／查询／规则能力；候选生成不自动写入正式图。正式来源、项目采用和图版本仍按原体系，图陈旧／失败／未知不会被新观察静默掩盖。
5. 业务指标／方法的公式、单位、适用条件与发布继续由原SAP等专业库及Studio维护；数据说明解释本项目实际材料与用法。Semantica派生图不是第二份公式或发布权威，推理成功不等于报告专业正确。

**示例：** 用户问“哪些门店复购偏低”。Agent可发现订单／会员表、保留真实`tenant_id＋member_id`关系并核对退款／交易状态；没有足够历史时保留观察不足。复购定义优先按合格准确版本读取，缺失或冲突时形成说明／候选。Host不预写复购SQL、不替Agent选择观察窗口，也不把样本中的首次购买自动发布成企业首购定义。用户无需先建齐语义图或逐表维护映射。

## 9. DBM07：变化、撤权与历史

换实际来源实例，或后续按需读取发现、由已有可靠通知获知相关对象／有序键／类型／视图定义差异时，只将已知受影响映射标待核验，不全面否定无关资产；依赖或覆盖无法定位时保留未知，不把未检查关系标为通过。这里不新增实时DDL监控、全库变化捕捉或所有差异均已发现的承诺，原结构回执仍只是其观察范围／时点的事实。数据变化产生新观察，不改写旧样本。凭据轮换本身不等于业务语义变化，但旧／新身份和访问资格必须重新核验；权限不足或读取失败不等同对象删除。

新观察／说明／候选／正式版本各自留沿革，旧报告仍引用旧输入与旧定义。正式资产不因换库同名字段就自动适用，Agent核查差异；Host不凭时间戳自动修复Binding或重写历史。撤权、归档、停止及迟到仍沿DB14／16：拒绝新派发和越权保存，未知不重放；迟到只补原操作技术事实，不触发新说明、候选、发布或核算。

## 10. DBM08：核算与冷读边界

默认RCR是知情复核，CNR不重算；数据库独立候选仍按原父请求择一与受管准入。元数据、语义和关系补充不扩大核算profile工具或文件权限，不把公开普通工具直接装进受保护会话。

首次冷读可用中性的真实目录观察、足够原始的固定输入及合格事前语义；**作者在本次分析中新增的关系推断、关联筛选、SQL表达式、脚本和答案属于作者方法／产物，不因保存成数据说明、Studio候选乃至后来发布就洗成事前材料。** 按产生时机和作者关联隔离，首次依据保存后才揭示。确需提前提供时应如实记为知情范围，不能仍称同范围冷读；新的技术材料格式不绕过该规则。

固定结果上的重算不证明关联／过滤／去重或时段完整；语义抽取、图构建／推理成功也不证明取数业务正确。同SQL实时再查是新观察，库可复现快照／充分原始范围仍按DB13及驱动合同核定，不由新关系候选替代。
