## 第1项：复用、归属与组件

**我的建议 A：** 正文、标题、范围和业务时间继续使用EnterpriseMaterial及其精确revision；工作历史仍归Pi；固定报告仍归M2／Project。仅新增本机个人保留决定与来源的引用记录、个人聚合查找UI。分类为知识／经验；概念投影已有明确引用，不新建概念对象。暂不安装记忆包、embedding或搜索服务。

**原因：** 既有正文、版本、检索工具都存在，缺的是人的保留与查找语义。固定`pi-memory`有启动／注入／压缩前写入等额外行为，`pi-memory-md`的完整实现及兼容没有验证，均不能凭研究当作可直接采用。细节见复用核查。

**替代 B：** 安装第三方包再配合一套自有正文／版本／检索库；扩大副作用与重复建设，不推荐。若后续出现词汇检索不足等已验证缺口，再独立评估组件，不用本包预批。

## 第2项：整理内容与身份

**我的建议 A：** 一个个人条目对应一个真实Enterprise `{storeId,materialId}`，不再造全局资产ID。允许两条真实路径：直接保留已有精确资料修订；或新建独立资料草稿写自己的整理，原文不改。后者复用既有编辑组件及原create／update，不再建正文编辑器／文件库。

正文标题、body、scope、effectiveTime、source、owner仍由Enterprise维护；适用前提、局限、反证、反馈或未知写在正文中。个人记录只增分类、别名、用户提醒和精确来源，不能另存第二份正式正文／公式。标题／列表预览从所选revision投影，不做第二份持久标题或Host语义摘要。

同一material只有一个个人条目；多次保留追加决定，不按标题或正文hash把不同material自动合并。来源关系由个人条目指向原权威，可多对多；删除／丢失来源不级联删个人条目。

初次个人整理资料为disabled，在原资料页仍可见。新增`freezeExact`仅固化已保存draft为给定稳定revisionId，**不切换enabled或activeRevisionId**。用户可在原资料页另行启用；现有catalog会显示该enabled资料的全部revision，后续固化也会沿原规则可见。个人保留、归档不撤回这种另行启用，不承诺“仅个人私有”或全系统隐藏。

**原因：** 保留≠资料启用。保持原schema1和目录权威，比加入私有资料类型／ACL、藏入Markdown frontmatter或给原索引加个人字段更小。当前个人阶段没有新增账号／团队共享。

**替代 B：** 用category、enabled或正文中的隐藏frontmatter推导保留状态；会混淆权威，且仍产生未明示的新合同，不推荐。

## 第3项：来源、字段与未知

**我的建议 A：** 保留时冻结以下个人元信息及精确来源；只接受原权威可校验的身份，全部来源都不等于已核验。

| 字段组 | 含义、格式及空值 |
| --- | --- |
| 个人分类`kind` | 用户明确选择`knowledge`／`experience`；不是按标题／category自动分类，不是事实可信度 |
| 别名`aliases` | 用户词汇列表，可空；最多20项、每项100 UTF-16字符；不自动认定同义词或改原定义 |
| 适用提醒`caution` | 用户填写的短提醒，可null，最多2,000 UTF-16字符；随保留版本固定，查找结果直接展示，不由Host抽取／判断 |
| 草稿元信息 | 上述kind／aliases／caution／sourceRefs的未发布编辑；与当前保留快照分开，带个人条目CAS |
| 精确内容引用 | `{storeId,materialId,revisionId}`，并核原权威正文hash；已保留版本不指向可变draft |
| 来源列表`sourceRefs` | 可空。无外部引用的人工笔记显示“人工记录，外部原文未记录”；不能造来源或默认成功 |
| 来源资料 | Enterprise三元ref；片段复用UTF-16半开`[start,end)`，校验边界及精确原文 |
| 固定报告／附件 | `{projectId,citationId}`及明确报告／附件位置；必要片段指向该固定文本，不复制M2证据；不能只用工作路径／hash代替旧稿 |
| 原生回复 | 真实`projectId/taskId/sessionId/messageId`及预览全文SHA-256，可选片段；按原`readSavedTaskReply`校验，不复制JSONL，不调用Agent |
| 反馈修订 | 真实`sourceProjectId/boardTaskId/feedbackRevisionId`；核Task→Item→Project和该revision归属，不能用updatedAt冒充历史 |
| 保留决定 | 稳定`operationId`／决定ID、决定动作／时间、个人标签（可null）、精确内容ref、元信息快照；标签不冒充认证身份 |

来源可多项；同一原材料可支持多条整理。新保留引用必须真实存在且精确文本可校验；已停用但旧稿可读的资料可明确按旧稿保留，并显示停用。缺失／损坏的新绑定拒绝，草稿保留；用户可另行改成无外部原文的人工记录，系统不能自动删掉坏ref后伪报成功。历史来源后来不可用时保留ref并提示，个人整理正文仍按自己的精确revision读取。

所有可选文字片段统一按所引用精确文本的UTF-16半开`[start,end)`，无片段即引用全文，不代表全文已读或已核验。附件没有可读文字时只保留其原精确身份／文件定位，不编造文字片段或自动OCR。

**原因：** 四种来源已有稳定读取接缝，不必扩成六库统一枚举。当前Case／Board行没有完整历史读取，本包不为凑类别再造快照；需要当时决策可用固定报告或反馈revision。业务时间可未知，不能拿保存时间替代。

**替代 B：** 只存自由文本链接，或复制所有会话／报告进新库；分别丢来源可核性或重复原权威，不推荐。

## 第4项：草稿、保留、修订和归档

**我的建议 A：** 个人条目保留“工作草稿”与“当前已保留版”两个含义，而非编辑一下就撤掉旧保留版。

- 保存草稿：沿原资料保存正文；个人草稿信息另存为未发布记录。任何一个环节未核定成功就显示部分／UNKNOWN，保留输入，不把它说成原子成功。
- 首次保留：用户明确核对已保存内容及个人信息；成功发布后才出现默认已保留项。标题和字段上限沿现有API；内容至少有文字正文或可回读的原资料附件，二者皆空不保留。仅附件时明确“无文字正文”，沿原附件阅读，不自动OCR或制造正文命中；业务范围、时间、反馈可未知。
- 保留旧修订：用户可明确选一个已有精确revision，不固化当前新draft；内容与来源按本次选择记录。
- 已保留后编辑：旧保留ref和元信息仍为默认版本，新稿提示“尚未保留”。明确保留新稿才更换指针，普通草稿保存不自动升级。
- 归档：设置个人发现状态，旧决定和正文继续可读；草稿条目也可归档。它不删除Enterprise内容／源材料，也不改变enabled。
- 恢复：恢复个人发现资格；有旧保留ref就继续用该旧版，无保留ref仍是草稿。不自动保留最新draft、不判断业务仍适用。

个人决定及其内容ref／来源／分类／提醒只追加历史；当前指针可变，不回写旧决定。正文history仍只由Enterprise承担，没有第二套正文版本引擎。

**原因：** 将人的保留决定与资料编写、业务正确性和实际效果分开，历史引用不会随今天编辑漂移。

**替代 B：** 保存即保留、修改即覆盖旧稿、归档即删源、恢复即用latest；均不采用。

## 第5项：个人查找与本期接入范围

**我的建议 A：** 在现有工作台增加一个“个人资料”入口，用一个查找页按概念／知识／经验／项目数据浏览，不新增四个工作台。

| 查找对象 | 当前依据与边界 |
| --- | --- |
| 知识／经验 | 默认个人已保留且未归档的精确版本；草稿／归档由用户显式打开筛选；来源不可用仍显示具体提示 |
| 概念说明 | 聚合M2字段映射中用户实际选过的精确Enterprise refs，不从标题／category猜概念；没有登记就显示空态并可回原资料／映射入口 |
| 项目数据 | 仅聚合M2真实登记及项目归属、固定版本元信息；原项目中阅读／维护，归档项目明确标识，不扫工作区或010 |
| 默认列表／关键词 | 名称、别名、范围及正文预览；匹配标题／别名／范围，可显式包含正文关键词匹配。查询最多200 UTF-16字符，分页显示，不静默省略不可读取的来源 |

复用目录筛选与精确正文读取，按请求做确定性匹配；不持久化新的全文／向量索引，不调用模型生成摘要。正文预览是明确的截取，不当作语义总结。来源读取失败可报告部分结果和未核范围，不把失败当空结果，不用相关性判断正确性。中文近义词先由用户别名表达，代表场景不足再提出检索增强，不预先承诺语义召回效果。

本期提供阅读、来源打开及回原项目入口；不自动给任务注入保留内容、不新增`providedContext`或memory会话。M4才把保留内容接进第二事项的显式提供／引用及适用／拒用。原Enterprise资料本来可被普通任务使用，仍按其独立的启用与选择合同工作。

**原因：** 补齐真实个人资料查找，复用已有读取能力；不会把虚拟能力目录当真实资产，也不先建通用搜索后端。

**替代 B：** 自动把所有经验塞入每次会话、默认语义搜索／后台整理；会越过本期范围和原profile边界，不采用。

## 第6项：最小持久化、并发、失败与回退

**我的建议 A：** 在`dataRoot/personal-retention/records.json`增加一个schema1个人引用／决定文件，绑定真实Enterprise storeId。该文件是个人决定权威，不是第二正文库或搜索数据库；索引／查找投影在内存按原权威派生。

| 逻辑组 | 最小职责 |
| --- | --- |
| 文件头 | schemaVersion、storeId及技术文件revision；未知格式／损坏／丢失历史不重置 |
| 个人条目 | materialId、个人已提交条目revision、草稿元信息、当前保留决定ref或null、归档状态；没有保留ref即未保留 |
| 决定历史 | 以operationId为稳定决定ID；保留／归档／恢复动作、时点、精确内容ref和本次元信息快照；显式结束未完成保留另留终结回执及原请求／fingerprint、原失败或UNKNOWN、已知固化ref或null；保留时间不代替业务时间 |
| 待完成保留 | 每条目至多一个局部intent：operationId、完整规范化fingerprint、目标revisionId、个人基准revision、原material version／draft身份及待发布元信息；不移动旧保留指针 |

### 保留的发布点

1. 普通正文草稿先沿原资料create／update明确保存并取得materialId。它们目前没有完整操作幂等；回应不明时回查并保留UNKNOWN，不能盲目再创建或宣称已成功。
2. 新保留请求固定operationId。保留已存在revision时直接核该ref；保留已保存draft时，目标revisionId可复用该operationId。
3. 在原Host短时文件变更门内核个人条目CAS、正文身份和来源，先原子保存完整待完成intent／fingerprint，旧保留版继续可读。它只约束本条目，不建立全局Agent或事务队列。
4. `freezeExact`以给定material version／draft身份固定目标revision；目标已存在则只核原内容，不改为固化当前新draft；enabled／active不切换。
5. 回读精确内容后，原子发布个人决定快照及当前ref。**此步才是“已保留”。** 成功后决定本身承担同操作回执，无第二操作台账。

同操作／同完整请求跨重开回读原结果；同ID改分类、来源或内容拒绝。intent已写、正文未固化或正文已固化、个人决定未发布都保持未完成／UNKNOWN；只允许显式同请求核对／继续，不自动重放、合并、换ID或切latest。个人目标基准已变、正文在固化前已变、精确来源不符则冲突并保留现场；已经固定的目标仍按旧hash核，不受后来draft变化替换。并发归档／修改同条目须先处理待完成操作；无关条目不被局部intent长期占用。

**显式结束未完成保留：** 用户可选择“结束本次保留”。在原Host变更门内，先排除该条目仍在途的写入并核读个人权威；若同operation已发布，返回原成功，不把成功伪改取消；若确认未发布，追加上述终结回执，释放该条目的intent占用，旧保留指针不变。原请求、失败／UNKNOWN及已固化或状态尚不明的正文全部保留，不删除／回滚正文，不宣称固化从未发生。个人权威无法核读时继续UNKNOWN，不能清空记录。已终结operation后续只回读原终结结果，不能再继续固化／发布；用户修正草稿／来源后可明确发起新ID的新请求，两次历史分别可查，不能自动换ID掩盖旧失败。

普通草稿信息写入也核个人CAS；正文保存与个人信息若部分成功须分别反馈。个人记录复用已有安全路径／原子JSON原语，技术文件首版限2MiB，写入超限明确拒绝并保留旧文件；正文沿Enterprise既有1MiB限制。它们是材料／存储预算，不是Agent方法或调用配额。

不改Enterprise schema1、Pi JSONL、M2 schema1、Project schema2、SQLite或RAP／SAP。旧资料不自动标保留；新个人文件不存在时显示空库，存在但损坏不得以空库替代。回退代码忽略个人文件并继续读原Enterprise内容；保留全部新正文／决定／UNKNOWN，不恢复旧数据覆盖新工作，不自动清理孤立内容。

**原因：** 固化正文与发表个人决定是两个权威，局部intent避免“正文写成就冒认保留成功”及中断后换来源重试。它是已验证的新业务差额，不扩成跨库事务平台或平行SDK运行机制。

**替代 B：** 只存最后指针、freeze后无完整请求记录、失败重建空库或重试当前draft；会丢保留决定／历史身份，不采用。
