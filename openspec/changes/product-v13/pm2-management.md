# 所选目标的经营要求和原讨论人工采用

## R3 项目采用准确的历史版本

在 GSA 已有 v2 时，从 v1 的入口新建项目。v1 和 v2 都有各自的截止日、资源、必要条件、目标、策略和负责者。合成项目没有 Case 或旧 Plan。真实 Chromium 重开项目并依次向 Project Agent 与手建 Task 发送一次，两份原生 Pi 实收内容均与 v1 一致。项目页的「所选目标」可读这三项。由侧栏独立建立的项目仍可用。原测试在 Pi 请求里找不到 v1 日期，修正后通过。记录见 `.local/product-v13/pm2/management/project-{red,green}.log` 及 `tests/browser-v13-project-goal.mjs`。

## R5 战略原讨论内的人工采用

战略原讨论与 GSA 共用目标 G、策略 S 对照组件。首次采用显示将建立的内容。用户在原讨论编辑候选时，对照随草稿更新，区分仅 G、仅 S、两者均有变化；原截止时间在日期未编辑时按原值保存。确认发送用户所见的采用版本、候选版本、准确内容摘要与原操作 ID。另一位使用者改变采用版时收到 409，界面重新显示当前正式对照并保留已填内容。已经另存的新稿可以接着确认。

Chromium 操作原讨论窗口，并以同一 Host 的公开采用请求模拟另一位操作者。实测首次采用、只改 S、v1 切到 v2 期间确认 v3 被拒、明确重看后采用 v3。编辑 v5 产生 v6 时另一窗口采用 v4，原编辑仅新增一个 v6。还分别在编辑后及未编辑状态模拟保存已完成而浏览器未收到应答，重开沿原收据恢复。原来「已采用」的卡片没有恢复入口时测试失败，现仅对有待核操作的卡片开放读回。同一已完成 POST 原样重送返回原结果，改写决定仍为 409。旧格式按当时完整版本计算的操作摘要也沿原口径精确核对。引语采用与 UI 确认分别保留各自的来源。记录见 `.local/product-v13/pm2/management/discussion-{red,green2}.log`、`reopen-red.log`、`adoption-quote-{compat,green2}.log`，以及隔离回退演练。原生提供端只用于生成原讨论候选，人工确认过程中没有调用模型。

独立规格、规范复核与固定提交全量回归见本轮最终回交。对批准产品的达成程度由原 PM 独立复核。
