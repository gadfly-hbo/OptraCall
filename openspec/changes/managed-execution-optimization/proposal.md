# 托管执行资源优化方案

日期：2026-11-01。状态：用户已通过方案／spec，内部合同 D1–D8 全采用 A，已授权本地实施、检查、性能对照复测及非作者独立复核；不做 Git/CI 交付、不切换运行服务。

## 方案要解决什么

把频繁文件工具的重复启动与初始化减掉，把已确定结束的执行组及时收回。后台计算继续归原任务管理；原件保护、停止及 UNKNOWN 继续成立。

依据是[已完成的资源评估](../automatic-verification-revision/resource-overhead-evaluation.md)，不是新测量：同一候选 5 的 18 次本地固定 Provider 对照中，48 次 read＋12 次 bash 的工具往返段中位数从关闭托管的 0.360 秒变成 21.664 秒；托管阶段保留了 60 个 guardian 和 60 个已退出的组 leader。60 个 guardian 自身 footprint 约 567 MiB。阶段关闭后均释放，本次优化针对阶段内积累与重复开销。

这不代表 29 秒 CPU 增量全来自监督轮询。导入、创建、工具初始化、保护检查等尚未做函数级归因。当前 guardian 探针、权限 profile 和解释器选择已经按 scope 初始化，不能再次将它们“提升到 scope”算成新收益。

## 大白话要点

1. **读写文件时，不再每次重新开一整套工具环境。** 同一阶段准备一套受保护的文件工具，反复使用；主 Agent 与核算 Agent 各有自己的环境。
2. **计算仍由 Agent 决定怎么做。** bash、Python、codemode 继续独立执行，可以并行、可以在后台跨工具运行；本期不把任意代码放进同一个共享进程。
3. **做完且确认没后台工作的，就及时收走。** 工具返回不等于后台结束；仍在计算的保留，已经真正结束的释放，不再累计到整个阶段结束。
4. **停止和“不知道是否收干净”继续认真处理。** 用户停止仍收回整个任务范围；无法证实就保留忙碌／UNKNOWN，不冒充完成，不自动重跑分析。

## 采用的具体方案

### 1. 只在原执行 scope 内复用文件工具

复用单位是现有不可变 execution scope：同一公共 Resource／owner、执行代际、profile、cwd、读写目录、工具集合、环境快照及保护策略。以原 scope 身份为准，不能仅以路径相同判断可以共用。

一个 scope 最多建立一套 **native 文件执行器＋其 guardian**，只承接现有 `read`、`write`、`edit`、`ls`。它没有模型、会话 API 或 Agent JS 执行入口。现有 SDK 通过 `src/agent/sdk.ts` 创建这些原生工具；工具定义与初始化复用，每次调用仍使用独立 toolCallId、参数、AbortSignal、进展和结果接收器。

四工具白名单由共享 worker 自身固定，不能只信请求里的 toolNames；不创建 codemode、`context.executeTool` 或动态 module/source 入口，也不接受每条消息改变环境、目录权限或会话身份。

这四个工具在当前 SDK 中主要使用文件操作。`read` 仍保留图片支持及 SDK 自己的图像处理，不能为了复用关闭图片功能或改变输出；图片线程、取消后的异步尾部也属于本 scope，关闭时必须等实际进程消失。`write/edit` 保留 SDK 自带同文件 mutation queue，不再加 Host 分析队列，不串行不同文件的调用。

文件执行器按首次实际文件调用创建，不在选择任务、GET、保存设置时预热。一个初始化 Promise 合并同 scope 的并发首次调用；创建失败不另起第二套环境，也不自动重放已受理调用。整个 scope 不用文件工具就不创建它。

### 2. bash、codemode、grep、find 保留独立执行组

这些工具本期仍沿用每调用独立 guardian／受限 Node 执行组。bash/Python 的后台与并行能力、codemode 内的任意 Agent JS 和嵌套工具保持原路径。grep/find 有 SDK 子进程与取消时窗，先保留隔离，避免同时改造其执行合同。

**本期明确不消除上述四类工具的单次创建成本。** 60 次基准中的 12 次 bash 仍要创建原执行组。若实际工作主要由 bash/codemode 构成，本期主要改善留存，而不保证明显缩短启动时间。

不新增跨信任边界的 shell 启动 broker、一次性执行凭证系统或全局进程池；不将 codemode 放入文件执行器。后续若要消除 bash 初始化成本，需另行证明原生 BashOperations、单调用取消和后台组身份的等价性，不能隐含在本期实现中。

### 3. 已自然结束的独立组提前回收

原来独立工具结果返回后，guardian 及未 reap 的 leader 通常留到阶段结束。本期允许 guardian 持续观察自己已持有身份的那个组：确认只剩已退出、不能再执行的 pinned leader，再 waitpid，最后核对组不存在，才完成该组的自然回收。

这是无信号的自然结束收集，不是按工具结果启动一次强制 close。工具返回但后台子进程仍存在、后台重定向后继续计算、JS 定时任务仍在运行时，不得回收。结果先返回，回收可在后续工具及 Agent 思考期间完成；不因此阻塞下一个已获准工具。

首次自然收集与显式 stop／close 共用同一组的一次退休过程及结果。失败后保留原失败，不由下一次工具、finally 或定时器暗中重试。只有原公共生命周期授予的显式 `retryFailed` 才可重试清理；不能重跑工具或模型。

当前 supervisor 的 `clear_group()` 会发送 SIGKILL，不能用于这条自然收集路径；需要明确区分无信号的自然核定与已授权强制停止。

### 4. 文件工具取消与整个 scope 停止分开

单次文件工具取消只传给该次 SDK AbortSignal，不杀共享文件组，更不能杀另一个 bash/codemode 组。保持原生取消结果与错误语义；不得回放调用，或把已经发生的写入报告成回滚成功。

当前 SDK 的 read/ls 可能在内部异步工作结束前先 reject 外层 Promise；read 图片处理也可能仍有线程。因此“所有工具 Promise 已 settle”只用于停止接收新调用和释放协议保活，**不能用来证明资源已结束**。潜在异步尾部仍归当前 scope，正常交接必须经过下面的实际退出证明。

用户 stop 则经原公共 owner/lease 收回本 scope 的共享文件组和全部独立组；仍由各 guardian 持有实际身份并核定关闭。不能给共享 worker 加 `process.exit()` 伪造自然完成，也不能把工具取消升级为静默重启共享执行器。

### 5. 阶段交接仍要真正排空

普通执行→核算、核算→主 Agent 修订、修订→新稿复查，继续使用原公共 v3 `quiesce/drain/close` 边界：

1. 封住本 scope 的新派发，处理已受理调用；晚到消息不能再开工。
2. 文件执行器只释放控制连接自身的 event-loop 保活，让 SDK 异步工作及线程自然结束，不发强停信号。
3. 等文件执行组实际自然退出；独立组则等后台自然完成。所有组都须完成 held leader→只剩已退出 leader→waitpid→最终组消失的证明。
4. guardian 自身、通道与驱动资源也要实际释放。只有全部已关闭，公共 Resource 才能结束占用，并由可信 SDK 写入原 `closed` 记录。

显式 stop 可以打断自然等待并沿原权限强制清理；证明失败仍 busy／UNKNOWN。Host 重启丢失可信身份时，不从记录或数字 PGID 恢复接管，不自动换成非托管执行。

正常释放必须有独立协议含义。现有 worker 的通道结束会触发 shutdown/abort，不能直接沿用为正常 drain；意外断连仍走故障／停止路径，不能当作自然释放。

### 6. 释放对象，保留证据

每次调用的缓冲、进展回调、Abort listener、timer 和 pending Promise 在实际不再使用时释放；已证明关闭的独立组从活动集合移除。未关闭组、未证实的异步尾部及失败退休记录不能被当作垃圾删除。

同一 scope 的调用去重身份仍保留到原合同允许释放的边界，不能为了内存曲线删除到允许同 ID 再次执行。少量去重元数据可随调用数增长，需单列测量；本期要求不再保留每个已完成调用的一整套进程、SDK、监听器和结果副本，不承诺所有字节严格恒定。

codemode store 路径、内容与现有并发语义本期不改，不改成共享内存服务、不截断、不迁移；文件执行器不加载它。原生历史、工具进展、报告、新稿和 FAIL/UNKNOWN 证据照常保留；清理运行对象不等于删除文件。

## 权限与产品原则

| 责任 | 本期做什么 | 边界 |
| --- | --- | --- |
| Host／公共生命周期 | 提供同 scope 资源、权限、消息关联、停止与实际关闭记录 | 不判断业务正确性、不补算、不重放模型 |
| 无模型执行器与 guardian | 调用原生 SDK 工具；管理自身进程及 OS 身份证明 | worker 数据不能成为生命周期控制指令；不持有 native／凭据权限 |
| Agent | 自主选工具、写代码、并行、后台、解释和修改分析 | 不增加固定分析步骤、工具次数或时长限制 |
| 用户 | 原有任务／自动核算设置及显式停止 | 不新增产品开关或必须学习的工作流 |

这项调整符合“Host 管环境、Agent 自主分析”：路由只按工具的执行隔离需求决定资源放置，不按问题、计算方法、结论或核算意见决定 Agent 下一步。共享文件工具不能变成 Host 的计划执行器，也不能通过排队或关闭后台工作变相限制分析。

保留原 profile、sandbox、native／凭据禁读禁写、不可变代码、禁止脱组及外部间接执行、同版本直达解释器和环境去密钥。逐调用 `plainTree` 检查先保留；本轮不做目录安全检查缓存。已有扩展／MCP 准入限制不扩大，也不解除。

权限按既有 profile 的适用范围保留：普通托管阶段仍可写原 020/060，010 仍是原软提示；核算／返修的原件只读和专属输出范围不能扩成全产品普通分析限制。

## 接入与兼容

公共 Interface 保持 **v3**；普通非自动任务仍用既有模式，业务 v1/v2 消费者不变。owner/profile 和公共 busy／stop／retirement 权威不变。内部多路消息格式需要版本握手，但不是公共 Interface v4。

`optracall.execution` 的 v1 `opened/closed` 含义不变：它们覆盖整个 scope，而不是某一个工具组；不能每收掉一个子组就提前写 `closed`。可信 SDK 仍是唯一 native 写入者。

不增加业务表、持久恢复证书或项目迁移。不跨任务、主 Agent／核算 Agent、阶段、权限或 Host 重启复用。项目、会话、原文件及现有 WIP 全部保留。UI 无变化，因此本次不另做 UI Demo。

## 实施顺序与验证门槛

实施按固定内部合同和失败路径、文件执行器复用、独立组自然收集、性能对照的顺序进行；安全项通过后才评价收益。具体要求见 [spec](spec.md)、[已确认内部合同](structure-decisions.md)与[验证计划](validation-plan.md)，实际完成范围见[实施结果](implementation-result.md)。

已确认的工程实验目标：原 60 次混合工具场景中，工具往返段相对当前托管中位数下降至少 70%；频繁场景配对 CPU 增量下降至少 60%；主要受益应来自 read 及少保留进程，不能要求仍隔离的 bash 同样达到低延迟。这些数字是本轮实验验收门槛，不是生产 SLA；实际结果见[性能复测](performance-result.md)。

本方案不改善模型的专业检错能力，也不改变独立核算链的分析策略。既有专业错误、漏报、取消及 UNKNOWN 保留，性能优化不能作为其验收通过的替代。
