## 3. 同批性能对照

原 18 次记录只作历史参照。未来主试验采用三个条件：关闭托管、原候选 5 托管、新候选托管；每场景每条件 3 次，共 **27 次**。预先固定轮换顺序；原 off／原托管仍覆盖原 18 次的全部条件与固定工作量。另做新候选 off 兼容核对，不能默认新代码对 off 没影响。

三个负载继续使用原已冻结工作量：

- 长计算：286,123,113 次同一哈希迭代，不重新校准成不同工作量。
- 频繁调用：48 read＋12 简单 bash，之后同一 30 秒无新工具窗口。每次内容与命令不改，不以工具合并代替 60 次调用。
- 后台并行：4 个各 38,149,748 次迭代任务；主请求另做 8 次 read，最终两边都等同一批真实工作完成。

每次记录版本／完整 WIP 快照、Node/SDK/Python、解释器实际入口、硬件／系统、参数、HTTP／工具数、stdout、计算摘要、PID/PGID/PPID、角色、实际关闭证明、请求耗时、CPU 秒、footprint、RSS、活进程和 Z。新旧入口不同不得归因为纯监督微基准；必要时另做同解释器诊断，但不替换产品实际路径对照。

不丢失败、不按结果补跑。确定性 Provider 只用于消除推理／网络抖动，真实模型请求为 0；此项不证明模型策略或专业可靠性。生产模型全链路是否另测，按后续实施授权与验证范围报告。

### 统计口径

- 用 Provider 发出工具至匹配回复请求的时间测本地工具 RTT；SSE 展示事件可能合并，不能当单工具精确时钟。p50/p95 先每次计算，再汇总中位数。
- 主请求、纯工具段、scope drain／close 分列；提前回收的 CPU 仍纳入整个 Host 生命周期，不能挪到观察窗外省略。
- 用同批每组 off 配对计算 CPU 增量，再比较两种托管增量；若原增量接近 0，则不计算误导性降幅，改报原值与“不适用”。长／并行主请求退化门槛相对同批原托管，中位数之外保留全部个体与配对范围。
- `/usr/bin/time` 的 Host＋已等待后代与 PPID1 后台家族分开核对，避免遗漏或父子双算。libproc 原 CPU ticks 必须用实际 Mach timebase 换算。测量器、time wrapper 和 Provider 不混进产品资源数，测量器自身负载单列。
- RSS 合计可能重复共享页，footprint 合计也不是整机净增 RAM；均按 MiB（2^20 字节）。CPU 百分比按单核说明。采样峰值是观测值，附采样间隔与短命进程漏采限制。

MO11 的 70%／60%／5% 已随 spec 获得用户确认，只是实验验收门槛，不是已实现收益。所有门槛按同批原始值重算，不直接拿旧机器负载下的 21.664 秒当新批次分母。不得把它们实现为 Agent 超时、预算、工具次数或并行限制。

## 4. 积累、长驻及真实并行

在独立合成 scope 内，预先固定 60／300／1000 次短文件调用阶梯；每档结束观察无新调用窗口，记录常驻组、已闭组、未闭组、去重项、buffer/listener/timer、堆与 GC。成功自然收集后已闭独立组不能累计为一组一 guardian／Z。

另设预定 1 小时留驻观察，覆盖文件调用、无工具等待、正常后台与显式停止；**1 小时仅为测试长度，不是产品执行上限**。同时观察真实后台活动量增长与已完成调用积累，不能用仍在计算的作业证明“泄漏”。完成或停止后核各实际身份及最终 OS 消失，不能只看父进程列表。

补大目录逐调用 plainTree、较大文件／图片及多个项目并发，给出数据规模与原始值；这些是拓展测量，不把小项目目标直接变成大目录 SLA，不自动引入目录缓存。共享文件 worker 崩溃时不能换新 worker 续跑来美化长驻曲线。
