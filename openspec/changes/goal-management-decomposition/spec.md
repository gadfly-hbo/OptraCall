## 3 用户路径与业务合同

### 3.1 承接与确认总 GSA

GM01–02。已有有效正式战略发布时导入该目标及发布身份。可供目标管理承接的正式地图须含明确目标值，在战略选择发布前校验。现有“无可承接目标的战略记录发布”保留为记录，但不能标成可承接地图。不得从方案标题或文本片段猜测正式数值。指标引用准确 SAP 版，范围沿用当前明确选择，基线未知可标待补。

该事项／范围的战略未启动或尚无可承接正式地图时，在同一张 GSA 手动拟定 G 并标记来源。仅有“0 个可承接目标”的战略记录不等于已有适用正式地图，既不把它当 G 导入，也不能因此把两种目标入口都锁死，保留补目标后再正式发布的原路径。若之后对应地图正式发布，展示手填值和发布值，负责人决定承接，不能覆盖旧记录。已有适用正式版时不得绕过它手填另一个组织总目标。

无正式战略值时，允许在总 GSA 确认前，基于当前准确的总目标草稿和获准材料取得或引用整体可达测算，作为手动拟定 G 的依据。草稿测算沿原 goal-draft owner 的明确受限分析变体，经同一会话域接入，不开放采用／发布工具；原有未启用分析的 goal-draft 权限保持。测算不先确认一个临时 G，不强制创建 Task，确认 G／S／A 后才进入正式贡献拆解和时间计划。已有正式值也可先核可达性，但不改发布值。

总 GSA 包含 G 的期间、范围、定义、正式值与责任人，S 的具体策略、来源与假设，以及 A 的关键行动、上层阶段检查点和观察依据。从战略承接候选后直接进入该表，保留已预填值。总 GSA 一次确认同时完成原目标采用和计划 A 的确认。原产品已采用但缺计划 A 的目标补确认 A 后才开始新的拆解，不改写历史采用事实。

计划 A 单独标识为计划，既有 `GoalActionArrangement` 继续只代表从原任务／Case／看板取得的实际授权安排。确认 GSA 不创建任务、不派人执行、不产生 Board 授权。例如计划“安排首购回访”或修订该 A 不发起触达，不因关联过去的授权就显示本期已执行。总目标只有 G＋S 时可存草稿并继续讨论，尚不能发布子目标计划。

#### 试用修正 · 拆解入口和总 GSA 修改（已确认）

- **正确的工作目标。** 目标管理作为独立一级模块。新建、战略承接、修订成功后使用回执中的目标身份与版本打开唯一工作区；取消后回到原目标。重开恢复上次选定的目标和阶段。处于已结束周期时显示只读状态及切换到当前目标的入口。
- **首屏能进入拆解。** 总 GSA 已确认就直接继续已有工作。资料齐备但待确认时，标题旁可一次确认并进入。缺资料时，首屏一次列出正式 G 及来源、策略 S、计划 A、阶段检查点、观察依据中实际缺少的项目。“查看并补齐”定位到第一个待办项目，真正的确认按钮待资料齐备后启用。已登记的适用战略发布可在原表明确承接 G 和 S，已填内容保留。
- **确认前修改，确认后修订。** “修改 GSA”可增删和修改计划 A、检查点及观察依据，保存仍是候选。“修订总 GSA”先形成修订草稿。负责人核对差异并写明原因后才形成新的正式 GSA 版本。取消保留原文，内容未变时不能另发新版。采用上游正式目标的场景先沿正式战略修订、发布再承接。仅调整拆解分配或下层周计划时按 GM09 只修订拆解。
- **历史与继续工作。** 已发布的拆解、阶段检查、Case 及导出绑定原 GSA。承接新 GSA 后，已有草稿或正式表由负责人明确核对新旧上层计划再继续。发布结果待核时沿原意图恢复。

**按手填要点优化。** 当前 G、S 已明确时，计划 A、阶段检查点或观察依据的任一框有关键词或句子，负责人即可主动点「Agent 一键优化计划」。Agent 同时读取本行文字和当前 G、S，把要点整理成行动、检查安排和建议核对的记录，直接填回三个原框。原有“推荐”仍只补空项；只有“优化”会改写已有文字。可以跳过两项辅助，直接手填并确认。

- **保留业务约束。** 原文给定的数额及单位、上限／下限、范围及排除对象、时点、先后关系和禁用资料均属约束。例如“华东 3 家门店，周五前完成新品陈列，不追加预算”，优化稿须保留三家、区域、期限和预算限制。检查依据可建议查阅的记录，不能将建议写成已核实的事实或新增经营承诺。若同一句另写“仅用 POS 日报，不用照片”，检查栏须承接原期限，依据栏须沿用获准凭证；日报查不到的陈列事实保留为待核。如果只写了禁用的凭证而没有可用依据，保留原限制并提示补观察依据，继续按缺项保存草稿；补上允许使用的依据后可确认。来源有歧义时保留原意，需取舍的部分交负责人。空白原文不可发起优化。
- **改后仍是同一草稿。** 在本次编辑中，负责人可就地改写或撤销刚完成的优化。撤销按字段恢复优化前的文字，保留优化后已由负责人改动的字段。编辑器内取消、保存、正式确认或修订按原流程执行。确认值取负责人最后所见的正文，保留历史版本。
- **失败、晚回和并发。** 正式产品仅在本次目标、G/S、版本和编辑行仍匹配时应用结果。发起后人工又改动的字段优先；返回失败或资格变化保留输入，可以手填或主动重试。撤销和迟到回复不能改到另一行、另一目标或已确认版本。

**正式产品接入。** 沿用项目锁定的官方 Pi 1.4.0、统一业务角色会话和原生工具结果回读。现有 `propose-goal` 产物对应整份目标候选；本增量需承载 GSA 计划项与检查点的结构化建议，保留本次选择的「只补空项／优化已有文字」与发起时的字段值，按当前目标、G/S 及编辑行校验后回填。由 Agent 决定行动及依据，由 Host 管上下文、权限、返回的归属及表单合并。沿用现有草稿保存和 GSA 确认契约。推荐和优化各由负责人自愿点击一次。原手填路径照常可用。

**验收边界。** Demo 的 Agent 使用合成零售样例。产品工程须以不同 G/S 和人工输入经真实 Pi 接线验证建议对应当前策略，并检验失败、晚到回复和人工改稿。推荐或优化的结果在负责人确认前均为草稿。

### 3.2 Agent 协作与三步成果

GM03–05。从当前已确认 GSA 发起普通对话，默认带入准确版及已经获准、未被排除的资料。无需新建项目、重传文件、安装 Skill 或逐次批准普通读取。资料或插件需要新增授权时才使用原有授权入口，当前许可不足可继续有依据的部分。

第一步形成整体可达测算。三情是证据分类，不是三个必须填满的表单，也不指定权重、算法或调用次数。测算与正式值必须同指标定义、单位、范围、期间才计算差额。缺口为正式值减测算值，负值显示预计余量，不虚构补缺需求。

第二步按贡献拆解。目标行记录覆盖对象、责任范围、G＋S、贡献性质、依据及上层关系。责任分配、可加总关系和策略驱动假设分别表达。同一批销售的渠道／品类／人群只是不同视图，共用一组明细身份，不能多次计入总目标。比率保留同定义分子分母，预计分母标假设，实际按成熟且可比的分母重算。不能平均各门店比率，也不能用销售额相加规则处理里程碑目标。

第三步安排时间计划。按商品季、上市与供货、节假日和活动等已知约束分布到月、周，必要时细到日。每个纳入跟进的责任目标至少有一个明确检查点和证据来源。阶段目标尚未商定显示“本期未定计划”，不可自作线性均摊。观察窗未满显示待观察。

这三步描述应交付的业务结果与承接顺序。Agent 可先核上市时间再回改测算，也可反复查询、计算、重算。Host 不编排固定分析链。对话修改保留人的原输入，更新草稿 revision 并呈现受影响数字、依据及检查点，不覆盖期间的人工修改。

**首张拆解表与自动保存（F9、F10）。** GSA 确认后，负责人可以发送自定义要求，也可核对界面展示的完整快捷要求，点一次即按原文起草。其他已写的输入保留。确认 GSA、浏览建议均不会发送指令。输入中未承诺的预算、预留负责人或补缺策略不能冒作负责人要求。Agent 的建议在草稿内注明，正式承诺由负责人发布时核对。

人工修改与 Agent 更新均按目标和草稿版本自动保存。显示保存中、已保存或失败；失败留住改稿并提供重试。刷新、换目标、迟到保存不能造成串写、覆盖较新草稿或把未保存显示成已保存。发布预览只可读取已成功保存的准确草稿；进入预览与确认发布分开。交叉项不一致仍可保存，正式发布继续由既有校验把关。

### 3.3 发布校验

GM06–07。“核对并发布”先打开只读预览，不生成发布意图、不保存正式版。预览与主表共同提供准确总 GSA 计划版、测算与差额、贡献和时间计划、预留、补缺策略、校验问题及版本变化；负责人能核对本次正式承诺行的准确 G／S、责任范围／负责人和检查点，再一次“确认发布 vN”。主要信息直接可读，来源与技术身份按需展开，不逐行会签。获批原型只展示主表及汇总确认，不是完整正式字段或真实服务端校验已实现的证据。

Host 在提交时重新核对确定性合同，界面按钮禁用不构成唯一防线。发现问题返回准确对象和原因，供 Agent 在原许可内修正。业务含义及协商结果由 Agent 说明和负责人决定。

| 发布条件 | 通过 | 不通过时 |
| --- | --- | --- |
| 采用依据 | 准确总 GSA 已确认，发布内容、范围及父版本与预览一致。 | 保留草稿，展示变更，不能静默改用最新 GSA。 |
| 金额分配 | 同口径已分配＋有用途、有责任人的预留＝总目标。 | 展示余额、重复归属或无效预留，不能自动平差。 |
| 同口径交叉 | 指标版、期间、覆盖范围、交叉身份一致的断言值一致。 | 两边合计相等仍不得发布，列双方值及原依据；不同口径先标不可比。 |
| 测算缺口 | 有策略／行动、预期贡献及不重叠范围，贡献覆盖正缺口。 | 无策略、无金额、重叠或仅覆盖 7／8 万时仍为草稿。 |
| 责任与计划 | 责任范围、期间、汇总规则及纳入跟进的检查点可核对。 | 返回具体行；不强制无关行的日计划或全组织签章。 |

补缺金额只表示预期增量，不能据此认定将达成。对预期贡献的可行性由 Agent 分析、负责人核对，Host 只核已约定的字段、可比范围和算术覆盖。预算余额预留、跨部门交叉差异、正式目标与测算差额分别保存，不得互相抵消。

交叉场景使用两个视图的同一期净销售额，按相同交叉行身份排序，依次为线下×羽绒服、线上×羽绒服、线上×针织、线下×针织。渠道明细为 50、30、20、15 万，品类断言为 45、35、20、15 万，各加预留 5 万均为 120 万。前两格分别为 50／45、30／35，存在两处相关差异，都须展示和解决。负责人取得双方协商依据并确认线下×羽绒服的唯一值，以及相应线上分配，Agent 展示两个格子的变化及重新汇总，不替部门决定 45 或 50。配平是经负责人核对的方案修改，不是静默裁决。仍有余额再走预留规则，缺口策略依然独立校验。

### 3.4 发布事务与失答恢复

GM06、08、13。拆解发布是业务持久操作，不能用 SDK 文本“发布成功”、HTTP 已接受或 Agent 终态代替耐久回执。

1. 负责人在只读预览中点击“确认发布 vN”才正式提交。前端固定负责人实际核对的准确 GSA 计划身份、草稿 revision／内容指纹、预期有效发布版及确认内容，生成并耐久保存本次最小待核意图后发送。预览开启至确认之间若内容、父计划或有效版变化，提示重核，不静默替换成新内容再提交。取消预览没有发布副作用。刷新、关闭再开或应用重启仍应能定位原操作，不能仅放组件 useRef 或页面内存。保存失败则不发送，恢复读取失败则保持待核而非另发新编号；技术身份不要求用户抄录。校验与正式写入期间不能换行、换目标或改内容冒充原提交。
2. Host 在同一业务一致性边界中核验操作 UUID、归属／读取权限、动作及内容指纹，并先查原操作。已成功的同号同内容回读原结果，同号异内容拒绝，即使原版后来被替代也不能改返当前版。新写入再检查范围写权限、GSA 资格、草稿 revision、预期有效版及全部发布条件。复用／修订已有子目标时逐行比较预览所见 `goalId／currentVersion／adoptedVersion`，关系同时核预期修订，避免原目标页的并发修改被表发布覆盖；版本冲突返回差异而非改用最新值。
3. 正式表版、此次明确承诺的正式目标行／关系、有效版指针和成功回执一次原子提交。发布预览明确列出本次采用的准确 G／S、责任范围／负责人及正文，按原 Goal／SAP 资格校验；只有这些合格目标行随发布采用。预留、聚合投影、检查点、补缺及驱动假设、待定行不会自动成为 adopted 目标。独立驱动目标只有被明确纳入业务承诺才采用。任一失败都不能暴露半张表、只有候选的正式行或无回执的独立成功状态。不可变正文若拆文件，应先耐久保存再原子提交唯一权威索引，孤立临时文件不成为有效发布。
4. 响应丢失显示“发布结果待核”，保留原意图、草稿和最后已知正式版。刷新、切走再回、重启后仅查询原操作及准确版，不自动重发模型或发布。查询本身不能创建会话或写发布物。
5. 查到成功回执时回到同一个正式版，版本数不增加。原编号只是查不到，或无法排除原写入仍在途时，继续待核，不能据此重试。
6. 只有服务端已登记原尝试并耐久记录“确定未提交且已排除迟到写入”的可重试结果时，才可给安全重试资格。现有成功回执机制尚不能证明这一状态，须补最小业务操作状态及恢复核验，不新增 Agent 生命周期账。用户显式同号同内容重试时，在同一写锁内 CAS 可重试状态并重新核权、指纹及版本；已有成功回执优先回原结果。同一意图不增加第二个成功版。GET 404、原 POST 是否收到不明、重启后看不到在途，都仍未知。校验已变时返回业务冲突。如果用户修改内容，先明确结束原未提交意图，再按新预览建立新操作，不复用旧编号。

发布成功后下游按 `发布表身份＋版次＋内容指纹＋行身份` 引用，行映射至原系统可采用的准确 `GoalRef`，并保留对应具体 S。表头显示业务版次，机器身份只在详情展示。读不到原版时报告失读，不替换成新版。

### 3.5 修订、检查、Case 与下一期

GM09。仅变子目标金额分配或检查点等拆解计划，且总 G／S／上层 A 不变时，修订并发布拆解新版即可。触及总 G／S／上层 A 时重新确认总 GSA，来自正式战略的总值改变先回战略选择修订发布。新版记录生效时间、原因与差异，进行中的下游由负责人决定是否切换，已完成检查与历史报告保持原引用。

GM10。负责人提交或选择一次实绩后，Agent 核指标定义、单位、期间、截至日、覆盖与观察成熟度。完整可比才给整体偏差。部分缺失不能补零，未成熟不能计作已确认偏离。每次检查固定准确总 GSA 计划、拆解发布版、行／检查点及其计划值、实绩来源与已用值、可比性、当时阈值、计算口径／结果、触发规则／原因和负责人的 Case 选择。新阈值、新草稿或新版计划不回改这份快照；负责人明确开始下一次检查才采用届时生效版，历史仍可原样回看。补齐后形成追加核对记录。局部 27 万缺两店时，在跟进、历史、来源详情及导出中都只报覆盖结果与整体待核，不能另算或显示整体 −10%。

**实绩选择和截至时间（F11）。** 已保存实绩显示报表、期间、覆盖与截至时间，负责人点选该份报表即可发起核对。上传或粘贴新报表在同一入口完成；Agent 提取数据截至时间、展示相应原句和原件身份。缺少时间或有多处冲突时由负责人补充或选定，再核可比性；同一凭证中实绩数值互相矛盾、任一实绩单位不明，或原文另有排除门店／渠道时，保留该凭证的待核状态，不能据此给出整体偏差。示例材料须明确标识。

GM11。阈值按指标与检查周期设置，幅度达到或连续偏离期数达到任一项即提示，明确不利偏差方向、单位（百分比或百分点等）与算法。连续期须为同目标／责任范围／指标口径／周期的相邻、已成熟且可比检查。不可比期间不计作已确认偏离期，也不推断其达成，不把两段跨未知或跨范围记录拼成连续偏离。零计划不伪算百分比，仍展示绝对差。未配置时仍比较并提示尚未启用自动 Case 提示。负责人可继续观察、安排补证、续接或决定另建。已有同一 G＋具体 S／问题的 Case 优先，核当前状态与范围；历史版匹配、已关闭或草稿待确认不能当作正在进行的事项默认续接。提示不创建 Case。主动试点或跟进另建先保留草稿，在原 Case 入口完成原准入与明确确认后才进入相应状态，不因产生草稿显示“进行中”或获得行动授权。

Case 草稿及关联目录使用稳定身份，同一创建意图重开／重试／多处查看只复用同一草稿；不同独立创建意图不得共用固定演示 ID 或挂接第一次检查。每条保留自己的准确目标、具体 S、原检查／表版／行／检查点与实绩证据，缺少的资料不伪造。目录同一 Case 去重，逐行标当前或历史主目标绑定及其准确版本，不按今天的生效版重绑。获批原型的固定 C-015 只演示单一检查意图，多个独立意图属于正式验收项。

GM12。期末以该期间最后生效的正式总 GSA 中 G 为准，上游新版尚未承接、拆解微调或测算变化均不自动改评价目标。期初承诺仅备忘，历史检查原口径留存。负责人选定带入下一期的复盘结论，Agent 携原证据和适用范围起草。跨范围推广，或即使同范围但原证据未成熟／策略因果尚未验证，都须标为待验证假设；不能由总量达成认定某项策略已有效。新草稿再走正常 GSA／拆解确认，不自动发布下一期。涉及重定总目标或重审战略假设时，把问题、复盘结论、支持／反证及原证据准确版本交回战略选择，保留原记录，不直接覆盖战略发布。

**先拟复盘结论（F12）。** 负责人进入期末复盘可直接看到 Agent 根据当期可读结账报表、已有检查及 Case 准备的结论草稿，逐条附原证据及版本、适用范围和待验证点。每条可以改写或舍弃；选定子集后才起草下一期。新稿带入负责人的最终文字与原引用。有范围差异、资料失读、证据未成熟或未发生检查时如实保留；总量达成不能用作策略有效的因果证明。

## 4 结构、权威与兼容设计

以下为拟实施的业务结构，不声明当前代码已具备。沿用 `StrategyGoalsStore` 的唯一目标权威和写锁／原子保存，追加总 GSA 计划与拆解记录。确认的总 GSA 计划具有独立不可变的计划 ID＋版次／指纹，并绑定准确 `GoalRef`。只改上层 A 时，可以在同一个 GoalRef 下确认新 GSA 计划；不能仅凭 GoalRef 判断父计划未变。草稿、发布、检查及承接都冻结该计划身份，迟到工具提交同时核父计划与草稿 revision。它是业务计划版本，不是新 Agent 会话或平行 Runtime，原 goal owner 继续沿统一入口。

总 GSA 确认先固定 G／S／计划 A，随后拆解发布再固定明确承诺的目标行、关系、表版、有效指针及回执。负责人一次发布即采用预览中明确列出的分配承诺，不要求再逐个采用子目标。禁止另建一套“表内正式、原系统仍候选”的目标。已有 Case 继续保留原 G＋具体 S 与历史上下文，新的计划身份不自动换绑旧事项。

子目标和明细使用稳定身份。仅改时间计划或投影视图时复用既有 GoalRef，不能整表发布就重建所有 Goal。改变承诺的目标行才追加版本，原 Case 的同 Goal／具体 S 连续性保持。将行移出新表不删除历史目标或改写原引用。只在投影出现的金额格不各自建立一个目标。

| 对象 | 最小信息与权威 |
| --- | --- |
| 总 GSA 计划版 | 不可变计划 ID、版次及内容指纹，绑定准确 GoalRef、S、计划 A／上层检查点、来源、确认人与生效时间。与原目标版本、战略版及实际行动权威分别保存。 |
| 拆解草稿 | 父 GSA 版、revision、测算／正式值／差额、明细、各视图断言、预留、补缺、计划与证据，支持未齐备草稿。 |
| 拆解发布版 | 不可变草稿快照、正式行与关系映射、生效时间／原因、前版引用、内容指纹。准确版与有效版指针分别保存。 |
| 发布操作回执 | 客户端发送前一次生成并保存 UUID，Host 核验并绑定归属、动作和不可变输入指纹，记录状态与准确正式版。在发布事务内耐久保存成功结果，确定未提交的可重试状态须可证明且持久。它是业务操作记录，不是新 Agent 生命周期账。 |
| 检查与复盘 | 父 GSA 计划身份、发布版、行／检查点与计划值、实绩原来源／值、可比性、当时阈值与计算／触发、Case 选择、结论及适用范围，历史不可被新目标／阈值／工作意图追改。 |

当前 Goal Store 有文件大小上限，实施前用代表性多维／时间拆解做预算，不能通过无界内嵌撑破原存储或任意扩大限制。优先紧凑明细及按需分页读写，不将多视图复制成多套事实。若需要拆文件，须保持上述单一提交权威及兼容读取，不引入跨 Store 半提交。

通用目标目录必须显式投影原允许字段，不因 Goal Store 追加内部字段就把全部拆解草稿、实绩、证据及操作状态通过旧 index 路由返回。新增查询按 owner、当前读权、准确版和分页投影，原目标目录及其他角色不自动取得新增材料。

旧目标、采用、Excel 目标表、Case／Board、关系、原生 JSONL 原位可读，不从旧导出补造计划 A 或正式拆解发布版。新增结构采用显式新 schema 与兼容读取，GET 不迁移、不批量回填。旧二进制是否能读新 schema 须实测，不能假定可安全回切。回退用能读取新记录且关闭新写入口的兼容候选，保留期间新资料，不以旧备份覆盖。

UI01 的目标目录从标题旁按需打开，展示周期、范围、责任、候选／生效状态及准确目标身份。默认继续当前目标或明确的承接上下文，普通工作不先选一遍目录。切目标只切视图，各 owner 的未发送输入、对话、草稿、检查及发布意图独立保存，返回与重开不重发。明确历史／只读示例不能套用当前 120 万目标的草稿。新建／导入候选沿两种总目标来源规则，Excel 不构成第三种正式来源。

UI02 的“版本与来源”在任何阶段可达，页面直接显示当前已知生效身份。最新保存版可能是候选或已采用版，不能拿它替换当前采用指针；历史采用版仍保留当时采用事实。总 GSA、拆解表、原战略发布／SAP 定义分别显示已核实版本，按对象展示原资料实际提供的期间、范围、责任和修订原因，不为其他对象补造字段。查看旧版只读，不改当前生效版、不影响旧检查。发布结果未知时只显示最后已核实版本，不能展示模拟服务端已落盘但未核实的新版或计数。旧 GSA 精确导出保留原 A 的实际安排口径；新 GSA 才单列计划 A，正式拆解另按独立表／版／行／检查点导出，保留该版冻结的检查点 ID、责任行、日期及目标值。尚无表、原检查点缺失或失读时保留准确引用并标待核，不从当前草稿补造、不退回最新版，也不以此生成新承接依据；既有合法项目入口仍可读用。

UI03 的“关联决策”按所选目标及经营期间查原 Case，可以同时列出该目标不同版本的历史事项，逐条保留自身的准确主目标绑定。既有年表的年度可作筛选，清楚标识“作为主目标承接”的覆盖范围，不把它描述为全部关联事项或执行总览。显示具体 S、当前／历史绑定、生效期间、草稿待确认／进行中／已关闭及原依据，按需打开原 Case。续接同问题优先，历史匹配、草稿或已关闭先核原准入，不静默把旧 Case 绑到新表。提示、查看与发布不创建 Case。已采用 G＋S 的重点试点可在阶段偏差出现前主动发起，不能新增必须选实绩／达到阈值／发布新表的门槛。草稿同意图去重与不同独立意图各保留原证据分别验收。

UI04 的“执行承接”同时提供旧真实记录回看与按新正式表承接。直接项目核准确 `goalOrigin`，Case 内项目取原关联及事项上下文，不能按标题或范围猜归属。新拆解行交原项目时预带准确总 GSA 计划身份、GoalRef、表版、责任行／范围和该版冻结检查点；具体项目方案确认和行动授权仍沿原入口，未发布草稿不能充当正式表依据。旧已采用目标没有新拆解表时，仍可读已有项目／看板，原合法项目准入不受阻。确认 GSA、发布表、查看或承接预览均不产生项目／任务或授权；负责人沿原入口明确办理后才保存对应引用，同一意图与来源已有工作优先回原记录，新版不迁移旧引用。Demo 仅模拟方案草稿引用及零写入预览，不接真实项目后台。

读取版本、检查／Case 原证据、导出及新承接分别按准确对象、原权威和本次读取／导出／承接时仍有效的权限重新核验。撤权或失读时报告原对象待核，不跨入口绕过、不换新版，也不抹去合法历史身份。获批原型的失读开关只覆盖版本正文与导出，不构成其他消费者已经统一核权的证据。

计划 A、项目方案、行动授权与发生／反馈分别展示。原看板“已授权但未回录”“已撤回”“暂不可读取”等照实保留，不以任务 done 或 Case 选择证明实际效果或目标实绩。main 既有泛跳看板不被声明为已经精准跳到行动行，Demo 的原记录预览标明合成边界。执行、策略及战略假设三层反馈按原来源带入跟进／复盘，不要求用户另填一套例行反馈表。保留原可选的“记录目标层反馈”入口，对已采用的准确目标引用当前可读原记录，无新拆解表的旧目标也不被锁住；这不是新增例行必填步骤，本轮原型可展示反馈引用而不模拟完整后台写入。

原模块带来的定位意图继续保留。Case／Task（含逐条原回复）有已核绑定时携准确 GoalRef 与原依据进入相应核对、历史只读或目标 Agent；尚未绑定目标时，携原依据和获准范围定位独立 goal-draft，不猜目标或扩大权限。这与原绑定存在但不可读取的情况分别处理，后者保留失读及原身份，不另建草稿或偷换最新版来绕过。Teach 可打开当时准确版并返回原 Case／issue。移除旧 tab 只改变呈现，不能把这些深链一律改为普通首页。本轮 Demo 展示所带上下文，不接入真实跨模块消息或会话后台。

场景注入、重置和模拟重开放在独立折叠的“原型评审（非产品功能）”区域，不占业务顶栏，也不成为正常操作前置步骤。原型中区分“沿用 main 的入口”和“拟新增的目标拆解能力”。真实 main 的单目标建议、采用和会话恢复，不代表多行拆解、正式表发布或发布失答恢复已经上线。

### Issue #138 接入落实

计划推荐与优化使用同一 `business-role-discussion` 域中的 `goal-plan` 变体，owner 绑定准确目标版本，请求再绑定编辑行与本轮原文。正式确认前也可使用，工具只返回结构化建议。复盘使用 `goal-review` 变体，请求绑定所选期间、结账资料及检查，结果保留原范围。两者沿官方 Pi 1.4.0 与 Interface v3 的原模型配置、占用、取消、事件和原生历史读取。
