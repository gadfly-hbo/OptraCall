## 1 目标与依据

让原项目任务在已有授权内把适合外部完成的一段工作交给第三方 Agent，对方通过 OptraCall 的受保护远端 MCP 取得准确语义/分析依据，交回成果及证据，原任务自动续接并核验，继续项目与反馈闭环。能在内部完成的部分继续内部执行，重要经营取舍由相应负责人作出。

本期以独立的GitHub Issue通用外派＋资产远端MCP为核心；原Task内部完成始终可选。WorkBuddy本机助手远程触发为可选适配，具体配置真实联合测试通过后才启用；未配置、离线或未验证不阻断内部工作和纯GitHub闭环。

## 2 范围和职责

六类任务为需求、分析、计划、决策、执行、反馈。外派是任务中的工作，不新增第七类任务，不为每张工单另建项目/Task。一个原 Task 可同时保留内部工作与多个外派工作，依赖和方法由 Agent 决定。

| 负责方 | 职责 |
| --- | --- |
| 用户 | 首次配置连接/执行者和受保护服务入口；明确目标及授权范围；处理超范围、重大经营决定和第三方确需的授权。 |
| 原任务 Agent | 自主分析与拆分、在范围内发布/跟进/补充或重新委派、读取交付、专业核验与接受，按原工具保存成果及提出资产候选。 |
| Host | 真实身份、任务权限、持久保存、原子领取、去重、版本、有限收件同步和同 owner 续接条件；不作专业判断、不选择分析步骤或代人采纳经营方案。 |
| 外部 Agent | 用自身平台及工具执行获准工作，调用获准 MCP，回传准确产物、资产引用、实际操作与限制。无需改用 Pi。 |

首期仅对既有四服务工具可用的普通项目任务开放；受管普通、protected、fixed-draft、专属业务 workspace、受限会员包等不能经外派获得额外工具或数据。六类用途不改变 profile 准入。保留原 SDK/受管资源规则。

本期不新增飞书/邮件完整工单链路、WorkBuddy 云任务适配、任意厂商自动唤醒、远端计算/规则推导、Skill/脚本分发、资产正式写入或自动发布。已有四服务连接不回退。原始业务数据/文件外传、经营系统写入、发信/支付/交易/合并等实际动作须各自明确授权；本期不因外派授权自动补建这些业务权限。

### 2.1 与最新日常工作台衔接

沿 main 的单一 **Decision Case** 一级入口及同级「Case 总览／全部项目」进入工作。Case 保留「当前工作／项目与任务／成果与依据／历史」四页签、当前事项/轮次和用户手选范围；任务仍只属于原项目。可以从已关联 Case 的项目任务进入，也可由全部项目进入独立任务，不能为外派改建 Case、复制共享项目或默造事项绑定。

本期新增控制集中在原 Task；同一 Task 的只读外派摘要可出现在原项目的准确 Task 行，以及已核真实关联的 Case「项目与任务」行。首页现有人的明确待回应、继续工作和 `ProjectWork.awaiting_feedback` 外部等待继续各用原权威；本期不新增首页外派待办或完成库，不把外部工作到达/接受伪装成 `CaseDecisionRequest` 的取舍或原始观察回应。Case「成果与依据」只有沿原发布/关联合同取得准确来源资格后才显示相关内容；单独的ExternalDeliveryRef仅由原Task外派详情回读，不自动写CaseArtifact或伪native来源，也不因共享项目而成为所有Case的资料。

目标管理修正后的原目标版本、上游承接快照、实绩可比性/阈值与发布核对继续由原模块负责。接受外派片段不自动采纳目标、发布分解、填实绩、完成 G/S、推进 Case 轮次、作取舍或保存行动观察。外部交付、Agent 自身成果和原业务决定始终分开。

## 3 正常用户路径与独立门槛

1. 用户在原Task表达目标。Agent可推荐外派，但必须保留“在OptraCall内完成／通过GitHub外派”的明确选择。前者沿原权限/工具/会话继续，不发布Issue、不触发外部执行者、不创建外派工作或开放外部资产；外部连接全未配置也不得阻断内部任务。能力不足如实说明，不强制外派、不假报内部已完成。
2. 用户选择外派后，默认GitHub Issue通用接单。一次确认目标/片段/禁做项、指定仓库、允许的可信执行者集合、资产精确refs和资源/时效；取消授权零外部动作。通用Agent按认证principal/有效claim接单，不以GitHub留言或assignee取得权限。
3. 核心就绪只核GitHub连接、受保护资产/工作MCP、通用执行者接入及其闭环测试、适用资源策略。无需WorkBuddy OAuth、在线助手、Connector或联合测试。获准Agent发现Issue后领取、查读、执行、回交，原Task Agent核验/保存/续接。没有领取时显示等待，不偷偷调用WorkBuddy。正常范围内不逐条审批。
4. 只有用户主动选择可选WorkBuddy适配，且该具体配置已授权、助手在线、API发起任务实际完成同一MCP领取/查读/回交/原Task核验的真实联合测试，才允许远程尝试触发。单项API/在线/Connector通过不足；未验证默认禁用。离线/失败不阻断纯GitHub，也不静默切换已发工作或重复派单。
5. OptraCall与WorkBuddy无需同机；目标本机助手已在线且能访问受保护资产MCP即可按官方接口设计跨环境调用。但未证明远程开机、唤醒睡眠MacBook、启动退出应用或同账号多设备精确路由，不承诺这些能力；不做WorkBuddy云任务。
6. 收件/保全/原Task忙时待处理、原Agent核验/接受/需补充及既有成果/候选机制沿下文。Issue关闭不等于接受，接受不等于Case/目标/经营效果完成。已外派后改走内部须沿取消/在途UNKNOWN规则核对，不假称外部停止或重复启动相同副作用。

每份外派授权默认1work/24h，较低已批准策略优先；GitHub/MCP适用额度和未知费用清楚列在授权及回看快照。只有启用WorkBuddy时额外继承最多3次API触发含修订的适配额度，submitted/UNKNOWN占额、不盲重试且不得跨turn/revision重置；纯GitHub不申请或消耗WorkBuddy额度，内部任务不为此申请外派授权。上限不是必须返工次数；新目标/执行者/仓库、增权/扩额或真实经营动作另核授权。正常路径继承已批准策略，不增加日常必填。

设置中分别展示核心与可选适配状态。实际联合验证未通过的WorkBuddy保持integration_unverified且禁止启用；其工程合同/禁用门槛可用隔离供应商模拟验证，真实采用属于E08，不把未完成实号采用作为核心工程验收或内部可用的前提。

## 4 业务记录与可恢复状态

外派记录始终绑定真实 `projectId/taskId`，原 `TaskAssignment.issue` 是 Case 事项引用，不能拿来存 GitHub Issue 编号。新增业务记录与原 Task/Case/native 权威分开，旧数据无外派字段时仍按旧行为读取。

存在真实 Case 来源时，保留准确 `caseId/issueId`、原任务约定和来源版本；保留浏览返回所需的工作区/页签/手选范围/事项及焦点，不能从任务标题、最近打开 Case 或项目共享关系猜归属。导航快照不是访问凭据或新的 Case 权威。Case 事项、GitHub Issue 和外派 work 使用不同身份；外部交付的 id、领取 id 也不充作原业务请求回应引用。

当前 main 的项目协作已有部分 `projectCase/projectIssue`、`returnCase/returnIssue` 导航，但报告来源返回不完整携带事项/页签。本期须为外派入口补最小准确 origin（Case/事项/页签/范围/Task/work/焦点）并重核原对象可读，不能声称原报告回链已覆盖这项增量；原事项暂不可读时保留定位并明确提示，不跳到首条或另一 Case。该 origin 只恢复导航，不改变原 Task 绑定或 Case 合作上下文。

| 记录 | 必须保留的身份与含义 |
| --- | --- |
| 任务授权 | 授权版本、目标/范围、允许执行者与仓库、精确资产 refs、显式企业、有效期、资源策略及额度快照/占用、自动续接/真实动作约束，以及源任务约定/Case/输入身份。 |
| 外派工作 | 稳定 workId、revision、原 owner、固定工作内容/摘要、交付标准、输入/资产版本、目标执行者、授权引用。工作修订保留旧版。 |
| 发布/触发尝试 | 每 work revision 的稳定操作身份、确切出站内容 hash、服务调用引用、GitHub 仓库/Issue 稳定 ID、WorkBuddy message_id、成功/失败/UNKNOWN。 |
| 有效领取 | 经认证 principal、claim/epoch、服务端租约期限、当前 revision、释放/撤销/过期原因；同一工作版本最多一个有效领取。 |
| 外部交付 | deliveryId/版本、幂等键、工作和领取身份、产物 manifest 与保全状态、实际使用资产/read receipt、已做/未做/失败/未知事项、迟到标记。 |
| 核验与续接 | 原 Agent 接受/补充/拒绝及理由、准确 delivery hash；供应商去重/游标、稳定续接 requestId、实际 native accepted/settled 状态。 |

用户可见进程为：建议/待授权 → 准备 → 发布待核或待领取 → 执行中 → 结果待处理/待验收 → 已接受或需补充；取消、失败、授权变化和停止待核单独显示。业务记录分开保存发布、执行器触发、领取、访问、交付、核验事实，不靠一个“成功”字段推断全部完成。

## 5 GitHub 通信与单次有效派发

工单写明目标/范围、输入引用、验收条件、禁止事项、交付方式及非敏感工作标识、MCP 入口和授权引用。不得包含令牌、客户端 secret、真实资产正文或默认完整企业目录。采用明确仓库稳定 ID 与可信可见性；默认私有业务仓库。允许公开时需在任务授权明确公开范围并核对确切出站内容，不能把选择 GitHub 当业务资料公开许可。

每项 work 对应一张 Issue：首次创建，后续工作修订在同一 Issue 追加有版本的说明与关联，不抹掉原说明和旧交付。先持久预留 work/revision/动作类型的唯一发布操作，再调用现有已核验连接器。重复工具编号、新 turn、断线和重启都不能绕过发布身份。响应丢失进入 UNKNOWN；仅只读核对准确仓库、作者、关联标识、正文版本及外部回执。唯一准确匹配才关联，多个匹配报冲突，查不到仍可能待核，不自动再次创建/追加。

有效领取/交付/验收由 Host 台账裁定，GitHub 是通信与证据。评论中的名字、领取/完成文本、assignee、Issue 开关均不授予身份、权限或验收通过。可接受结构化评论作为线索，必须核对认证身份与工作合同；任意访客留言、Issue 编辑或提示注入不能改变授权、范围或派发内容。

收件首期采用受限轮询，重启可恢复已授权精确仓库/Issue 的读取；默认 60 秒、有条件退避/尊重供应商 Retry-After。仅保存并去重真实事件后推进游标，停止该同步/换号/失权后不再拉取。可选 webhook 只做去重的到达提示，不能成为唯一恢复依据或无鉴权触发入口。后台读适配器不能伪造前台 Agent tool context 来借用服务端 port；它只收件，业务就绪处理按第9节核条件续接，不由读适配器重放外部写入或另建模型循环。

## 6 通用工作交接与可选 WorkBuddy 适配

受保护 MCP 提供两个独立能力面：资产只读，以及最小工作记录操作。可观察语义固定如下，最终工具命名可在同一合同内确定并在接入说明公布：

| 操作 | 合同 |
| --- | --- |
| work.read / 待领取目录 | 只列出当前可信 principal 被明确允许的工作与非敏感说明，不暴露其他 Task/企业目录。 |
| work.claim | 仅对已发布可领取、无未核外部动作的准确 workId/revision 原子领取，返回服务端 claim/epoch 与期限；重复相同请求返回原收据，竞争者得到冲突。取消/过期待核/待补/已接受均不能直接重新领取。 |
| work.renew / release | 核对当前领取者、epoch、授权及时效。release 不证明真实操作已经结束。 |
| work.deliver | 有效交付核对当前领取、输入/工作版本、manifest；相同幂等键同内容返回原收据，异内容冲突。旧 epoch/工作撤销后的历史已授权身份可提交隔离迟到证据，不覆盖当前交付或恢复资产资格；认证凭据已无效则直接拒绝，不能绕鉴权保存任意人材料。 |

认证身份来自服务端核验的客户端登记和操作者授权关系，不能用自报 Agent 名称、taskId、claimId 或工单 URL 替代。共享一个账号的多个实例仍按 claim/epoch 单独裁定，不承诺平台未提供的进程身份认证。

以下仅适用于用户选择且具体配置真实联调已通过的WorkBuddy适配；纯GitHub路径不执行这些调用。

WorkBuddy 通过官方用户 OAuth 保存其 API 授权，查询本机助手在线状态后，经官方 Local Assistant 消息 API 触发工作。返回的 message_id 只是触发回执/当前账号消息历史的收件游标，不是独立任务或会话 ID，不能根据其后消息、时间邻近或“最近一次触发”判定工作归属/执行状态。仅有可信供应商关联证据、或与既存 work/revision/认证 claim/delivery 准确核对的消息才关联该工作；不能准确关联的消息不保存正文到任务、不发给模型，最多保留最小诊断元信息。有效领取/进展声明/交付由受保护 MCP 工作记录核定，消息文本和其后出现的回复不代替 work.deliver。

首期同一 WorkBuddy 连接只允许一项 OptraCall 工作进入已触发/领取的有效执行阶段，其余工作保留“等待执行者”，原任务内部工作不因此停下。这是官方当前接口未提供已证实的独立任务/会话查询所需的最小适配，不限制外部 Agent 内部方法或通用协议的多执行者能力，也不证明该助手没有非 OptraCall 的工作。未知触发/在途动作未核定时不释放该执行器的安全派发条件。不能承诺第三方平台历史或进程具备本产品同等级的隔离。

触发消息只交付工作指令及定位信息，不把 OAuth/MCP 令牌发送给模型。每个 work revision 保留独立触发操作；触发回执丢失保持 UNKNOWN，不因“离线/重启/无消息”自动发第二条。API 连接授权、助手在线、Connector 授权与完整联通验证是不同事实。

可选WorkBuddy适配初次接入需要外部平台注册/连接应用、用户 OAuth、资产 Connector 配置/授权、已批准资源策略及允许的工具策略。真实 API 触发会话必须实际完成领取、资产读取和交回，才能将该执行者标记“就绪”；未证明时为 `integration_unverified`。首次完整测试使用明确告知的合成工单/资产，用户单独触发测试并获知实际第三方调用，不使用真实业务或制造假通过。第三方再次要求许可时显示“等待外部授权”，不绕过其权限规则。详细官方依据和未证明项见 [接入研究](integration-research.md)。

通用执行者遵守同一合同，可使用自己的 GitHub、标准 MCP、调度器和 Agent；不要求使用 Pi，也不由 OptraCall 接管其内部方法、SDK 或进程。首期不承诺 WorkBuddy 云任务注入自定义 MCP，也不承诺任意第三方无配置自动接单。

## 7 资产远端 MCP 与认证

资产保留原运行端及原 Store，复用本地目录、准确来源读取和受限语义查询；不复制出一套可修改的正式资产库。首期资产能力为：

- 查获准资产目录和适用条件；读准确语义/主数据定义、数据映射说明、已发布指标公式与口径、已发布方法的条件/逻辑/判断/局限。
- 取获准来源的准确片段、版本/hash/位置；关系查询和 trace 仅在已授权 refs 范围内展开。
- 原始业务数据/其他项目文件、会员包内容、Skill/脚本分发、任意代码/SQL、`reason` 规则执行、写图/修订/发布不因本服务开放。数据/输入交付另有明确范围，并保留最小传递原则。

每次目录、正文、来源、trace 和分页均同时核对：可信 principal ∩ 有效任务授权 ∩ 有效 work/领取 epoch ∩ 显式企业 ∩ 工作资产精确 allowlist ∩ 原项目/Studio 当前资格 ∩ 确切 authority/id/version/hash。实际调用前及异步读取后的返回/下一片发送前复核当前资格，撤销/取消不能返回尚未交付的迟到正文；已发送片段仍按已披露记录。尚未领取者只能看获准工作说明，不能读取资产。旧项目无企业或内部 legacy 默认放行不能成为远端授权。目录元数据、隐藏邻接关系或来源也不能先泄露后筛选。

版本缺失、hash 不符、来源/项目资格撤回、工作过期分别明确拒绝，不落到 latest。撤回阻止后续读取；已传出内容无法靠撤回追回。实际读取回执只证明交付内容与范围，不证明执行者采用或专业正确。保留历史引用，不篡改旧报告和原资产。

远端协议采用已锁定官方 MCP SDK 的公开 Streamable HTTP 能力及其支持的协议协商。核心远端MCP的认证不依赖WorkBuddy Connector；后者仅属可选适配。MCP 是受保护资源，采用 OAuth 2.1 与资源元数据发现、PKCE、准确 redirect URI/resource/audience/issuer 和逐请求 Bearer Header 校验；过期/无效 401，权限不足 403，超限 429。首期支持经验证的预注册客户端，覆盖 WorkBuddy Connector 兼容；不依赖任意动态注册，不能把客户端 secret 放公共配置或接受其他资源的令牌透传。具体标准和兼容核对见研究记录；公开接口无法解决的兼容缺口交 PM 核定，不改官方包、不静默升级或放宽校验。

客户端登记、首配授权及凭据管理在本地受信管理面完成；公共授权页面不能凭访问 URL 批准访问。远端令牌只证明其 principal 和上限，实际工作/资产资格每次在原实例核对，外部请求不能自选企业/Task扩大权力。

对外只暴露必要 MCP/元数据/认证路径，保留现有 localhost/Origin 管理面防护。受保护 HTTPS 入口和原实例在线是运行前提；网关/反向代理只能转发明确允许路径并验证配置，不把整个 Host API 转到公网。工程交付服务端、部署/接入说明和隔离 TLS/OAuth/MCP 检查；实际公网/设备部署须另按用户指定环境与授权执行。本次准备不开放端口、复制资产或部署。

## 8 交付保全、验收与经验

外部交付使用独立 `ExternalDeliveryRef`，带真实外部身份、工作/领取/交付版本、准确 hash、时间、来源与保存状态；不能伪装原 Task native 的 `write-report` 收据。GitHub 链接、外部消息、本机已保全字节分别显示，链接失效或后来变更不等于原材料已保存。

支持文本及证据文件的受控传输，复用原项目文件名/类型/50 MiB 单文件上限、原子保存和 hash 核对；MCP 大文件分块传输并校验完整 manifest。默认单次请求总参数上限1 MiB、原始上传片段上限512 KiB，单交付最多20文件/累计100 MiB，manifest/正文上限256 KiB；若原工具/供应商上限更低，取更低值，超限须分页/分片或明确拒绝。分片、结束和提交有幂等收据，并在写前及异步保存后提交前核当前领取/授权；部分上传和过期领取不可标完整。路径由 Host 分配，不接受任意本机路径，不自动打开/执行文件或从任意 URL 下载。精确 GitHub blob 可按原授权仓库/提交读取；其他外链只能先标“仅链接/待保全”，不能冒充字节已验。未完成上传24小时后可清理临时分片，保留失败/未知/审计元数据；已确认交付不因临时清理删除。实施说明明示限额/清理策略并测试，不能无限保留临时文件。

交付必须报告已做/未做、验证与未验证、失败/UNKNOWN、实际外部动作及其回执，以及使用的准确资产引用。Host 核对读取身份、允许范围和已保全字节；原 Agent 核对是否满足业务标准、是否需要补充及结论的适用范围。模型在原授权内自行检查或要求补充，不能因为缺件直接宣称成功。采用资产版本、读取回执和自述引用分别记录，不补造“已使用”。

要求补充保留同一 workId 和 Issue，新增 work revision 并引用准确旧交付及补充要求；旧领取失去有效资格，新的有效领取再执行，旧版交付保留。补充不自动扩大目标、执行者、资产、权限、资源或实际动作范围；无法在原范围完成时交用户决定。源码工程的“二审终审”不强制套给全部业务工作，当前产品不设置必须凑够的返工轮次。

原 Agent 接受后，可用既有工具将自己的核验/综合输出保存为原 Task 成果，保留对外部交付的准确引用。事实接受、原 Task 运行终态、Case/目标进展、经营效果与新资产正式发布分别发生。新语义/方法经原候选、核定、发布流程进入后续任务；成功、失败和无增益都保留适用范围，不从收据数量推断系统变强。

## 9 自动续接、停止与恢复

结果到达只产生可信关联的业务收件；后台组件不得以交付内容编排分析或代替 Agent 判断。原 Task 空闲、未暂停、未归档、授权有效、目标/约定与配置可用时，沿现有 `project-tasks` 域和 `startProjectMessage` 发起同一 native 会话的新 turn。输入仅包括已保存交付引用与原工作/验收条件，不把外部文字升级成系统指令，不直接续用过期 ActiveRun/signal。

同 owner 的原请求指纹及 `providedContext` 必须包含确切 workId/revision/deliveryId/hash 与授权版本，不能只凭一段同名文本去重；沿 Host 原调用将本次输入标为 `origin.userText=false`，外部文字不能取得“用户原话”或原生回复来源资格。原有 `completeNewDelivery` 等后处理只消费原 Agent 自身合法声明的成果；外部收件/保全回执不能绕过该 Agent 判断、伪造 native delivery 或自动触发原 Case 请求回应。当前 main 未实现外派续接/停止暂停字段，均是本单待开发差额，不能把接口可复用写成能力已存在。

每份待验交付使用稳定 requestId，并在派发前持久预留；原 Task 忙则保留收件，空闲后检查条件再派发。重启先回读原 accepted/native 收据；已受理但终态未知不能自动换 requestId 再跑模型。配置缺失/改变、目标/约定变化、企业/Case资格变更时标待处理，不能静默改模型、换 owner 或覆盖新草稿。沿当前 main 的原 Task/Case 资格及来源校验，不借页面正在浏览的另一事项改写发送背景；Case 导航不启动 Case Agent，外派自动续接也不变成对原取舍/观察请求的自动回应。工作台准备草稿、带入片段和各事项草稿沿原存储，外派记录不接管或自动追加这些文本。

“停止本轮”沿既有 Task stop 收回本机当前操作，并将该 Task 的外部结果自动续接标记暂停；外部工作仍显示真实状态。用户可在原任务恢复自动处理。“取消外派”则撤回工作的新领取/访问资格，发送有明确操作身份的取消请求（平台支持时），等待外部确认；本机不能声称终止了别的平台进程。

本机模型空闲、正在等外部工作时，也可在原 Task 外派卡按需暂停/恢复自动续接，不要求先启动模型再使用 stop。该可选控制不替代取消外派，也不是正常完成闭环的必做步骤；持久暂停和此入口为本单新增，当前 main 的运行中 stop 按钮不自动具备它们。

现有 stop/cleanup 的准确请求身份继续生效；旧请求或迟到cleanup不能停止、暂停或撤销新turn/新工作，须分别核对本机运行请求与外派工作资格，不以一个共享“已停止”字段代替。

默认领取租约 15 分钟、可每 5 分钟续租，受任务授权到期约束；值可在服务策略中配置，普通用户不用填写。过期/取消/失权的迟到消息保留证据，不能复活原授权或覆盖新 epoch。存在未知外部动作或取消未核时进入“停止待核”，不能仅凭超时自动重派。确认旧工作已无在途未知动作后，原 Agent 才可在授权内重新委派。

关闭 OptraCall 后不承诺外部服务仍能访问本机资产；重开恢复的是已授权读取、收件和待核业务记录，不自动重放未知发布/触发/业务操作。第三方未确认停止、失败或部分完成均如实显示。

## 12 实施责任与交付

沿 Interface v3，owner/profile 为现有 `project-tasks`/普通合格项目任务。新增最小 owner-bound 外派业务 port，模型不接凭据、管理域或任意 sessionFile/workspace。Codex负责Host/Agent/SDK接缝与整合；其他领取者按Issue明确分工实施独立业务、适配器、UI或测试，共同维护契约。先按复用核对确认现有能力，再补缺口，不另建 Runtime、全局模型队列或第二正式资产库。

允许路径为 `src/host` 的外派/收件/设置/MCP服务/资产只读薄适配，`src/agent` 的任务端口与工具/上下文交付，实际影响的 `extensions/business-plugins` 查询接缝、`tests`、最小边界检查脚本及相关说明；新模块须明确owner。Pi与MCP官方包固定现有精确版本；不得改官方源码、补丁、运行时对象或为了兼容升级SDK。新增依赖仅在确有缺口时记录官方来源/精确版本/理由并按授权核定，不默认引入云数据库或自建分析引擎。

分段实现与验收见 [tasks.md](tasks.md)。开工前补接口/持久迁移与回退的最小设计，先获得可检出错误的反例，再实现最小真实切片；不是实现后补写通过测试。兼容回退保留新增业务记录、外部操作/UNKNOWN和文件，不用旧数据副本覆盖。

当前交付为待确认准备包，不含产品代码/真实账号/部署。本轮只更新设计，真实产品截图门禁不适用于这份静态原型本身，不能将Demo截图登记为真实产品截图确认。本轮可推送明确标记为待确认的预览分支，并同步已有Issue #155的准备件链接；这不构成设计确认或开放领取。用户确认本版spec、清单和Demo后，PM记录确认对象的完整SHA/摘要、将同一Issue更新为正式可领取版本，不另建重复Issue。
