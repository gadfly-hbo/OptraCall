## 核实事实与取舍

- 现有设置、任务能力和 Interface v3 可承接入口与生命周期。个人账号需新增明确的账号／权限绑定，防止全局账号更换或方案继承扩大任务访问。
- GitHub 官方远端 MCP 提供所需的仓库、Issue、PR 与 Actions 能力。账号使用自己的访问令牌或注册应用，与当前会话所在平台的授权分别建立。
- Gmail 官方新目录已包含发送、回复和转发，上轮可行性答复中的发信范围按新资料修正。官方新交互协议和 Pi 1.4.0 之间存在实际版本差额，选用公开传输接缝的自有适配方案。
- Google 官方 CLI 的动态命令及交互需要额外桥接，当前未发现直接标准 stdio MCP 模式。当前方案以公开传输接缝为主，官方包版本保持本次基线。

## 正式账号仍需核对的供应商条件

2026-11-27 再读 Google [Gmail MCP 配额与开放范围](https://developers.google.com/workspace/gmail/api/guides/quotas)，官方注明 `send_message`、`reply`、`forward`、`update_draft`、`update_label` 等需要 partner access，尚未普遍开放。产品按当前账号真实发现的目录与已获权限取交集；没有对应工具时不显示其能力可用，也不自动改走 Gmail REST。发信支持的工程协议与某个正式账号已获发信权限分别记录。

Gmail 的公开 `send_message` 不提供独立 From／send-as 选择。确认展示绑定的已核验邮箱账号；实际 Gmail 默认发件别名仍须在 GG15 的真实账号检查中核对。可变草稿编号、自动签名和隐含回复对象不直接复用内容批准，Agent 先读取并组成完整显式内容；回复／转发冻结为同账号的 `send_message`，保留实际来源和附件字节。

飞书当前公开接入说明能确认托管 OAuth、云文档、消息及群组，但本轮未取得真实账号的工具目录和用户授权回执。工程按实际确切工具白名单与 schema 接入；现有文档修改还要求实际工具支持明确版本前置条件，不接受无版本覆盖。托管 OAuth 令牌与当前用户身份查询通道的真实兼容性、具体消息工具名称及管理员放行结果仍为 NOT_RUN／NOT_PROVED，不能由合成服务替身推断。身份未核实则保持不可用，不替换为机器人身份。

GG15／GG22、真实模型、四项正式账号授权、服务切换及设备运行版本均未在本轮工程检查中执行。用户后续自行更新所选设备并授权账号时再留实际回执。
